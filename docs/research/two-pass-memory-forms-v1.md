## 무엇을 다르게 쓰고 어떻게 읽을까

각 경험을 독립된 빈 은행과 새 Luna 작성 세션으로 분기한다. 공통 지침은 가치 있는 내용을 선택적으로 저장하고 불확실성과 적용 조건을 보존하도록 한다. 그 뒤에 아래 의도에 해당하는 영문 지침 한 문장만 붙인다. 연구자가 좋은 기억을 골라 주거나 사건을 교훈으로 고쳐 쓰는 단계는 없다. 저장하지 않은 정상 완료, 틀린 본문, 지침과 다른 형태로 쓴 본문도 원 배정에 둔다. [공통 작성 지침](../../protocols/instructions/optional-experience-writer-v1.txt) · [조건별 지침 원문](../../protocols/drafts/tau2-two-pass-memory-forms-v1.json)

| 주 비교의 열 | 1회차 뒤 하는 일 | 2회차에 보이는 과거 정보 |
| --- | --- | --- |
| 순수 무기억 | 작성 없음 | 원래 벤치 문맥과 업무 도구만 제공 |
| 단순 정보 | 관찰한 사실·값·적용 범위·불확실성을 기록 | 해당 작업자가 남긴 제목과 본문 |
| 에피소드·일기 | 상황, 시도, 반응과 결과를 시간 순서대로 기록 | 같은 방식으로 제공 |
| 교훈 | 경험이 뒷받침하는 원칙·주의점과 적용 조건을 기록 | 같은 방식으로 제공 |
| 절차 | 확인 순서, 조건별 행동, 멈춰야 할 시점을 기록 | 같은 방식으로 제공 |

첫 실험의 기억 범위는 **다시 풀 과제의 1회차 경험에서 해당 작성자가 남긴 모든 항목**이다. 2회차 시작 시 저장 순서대로 본문을 제공하고 에피소드 중 기억 조회·쓰기는 끈다. 각 형태의 실제 길이와 내용 선택은 측정 대상이다. 같은 저장 상한과 제공 방식을 쓰므로 비교 대상은 그 지침으로 작성한 기억의 전체 효과다. 이후 전체 1회차 은행에서의 자율 선택과 새로운 과제로의 전이는 여기서 봉인한 은행을 사용해 따로 평가할 수 있다.

보조 대조는 두 가지 목적을 갖는다.

- **빈 메모**를 28개 과제 전부에 배정한다. 네 작성 조건과 같은 안내·역할·위치에서 빈 목록을 제공한다. 순수 무기억과의 차이는 안내와 입력 형식의 영향까지 포함하므로, 본문이 기여했다는 해석에는 각 형태와 빈 메모의 차이도 제시한다.
- **지난 공개 대화 원문과 일반 요약**을 3·17·23·42번에 배정한다. 각각 회원 등급·정책 판단, 여러 변경의 순서, 결제·승인, 예약별 사실 대조를 볼 수 있는 개발 사례다. 네 과제는 서로 다른 고객이며 1회차 성공과 실패가 두 개씩이다. 원문 조건은 writer가 볼 수 있었던 공개 기록 전체를 과거 자료임이 표시된 한 항목으로 제공한다. 일반 요약은 같은 작성자가 같은 경험을 자유롭게 간추린다. 이 대조의 결과 범위는 해당 네 과제다.

## 반복·배정·실행 규모

과제마다 두 블록을 돌린다. 블록마다 네 형태를 **새로 작성**하고 각 은행으로 2회차 에피소드를 한 번 수행한다. 블록 안에서 같은 과제·초기 DB·모델 설정·native seed를 사용한다. 매번 새 작업자·사용자·대화·DB와 은행 복제본으로 시작하며 1회차 주문 상태나 대화 이력을 이어받지 않는다. 공통 무기억 응답 하나는 그 블록의 네 비교에 함께 쓰이고 실제로는 한 에피소드다. 두 블록의 차이에는 작성 변동과 실행 변동이 함께 들어간다.

| 배정 | 계산 | 설계 수량 |
| --- | --- | ---: |
| 주 비교용 작성 | 28과제 × 2블록 × 4형태 | 224세션 |
| 진단용 일반 요약 작성 | 4과제 × 2블록 | 8세션 |
| 주 비교의 2회차 | 28과제 × 2블록 × 5조건 | 280에피소드 |
| 빈 메모 대조 | 28과제 × 2블록 | 56에피소드 |
| 원문·일반 요약 대조 | 4과제 × 2블록 × 2조건 | 16에피소드 |

따라서 계획량은 **작성 232세션, 새 벤치 에피소드 352회**다. 각 세션은 API 요청을 여러 번 쓸 수 있다. 한 조건에서 성적이 좋아졌다는 이유로 반복을 늘리거나 결과가 같다는 이유로 정상 배정을 생략하지 않는다. 빈 작성을 전달한 경우와 빈 메모 대조의 입력 바이트가 같아도 각각 배정된 새 응답을 기록하고 동일 입력이라는 사실을 표시한다.

규모를 가늠하면, 보존된 28개 에피소드는 평균 17.25번의 모델 요청을 썼다. 이 평균을 적용하면 2회차에 약 6,072요청이고 작성 요청은 별도다. 기억 제공 뒤의 대화 길이와 현재 단가에 따라 실제 요청 수와 비용은 달라진다.

먼저 모든 은행을 봉인하고, 그다음 56개 과제·반복 블록의 2회차를 실행한다. 과제 순서와 블록 내 조건 순서는 결과를 보기 전에 계산했다. [기계 판독용 설계](../../protocols/drafts/tau2-two-pass-memory-forms-v1.json)의 `allocation.blocks`가 전체 배정표다. `write` 열을 먼저 전부 읽고 `solve` 열을 읽으면 예정된 584개 작업 순서가 복원된다. 이 순서의 정규화 SHA-256은 `4428e71e73c580c4c5a3d955e5a9b47c7db1cb65cd842515d2cc170f619f1e85`이다.

Luna low 작업자·writer와 DeepSeek V4.1 Flash 1017 사용자 시뮬레이터의 경로·출력 설정은 기존 역할 프로필을 따른다. 두 블록의 writer seed 제안은 0·1, native/작업자 seed 제안은 2·3이다. 사용자 wire seed는 보내지 않는다. 시드는 입력을 맞추는 수단이고 같은 대화 경로를 보장하지 않는다. writer는 `memory_store`만 사용한다. 2회차 기억 조건에서는 같은 과거 메모 안내문, 같은 업무 지침과 도구를 사용한다. 과거 ID는 현재 고객의 신원 확인을 대신할 수 없다. ## 성적표와 실패 경로

**주 지표**는 형태별로 동일 2회차 과제·블록에서의 공식 성공 여부에서 순수 무기억의 공식 성공 여부를 뺀 값이다. τ²의 고정 DB/COMMUNICATE 채점과 substring 설정을 사용하고, 채점된 reward가 1.0일 때 성공으로 센다. 차이를 블록 안에서 짝지은 뒤 과제 안에서 평균하고, 28개 과제에 같은 가중치를 준다. 완전히 채점되면 한 형태당 56쌍이다. 1회차 성적은 원천 경험의 특성으로 따로 표시한다.

| 보고 단위 | 산출물 |
| --- | --- |
| 과제 × 작성 형태 | 배정·시작·채점·성공 수, 무기억 실패→기억 성공, 무기억 성공→기억 실패, 양쪽 성공·양쪽 실패, 미채점 |
| 형태 간 차이 | 네 형태 각각의 무기억 대비 차이(%p), 빈 메모 대비 차이, 같은 과제에서 네 형태끼리 직접 비교한 6개 차이 |
| 과제 구성과 변동 | 참조 DB 변경 있음/없음(11/17), 1회차 성공/실패(24/4), 블록 간 무기억 성공 반전 수, 고객 그룹별 차이 |
| 노력과 위험 | 실제 저장 항목·바이트·토큰, 입력된 제목·본문, 재질문·승인 누락·부적합 도구 인수, 최종 DB·공식 전달 요구, 역할별 요청·토큰·비용 |

불확실성은 두 블록과 모든 조건을 함께 묶은 고객 그룹 22개를 복원추출해 본다. 매번 뽑힌 그룹 안의 모든 과제를 유지해 과제 평균 차이를 다시 계산한다. 제안은 5,000회, seed 20261118, 2.5·97.5 백분위의 기술적 구간이다. 그룹을 하나씩 뺀 차이도 확인한다. 공개 개발 표본에서 가장 높게 나온 점수와 다른 과제에도 적용되는 순위 주장은 구분한다. 1회차 실패 출처 네 개의 결과는 사례와 분모를 그대로 제시한다.

작성 자료는 배정명과 2회차 성적을 가린 채 실제 본문에 사실·사건 순서·교훈·조건부 절차가 각각 있는지 복수로 표시한다. 원천에서 뒷받침되는 문장, 근거가 부족한 추정, 길이, 빈 작성을 기록한다. 서로 다른 지침에서 비슷한 기억이 나오는 것도 관측이다. 1차 성적은 처음 배정한 조건으로 계산하고, 실제 내용 주석은 그 차이를 설명하는 데 쓴다.

**왜 결과가 달라졌는지**는 무기억과 각 형태의 공식 결과가 뒤집힌 모든 쌍을 검토한다. 양쪽 성공과 양쪽 실패에서도 형태별·방향별 한 쌍씩, 해당 쌍이 있으면 배정 순서상 첫 사례를 함께 본다. 먼저 조건명을 가린 공개 업무 대화와 도구 호출로 최초의 중요한 행동 차이와 승인·결과 근거를 판정한다. 그 뒤 원천 공개 기록, 작성 본문과 실제 입력 구간을 연결한다. 참조 답안과 공식 점수는 최종 해석 자료이며 writer나 solver에게 전달하지 않는다. 공개 기록에 사실이 없었는지, 기억에 빠졌는지, 잘못 기록됐는지, 입력은 됐지만 행동에 반영된 근거가 있는지, 다른 이유로 최종 실패했는지를 구분한다. 같은 기억을 본 모델이 수량을 확인한 뒤 잘못된 날짜로 예약했다면 수량 확인과 공식 실패를 모두 남긴다. 한 응답 재전송은 갈림길에서 해석을 점검할 별도 진단이다.

예를 들어 23번에서는 기억에 적힌 결제액, 이번 대화에서 확인한 잔액, 고객이 승인한 분할, 실제 예약 인수를 한 줄에 놓는다. 이전 금액을 그대로 써도 통하는 재시도와 현재 자료로 다시 계산한 행동을 구분할 근거가 있는지 본다. 42번에서는 과거 예약 번호가 공개 답변에 처음 등장한 시점, 현재 고객의 신원 확인, 어떤 예약·날짜를 조회했고 어떤 예약이 바뀌었는지를 연결한다. 여러 설명이 같은 기록에 들어맞으면 원인을 미확정으로 남긴다.

## 오류·비용·실행 준비

자발적 빈 작성은 정상적인 정책 결과로 2회차까지 수행한다. writer가 오류나 한도에서 끝내지 못하면 부분 snapshot과 원인을 보존하고 그 은행에 의존한 2회차를 미시작으로 남긴다. 업무 도구 오류는 native 전이·종료 규칙을 따른다. 중단 시점의 진단 점수는 공식 완료 점수와 분리한다. 모든 셀의 오류·미채점·미시작·비용 미확인을 보고한다. 양쪽이 채점된 쌍으로 계산한 차이에는 과제·쌍의 실제 분모를 붙인다. 최대 56쌍의 계획 분모에서도 미확인 기억 결과를 0/1, 미확인 대조를 1/0으로 각각 두어 가능한 최저·최고 차이를 제시한다. 이 범위와 공식 성적은 별도 열에 둔다.

현재 제안 한도는 writer당 요청 4회·저장 4항목·제목과 본문 합 16,384바이트, 2회차당 worker/사용자 각 100요청 이내·native 200단계·오류 10회·600초다. 실제 송신 입력 한도 제안은 양쪽 128,000바이트다. 원문 대조도 들어갈 수 있도록 읽기 은행 용량은 모든 기억 조건에서 동일하게 두고 정확한 렌더링 크기를 확인한다. 원문이 너무 크면 명시적 한도 오류로 기록한다. 예산·시간 한도 도달 또는 미확인 청구 발생 시 새 요청을 중단하고 남은 배정 식별자를 보존한다. 실제 지출은 1회차 공통 수집비, 형태별 작성비, 2회차 worker·사용자비, 진단 대조비로 나눈다. 한 블록의 공통 대조 비용은 한 번만 센다.

이 설계에서 확인한 범위는 보존 원본의 해시, 28개 공개 입력의 재구성, 사례·그룹·배정 순서와 수량이다. 실행 단계에서는 기존 writer와 native 전체 에피소드 실행기를 위 배정표에 연결하고, 순수 무기억·빈 메모·작성·원문 조건의 실제 요청 차이, 빈 작성·부분 오류, 공식 채점과 중단 시 누락 보존을 오프라인으로 대조한다. 이후 별도 ready 프로필에 실행 commit, 실제 endpoint·단가, 전체 요청·시간·금액 상한과 새 출력 위치를 고정한다. 종전 $5는 앞선 48요청의 상한이었다.
