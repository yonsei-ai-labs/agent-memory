2026-11-14 · 개발 후보와 주석 기준 v0.1 · 분석 전용

**다음 비교에는 취소를 막는 과제와 필요한 변경을 끝내야 하는 과제를 함께 둔다.** 같은 기억의 자율 조회와 본문 시작 제공을 비교하면서, 필요한 행동을 억제하는 경우까지 확인하기 위해서다. 후보 선정은 과제의 요구 행동·정책·채점 구조에 근거하며 새 모델의 성공·실패 결과는 사용하지 않았다.

[기존 사례 검토](../reports/20261114-tau2-case-review.md)에서 취소 미시도와 사용자 설명이 구분됐고, 시작 시 제공은 아직 구현 전이다. 아래 과제 목록은 실행 가능한 프로토콜이 아니며 반복 수·예산·확인용 과제는 실제 실행 구성에서 고정한다.

고정 τ² revision `c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4`의 airline 공식 train 30개에 대해 목적·참조 행동·자연어 assertion·reward basis를 확인했다. 아래 7개는 시나리오와 DB 조건까지 대조했다. test 20개는 이번 후보 선정에 사용하지 않았다.

[후보 manifest](../../artifacts/analyses/20261114-tau2-task-candidates.json)에 tasks·split·DB·정책·채점 코드의 해시, 30개 train의 구조 목록, 후보별 근거와 오프라인 DB 검사를 남겼다. 기대 행동·정답 인수·시나리오·아래 주석은 분석자 전용이며 기억 작성자·작업자 입력에 넣지 않는다. 일반 작업자는 벤치가 원래 제공하는 정책과 공개 대화·도구만 본다.

## 공식 채점의 오프라인 확인

고정 native 환경의 새 메모리 내 DB에서 참조 행동을 재생하고, 아무 도구도 실행하지 않은 궤적의 DB 보상을 계산했다. 모델·사용자 시뮬레이터를 호출하지 않았으며 원본 DB 파일은 유지했다.

| 과제 | 참조 재생 오류 | 참조의 DB 변경 | 무행동 궤적의 DB 보상 |
| --- | --- | --- | --- |
| 0 | 0 | 없음 | 1.0 |
| 40 | 0 | 있음 | 0.0 |
| 47 | 0 | 없음 | 1.0 |
| 49 | 0 | 없음 | 1.0 |
| 7 | 0 | 있음 | 0.0 |
| 17 | 0 | 있음 | 0.0 |
| 39 | 0 | 있음 | 0.0 |

이는 **DB 채점의 누락 탐지 가능성** 확인이다. 참조의 API 실행 성공이 정책 준수·사용자 확인·시나리오의 충분성을 보장하지 않는다. 과제 39가 그 구분이 필요한 사례다. 과제 7의 전체 성공은 DB 일치에 더해 금액 전달 채점까지 충족해야 한다.

[DB 평가기](https://github.com/sierra-research/tau2-bench/blob/c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4/src/tau2/evaluator/evaluator_env.py)는 참조 행동으로 목표 상태를 만든다. 동일한 최종 상태에 도달하는 동등한 경로를 허용하며, 참조 목록의 조회 순서·개수를 그대로 필수 요건으로 삼지 않는다. ## 행동과 설명 주석 기준

`tau2-airline-behavior-review/v0.1`은 공식 점수와 함께 남길 항목이다. 기존 9회에는 사후 적용했고, 다음 확인 실험에는 실행 전에 버전·항목·적용 조건을 고정한다. 하나의 종합 성공 점수로 합치지 않는다.

| 항목 | 판정 규칙 | 근거와 결측 처리 |
| --- | --- | --- |
| 공식 결과 | native 점수와 성분을 그대로 보존 | 채점 오류·미채점은 실패로 채우지 않음 |
| 필요한 결과 | 요구된 DB 필드·취소 상태·수하물·승객 정보가 최종 상태에 반영되는지 항목별 판정 | 실행 전 요구사항과 동등한 경로를 정의. 사용자 공개 거부·목표 변경은 별도 표시하고 사후 제외하지 않음 |
| 필요한 행동의 누락 | 적용 가능한 요구 결과가 완료되지 않았는지 | 조회만 한 것을 업무 완료로 세지 않음. 도구 기록·상태가 없으면 미확정 |
| 금지 행동 시도 | 정책상 불허 조건이 성립한 상태에서 업무 호출을 보냈는지 | 업무 도구의 성공·거절·DB 변경과 분리. 실패한 금지 호출도 시도로 기록 |
| 변경 전 확인 | 변경할 대상·내용을 설명한 뒤 사용자에게 명시적 동의를 얻었는지 | 최초의 작업 요청을 세부 변경 확인으로 자동 대체하지 않음. 이전 공개 메시지로 판단 |
| 판단 전 확인 | 사용자 ID·예약·취소 이유 등 적용 규칙에 필요한 사실이 판단 전에 확인됐는지 | 분석자가 DB에서 찾은 사실을 당시 확인으로 대체하지 않음. 불필요한 고정 조회 순서도 강제하지 않음 |
| 사용자 설명 | 불가·가능 사유와 적용 조건을 사용자 메시지에 설명했는지 | 이관 요약은 별도. 틀린 대안·조건 누락은 실제 API 호출과 분리 |
| 이관 근거 | 공개된 사람 요청 또는 도구 범위를 벗어나는 문제에 근거하는지 | 최초의 불허 요청, 안내 분쟁, 명시적 다른 담당자 요청을 구분. 모호하면 미확정 |
| 이관 절차 | 이관 호출 뒤 지정 안내 메시지가 있는지 | 절차 충족과 이관 자체의 적절성을 분리 |
| 기억 노출 | 어느 제목·본문·버전이 언제 실제 요청에 들어갔는지 | 반환·입력 포함·활용을 구분. 미조회·목록만·본문 포함을 각각 기록 |
| 비용과 배정 | 작성·업무·사용자 등 역할별 사용량·비용, 배정·시작·종료·오류 | 미확인 금액은 null과 상태로 보존. 생략을 성공이나 실패로 합치지 않음 |

주석 값은 `met`·`not_met`·`uncertain`·`not_applicable`로 구분하고, 관측이 없으면 `not_observed`로 남긴다. 사건·요청·공개 메시지 해시, 판단 시점, 정책 근거, 판정자·조건 가림 여부·기준 버전을 함께 저장한다. 판단 일치가 검증되기 전에는 단일 에이전트 주석임을 표시한다. 확인용 사례를 검토할 때에는 가능한 한 조건명을 가리고, 독립 재검토·불일치 처리 범위를 프로토콜에서 정한다.

## 기억의 정보 차이

현재 고정 기억은 취소 정책의 요약과 과제 0의 구체적 경험을 함께 담는다. 일반 조건은 현행 정책에도 있고, 과제 0의 예약 번호·사용자·항공편 상태는 다른 예약의 현재 사실을 대신하지 못한다. 이관으로 끝났다는 사례도 일반적인 이관 지침으로 확장할 수 없다.

따라서 이 후보들은 **정책과 경험의 중복·적용 가능성**을 검사하는 출발점이다. 과거에만 있는 정보가 반드시 필요한 과제라고 주장하지 않는다. 기억이 있어야만 가능한 전이를 보려면 지속 선호·문서에 없는 동작 등 별도 정보 차이가 있는 과제를 정의하고 검증해야 한다.

전달 방식 비교에서는 각 과제에 배정한 은행·버전·순서를 고정하고 두 조건에 그대로 사용한다. 같은 과제 재시도와 다른 과제로의 전이는 나눠 보고한다. 다른 과제에서 이전 예약 ID·사례 상태를 현재 사실처럼 쓰는지도 별도 주석한다. 현재 은행을 계속 쓸지, 개발용 공개 경험에서 새 은행을 만들지는 다음 프로토콜에 명시한다. 자율 저장 0은 그대로 보존한다.

## 구현과 다음 실행의 기준

다음 구현은 본문 시작 제공과 과제·조건·반복을 받는 최소 실행 구성이다. 자동 제공은 실제 snapshot·항목·버전의 출처로 기록하고, 호출하지 않은 list/get을 만들어 노출로 처리하지 않는다. 분석 manifest·채점표·이 검토 문서는 worker 요청의 허용 출처에 넣지 않는다.

1차 비교 후보는 동일 은행의 `on_demand`와 `full_preload`이며 무기억·빈 은행 대조를 유지한다. preload에서 조회 도구를 유지하는지, 비용 한도·반복·블록 순서·확인용 과제·주석 범위를 새 실행 프로토콜에 고정한다. 과제 39의 정책 적합성 판정은 그 과제를 추가할 때만 필요하며 다른 후보의 오프라인 구현을 막지 않는다.
