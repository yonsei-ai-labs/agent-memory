# 카드 재발급이 실제로 끝났는지 확인하는 은행 사례

τ³ 은행 036번은 앞선 두 묶음의 여덟 과제에 들어 있지 않았다. 고객은 모르는 거래를 확인한 뒤 카드 재발급을 요청한다. 시뮬레이터의 주문 도구는 기존 카드를 닫고 새 주문을 저장한다. 이번 사례에서는 현재 상담에서 확인한 카드, 배송지, 사유, 배송 방식으로 주문했는지와 다른 카드까지 닫았는지를 실제 DB에서 판정한다. [고정한 사례·두 작성법과 배정](../../protocols/pilots/tau-banking-replacement-v1.json)

## 난도와 데이터 점검

고객의 신용카드는 네 장이고 전체 거래 47건 중 실버 카드 거래가 16건이다. 고객이 모르는 $487.99와 $299.95 거래는 실제 고객별 조회의 첫째·둘째 항목이었다. 거래 이름을 찾아내는 데 필요한 탐색은 짧을 수 있다. 확인할 판단은 **본인확인에 쓴 집 주소와 새로 요청한 직장 배송지를 구분하고, 올바른 카드 하나만 닫으며, 요청한 방식으로 실제 주문까지 마치는가**다. [원래 DB와 조회 반환의 순위·해시](../../artifacts/analyses/20261125-banking-replacement-case.json)

벤치 작성자의 설명에는 두 거래가 2024년 11월로 적혀 있지만 실제 DB와 업무 조회 결과는 2025년 9월 4일·6일이다. 고객 대본은 상호와 금액으로 두 거래를 지목한다. 예전 날짜가 작업자·고객의 시스템 입력에 들어가지 않음을 확인했고, 보조 분석도 실제 조회에 나타난 상호·금액을 따른다. [데이터 대조](../../scripts/analyze_banking_replacement.py)

## 기억 비교

원래 대본과 초기 DB로 무기억 상담을 한 번 실행한다. 같은 공개 대화·도구 기록과 공식 성패 한 값으로 기존·보완 지침별 사실·경험·절차·교훈·자유 메모를 하나씩 저장한다. 후속 상담 10개는 원천의 첫 공개 질문을 독립 환경에서 복원한 뒤 각 메모를 자동 제공하고 끝까지 진행한다. 2회차 무기억 배정은 0건이다. 작성자 입력에 채점용 주문 인수를 추가하지 않는다. 원천에서 업무 단서를 얻지 못했거나 메모에 저장되지 않은 경우에도 해당 배정을 보존한다. [실행기와 원천 연결](../../scripts/run_banking_replacement.py)

주 지표는 전체 상담의 공식 DB 일치다. 같은 형식에서 기존만 성공·보완만 성공·공동 성공·공동 실패·기술 결측을 센다. 공동 성공에서는 호출·고객 발화·토큰·비용을 비교한다. 보조 분석은 원천에서 보인 단서, 실제 전달된 메모, 주문 직전의 현재 대화·도구 근거, 주문 필드와 비대상 카드 취소를 연결한다. 다섯 형식은 한 고객·한 무기억 상담을 공유한다. [근거·주문 재생 분석기](../../scripts/analyze_banking_replacement.py)

이 단계에서 완료된 것은 무과금 검증이다. 새 모델 실행의 예상 비용은 $0.05~0.15이고, 1회차 1건·필수 작성 10건·2회차 전체 상담 10건에 제안한 새 총한도는 $0.30이다. 이전 과제 예산은 그 실험에서 종료됐다.

공식 과제는 과거 대화와 초기 변경이 모두 빈 초기화 객체를 명시한다. 무기억 시작과 새 세션 복원에서 동일한 첫 업무 입력과 초기 DB를 확인했고, 대화·초기 동작·DB 변경이 실제로 들어 있는 경우는 기존 거부 조건을 검증했다. 도구·채점·격리 점검에 든 유료 호출은 0건이다. [시작점 검증](../../tests/test_banking_replacement.py)

```bash
uv run python -m scripts.run_banking_replacement preflight --workspace . --output /tmp/banking-replacement-preflight.json
uv run python -m scripts.analyze_banking_replacement case --workspace . --output /tmp/banking-replacement-case.json
```
