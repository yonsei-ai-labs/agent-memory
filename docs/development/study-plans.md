# 선언형 실험 계획과 공용 실행기

2026-11-27 · [프레임워크와 점수 체계 보완 계획](framework-scoring-plan.md)의 3단계(실행 계층) 구현 설계

**새 실험은 계획 파일 하나로 만든다.** 벤치, 과제, 1회차, 작성 방식, 조회 방식, 반복, 예산, 재시도를 선언한다. 같은 실행기가 돌리고 같은 점수표로 무기억과 다른 정책을 비교한다. 실험을 추가하려고 실행 코드를 고치거나 분기를 더하지 않는다.

## 왜 바꾸는가

11월 27일에 돌린 실험 네 개는 모두 공용 실행기를 거치지 않았다.

- 은행 실험은 `scripts/run_banking_memory.py`의 실험별 `--series` 분기로 돌았다. 분기는 그날 2개에서 5개로 늘었다.
- 실험 전용 어댑터 `banking_memory_cohort.py`는 그날 만들어진 뒤 다섯 번 더 고쳐졌다.
- 작성 형식 다섯 개와 조회 방식 두 개는 코드 상수(`paired_repetitions.FORMS`, `MODES`)에 묶여 있다.

[연구 계획](../research/plan.md#실험자와-플랫폼의-역할)의 최종 목표는 탐구 에이전트가 저장·조회 방식을 스스로 바꿔 보는 프레임워크다. 다섯 형식과 자동 제공·자율 조회는 예시 정책이다. 따라서 작성 방식과 조회 방식은 고정 목록이 아니라 선언하는 값이어야 한다.

## 목표와 범위

| 구분 | 내용 |
| --- | --- |
| 목표 | 계획 파일 하나로 τ³ 은행(빈 DB·채워진 DB 시작 모두)과 BFCL을 같은 단계로 실행하고, 같은 점수표를 낸다. |
| 목표 | 작성 방식(공통 지침·표현별 지침·피드백)과 조회 방식(제공 방식·안내문·도구 설명)을 이름과 내용으로 선언한다. |
| 목표 | 이미 기록된 1회차와 기존 정책의 결과를 다시 쓰고, 같은 원천 위에서 새 정책만 추가로 실행할 수 있다. |
| 목표 | 일시적인 공급자 오류는 계획에 미리 적은 규칙대로 다시 시도하고, 처음 기록은 남긴다. |
| 비목표 | 과거 실험의 재현 경로 교체. 과거 실험은 [고정 commit 재현](historical-reproduction.md)으로 확인한다. |
| 비목표 | AppWorld 연결, 외부 기억 시스템 연결 |
| 반목표 | 새 실험마다 실행 코드에 분기를 더하는 것 |
| 반목표 | 한 가설에만 쓰는 지표를 공용 점수표의 기본 항목으로 넣는 것 |
| 반목표 | 원본 기록을 덮어쓰거나, 결과를 본 뒤 재시도·제외 규칙을 바꾸는 것 |

## 계획 파일

형식은 `agent-memory-study-plan/v1`이다. [스키마](../../schemas/study-plan-v1.schema.json)

| 항목 | 내용 |
| --- | --- |
| `id`, `purpose`, `question` | 실행 이름, 개발·확인 구분, 이 실행으로 알고 싶은 것 |
| `benchmark` | 어댑터 이름, 고정된 벤치 설정 파일, 과제 목록 |
| `first_pass` | 무기억 1회차를 새로 돌릴 횟수, 또는 다시 쓸 기록 |
| `writing` | 공통 작성 지침, 작성자 피드백(`none`, `result_only`), 표현별 지침. 표현 이름은 자유롭다. |
| `reading` | 조회 방식별 제공 방식(`preload`, `on_demand`), 안내문, 도구 설명. 이름은 자유롭다. |
| `conditions` | 실행할 표현×조회 조합 |
| `references` | 같은 원천에서 이미 기록된 정책 결과. 새로 실행하지 않고 점수표에 함께 싣는다. |
| `repeats`, `limits`, `budget`, `retry` | 반복 수, 입력·호출 한도, 누적 금액 한도, 재시도 대상 오류와 대기 간격 |

상세 설계 [5절의 정책 계약](../design/architecture.md#5-정책-계약) 용어를 따른다. v1.1의 `representation` 열거값은 기억 형식을 고정하므로, 이 계획에서는 표현 이름과 지침 내용을 직접 선언한다.

## 실행 단계

1. `plan validate`: 형식, 참조 파일 해시, 조합의 유일성, 무기억 조건의 정보 차단을 확인한다. 모델을 호출하지 않는다.
2. `plan resolve`: 과제를 벤치에 연결하고 배정 목록과 비용 추정을 만든다. 결과는 `runs/<id>/resolved-plan.json`에 해시와 함께 고정된다.
3. `run`: 고정된 계획과 같은 해시를 가진 사용자 승인 기록이 있을 때만 시작한다. 1회차 → 작성 → 2회차 순서로 돌고, 단계마다 영수증을 남긴다.
4. `resume`: 중단된 실행을 같은 계획으로 이어 간다. 이미 보낸 상담은 다시 보내지 않는다.
5. `analyze`: 저장된 원본만 읽어 점수표를 만든다.

```text
python -m agent_memory_eval.study plan validate --plan protocols/studies/<id>.json
python -m agent_memory_eval.study plan resolve --plan protocols/studies/<id>.json
python -m agent_memory_eval.study run --plan protocols/studies/<id>.json
python -m agent_memory_eval.study analyze --plan protocols/studies/<id>.json
```

## 점수표

벤치와 정책에 관계없이 같은 항목을 낸다.

- 조건별 배정 수, 채점 수, 결측 사유별 수
- 성공 수와 성공률. 무기억 기준은 같은 과제의 1회차 성공률 평균이다.
- 자기 원천 대비 회복(실패→성공)과 악화(성공→실패)
- 같은 원천을 공유한 두 조건이 모두 성공한 상담에서의 업무 호출·토큰 차이
- 기억 노출: 시작 제공 여부, 목록·본문 조회 수
- 단계별 비용과 호출 수

## 어댑터

| 어댑터 | 연결 |
| --- | --- |
| `tau-banking` | τ³ 은행 원본 과제와 고객 시뮬레이터. 실행 핵심은 `experiments/forms_batch.execute_prepared`를 그대로 쓴다. |
| `bfcl-relevance` | BFCL 단일 판단 문항과 로컬 모델. 실행 핵심은 `runner/bfcl_relevance`의 작성·풀이 함수를 쓴다. |

어댑터는 과제 준비, 단계 실행, 결과 판독 세 가지만 맡는다. 정책 해석·배정·예산·재시도·점수표는 공용 코드가 맡는다.

## 검토한 방식

| 방식 | 판단 |
| --- | --- |
| 기존 `policy_round`를 넓힌다 | 은행 쪽이 `scripts/run_banking_policy_cycle.py`로 넘어가고, 계좌 개설 프로필 하나만 받는다. 은행 실행 경로가 두 개로 남아 채택하지 않았다. |
| 새 계획 형식과 공용 실행기를 만들고 실행 핵심은 재사용한다 | 채택했다. 실험마다 달라진 부분(경로 상수, 형식·조회 하드코딩, 실험별 분기)만 계획으로 옮긴다. |
| 실행 핵심까지 새로 쓴다 | 검증된 원장·채점 경로를 버리게 되고 시간이 많이 들어 채택하지 않았다. |
