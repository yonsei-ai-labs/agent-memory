# 선언형 실험 계획과 공용 실행기

2026-11-28 · [프레임워크와 점수 체계 보완 계획](framework-scoring-plan.md)의 3단계(실행 계층) 구현 설계

**새 실험은 계획 파일 하나로 만든다.** 벤치, 과제, 1회차, 작성 방식, 조회 방식, 반복, 예산, 재시도를 선언한다. 공식 과제의 1·2회차는 공용 점수표로 무기억과 다른 정책을 비교한다. 재방문은 이전 첫 판단을 이어가는 전용 경로를 사용한다. 실험을 추가하려고 실행 코드를 고치거나 분기를 더하지 않는다.

## 같은 과제의 1회차 기억과 혼합 기억

v3 계획에서 `transfer.bank_comparison`을 `own_vs_mixed`로 선언하면 등록된 모든 과제가 원천이자 목표다. 각 과제가 무기억으로 한 번 수행한 경험을 작성자들이 공유한다. `other_sources`는 혼합 조건에서 자기 메모에 더할 과제 ID다. 두 은행은 동일한 자기 메모 버전을 쓴다. 결과표는 작성 방식·전달 방식·후보 구성을 하나씩 바꿔 비교하고, 같은 목표의 1·2회차 전환과 메모별 노출을 함께 낸다. [네 벤치의 과제 목록과 분석 기준](../research/own-mixed-cohort.md)

### 보충된 1회차에서 메모 작성 이어가기

무기억 1회차만 승인한 뒤 기술 결측을 보충한 경우, 작성 단계는 최종 원천 목록을 별도로 고정한다. 아래 명령은 각 과제의 실행 ID, 봉인 해시, 공개 경험과 공식 성패를 원기록과 대조한다. 뱅킹·리테일·항공·BFCL에 같은 명령을 쓴다. [네 벤치의 원천 자료](../../artifacts/studies/own-mixed-round1/writer-sources.json)

```bash
uv run --no-sync python -m agent_memory_eval.study plan resolve \
  --plan protocols/studies/cohort/own-mixed-bank-01.json \
  --writer-sources artifacts/studies/own-mixed-round1/writer-sources.json
```

작성비 승인은 네 계획이 한 건을 공유한다. `authorize --through-stage write --writer-sources`에 원천 목록 경로, 승인자의 문구와 총액, 각 계획의 `--writer-cap PLAN=USD`를 지정한다. 계획별 `run --through-stage write`와 `resume --through-stage write`에는 같은 계획과 원천 목록을 전달한다. 이 경로가 보내는 모델 요청은 메모 작성이며, 누적 예약과 청구액은 승인된 작성비에서 차감한다. 중단 후 재개할 때는 작성 실행에 고정한 코드 커밋을 쓴다.

### 봉인된 메모로 2회차를 이어가기

`--reader-batch`는 기존 코호트의 2회차 실행 대상을 제한한다. 배정 파일은 원래 v3 계획, 작성 결과, 판독 기준, 벤치별 목표 ID와 비용을 고정한다. `plan resolve`는 과금 없이 해당 목표의 원천·후보 메모와 수행 가능 수를 확인한다. 네 벤치에 공통으로 쓰는 배정 승인은 `authorize --reader-batch`로 한 번 기록한다. 각 벤치의 `resume --reader-batch`는 그 벤치에 명시한 목표만 수행한다. `--tasks`는 분석 행을 고를 때 쓴다. [첫 48건의 배정과 한도](../../protocols/diagnostics/own-mixed-readers-smoke-01.json)

```bash
uv run python -m agent_memory_eval.study plan resolve \
  --plan protocols/studies/cohort/own-mixed-bank-01.json \
  --reader-batch protocols/diagnostics/own-mixed-readers-smoke-01.json

uv run python -m agent_memory_eval.study resume \
  --plan protocols/studies/cohort/own-mixed-bank-01.json \
  --reader-batch protocols/diagnostics/own-mixed-readers-smoke-01.json
```

각 실행의 `reader-batches/<배정 ID>/registration.json`은 실행 구현·쓰기 체크포인트·메모 해시·승인과 목표 목록을 묶는다. 정산이 끝나면 같은 디렉터리에 `result.json`을 만든다. 비용에는 실제 청구와 미정산 예약이 함께 들어간다. 새 배정은 이미 등록한 목표와 겹칠 수 없고, 앞선 배정도 남은 누적 한도에 반영한다. 총한도를 올리는 후속 배정은 계획별 `cumulative_max_usd`와 해당 배정의 승인을 기록한다. 하나의 목표에서 12조건은 같은 1회차와 같은 두 작성물을 공유한다.

운영 조건을 바꾸어 다음 목표를 시작할 때는 배정의 `runtime_commit`에 실행 코드를 고정하고, `closed_reader_batches`에 앞선 등록·결과·보충 결과 해시를 명시한다. `plan resolve`는 새 배정을 기록하기 전에 과제 중복 여부, 앞선 배정의 봉인과 금액, 코드 일치를 확인한다. 기존 배정을 재개할 때는 등록 당시 구현을 사용한다. `operations.max_concurrent_tasks`가 과제 병렬 수를, `transient_backoff_seconds`가 해당 벤치에서 제공자 장애 후 새 상담을 시작하기까지의 대기를 정한다. 각 원장에 과제별 등록과 실제 요청 비용·미정산액이 남는다. [네 벤치 최종 배정](../../protocols/diagnostics/own-mixed-readers-final-01.json)

τ²의 후속 상담 시작 발화, 혼합 메모 출처, 전환표는 작성기가 사용한 1회차를 함께 참조한다. BFCL은 1회차 체크포인트까지의 저널 바이트를 검증하고 그 뒤에 작성 기록을 추가한다. 결과표의 1회차 비용은 최초 시도와 보충 시도를 모두 포함한다.

## 서로 다른 과제 사이의 행동 전이

이 설계는 한 과제에서 남긴 경험이 다른 과제의 판단을 돕거나 방해하는지 살펴본다. 일반 계획 v3의 `transfer.pairs`에 원천, 목표, 원천에서 찾아볼 공개 단서(`source_cue`), 목표에서 확인할 행동을 먼저 적는다. 단서는 분석자용 가설로 기록한다. 아래 세 계획은 실행 경로를 검증하는 개발용 배정이다.

| 벤치 | 무기억 원천 | 같은 메모를 적용할 서로 다른 두 목표 |
| --- | --- | --- |
| [리테일](../../protocols/studies/retail-behavior-transfer-dev-01.json) | 44번 고객의 주문 품목 변경 | 37번 고객의 미처리 주문 품목 변경, 58번 고객의 배송 완료 주문 품목 교환 |
| [항공](../../protocols/studies/airline-behavior-transfer-dev-01.json) | 17번 고객의 예약 변경 | 15번의 예약·좌석 등급 변경, 36번의 변경 제한 예약에서 날짜 변경과 취소 보류 |
| [BFCL](../../protocols/studies/bfcl-behavior-transfer-dev-01.json) | 행사 예약 함수의 적용 여부 | 다른 질문에서 영화 상영관 함수를 호출할 수 있는 경우와 주어진 함수로 흥행 순위를 구할 수 없는 경우 |

1. 1회차에 무기억 작업자가 원천을 수행한다. 같은 모델의 작성자가 원천의 공개 경험과 그 과제의 성공 여부 1비트를 받고 메모 한 건을 작성한다. 정책 A에서는 저장이 필수이고 내용과 표현은 모델이 정한다. 목표의 질문·정답·채점 설명은 작성 입력에서 제외한다.
2. 2회차에 **같은 목표**를 각각 새 세션에서 푼다. 한쪽에는 봉인된 원천 메모, 다른 쪽에는 빈 저장소를 연결한다. 두 조건이 보는 목표, 업무 도구, 조회 도구 설명은 같다. 일반 조회와 when-needed 조회는 목록 도구 설명만 다르고 작업자가 건너뛸 수 있다. 자동 제공에서는 같은 메모와 빈 목록을 각각 시작 입력에 넣어 조회를 거치지 않아도 내용이 도달하는지 확인한다. 각 τ² 원천·목표 쌍의 고객 관계를 `same_customer` 또는 `different_customer`로 선언하고 실제 신원과 대조한다. 세 개발안 중 τ² 두 계획은 다른 고객으로 고정했다. 목표마다 별도의 무기억 상담에서 첫 고객 발화를 확보한다. 이후 상담이 채점에 실패해도 이미 확보한 첫 입력을 사용할 수 있다. 이 상담의 비용을 기록한다. 처음 등록한 실제·빈 저장소 짝 비교는 그대로 계산하고, 점수표 v2에서는 목표의 무기억 상담과 각 후속 배정 사이의 전환도 별도로 낸다. BFCL은 고정된 원본 질문과 함수 목록을 사용한다.
3. 점수표는 원천·목표·원천 추출 회차·반복별로 실제 메모와 빈 메모를 짝짓는다. 사전 지정한 판단과 최종 공식 성공 각각에 대해 실제만 성공한 쌍, 빈 조건만 성공한 쌍, 일치, 결측을 낸다. 목표마다 같은 가중치를 준 최선·최악 차이는 **결측 범위**다. 표본 변동을 추정하는 신뢰구간은 별도로 필요하다. 메모 목록을 요청한 경우, 본문을 요청한 경우, 판단까지 본문이 실제 입력에 들어간 경우도 기록한다. 조회한 상담만 선별해 효과를 계산하면 선택 편향이 생긴다.

τ²의 행동 지표는 등록한 업무 도구 중 첫 호출과 명시한 인수만 검사한다. 예를 들어 리테일 37번에서 도구 종류와 이번 주문 ID가 맞는지는 판독하지만 가격 조건 전체는 공식 채점에서 확인한다. 호출을 보류해야 하는 목표는 정상 종료한 상담에서 해당 호출이 없었을 때만 보류를 인정한다. BFCL의 공식 범위는 업무 함수 **호출 여부**다. 함수 인수 전체의 정확성을 뜻하지 않는다. 정해진 조회 횟수를 소진하고 업무 결정을 내리지 못하면 행동 지표 실패로 기록하며 공식 채점 가능 여부를 따로 남긴다.

세 계획은 동일한 [표준 모델 프로필](../../protocols/models/project-standard-v1.json)을 고정한다. BFCL 전이 경로는 고정된 BFCL 공개 데이터와 공식 출력 판독기를 사용하고 OpenRouter 경유 Luna의 리비전·제공자·요금을 실행 전에 대조한다. 각 개발 계획은 원천 하나·목표 둘·조회 방식 셋이며 방식마다 실제·빈 메모를 배정한다. 벤치당 2회차 12건, 세 벤치 합계 36건이다. 아래 명령은 모델 호출 없이 각 배정과 실행 전 결측을 확인한다.

```bash
for domain in retail airline bfcl; do
  plan="protocols/studies/${domain}-behavior-transfer-dev-01.json"
  uv run python -m agent_memory_eval.study plan resolve --plan "$plan"
  uv run python -m agent_memory_eval.study analyze --plan "$plan"
done
```

BFCL의 고정 체크아웃이 기본 작업공간 밖에 있으면 `--checkout`으로 지정한다. 실제 실행에는 별도 지출 승인이 필요하다. 각 파일의 1달러는 설정 상한이다. 본실험에서는 개발에 쓴 목표와 분리해 절차가 통하는 경우와 달라져야 하는 경우를 미리 선정하고, 독립 목표 수와 판정 기준을 확정한다. 리테일 재방문은 이전 주문 정보가 실제로 유용한 양성 대조로 별도 해석한다. 기존 같은 과제 재시도 결과와 합산하지 않는다.

### 목표의 무기억 반복과 전환

새 전이 계획에서 `transfer.target_no_memory_repeats`에 **목표 한 개·추출 회차 하나당 순수 무기억 수행의 총횟수**를 지정한다. 1회는 기준이 되는 목표의 첫 수행이고, 2회부터는 같은 공개 입력과 동일한 첫 작업자 요청으로 시작하는 독립 수행이다. 상담은 새 세션·초기 DB에서 시작한다. 같은 목표에 여러 원천이나 정책이 연결되면 무기억 수행은 공유한다. 횟수를 생략한 기존 τ² 계획은 원래 기록한 목표 첫 상담 한 건을 사용한다. 원래 BFCL 계획은 고정 질문만 사용했으므로 목표 무기억 수행은 0건이다. 새 BFCL 계획도 같은 항목으로 순수 무기억 수행을 등록할 수 있다.

`analyze --save`는 각 후속 행에 `target_baselines`를 연결하고 별도 해시의 v2 행과 점수표를 만든다. `versus_target_first_pass`는 목표의 첫 성패와 각 정책에서의 같은 목표 성패를 네 칸으로 집계한다. 공식 성공과 등록한 행동 판단을 각각 계산한다. `gain`은 실패→성공, `loss`는 성공→실패다. 결측 사유·관측 짝 수·서로 다른 첫 수행 수를 함께 읽는다. 1회차 성적으로 목표를 고른 실험에서는 이 비교에 선별 편향이 생긴다.

자연 변동의 기대 건수는 목표·추출 회차별로 첫 결과를 고정하고, 같은 첫 입력의 추가 무기억 수행에서 얻은 성공 비율을 각 전환 칸에 배분해 계산한다. 같은 범위를 비교하도록 기대값을 계산할 수 있는 짝의 관측표도 함께 낸다. 추가 수행이 없으면 기대값은 `null`이다. 시작 제공과 선택적 조회는 각각 실제·빈 저장소를 비교하고, 조회 도구가 있지만 열지 않은 세션의 변동도 첫 요청 해시가 같은 세션끼리 따로 표시한다.

`writing_by_source`에는 작성자가 받은 공개 원천의 경로·해시, 작성 지침별 메모 원문, 피드백과 본문 첫 줄의 일치 여부, 제목에 적힌 명시적인 성패 표현이 있다. 원천 성패는 작성 단계의 입력이다. 후속 에이전트에 들어간 것은 반환 기록과 실제 작업자 요청으로 추적한다. `exposure`에서 목록·본문 요청, 반환한 항목의 필드, 요청에 들어간 제목·본문, 등록 판단까지 본 제목·본문을 확인한다.

`effort_from_first_worker`는 목표의 첫 작업자 요청부터 작업자와 고객 시뮬레이터가 쓴 호출·토큰·금액을 센다. 역할별 입력·출력 토큰과 그 안에 포함된 캐시 입력·추론 토큰을 기록하며 확인할 수 없는 값은 `null`이다. 공식 성패 전환별로 호출·토큰·금액 및 고객 발화·질문·반복 질문의 짝 차이를 낸다. 같은 첫 상담이 여러 정책과 짝지어지므로 이 비교의 합계는 지출 총액과 다를 수 있다.

리테일·항공의 `state_diagnostics`는 등록 도구의 첫 호출과 후속 호출, 실제 인수, 벤치 도구의 반환·오류, 정답 행동과 다른 인수를 남긴다. 공식 채점이 있는 상담에서는 고정된 벤치와 기록된 판정 응답으로 다시 채점해 최종 DB 해시를 대조하고, 대상 주문·예약의 실제 값과 정답 값을 함께 남긴다. 공식 성패와 사전등록 판단은 각각 원래 기준을 따른다. 뱅킹은 이관 등 해당 과제의 등록 행동을, BFCL은 공식 함수 호출 여부를 보고한다.

### 단일 기억 전이의 판독 순서

원천의 공개 대화에 목표 판단에 쓸 수 있는 단서가 있었는지 먼저 기록하고, 작성한 메모가 그 단서와 적용 조건을 실제로 보존했는지 확인한다. 조회율·반환·본문 입력·목표 판단·공식 결과를 그 순서대로 대조한다. 자율 조회가 0이면 해당 배정에서 확인한 행동은 조회 생략까지다. 자동 제공에서도 판정이 같으면 원천 단서, 작성 내용, 목표의 난이도와 측정 지점부터 확인한다. 단서가 노출되고 판단이 달라도 개별 사례만으로 인과 효과를 확정할 수 없다.

여기서는 한 번에 원천 하나를 배정한다. 여러 경험 중 선택하는 `mixed_experience`는 [별도 연구 질문](../research/experiment-protocol.md)이다. 후속에서 목표별 관련 원천을 공개 경험의 근거로 사전 등록하고, 관련 원천을 비슷한 길이의 다른 원천으로 교체한 같은 크기의 은행, 빈 은행, 관련 항목의 위치 교차를 둔다. 등록한 단서·실제 저장·첫 선택 위치·판단 전 본문 노출을 각각 남긴다. 11월 20일의 528회는 자기 은행 264회와 혼합 은행 264회의 합이며 모두 조회 0회였다. 11월 23일의 109/116은 한 상담의 여러 표현 사이에서 첫 항목을 연 빈도다. [혼합 은행 결과](../reports/20261120-retail-candidate-pools.md) · [선택 위치 결과](../reports/20261124-framework-validity-review.md)

## 왜 바꾸는가

11월 27일에 돌린 실험 네 개는 모두 공용 실행기를 거치지 않았다.

- 은행 실험은 `scripts/run_banking_memory.py`의 실험별 `--series` 분기로 돌았다. 분기는 그날 2개에서 5개로 늘었다.
- 실험 전용 어댑터 `banking_memory_cohort.py`는 그날 만들어진 뒤 다섯 번 더 고쳐졌다.
- 작성 형식 다섯 개와 조회 방식 두 개는 코드 상수(`paired_repetitions.FORMS`, `MODES`)에 묶여 있다.

[연구 계획](../research/plan.md#실험자와-플랫폼의-역할)의 최종 목표는 탐구 에이전트가 저장·조회 방식을 스스로 바꿔 보는 프레임워크다. 다섯 형식과 자동 제공·자율 조회는 예시 정책이다. 따라서 작성 방식과 조회 방식은 고정 목록이 아니라 선언하는 값이어야 한다.

## 계획 파일

### 리테일 재방문의 최종 상담

[재방문 후속 계획](../../protocols/studies/retail-revisit-followup-03.json)은 11월 23일에 같은 현재 대화·주문 목록에서 조건부 조회를 허용했던 상담을 이어간다. 주 질문은 지난 주문을 가리킨 고객이 어느 주문인지 다시 알려 주지 않아도, 상담원이 현재 승인을 받아 목표 주문을 취소할 수 있었는가이다. 실제 메모와 빈 메모에는 같은 안내와 도구가 제공됐다. 메모는 첫 방문에서 당시 작성자들이 남긴 네 형식의 묶음이다. 이 비교가 평가하는 것은 고정한 기억의 조회와 활용이다. [기존 첫 판단과 등록 기준](../reports/20261123-retail-conditional-retrieval.md)

1. `plan resolve`는 원등록·첫 방문 154개의 작성 원본·체크포인트 영수증을 대조하고 실제 모델을 호출하기 직전의 네이티브 상태 622개를 복원한다. 77명의 첫 판단 1,848개와 사용량을 원기록에서 다시 집계한다. 안내가 같은 924쌍의 첫 요청이 맞아야 하며, 보관된 154쌍에서 실제 메모만 정답 75개, 빈 메모만 정답 3개가 재현된다. [사전 검증 결과](../../artifacts/analyses/20261128-retail-revisit-followup-v3-preflight.json)
2. 전체 상담 표본은 첫 판단 전에 정한 26명이다. 두 과거 이력, 세 현재 요청, 네 조건에 배정한 624개 모두가 점수표에 들어간다. 주 비교는 26명의 지난 주문 이력 52쌍이다. 현 주문을 직접 말한 두 유형에서는 현재 주문 존중 여부와 잘못된 취소 제안을 본다. 이 26명은 기존 77명에 포함된다. [표본 선정](../research/retail-conditional-retrieval-v1.md#어디까지-실행할-것인가)
3. 첫 판단에 도달한 622개 상담은 동일 세션·DB·기억의 사본에서 이어간다. 실행기는 상담을 시작하기 전에 별도 사본에서 다음 요청을 구성해 승인 금액으로 보낼 수 있는지 확인한다. 첫 요청을 보낼 수 없으면 원장과 미시작 배정을 보존한다. 실제 전송 후 한도가 소진되면 해당 상담과 확인·보류 비용을 기록하고 중단한다. HTTP 408·429·5xx 또는 전송 불명 장애가 두 상담 연속 발생하면 중단한다. 자격증명·경로를 공급자가 거부하면 첫 오류부터 중단 사유를 남긴다. 재개할 때 봉인된 상담은 원장의 종료 근거와 대조한다. 프로세스가 끊겼을 때 첫 전송 예약이 없고 원장에도 전송 증거가 없으면 시도 원본을 `unsubmitted/`에 보존한 뒤 같은 체크포인트에서 이어간다. 예약이 하나라도 있으면 배정을 다시 보내지 않는다. 실행기 잠금과 배치 시작 식별자로 중단 전 회차의 요약이 새 회차를 대신하지 않도록 한다.
4. 주 지표는 정상 종료, 정확한 주문의 취소, 대상·사유에 대한 현재 동의, 주문 식별 재질문 0회를 모두 충족한 상담이다. 조회 한도로 끝난 2개와 네이티브 단계·오류 한도 종료는 이 지표에서 실패다. 작업자의 요청 횟수·입력 길이 한도도 실패이며 해당 역할을 원장에서 검산한다. 고객 시뮬레이터의 같은 한도는 기술 결측이다. 종료 시점에 네이티브 DB 성적이 없으면 별도 DB 지표는 미채점으로 보존한다. 기술 장애나 최종 판독 불가로 주 결과를 알 수 없는 상담은 전체 배정의 최선·최악 범위에 포함한다. 목표 DB에 도달하지 못한 것으로 확인된 상담은 발화 판독 상태에 관계없이 주 지표에서 실패다. 되물음, 잘못된 제안, 동의를 갖춘 취소, 네이티브 DB 채점값도 함께 보고한다. 고객의 두 이력을 먼저 평균한 뒤 고객별로 같은 비중을 준다.
5. 주 비교 52쌍에서 완료된 상담은 모두 조건과 정답을 가린 공개 발화로 직접 판독한다. 지난 11월 22일의 같은 26명·기존 조회 안내에서 주 비교에 해당하는 완료 상담은 103건이었다. 자동 규칙이 재질문을 놓친 5건에서 기존 가림 판독과 주 지표가 달랐다. 실제 메모 4건, 빈 메모 1건이었다. 다른 조건은 명확한 교환에만 자동 규칙을 쓰고, 모호한 대화는 직접 판독한다. [보관된 상담별 결과](../../artifacts/analyses/20261122-retail-two-visit-results-with-recovery.json) · [재현 검사](https://github.com/yonsei-ai-labs/agent-memory/blob/40f881aa1f70f5772f52484a4f1a19d0de01162d/tests/test_study_retail_followup.py)
6. 점수표는 첫 판단까지와 후속 상담에서 각각 목록·본문 요청, 반환, 답변을 생성한 작업자 입력에 들어간 제목·본문을 집계한다. 배정별 행에는 입력의 요청 ID와 반환 사건을 연결하고, 답변이 확인되지 않은 요청의 노출은 별도 표시한다. 완료·한도 종료·공급자 오류는 원장에 남긴 종결 사유와 결과 파일을 대조한다.

전체 상담과 발화 판독을 마친 뒤, 1차 지표의 고객별 95% 구간과 전체 배정의 결측 범위가 같은 방향으로 0을 벗어나면 이 고객군의 개선 또는 악화로 판정한다. 나머지는 효과 미확정으로 마무리한다. 고객 26명으로 작은 차이까지 확정하기는 어렵다. 예를 들어 동률이 없는 독립 고객 26명에서 양측 5% 정확 부호검정은 19명 이상이 같은 방향이어야 한다. 실제 개선 확률이 65%인 경우 이 예시의 검정력은 약 26%다.

[v2 계획](../../protocols/studies/retail-revisit-followup-02.json)과 [v2 준비 기록](../../artifacts/analyses/20261128-retail-revisit-followup-v2-preflight.json), [v1 준비 기록](../../artifacts/analyses/20261128-retail-revisit-followup-preflight.json)과 [당시 계획](../../protocols/studies/retail-revisit-followup-01.json)은 보관한다.

`analyze --review-packets <새 JSON 경로>`로 판독할 공개 대화를 내보낸다. 실행 전 판독 담당자를 지정하고, 판독에는 이 파일만 전달한다. 담당자는 조건별 결과와 정답에 접근하지 않는 사람 또는 독립된 새 에이전트 세션으로 두고, 보고서에 판독 주체를 기록한다. 상담원이 발화에서 메모를 언급하면 배정을 짐작할 수 있으므로 원문을 보존하고 그런 사례를 판독 메모에 표시한다. 파일에는 발화와 해시만 있으며 같은 대화는 한 번 판독한다. `analyze --reviews <JSON 경로>`로 해시별 판독을 반영한다. 주 비교에는 `method=blinded_direct_read`를 기록한다. `status=reviewed`이면 `turns_sha256`·`clarifications`·`proposals`·`responses`를, 직접 읽어도 판단할 수 없으면 `status=unresolved`와 같은 발화 해시를 제출한다. 점수표의 `awaiting_review`는 아직 판독이 필요한 건수이고 `unresolved`는 최종 결측 건수다. [공개 발화 채점](../../scripts/analyze_retail_two_visit.py) · [계획 계약](../../schemas/retail-followup-plan-v1.schema.json)

주 비교는 각 고객에 두 쌍씩 있어 한쪽 결과 한 건을 끝내 판독할 수 없을 때마다 전체 배정 최선·최악 범위의 폭이 약 1.92%p 넓어진다. 개별 오류도 그대로 집계하고 표본을 교체하지 않는다. 고객 단위 구간 또는 결측 범위가 0을 포함하면 결론은 미확정이다. 77명의 첫 판단에서 관측한 차이는 전체 상담 성공률의 기대 효과나 검정력을 결정하지 않는다.

상세 설계 [5절의 정책 계약](../design/architecture.md#5-정책-계약) 용어를 따른다. v1.1의 `representation` 열거값은 기억 형식을 고정하므로, 이 계획에서는 표현 이름과 지침 내용을 직접 선언한다.

## 실행 단계

1. `plan validate`: 형식, 참조 파일 해시, 조합의 유일성, 무기억 조건의 정보 차단을 확인한다. 모델을 호출하지 않는다.
2. `plan resolve`는 선언한 모델을 벤치의 실제 설정과 대조한다. τ² 계열에서는 과제를 연결하고 배정과 요청 예약금 한도를 산출한다. 실행을 시작하면 `runs/<id>/resolved-plan.json`에 그 배정을 고정한다.
3. `run`: 고정된 계획과 같은 해시를 가진 사용자 승인 기록이 있을 때만 시작한다. 1회차 → 작성 → 2회차 순서로 돌고, 단계마다 영수증을 남긴다.
4. `resume`: 중단된 실행을 같은 계획으로 이어 간다. 이미 보낸 상담은 다시 보내지 않는다.
5. `analyze`: 저장된 원본만 읽어 점수표를 만든다.

```text
python -m agent_memory_eval.study plan validate --plan protocols/studies/<id>.json
python -m agent_memory_eval.study plan resolve --plan protocols/studies/<id>.json
python -m agent_memory_eval.study run --plan protocols/studies/<id>.json
python -m agent_memory_eval.study analyze --plan protocols/studies/<id>.json
```

공식 과제의 1·2회차는 벤치와 정책에 관계없이 다음 항목을 낸다. 재방문은 위에 정의한 상담별 짝비교를 사용한다.

### 조회 방식의 안내문

조회 방식마다 안내문(`notice`), 도구 설명(`tool_descriptions`) 또는 둘 다를 선언한다. 벤치가 실제로 보여 주지 못하는 조합은 실행 전에 거부한다.

| 조회 방식 | τ³ 은행·τ² 항공·리테일 | BFCL |
| --- | --- | --- |
| 자동 제공(`preload`) | 안내문을 시스템 지시의 기억 정책 블록에 넣고 기억 본문을 첫 사용자 메시지로 준다. | 안내문을 작업 지시 뒤에 붙이고 기억 본문을 준다. |
| 도구 설명만 있는 자율 조회 | 안내문 없이 첫 입력이 1회차와 같고 `memory_list`·`memory_get`만 더해진다. 안내문을 함께 선언하면 거부한다. | 안내문이 없으면 작업 지시가 1회차와 같다. |
| 안내문이 있는 자율 조회 | 기본 도구 설명과 함께 안내문을 기억 정책 블록에 넣는다. | 안내문을 작업 지시 뒤에 붙인다. |

v1 기록과 로컬 BFCL 어댑터는 제공 방식(`read_mode`)별로 조회 조건을 하나씩 지원한다. τ² 계열 v2에서는 시작 안내문 없이 조회 도구 설명만 다른 여러 조건을 같은 작성물에 배정할 수 있다. 자동 제공 조건은 하나이며, 시작 안내문을 사용하는 조건들은 하나의 안내문을 공유한다.

### 정책 A의 자유 작성과 자율 조회를 점검하는 개발 실험

기존 A는 1회차 공개 경험과 과제 전체의 성패를 받은 작업자가 사실·경험·절차·교훈·자유 형식별로 `memory_store`를 호출하게 한다. 자유 형식도 이미 여러 내용을 합칠 수 있다. 자동 제공은 메모를 첫 입력에 싣고, 자율 조회는 제목을 볼 수 있는 `memory_list`와 본문을 여는 `memory_get`을 제공한다. 은행·항공·리테일의 자율 조회 조건에서 채점된 358건 모두 목록 호출이 0회였다. [실제 1·2회차 결과](../reports/20261128-fresh-four-benchmarks-round1-2.md)

새 개발 계획은 리테일의 기존 개발 과제 25·66·44·6·47에서 무기억 원천을 세 개씩 재사용한다. 각 원천에서 기존 자유 작성과 새 자유 작성을 한 번씩 수행하고, 각각의 고정된 메모를 세 조건에 한 번씩 배정한다. 새 1회차 0건, 재사용 15건, 작성 30건, 2회차 90건으로 해석된다. [계획과 판정 기준](../../protocols/studies/retail-memory-reuse-dev-01.json)

- **작성 비교**는 자동 제공을 고정한다. 새 지침은 제목에 유용한 상황을 드러내고, 본문에서 요청·시도·확인된 결과를 구별한다. 이전 승낙이나 완료 상태가 지금도 유효해야 하는 결정에는 다시 확인할 근거를 적는다. 첫 공개 경험, 성패 피드백, 작성 모델, 저장 한도는 같다. [기존 공통 지침](../../protocols/instructions/required-experience-writer-v1.txt) · [새 자유 작성 지침](../../protocols/instructions/free-memory-reuse-v1.txt)
- **조회 비교**는 동일한 원천과 작성물에서 기존 도구 설명과 새 도구 설명을 대조한다. 새 조건은 `memory_list` 설명에서 현재 결정에 지난 맥락이 필요한 예를 든다. 두 자율 조회 조건 모두 같은 공개 업무 메시지로 시작한다. 제목은 목록을 호출한 뒤, 본문은 해당 메모를 요청한 뒤에 작업자가 볼 수 있다. 점수표는 조회 횟수와 성패를 집계한다. 관련 판단 전에 본문이 실제 입력에 포함됐는지는 요청별 노출 기록과 대화 원문을 함께 판독한다.
- 15개 원천이 모두 성공했고, 기존 자유 작성의 자동 제공 성적도 14/15였다. 개발 판정은 이전 동의·완료 상태를 잘못 가져온 빈도, 과도한 재확인, 공식 성패 악화, 토큰과 비용을 본다. 조회 문구는 관련 판단 전에 본문이 실제로 도달하고 이어진 행동이 현재의 근거와 맞는지도 본다. 회복 측정에는 실패 원천이 필요하고, 기억 자체의 효과를 추정하려면 동시 무기억 대조가 필요하다.

이 개발안을 실행할 경우 판독 담당자를 먼저 정한다. 조건명을 가린 두 상담의 공개 발화·업무 행동을 읽고, 현재 확인 전 이월한 주문·동의·완료 주장과 해당 발화 번호를 기록한다. 이후에 원천 및 실제 본문 노출과 연결한다. 두 자율 조건의 조회가 모두 0회라면 보고할 수 있는 관측은 조회 문구와 호출 빈도까지다.

### 1회차 재사용과 참조 기록

- `first_pass.reuse`의 기록에서 같은 과제·회차의 1회차를 찾는다. 원래 실행과 과제·네이티브 설정·첫 고객 발화·채점 기준·초기 DB가 같을 때만 재사용한다.
- 개발 비교에서 특정 원천 묶음을 고정할 때는 v2의 `first_pass.required_sources_sha256`를 사용한다. 과제·반복 순서의 `[배정 이름, 1회차 실행 ID, 로그 해시]` 목록을 정규 JSON으로 직렬화한 해시다. 리테일 개발 계획은 15개 원천 중 하나가 없거나 다른 실행으로 바뀌면 배정 단계에서 중단한다.
- 재사용하려던 1회차가 미채점이면 아래 예산·재시도 규칙을 적용한다. 실행 중 1회차 미채점이나 예산으로 2회차 묶음 전체가 시작되지 않으면 종료 기록의 사유를 배정별 결측으로 센다.
- τ²의 `references`는 과제·반복 이름이 겹치는 배정에서 실제 1회차 실행 ID와 봉인된 로그 해시까지 대조한다. 양쪽 원천이 봉인됐는데 다르면 분석을 중단한다. 한쪽 원천이 아직 없으면 해당 참조 배정을 사유가 있는 결측으로 싣는다. 원천이 일치하는 2회차를 `<기록 이름>/<조합>`으로 점수표에 싣는다.
- 장애 복구 기록처럼 다른 기록의 재시도인 경우 `attempt_of`로 원래 기록을 지정한다. 그러면 같은 배정의 다음 시도로 읽는다.

### 재시도

- 2회차 상담이 계획에 적은 HTTP 오류(`retry.http_codes`)로 끝나면 `wait_seconds` 간격으로 그 상담만 새 세션에서 다시 실행한다. 원래 기억과 원래 배정 번호를 그대로 쓴다.
- 처음 기록은 `solve/`에 그대로 남고 재시도는 `solve-retry-<n>/`에 쌓인다.
- 점수표는 배정마다 처음으로 채점된 시도를 쓰고, 재시도로 채점된 수를 따로 보인다.

### 단계 나누기와 판단 기록

- 1회차만 도는 계획: `conditions`를 비우면 작성·조회 없이 무기억 1회차만 돈다. 다음 계획은 `first_pass.reuse`로 이 기록을 원천으로 쓴다.
- 확인용 과제: `benchmark.confirmation_tasks`에 적은 과제는 분석과 정책 결정에 쓰지 않는다. 다음 정책 변경은 이 과제에서 판정한다.
- 판단 기록: `decision`에 가설, 예측, 판정 기준, 근거 파일을 적는다. 근거 파일은 경로와 해시로 고정되므로, 정책이 어떤 분석에서 나왔는지 끝까지 추적된다.

### 예산과 기술적 실패

- 공급자 요청은 보내기 전에 입력 바이트 기준 예약금을 잡는다. `plan resolve`는 첫 묶음 한도가 가장 큰 요청 예약금의 두 배보다 작으면 실행 전에 거부한다.
- 재사용할 1회차가 예산 가드(`BATCH_SPEND_LIMIT`)나 계획에 적은 HTTP 오류로 채점되지 않았으면, 다음 계획 안에서 같은 조건으로 그 1회차만 다시 돌린다(`replaces_first_pass`). 과제 때문에 실패한 1회차는 결측으로 남는다.
- τ²는 단계 상한에 걸린 상담을 0점으로 채점한다. 점수표도 이를 실패로 세고 `step_capped`로 따로 보인다.
- 재시도까지 모두 실패한 배정은 마지막 시도의 사유로 결측을 센다.

### 분석 저장

`analyze --save`는 배정별 행과 점수표를 `artifacts/studies/<계획 id>/`에 내용 해시 이름으로 남긴다. 배정별 행에는 원천과의 짝, 기억 제목·본문, 시작 제공 여부, 조회 수, 첫 업무 호출(기억 조회와 문장 답변을 건너뛴 첫 도구 호출), 공식 성패, 토큰, 비용이 들어간다. `--tasks`로 개발용·확인용 과제만 따로 점수화한다.

## 명령과 승인

```text
python -m agent_memory_eval.study plan validate --plan <계획>
python -m agent_memory_eval.study plan resolve --plan <계획> --workspace <저장소>
python -m agent_memory_eval.study authorize --plan <계획> --max-usd <금액> --quote "<사용자 승인 문장>"
python -m agent_memory_eval.study run --plan <계획> --workspace <저장소>
python -m agent_memory_eval.study analyze --plan <계획> --workspace <저장소>
```

- 실행 기록은 `--workspace`의 `runs/`에 쓰고, 승인·계획·분석 파일은 코드 저장소에 둔다. 실행 폴더가 심볼릭 링크를 거치면 기록 장치가 거부한다.
- τ² 실행에는 `artifacts/approvals/<계획 id>.json`이 필요하다. 이 기록은 계획 해시, 해석된 배정 해시, 배정 수, 금액 한도, 사용자의 승인 문장을 담는다. 계획이나 배정이 바뀌면 실행하지 않는다.
- 현재 BFCL 어댑터는 로컬 체크포인트로 추론한다. 표준 Luna 프로필은 `plan resolve` 단계에서 모델 불일치로 중단된다. BFCL의 Luna 본실험에는 해당 모델을 실제로 호출하고 요청과 응답을 기록하는 경로가 필요하다. 명시적으로 등록한 로컬 모델 비교는 `--checkout`, `--model-python`, `--checkpoint`를 사용한다.
- 실행 전에도 `analyze`를 쓸 수 있다. 이때는 재사용 1회차와 참조 기록만 읽는다.
- `resume`은 같은 계획으로 이어 간다. 봉인된 묶음은 다시 보내지 않는다.
