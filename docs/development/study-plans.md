# 선언형 실험 계획과 공용 실행기

2026-11-28 · [프레임워크와 점수 체계 보완 계획](framework-scoring-plan.md)의 3단계(실행 계층) 구현 설계

**새 실험은 계획 파일 하나로 만든다.** 벤치, 과제, 1회차, 작성 방식, 조회 방식, 반복, 예산, 재시도를 선언한다. 같은 실행기가 돌리고 같은 점수표로 무기억과 다른 정책을 비교한다. 실험을 추가하려고 실행 코드를 고치거나 분기를 더하지 않는다.

## 왜 바꾸는가

11월 27일에 돌린 실험 네 개는 모두 공용 실행기를 거치지 않았다.

- 은행 실험은 `scripts/run_banking_memory.py`의 실험별 `--series` 분기로 돌았다. 분기는 그날 2개에서 5개로 늘었다.
- 실험 전용 어댑터 `banking_memory_cohort.py`는 그날 만들어진 뒤 다섯 번 더 고쳐졌다.
- 작성 형식 다섯 개와 조회 방식 두 개는 코드 상수(`paired_repetitions.FORMS`, `MODES`)에 묶여 있다.

[연구 계획](../research/plan.md#실험자와-플랫폼의-역할)의 최종 목표는 탐구 에이전트가 저장·조회 방식을 스스로 바꿔 보는 프레임워크다. 다섯 형식과 자동 제공·자율 조회는 예시 정책이다. 따라서 작성 방식과 조회 방식은 고정 목록이 아니라 선언하는 값이어야 한다.

## 계획 파일

### 리테일 재방문의 최종 상담

[재방문 후속 계획](../../protocols/studies/retail-revisit-followup-02.json)은 11월 23일에 같은 현재 대화·주문 목록에서 조건부 조회를 허용했던 상담을 이어간다. 주 질문은 지난 주문을 가리킨 고객이 어느 주문인지 다시 알려 주지 않아도, 상담원이 현재 승인을 받아 목표 주문을 취소할 수 있었는가이다. 실제 메모와 빈 메모에는 같은 안내와 도구가 제공됐다. 메모는 첫 방문에서 당시 작성자들이 남긴 네 형식의 묶음이다. 이 비교가 평가하는 것은 고정한 기억의 조회와 활용이다. [기존 첫 판단과 등록 기준](../reports/20261123-retail-conditional-retrieval.md)

1. `plan resolve`는 원등록·첫 방문 154개의 작성 원본·체크포인트 영수증을 대조하고 실제 모델을 호출하기 직전의 네이티브 상태 622개를 복원한다. 77명의 첫 판단 1,848개와 사용량을 원기록에서 다시 집계한다. 안내가 같은 924쌍의 첫 요청이 맞아야 하며, 보관된 154쌍에서 실제 메모만 정답 75개, 빈 메모만 정답 3개가 재현된다. [사전 검증 결과](../../artifacts/analyses/20261128-retail-revisit-followup-v2-preflight.json)
2. 전체 상담 표본은 첫 판단 전에 정한 26명이다. 두 과거 이력, 세 현재 요청, 네 조건에 배정한 624개 모두가 점수표에 들어간다. 주 비교는 26명의 지난 주문 이력 52쌍이다. 현 주문을 직접 말한 두 유형에서는 현재 주문 존중 여부와 잘못된 취소 제안을 본다. 이 26명은 기존 77명에 포함된다. [표본 선정](../research/retail-conditional-retrieval-v1.md#어디까지-실행할-것인가)
3. 첫 판단에 도달한 622개 상담은 동일 세션·DB·기억의 사본에서 이어간다. 실행기는 상담을 시작하기 전에 별도 사본에서 다음 요청을 구성해 승인 금액으로 보낼 수 있는지 확인한다. 첫 요청을 보낼 수 없으면 원장과 미시작 배정을 보존한다. 실제 전송 후 한도가 소진되면 해당 상담과 확인·보류 비용을 기록하고 중단한다. HTTP 408·429·5xx 또는 전송 불명 장애가 두 상담 연속 발생하면 중단한다. 자격증명·경로를 공급자가 거부하면 첫 오류부터 중단 사유를 남긴다. 재개할 때 봉인된 상담은 원장의 종료 근거와 대조한다.
4. 주 지표는 정상 종료, 정확한 주문의 취소, 대상·사유에 대한 현재 동의, 주문 식별 재질문 0회를 모두 충족한 상담이다. 조회 한도로 끝난 2개와 네이티브 단계·오류 한도 종료는 이 지표에서 실패다. 기술 장애나 최종 판독 불가로 주 결과를 알 수 없는 상담은 전체 배정의 최선·최악 범위에 포함한다. 목표 DB에 도달하지 못한 것으로 확인된 상담은 발화 판독 상태에 관계없이 주 지표에서 실패다. 되물음, 잘못된 제안, 동의를 갖춘 취소, 네이티브 DB 채점값도 함께 보고한다. 고객의 두 이력을 먼저 평균한 뒤 고객별로 같은 비중을 준다.
5. 주 비교 52쌍에서 완료된 상담은 모두 조건과 정답을 가린 공개 발화로 직접 판독한다. 지난 11월 22일의 같은 26명·기존 조회 안내에서 주 비교에 해당하는 완료 상담은 103건이었다. 자동 규칙이 재질문을 놓친 5건에서 기존 가림 판독과 주 지표가 달랐다. 실제 메모 4건, 빈 메모 1건이었다. 다른 조건은 명확한 교환에만 자동 규칙을 쓰고, 모호한 대화는 직접 판독한다. [보관된 상담별 결과](../../artifacts/analyses/20261122-retail-two-visit-results-with-recovery.json) · [재현 검사](../../tests/test_study_retail_followup.py)
6. 점수표는 첫 판단까지와 후속 상담에서 각각 목록·본문 요청, 반환, 답변을 생성한 작업자 입력에 들어간 제목·본문을 집계한다. 배정별 행에는 입력의 요청 ID와 반환 사건을 연결하고, 답변이 확인되지 않은 요청의 노출은 별도 표시한다. 완료·한도 종료·공급자 오류는 원장에 남긴 종결 사유와 결과 파일을 대조한다.

전체 상담과 발화 판독을 마친 뒤, 1차 지표의 고객별 95% 구간과 전체 배정의 결측 범위가 같은 방향으로 0을 벗어나면 이 고객군의 개선 또는 악화로 판정한다. 나머지는 효과 미확정으로 마무리한다. 고객 26명으로 작은 차이까지 확정하기는 어렵다. 예를 들어 동률이 없는 독립 고객 26명에서 양측 5% 정확 부호검정은 19명 이상이 같은 방향이어야 한다. 실제 개선 확률이 65%인 경우 이 예시의 검정력은 약 26%다.

```bash
plan=protocols/studies/retail-revisit-followup-02.json
uv run python -m agent_memory_eval.study plan resolve --plan "$plan"
uv run python -m agent_memory_eval.study analyze --plan "$plan"
```

유료 실행에는 이 계획에 승인된 금액과 실제 승인 발언을 `authorize`에 전달하고 코드·승인 기록을 커밋한다. 첫 판단의 과거 지출과 후속 상담의 신규 지출을 각각 집계한다. [v1 준비 기록](../../artifacts/analyses/20261128-retail-revisit-followup-preflight.json)과 [당시 계획](../../protocols/studies/retail-revisit-followup-01.json)은 보관한다.

`analyze --review-packets <새 JSON 경로>`로 판독할 공개 대화를 내보낸다. 판독자에게는 이 파일을 전달한다. 파일에는 발화와 해시만 있으며 같은 대화는 한 번 판독한다. `analyze --reviews <JSON 경로>`로 해시별 판독을 반영한다. 주 비교에는 `method=blinded_direct_read`를 기록한다. `status=reviewed`이면 `turns_sha256`·`clarifications`·`proposals`·`responses`를, 직접 읽어도 판단할 수 없으면 `status=unresolved`와 같은 발화 해시를 제출한다. 점수표의 `awaiting_review`는 아직 판독이 필요한 건수이고 `unresolved`는 최종 결측 건수다. [공개 발화 채점](../../scripts/analyze_retail_two_visit.py) · [계획 계약](../../schemas/retail-followup-plan-v1.schema.json)

### 공식 과제의 1·2회차

새 실행은 `agent-memory-study-plan/v2`에 사용할 모델을 명시한다. 기존 v1 계획은 원래 식별자로 검증·분석한다. [스키마](../../schemas/study-plan-v1.schema.json)

| 항목 | 내용 |
| --- | --- |
| `id`, `purpose`, `question` | 실행 이름, 개발·확인 구분, 이 실행으로 알고 싶은 것 |
| `models` | 표준 프로필의 경로와 해시. 다른 모델을 연구하는 계획은 별도 프로필과 `comparison: true`를 선언한다. [표준 모델과 역할](../../protocols/models/project-standard-v1.json) |
| `benchmark` | 어댑터 이름, 고정된 벤치 설정 파일, 과제 목록 |
| `first_pass` | 무기억 1회차를 새로 돌릴 횟수, 또는 다시 쓸 기록 |
| `writing` | 공통 작성 지침, 작성자 피드백(`none`, `result_only`), 표현별 지침. 표현 이름은 자유롭다. |
| `reading` | 조회 방식별 제공 방식(`preload`, `on_demand`), 안내문, 도구 설명. 이름은 자유롭다. |
| `conditions` | 실행할 표현×조회 조합 |
| `references` | 같은 원천에서 이미 기록된 정책 결과. 새로 실행하지 않고 점수표에 함께 싣는다. |
| `repeats`, `limits`, `budget`, `retry` | 반복 수, 입력·호출 한도, 누적 금액 한도, 재시도 대상 오류와 대기 간격 |

상세 설계 [5절의 정책 계약](../design/architecture.md#5-정책-계약) 용어를 따른다. v1.1의 `representation` 열거값은 기억 형식을 고정하므로, 이 계획에서는 표현 이름과 지침 내용을 직접 선언한다.

## 실행 단계

1. `plan validate`: 형식, 참조 파일 해시, 조합의 유일성, 무기억 조건의 정보 차단을 확인한다. 모델을 호출하지 않는다.
2. `plan resolve`는 선언한 모델을 벤치의 실제 설정과 대조한다. τ² 계열에서는 과제를 연결하고 배정과 요청 예약금 한도를 산출한다. 실행을 시작하면 `runs/<id>/resolved-plan.json`에 그 배정을 고정한다.
3. `run`: 고정된 계획과 같은 해시를 가진 사용자 승인 기록이 있을 때만 시작한다. 1회차 → 작성 → 2회차 순서로 돌고, 단계마다 영수증을 남긴다.
4. `resume`: 중단된 실행을 같은 계획으로 이어 간다. 이미 보낸 상담은 다시 보내지 않는다.
5. `analyze`: 저장된 원본만 읽어 점수표를 만든다.

```text
python -m agent_memory_eval.study plan validate --plan protocols/studies/<id>.json
python -m agent_memory_eval.study plan resolve --plan protocols/studies/<id>.json
python -m agent_memory_eval.study run --plan protocols/studies/<id>.json
python -m agent_memory_eval.study analyze --plan protocols/studies/<id>.json
```

## 점수표

벤치와 정책에 관계없이 같은 항목을 낸다.

- 조건별 배정 수, 채점 수, 결측 사유별 수
- 성공 수와 성공률. 무기억 기준은 같은 과제의 1회차 성공률 평균이다.
- 자기 원천 대비 회복(실패→성공)과 악화(성공→실패)
- 같은 원천을 공유한 두 조건이 모두 성공한 상담에서의 업무 호출·토큰 차이
- 기억 노출: 시작 제공 여부, 목록·본문 조회 수
- 단계별 비용과 호출 수

어댑터는 과제 준비, 단계 실행, 결과 판독 세 가지만 맡는다. 정책 해석·배정·예산·재시도·점수표는 공용 코드가 맡는다.

### 조회 방식의 안내문

조회 방식마다 안내문(`notice`), 도구 설명(`tool_descriptions`) 또는 둘 다를 선언한다. 벤치가 실제로 보여 주지 못하는 조합은 실행 전에 거부한다.

| 조회 방식 | τ³ 은행·τ² 항공·리테일 | BFCL |
| --- | --- | --- |
| 자동 제공(`preload`) | 안내문을 시스템 지시의 기억 정책 블록에 넣고 기억 본문을 첫 사용자 메시지로 준다. | 안내문을 작업 지시 뒤에 붙이고 기억 본문을 준다. |
| 도구 설명만 있는 자율 조회 | 안내문 없이 첫 입력이 1회차와 같고 `memory_list`·`memory_get`만 더해진다. 안내문을 함께 선언하면 거부한다. | 안내문이 없으면 작업 지시가 1회차와 같다. |
| 안내문이 있는 자율 조회 | 기본 도구 설명과 함께 안내문을 기억 정책 블록에 넣는다. | 안내문을 작업 지시 뒤에 붙인다. |

v1 기록과 로컬 BFCL 어댑터는 제공 방식(`read_mode`)별로 조회 조건을 하나씩 지원한다. τ² 계열 v2에서는 시작 안내문 없이 조회 도구 설명만 다른 여러 조건을 같은 작성물에 배정할 수 있다. 자동 제공 조건은 하나이며, 시작 안내문을 사용하는 조건들은 하나의 안내문을 공유한다.

### 정책 A의 자유 작성과 자율 조회를 점검하는 개발 실험

기존 A는 1회차 공개 경험과 과제 전체의 성패를 받은 작업자가 사실·경험·절차·교훈·자유 형식별로 `memory_store`를 호출하게 한다. 자유 형식도 이미 여러 내용을 합칠 수 있다. 자동 제공은 메모를 첫 입력에 싣고, 자율 조회는 제목을 볼 수 있는 `memory_list`와 본문을 여는 `memory_get`을 제공한다. 은행·항공·리테일의 자율 조회 조건에서 채점된 358건 모두 목록 호출이 0회였다. [실제 1·2회차 결과](../reports/20261128-fresh-four-benchmarks-round1-2.md)

새 개발 계획은 리테일의 기존 개발 과제 25·66·44·6·47에서 무기억 원천을 세 개씩 재사용한다. 각 원천에서 기존 자유 작성과 새 자유 작성을 한 번씩 수행하고, 각각의 고정된 메모를 세 조건에 한 번씩 배정한다. 새 1회차 0건, 재사용 15건, 작성 30건, 2회차 90건으로 해석된다. [계획과 판정 기준](../../protocols/studies/retail-memory-reuse-dev-01.json)

- **작성 비교**는 자동 제공을 고정한다. 새 지침은 제목에 유용한 상황을 드러내고, 본문에서 요청·시도·확인된 결과를 구별한다. 이전 승낙이나 완료 상태가 지금도 유효해야 하는 결정에는 다시 확인할 근거를 적는다. 첫 공개 경험, 성패 피드백, 작성 모델, 저장 한도는 같다. [기존 공통 지침](../../protocols/instructions/required-experience-writer-v1.txt) · [새 자유 작성 지침](../../protocols/instructions/free-memory-reuse-v1.txt)
- **조회 비교**는 동일한 원천과 작성물에서 기존 도구 설명과 새 도구 설명을 대조한다. 새 조건은 `memory_list` 설명에서 현재 결정에 지난 맥락이 필요한 예를 든다. 두 자율 조회 조건 모두 같은 공개 업무 메시지로 시작한다. 제목은 목록을 호출한 뒤, 본문은 해당 메모를 요청한 뒤에 작업자가 볼 수 있다. 점수표는 조회 횟수와 성패를 집계한다. 관련 판단 전에 본문이 실제 입력에 포함됐는지는 요청별 노출 기록과 대화 원문을 함께 판독한다.
- 15개 원천이 모두 성공했고, 기존 자유 작성의 자동 제공 성적도 14/15였다. 개발 판정은 이전 동의·완료 상태를 잘못 가져온 빈도, 과도한 재확인, 공식 성패 악화, 토큰과 비용을 본다. 조회 문구는 관련 판단 전에 본문이 실제로 도달하고 이어진 행동이 현재의 근거와 맞는지도 본다. 회복 측정에는 실패 원천이 필요하고, 기억 자체의 효과를 추정하려면 동시 무기억 대조가 필요하다.

### 1회차 재사용과 참조 기록

- `first_pass.reuse`의 기록에서 같은 과제·회차의 1회차를 찾는다. 원래 실행과 과제·네이티브 설정·첫 고객 발화·채점 기준·초기 DB가 같을 때만 재사용한다.
- 개발 비교에서 특정 원천 묶음을 고정할 때는 v2의 `first_pass.required_sources_sha256`를 사용한다. 과제·반복 순서의 `[배정 이름, 1회차 실행 ID, 로그 해시]` 목록을 정규 JSON으로 직렬화한 해시다. 리테일 개발 계획은 15개 원천 중 하나가 없거나 다른 실행으로 바뀌면 배정 단계에서 중단한다.
- 재사용하려던 1회차가 미채점이면 아래 예산·재시도 규칙을 적용한다. 실행 중 1회차 미채점이나 예산으로 2회차 묶음 전체가 시작되지 않으면 종료 기록의 사유를 배정별 결측으로 센다.
- τ²의 `references`는 과제·반복 이름이 겹치는 배정에서 실제 1회차 실행 ID와 봉인된 로그 해시까지 대조한다. 원천이 일치하는 2회차를 `<기록 이름>/<조합>`으로 점수표에 싣는다.
- 장애 복구 기록처럼 다른 기록의 재시도인 경우 `attempt_of`로 원래 기록을 지정한다. 그러면 같은 배정의 다음 시도로 읽는다.

### 재시도

- 2회차 상담이 계획에 적은 HTTP 오류(`retry.http_codes`)로 끝나면 `wait_seconds` 간격으로 그 상담만 새 세션에서 다시 실행한다. 원래 기억과 원래 배정 번호를 그대로 쓴다.
- 처음 기록은 `solve/`에 그대로 남고 재시도는 `solve-retry-<n>/`에 쌓인다.
- 점수표는 배정마다 처음으로 채점된 시도를 쓰고, 재시도로 채점된 수를 따로 보인다.

### 단계 나누기와 판단 기록

- 1회차만 도는 계획: `conditions`를 비우면 작성·조회 없이 무기억 1회차만 돈다. 다음 계획은 `first_pass.reuse`로 이 기록을 원천으로 쓴다.
- 확인용 과제: `benchmark.confirmation_tasks`에 적은 과제는 분석과 정책 결정에 쓰지 않는다. 다음 정책 변경은 이 과제에서 판정한다.
- 판단 기록: `decision`에 가설, 예측, 판정 기준, 근거 파일을 적는다. 근거 파일은 경로와 해시로 고정되므로, 정책이 어떤 분석에서 나왔는지 끝까지 추적된다.

### 예산과 기술적 실패

- 공급자 요청은 보내기 전에 입력 바이트 기준 예약금을 잡는다. `plan resolve`는 첫 묶음 한도가 가장 큰 요청 예약금의 두 배보다 작으면 실행 전에 거부한다.
- 재사용할 1회차가 예산 가드(`BATCH_SPEND_LIMIT`)나 계획에 적은 HTTP 오류로 채점되지 않았으면, 다음 계획 안에서 같은 조건으로 그 1회차만 다시 돌린다(`replaces_first_pass`). 과제 때문에 실패한 1회차는 결측으로 남는다.
- τ²는 단계 상한에 걸린 상담을 0점으로 채점한다. 점수표도 이를 실패로 세고 `step_capped`로 따로 보인다.
- 재시도까지 모두 실패한 배정은 마지막 시도의 사유로 결측을 센다.

### 분석 저장

`analyze --save`는 배정별 행과 점수표를 `artifacts/studies/<계획 id>/`에 내용 해시 이름으로 남긴다. 배정별 행에는 원천과의 짝, 기억 제목·본문, 시작 제공 여부, 조회 수, 첫 업무 호출(기억 조회와 문장 답변을 건너뛴 첫 도구 호출), 공식 성패, 토큰, 비용이 들어간다. `--tasks`로 개발용·확인용 과제만 따로 점수화한다.

## 명령과 승인

```text
python -m agent_memory_eval.study plan validate --plan <계획>
python -m agent_memory_eval.study plan resolve --plan <계획> --workspace <저장소>
python -m agent_memory_eval.study authorize --plan <계획> --max-usd <금액> --quote "<사용자 승인 문장>"
python -m agent_memory_eval.study run --plan <계획> --workspace <저장소>
python -m agent_memory_eval.study analyze --plan <계획> --workspace <저장소>
```

- 실행 기록은 `--workspace`의 `runs/`에 쓰고, 승인·계획·분석 파일은 코드 저장소에 둔다. 실행 폴더가 심볼릭 링크를 거치면 기록 장치가 거부한다.
- τ² 실행에는 `artifacts/approvals/<계획 id>.json`이 필요하다. 이 기록은 계획 해시, 해석된 배정 해시, 배정 수, 금액 한도, 사용자의 승인 문장을 담는다. 계획이나 배정이 바뀌면 실행하지 않는다.
- 현재 BFCL 어댑터는 로컬 체크포인트로 추론한다. 표준 Luna 프로필은 `plan resolve` 단계에서 모델 불일치로 중단된다. BFCL의 Luna 본실험에는 해당 모델을 실제로 호출하고 요청과 응답을 기록하는 경로가 필요하다. 명시적으로 등록한 로컬 모델 비교는 `--checkout`, `--model-python`, `--checkpoint`를 사용한다.
- 실행 전에도 `analyze`를 쓸 수 있다. 이때는 재사용 1회차와 참조 기록만 읽는다.
- `resume`은 같은 계획으로 이어 간다. 봉인된 묶음은 다시 보내지 않는다.
