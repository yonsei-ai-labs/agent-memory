# 선언형 실험 계획과 공용 실행기

2026-11-27 · [프레임워크와 점수 체계 보완 계획](framework-scoring-plan.md)의 3단계(실행 계층) 구현 설계

**새 실험은 계획 파일 하나로 만든다.** 벤치, 과제, 1회차, 작성 방식, 조회 방식, 반복, 예산, 재시도를 선언한다. 같은 실행기가 돌리고 같은 점수표로 무기억과 다른 정책을 비교한다. 실험을 추가하려고 실행 코드를 고치거나 분기를 더하지 않는다.

## 왜 바꾸는가

11월 27일에 돌린 실험 네 개는 모두 공용 실행기를 거치지 않았다.

- 은행 실험은 `scripts/run_banking_memory.py`의 실험별 `--series` 분기로 돌았다. 분기는 그날 2개에서 5개로 늘었다.
- 실험 전용 어댑터 `banking_memory_cohort.py`는 그날 만들어진 뒤 다섯 번 더 고쳐졌다.
- 작성 형식 다섯 개와 조회 방식 두 개는 코드 상수(`paired_repetitions.FORMS`, `MODES`)에 묶여 있다.

[연구 계획](../research/plan.md#실험자와-플랫폼의-역할)의 최종 목표는 탐구 에이전트가 저장·조회 방식을 스스로 바꿔 보는 프레임워크다. 다섯 형식과 자동 제공·자율 조회는 예시 정책이다. 따라서 작성 방식과 조회 방식은 고정 목록이 아니라 선언하는 값이어야 한다.

## 계획 파일

형식은 `agent-memory-study-plan/v1`이다. [스키마](../../schemas/study-plan-v1.schema.json)

| 항목 | 내용 |
| --- | --- |
| `id`, `purpose`, `question` | 실행 이름, 개발·확인 구분, 이 실행으로 알고 싶은 것 |
| `benchmark` | 어댑터 이름, 고정된 벤치 설정 파일, 과제 목록 |
| `first_pass` | 무기억 1회차를 새로 돌릴 횟수, 또는 다시 쓸 기록 |
| `writing` | 공통 작성 지침, 작성자 피드백(`none`, `result_only`), 표현별 지침. 표현 이름은 자유롭다. |
| `reading` | 조회 방식별 제공 방식(`preload`, `on_demand`), 안내문, 도구 설명. 이름은 자유롭다. |
| `conditions` | 실행할 표현×조회 조합 |
| `references` | 같은 원천에서 이미 기록된 정책 결과. 새로 실행하지 않고 점수표에 함께 싣는다. |
| `repeats`, `limits`, `budget`, `retry` | 반복 수, 입력·호출 한도, 누적 금액 한도, 재시도 대상 오류와 대기 간격 |

상세 설계 [5절의 정책 계약](../design/architecture.md#5-정책-계약) 용어를 따른다. v1.1의 `representation` 열거값은 기억 형식을 고정하므로, 이 계획에서는 표현 이름과 지침 내용을 직접 선언한다.

## 실행 단계

1. `plan validate`: 형식, 참조 파일 해시, 조합의 유일성, 무기억 조건의 정보 차단을 확인한다. 모델을 호출하지 않는다.
2. `plan resolve`: 과제를 벤치에 연결하고 배정 목록과 비용 추정을 만든다. 결과는 `runs/<id>/resolved-plan.json`에 해시와 함께 고정된다.
3. `run`: 고정된 계획과 같은 해시를 가진 사용자 승인 기록이 있을 때만 시작한다. 1회차 → 작성 → 2회차 순서로 돌고, 단계마다 영수증을 남긴다.
4. `resume`: 중단된 실행을 같은 계획으로 이어 간다. 이미 보낸 상담은 다시 보내지 않는다.
5. `analyze`: 저장된 원본만 읽어 점수표를 만든다.

```text
python -m agent_memory_eval.study plan validate --plan protocols/studies/<id>.json
python -m agent_memory_eval.study plan resolve --plan protocols/studies/<id>.json
python -m agent_memory_eval.study run --plan protocols/studies/<id>.json
python -m agent_memory_eval.study analyze --plan protocols/studies/<id>.json
```

## 점수표

벤치와 정책에 관계없이 같은 항목을 낸다.

- 조건별 배정 수, 채점 수, 결측 사유별 수
- 성공 수와 성공률. 무기억 기준은 같은 과제의 1회차 성공률 평균이다.
- 자기 원천 대비 회복(실패→성공)과 악화(성공→실패)
- 같은 원천을 공유한 두 조건이 모두 성공한 상담에서의 업무 호출·토큰 차이
- 기억 노출: 시작 제공 여부, 목록·본문 조회 수
- 단계별 비용과 호출 수

τ² 세 어댑터는 같은 단계 실행 코드를 쓴다. 도메인마다 다른 것은 과제 묶음과 분할, 채점 기준, 기본 업무 도구, 채점기 연결뿐이다.

어댑터는 과제 준비, 단계 실행, 결과 판독 세 가지만 맡는다. 정책 해석·배정·예산·재시도·점수표는 공용 코드가 맡는다.

### 조회 방식의 안내문

조회 방식마다 안내문(`notice`), 도구 설명(`tool_descriptions`) 또는 둘 다를 선언한다. 벤치가 실제로 보여 주지 못하는 조합은 실행 전에 거부한다.

| 조회 방식 | τ³ 은행 | BFCL |
| --- | --- | --- |
| 자동 제공(`preload`) | 안내문을 시스템 지시의 기억 정책 블록에 넣고 기억 본문을 첫 사용자 메시지로 준다. | 안내문을 작업 지시 뒤에 붙이고 기억 본문을 준다. |
| 도구 설명만 있는 자율 조회 | 안내문 없이 첫 입력이 1회차와 같고 `memory_list`·`memory_get`만 더해진다. 안내문을 함께 선언하면 거부한다. | 안내문이 없으면 작업 지시가 1회차와 같다. |
| 안내문이 있는 자율 조회 | 기본 도구 설명과 함께 안내문을 기억 정책 블록에 넣는다. | 안내문을 작업 지시 뒤에 붙인다. |

v1에는 두 가지 제한이 있다. 한 계획에서 조회 방식은 제공 방식(`read_mode`)마다 하나만 둔다. 은행에서 안내문을 보이는 조회 방식들은 같은 안내문을 쓴다. 다른 안내문을 비교하려면 계획을 나누고, 같은 원천을 `references`로 연결한다.

### 1회차 재사용과 참조 기록

- `first_pass.reuse`의 기록에서 같은 과제·회차의 1회차를 찾는다. 원래 실행과 과제·네이티브 설정·첫 고객 발화·채점 기준·초기 DB가 같을 때만 재사용한다.
- 채점되지 않은 1회차는 다시 돌리지 않고 결측으로 남는다. 그 원천의 작성·2회차도 결측으로 센다.
- `references`의 기록은 새로 실행하지 않는다. 같은 원천의 2회차 결과를 `<기록 이름>/<조합>` 조건으로 점수표에 싣는다.
- 장애 복구 기록처럼 다른 기록의 재시도인 경우 `attempt_of`로 원래 기록을 지정한다. 그러면 같은 배정의 다음 시도로 읽는다.

### 재시도

- 2회차 상담이 계획에 적은 HTTP 오류(`retry.http_codes`)로 끝나면 `wait_seconds` 간격으로 그 상담만 새 세션에서 다시 실행한다. 원래 기억과 원래 배정 번호를 그대로 쓴다.
- 처음 기록은 `solve/`에 그대로 남고 재시도는 `solve-retry-<n>/`에 쌓인다.
- 점수표는 배정마다 처음으로 채점된 시도를 쓰고, 재시도로 채점된 수를 따로 보인다.

### 단계 나누기와 판단 기록

- 1회차만 도는 계획: `conditions`를 비우면 작성·조회 없이 무기억 1회차만 돈다. 다음 계획은 `first_pass.reuse`로 이 기록을 원천으로 쓴다.
- 확인용 과제: `benchmark.confirmation_tasks`에 적은 과제는 분석과 정책 결정에 쓰지 않는다. 다음 정책 변경은 이 과제에서 판정한다.
- 판단 기록: `decision`에 가설, 예측, 판정 기준, 근거 파일을 적는다. 근거 파일은 경로와 해시로 고정되므로, 정책이 어떤 분석에서 나왔는지 끝까지 추적된다.

### 예산과 기술적 실패

- 공급자 요청은 보내기 전에 입력 바이트 기준 예약금을 잡는다. `plan resolve`는 첫 묶음 한도가 가장 큰 요청 예약금의 두 배보다 작으면 실행 전에 거부한다.
- 재사용할 1회차가 예산 가드(`BATCH_SPEND_LIMIT`)나 계획에 적은 HTTP 오류로 채점되지 않았으면, 다음 계획 안에서 같은 조건으로 그 1회차만 다시 돌린다(`replaces_first_pass`). 과제 때문에 실패한 1회차는 결측으로 남는다.
- τ²는 단계 상한에 걸린 상담을 0점으로 채점한다. 점수표도 이를 실패로 세고 `step_capped`로 따로 보인다.
- 재시도까지 모두 실패한 배정은 마지막 시도의 사유로 결측을 센다.

### 분석 저장

`analyze --save`는 배정별 행과 점수표를 `artifacts/studies/<계획 id>/`에 내용 해시 이름으로 남긴다. 배정별 행에는 원천과의 짝, 기억 제목·본문, 시작 제공 여부, 조회 수, 첫 업무 호출(기억 조회와 문장 답변을 건너뛴 첫 도구 호출), 공식 성패, 토큰, 비용이 들어간다. `--tasks`로 개발용·확인용 과제만 따로 점수화한다.

## 명령과 승인

```text
python -m agent_memory_eval.study plan validate --plan <계획>
python -m agent_memory_eval.study plan resolve --plan <계획> --workspace <저장소>
python -m agent_memory_eval.study authorize --plan <계획> --max-usd <금액> --quote "<사용자 승인 문장>"
python -m agent_memory_eval.study run --plan <계획> --workspace <저장소>
python -m agent_memory_eval.study analyze --plan <계획> --workspace <저장소>
```

- 실행 기록은 `--workspace`의 `runs/`에 쓰고, 승인·계획·분석 파일은 코드 저장소에 둔다. 실행 폴더가 심볼릭 링크를 거치면 기록 장치가 거부한다.
- τ² 실행에는 `artifacts/approvals/<계획 id>.json`이 필요하다. 이 기록은 계획 해시, 해석된 배정 해시, 배정 수, 금액 한도, 사용자의 승인 문장을 담는다. 계획이나 배정이 바뀌면 실행하지 않는다.
- BFCL은 로컬 모델이라 청구액이 없다. 실행에는 `--checkout`, `--model-python`, `--checkpoint`를 준다.
- 실행 전에도 `analyze`를 쓸 수 있다. 이때는 재사용 1회차와 참조 기록만 읽는다.
- `resume`은 같은 계획으로 이어 간다. 봉인된 묶음은 다시 보내지 않는다.

## 검토한 방식

| 방식 | 판단 |
| --- | --- |
| 기존 `policy_round`를 넓힌다 | 은행 쪽이 `scripts/run_banking_policy_cycle.py`로 넘어가고, 계좌 개설 프로필 하나만 받는다. 은행 실행 경로가 두 개로 남아 채택하지 않았다. |
| 새 계획 형식과 공용 실행기를 만들고 실행 핵심은 재사용한다 | 채택했다. 실험마다 달라진 부분(경로 상수, 형식·조회 하드코딩, 실험별 분기)만 계획으로 옮긴다. |
| 실행 핵심까지 새로 쓴다 | 검증된 원장·채점 경로를 버리게 되고 시간이 많이 들어 채택하지 않았다. |
