# 프레임워크와 점수 체계 보완 계획

2026-11-22 구조 점검 · 2026-11-23 보완. 구조 집계의 기준은 `554a281`이다. 소매 두 번 방문 실험의 본 실행·복구·감사가 끝나, 공개된 최종 결과(`6b66799`)를 0·1단계의 검증 자료로 삼는다. [최종 보고서](../reports/20261122-retail-two-visit-results.md)

**기록·출처·비용 기반은 대부분의 실험이 재사용하는 공용 코드가 됐다. 그러나 결과를 점수화하는 계층과 실험을 선언·실행하는 계층은 공용 코드로 자라지 않았다. 11월 20일부터 `src/` 추가는 하루 0~61줄이었고, 그사이 실험마다 전용 실행기·분석기·감사를 새로 썼다.**

연구 제목과 첫 두 기여 목표는 평가 프레임워크와 측정의 타당성이다. 그래서 측정 계층을 먼저 공용화한다. 구성 요소는 다음 다섯 가지다.

- 버전이 붙은 지표 정의
- 공통 결과 기록
- 기억 경로 단계 점수를 포함한 점수기
- 추론 대상을 밝힌 통계
- 점수 타당성 점검

이 계층이 준비된 뒤 시작하는 유료 실험은 이를 쓰게 하고, 실행 계층은 그다음에 일반화한다. 과거 공개 수치의 재현, 비교할 수 없는 지표의 검출, 결과에서 원천 증거까지의 추적을 함께 검증한다. [연구 계획](../research/plan.md) · [상세 설계](../design/architecture.md) · [11월 16일 실험 계층 개선 계획](experiment-layer-improvement-plan.md)

## 여러 벤치에서 평가 자체를 검증하는 순서

11월 25일 기준 다음 개발 산출물은 **여러 벤치의 보관 기록을 같은 분석 경로에 넣어, 어떤 기억 정책을 무엇과 비교했는지와 그 결론을 뒷받침하는 원문을 함께 내는 결과표**다. 메모가 도움 된 사례, 손해를 준 사례, 차이를 판정할 수 없는 사례 모두에서 평가가 정확해야 한다.

소매 재방문 `previous_only`에서 빈 메모를 시작할 때 받은 동일한 154건의 첫 목표 주문 조회는 27/154, 최종 DB 취소는 154/154다. 이전 공용 집계 함수에 이 두 지표를 의도적으로 섞으면 같은 정책에서 개선 127건이 나왔다. 공개 보고서는 각 지표를 올바르게 짝지었다. 보완한 집계기는 이 입력에서 두 지표 이름과 불일치 항목을 반환하고 계산을 중단한다. 같은 첫 조회끼리 비교하면 개선·악화는 0·0이다. ### 보관 결과 짝비교 실행

설치된 패키지에서 아래 명령으로 두 조건의 목표 주문 첫 조회를 비교한다. 같은 보관 파일에서 읽은 지표 정의·버전·시점·관측 단위·분모 기준·반복을 묶는 단위와 비교 대상 집합(`cohort`)이 맞아야 한다. 과제와 배정이 맞아도 이 항목 중 하나가 다르면 비교가 중단된다. 정책별 배정 수, 시작 수, 실제 채점 수와 성공 수를 각각 출력한다.

```bash
uv run --offline python -m agent_memory_eval.analysis.outcome_report \
  artifacts/analyses/20261122-retail-two-visit-results-with-recovery.json \
  --metric retail.first_target_lookup --mode previous_only \
  --reference empty_preload --candidate preload
```

| 보관 자료와 비교 조건 | 지표 | 재현되는 관측 |
| --- | --- | --- |
| 소매 재방문, 빈 메모와 실제 메모 시작 제공 | `retail.first_target_lookup` | `previous_only`에서 첫 업무 행동으로 목표 주문 하나만 조회한 횟수가 27/154와 129/154다. |

| 은행 작성 규칙, `existing`과 `candidate` | `banking.official_success` | 검증 상담은 7/20과 4/20이다. 036 원본은 조건별 5건 배정, 시작·채점 0건, 성공률 `null`이다. |
| BFCL 스크립트, `access_control`과 `read_enabled` | `bfcl.body_in_next_input`, `bfcl.official_answer` | 한 과제에서 본문 노출과 공식 채점은 각각 차단 0/1, 허용 1/1이다. 결과 종류는 `scripted_control`이고 통계 검정값은 `null`이다. |

각 관측에는 보관된 채점 행이나 값의 JSON Pointer를 남기고, 결과 파일에는 읽은 보관 파일의 이름과 SHA-256을 넣는다. 알려진 원본 해시를 `--sha256`으로 주면 읽은 파일과 대조한다. 소매의 반복은 고객, 은행은 원천 상담, BFCL은 선행 과제 단위로 묶는다. 새 지표를 연결할 때는 어댑터에서 고유 채점 필드를 읽는 시점에 지표와 근거 위치를 붙인다. 반복 일부가 결측일 때 어느 고객이나 원천을 집계할지도 지표에 기록한다. 소매 공개표는 한 쌍 이상 채점된 고객을 포함한다. 위 최종 DB 비교에서는 76명의 두 쌍이 모두 채점됐고, 한 쌍이 채점된 고객까지 77명이 포함됐다. 은행 공개표는 배정된 짝이 모두 채점된 원천을 포함한다. 결과는 전부 관측된 수(`complete`)와 원래 기준으로 포함한 수(`included`)를 함께 보여준다.

현재 공통 결과에서 역추적되는 범위는 보관된 채점 관측까지다. 다음 단계는 그 행에서 원천의 공개 문장, 저장한 메모 버전, 판단 전 실제 입력과 첫 업무 행동을 여는 것이다. 이때 입력에 이미 같은 단서가 있었는지, 조회하고도 본문이 들어가지 않았는지, 이후 고객 대화에서 갈라졌는지를 함께 기록한다. 업무 조건의 격리는 해당 실행의 요청과 프로토콜로 검증한다. ## 점검 범위와 검토

11월 25일 공통 짝비교기가 은행의 40개 채점 상담과 036의 10개 미시작 배정, 소매 77명의 보관 결과를 처리했다. 은행의 역할별 호출·접수 대상·부분 완료와 공개 근거의 검색 도달 여부도 검증했다. 별도 판독용 공개 자료 내보내기와 봉인, 설치본에서 BFCL 고유 도구 두 개를 거쳐 다음 입력과 공식 채점까지 연결하는 검증이 동작한다. 독립 판독의 실제 일치도와 새 고객에서의 정책 효과는 후속 항목이다. [실측 범위·재현 명령](../reports/20261125-common-policy-measurements.md)

11월 22일의 구조 점검은 `554a281` 시점의 코드·문서·git 이력과 당시 실행 기록을 읽어 집계했다. 11월 23일의 검증은 최종 보고서의 고정 커밋과 로컬 원본을 사용했다.

초안을 쓴 뒤 별도 검토자가 저장소를 먼저 읽고 자기 의견을 정한 다음 이 문서를 평가했다. 판정은 "부분적으로 맞음"이었다. 지적 사항은 저장소에서 하나씩 확인해 반영했다(맨 아래 '검토 반영' 절).

[소매 실험의 계획 점검](../reports/20261122-retail-plan-alignment.md)은 실험이 원래 연구 질문을 측정하는지를 다뤘다. 이 문서는 그 실험들을 만들고 점수화하는 도구의 상태를 다룬다.

11월 16일 계획은 무기억 기준선·전달 비교를 먼저 공통 기능으로 옮기고, 다음 실험이 같은 기능을 쓰게 하기로 했다(P1b). 이 단계는 완료로 기록되지 않았다. 이 문서는 그 방향을 잇되 기준을 바꾼다. 지금 가장 완결된 소매 실험들과 기존 항공 결과를 기준으로 삼는다.

   - `protocols/pilots/`의 프로토콜 36개 중 27개가 각자 다른 `format` 이름을 쓴다. 나머지 9개는 `profile_version` 등으로 구분하고 각자 스키마를 둔다.
   - 처음 설계한 [계획 스키마](../../schemas/run-plan.schema.json)에는 조건별 `read_mode`·`write_timing`이 있지만, 최근 소매 실험은 이 스키마를 쓰지 않는다.
   - 계획 해석기(`PlanCompiler`)와 `agent-memory run --plan` 명령은 설계 문서에 구현 예정으로만 남아 있다.
3. **실험 스크립트가 라이브러리 역할을 한다.** 다른 스크립트를 `scripts.*` 경로로 가져오는 파일은 28개다. `analyze_full_retail`을 쓰는 파일은 이 표기로 26개, 상대경로나 모듈 이름으로 가져오는 파일까지 합하면 29개다. [두 번 방문 실행기](../../scripts/run_retail_two_visit.py)는 이전 실험 스크립트 6개를 직접 가져오고, 실행·분석·감사 전체는 이전 스크립트 10개에 의존한다.
4. **보고서의 재현 명령이 현재 코드에 묶여 있다.**
   - 보고서 43개 중 29개가 현재 스크립트를 실행해 수치를 재현하도록 적혀 있다.
   - 고정 재현 목록에는 초기 항목 6개와 같은 항공 실험의 본 실행·보충 합산·최종 합산 항목 3개가 있다. 소매 재방문 실험은 등록 대상이다. [초기 v1](../../protocols/reproductions/historical-v1.json) · [항공 본 실행](../../protocols/reproductions/two-pass-forms-20261118.json) · [보충 합산](../../protocols/reproductions/two-pass-forms-combined-20261118.json) · [최종 합산](../../protocols/reproductions/two-pass-forms-final-20261118.json)
   - 공용 코드를 바꾼 뒤에도 당시 명령을 실행할 수 있도록, 분석 버전과 입력을 고정하고 보고서에서 재현 항목으로 연결한다.
5. **같은 기능이 여러 번 구현됐다.**
   - 비용: 요청별 예약·정산 구현이 세 곳에 따로 있고 기능도 다르다. `SpendGuard`(`src/agent_memory_eval/models/openrouter.py`), `CostReservations`(`src/agent_memory_eval/experiments/fresh_forms.py`), `ExpenseLedger`(`scripts/run_retail_two_visit.py`)다. 재시작 후 미정산 예약을 복원하는 것은 `ExpenseLedger`뿐이다.
   - 통계: 고객 단위 재표집과 부호검정이 최소 네 곳에 따로 있고, 재표집 횟수도 5,000과 10,000으로 다르다.
   - 추론 대상: 지금의 고객 재표집 구간은 은행을 고정한 조건부 구간이다(`scripts/analyze_retail_sample_expansion.py`의 `bootstrap_customer_interval`). [측정 명세](../research/metrics.md)는 정책 간 대응을 유지한 은행·반복 블록 재표집을 기본 후보로 두고, 두 추론 범위를 같은 구간으로 표시하지 말라고 한다.
   - 기억 정책: 조건 이름을 `MemoryPolicy`로 바꾸는 `policy_for`는 실험 파일 안에 있고, [정책 패키지](../../src/agent_memory_eval/policies/__init__.py)는 비어 있다.
6. **점수 정의가 측정 명세 밖에서 늘었다.**
   - 11월 23일 [측정 명세](../research/metrics.md#메모-문장과-득실을-연결하는-근거)에 작성·행동·득실 주장을 뒷받침하는 자료를 추가했다.
   - 첫 업무 판단, 동의를 갖춘 취소, 상담원이 먼저 시작한 이관, 되물음·잘못된 제안의 실제 채점은 여전히 개별 분석기에 있다.
   - 선택한 메모 문장에 대해 작성자의 원천 인용·저장 버전·행동 직전 입력·공개 응답을 잇는 공통 코드가 생겼다. 저장 보존율·정확성·도달률·부적합 노출·정정을 모집단에서 계산하려면 필요한 정보와 현재 적용 조건에 대한 주석이 더 필요하다. [항공·소매 적용 범위](../reports/20261123-memory-claim-evidence.md)
   - 결과 기록 형식도 실험마다 달라서(예: 두 번 방문 실험의 `db_reward`), 실험을 합칠 때마다 병합 코드를 새로 쓴다.
7. **장애 복구를 매번 새로 만든다.** 보충·복구·이어가기 성격의 프로토콜이 8개, 전용 스크립트가 11개다. 이번 실행에서는 503이 반복될 때 대기 시간을 늘리려고 별도 감시기를 붙였다. 이 감시기는 실행기가 대기하는 동안 프로세스를 외부에서 일시 정지시킨다.
8. **판독과 실행 감시 절차가 나뉘어 있다.** [판독 묶음 생성](../../scripts/analyze_retail_two_visit.py)과 [판독 봉인](../../scripts/code_retail_two_visit_turns.py), 비용·세션 감사는 저장소에 있다. 점검 당시 git에서 제외된 `.local/`의 운영 스크립트 23개가 판독 작업을 연결하고 단계별 실행을 감시했다.
9. **판독 독립성이 계획과 다르다.** [11월 16일 계획](experiment-layer-improvement-plan.md)은 사람이나 별도 모델의 독립 판정을 일부 포함하는 안을 준비하고, 같은 분석 에이전트의 재독해는 독립 판정으로 세지 않기로 했다. 반면 [두 번 방문 실험 설계](../research/retail-two-visit-v1.md)는 판독자를 이 작업을 수행하는 에이전트로 적었다. 독립 판정자와 일치도를 다루는 공용 모듈도 없다.
10. **연구 범위의 실험 유형 일부가 코드에 없다.**
    - 계획 스키마의 `continual`·`checkpoint_probe`·`write_read_cross` 설계는 실행 코드가 없다.
    - 공용 τ² 실행 경로는 수행 중 저장을 지원하고, 모의 응답으로 수행 중 작성과 사후 갱신을 검증했다. 공개된 두 회차 연결 프로필의 작성 시점은 종료 후다. [도구 연결](../../src/agent_memory_eval/adapters/tau2_memory.py) · [검증 범위](tau2-memory.md)
    - 환경이 τ² 하나뿐이라, 지금의 추상화가 τ²에 묶여 있는지 확인할 수 없다.

실험이 되풀이될 때마다 비용이 큰 이유도 여기에 있다. 소매 실험 7개는 나흘 동안 점점 더 좁은 질문으로 옮겨 갔다. 그 과정에서 채점기 둔감성, DB 점수 천장, 동의 판독의 필요성 같은 점수 문제를 찾았다. 그러나 이 발견은 공용 점수 체계로 쌓이지 않고 다음 실험의 전용 코드로 다시 만들어졌다.

두 번 방문 실험에서는 끝까지 관측한 2,305건 중 2,304건이 DB 점수 1점이었다. 같은 상담의 대상 확인·제안·승인을 함께 재현해야 조건별 차이를 알 수 있다. [상담 과정과 DB 성적](../reports/20261122-retail-two-visit-results.md#지난-주문을-지칭한-상담)

## 목표 상태

새 실험은 **실험 사양 하나, 과제별 플러그인 몇 개, 사전 등록한 점수기 목록**으로 만든다.

- 점수·통계·판독·장애 처리·비용 원장·보고 형식은 공용이다.
- 다른 연구자가 새 기억 정책을 추가해도 같은 사양 형식으로 실행하고, 같은 점수표로 기존 정책과 비교할 수 있다.
- 점수표는 여러 지표를 나란히 보고하며, 하나의 가중 점수로 합치지 않는다(상세 설계 11절).
- 패키지는 저장소 밖에서 설치해 쓸 수 있고, 새 정책과 새 실험을 추가하는 안내가 있다.

```text
실험 사양 → 계획 해석·배정 → 단계 실행기 → 기억 정책 → 벤치 어댑터
                                   │                     │
                                   └──→ 원본 기록 ←──────┘
                                           │
         점수기 → 공통 결과 기록 → 짝비교 통계 → 점수표
            ↑
         판독 모듈(가림·봉인·인용 검증·일치도)
```

### 1단계 · 측정 계층

11월 26일 은행과 BFCL의 실제 원장에서 원천 단서, 첫 판단의 기억 노출·함수·인수, 같은 기억의 반복 변동, 공식 채점·중단 시점의 업무 진척을 공용 결과 형식으로 재현했다. 은행은 작성 전에 채점 원천의 고객별 단서 수를 점검할 수 있다. [두 벤치의 재현 명령과 판정 기준](trajectory-outcomes.md)

1. **지표 정의의 버전화.** 각 지표에 정의·단위·분모·추론 대상·입력·버전을 적는다. 첫 업무 판단, 되물음, 잘못된 제안, 변경 전 동의, 이관, 비용과 진척을 각각 집계한다.

   기억 경로는 **특정 판단에 필요한 정보 한 단위**를 따라간다. 예를 들어 주문번호가 목록에 있는지와 그 번호가 *지난 방문에서 지칭한 주문*임을 알 수 있는지는 서로 다른 정보다.

   | 판단마다 남길 관측 | 판정 근거 |
   | --- | --- |
   | 과거와 현재의 정보 | 해당 사실을 원천 공개 경험에서 확인할 수 있는지, 현재 대화와 그때까지 받은 업무 도구 결과만으로도 알 수 있는지를 각각 표시한다. 두 출처에 함께 있을 수 있다. |
   | 저장과 노출 | 그 사실이 어느 은행 버전에 남았는지, 판단을 만든 모델 요청에 기억을 통해 들어왔는지 확인한다. 제목·본문·가공문에서 실제로 포함된 구절과 요청을 연결한다. |
   | 행동과 결과 | 실제 업무 호출이나 발화가 그 사실과 일치했는지 근거를 남긴다. 뒤이은 과정 지표와 최종 점수는 각각 기록한다. |

   주석할 근거가 없거나 분모가 0이면 ‘해당 없음’, 기록만으로 판정하기 어려우면 ‘미확정’으로 둔다. **메모 제공의 효과**는 동일 사례에서 사전 배정한 메모·대조 조건의 행동 또는 결과 차이로 추정한다. 개별 정답 행동은 관측된 행동 일치로 집계한다. [기억 품질의 분모](../research/metrics.md#기억-품질과-선택) · [정책 효과의 추론 범위](../research/metrics.md#정책-효과와-불확실성)

2. **공통 결과 기록.** 배정 하나의 결과를 실험과 무관한 한 형식으로 남긴다.
   - 사전 등록의 원 배정 ID를 기준으로 단계별 실행 ID·상태·영수증과 판독 파일의 출처를 연결한다. 본 실행 당시 상태와 복구 포함 상태를 각각 다시 만들 수 있어야 한다. 배정표는 요청이 미전송된 경우에도 분모를 보존한다.
   - 같은 원 배정의 복구는 적격 목록과 전송 기록을 확인해 한 번만 합산한다. 첫 판단, 정상 종료의 공식 점수, 중단 시점까지 관측한 행동에는 각각 상태와 분모를 둔다. 파생 자료는 기존 로그 계약 v1.1·v1.2를 읽는다.
   - 은행 snapshot·버전과 체크포인트를 가리켜, 누적 분석에서도 같은 기록을 이을 수 있게 한다.
   - 점수기 이름·버전을 남기고, 벤치 고유 점수의 원문은 그대로 보존한다.
   - 새 계약이므로 스키마·버전·fixture·문서를 함께 만든다.
3. **점수기 라이브러리.** 실험 파일에 흩어진 판정을 입력·출력·버전이 정해진 점수기로 옮긴다.

   | 점수기 | 현재 위치 | 읽는 자료 |
   | --- | --- | --- |
   | 공식 점수 | 실험별 영수증(`db_reward` 등) | 벤치 채점 결과 |
   | 첫 업무 행동 | `scripts/audit_retail_order_choice.py`의 응답 분류 | 첫 응답의 업무 호출 |
   | 기억 노출 | `src/agent_memory_eval/analysis/requests.py` | 요청 원본·도구 반환 |
   | 기억 경로 단계 | [선택한 문장의 원문 추적](../../src/agent_memory_eval/analysis/claim_evidence.py), 모집단의 전체 경로 점수는 후속 | 원천·현재 공개 입력·고정 은행 버전·판단 직전 요청·행동과 의미 주석 |
   | 제안·동의·되물음 | `scripts/analyze_retail_two_visit.py`의 `grade_turns`, `scripts/code_retail_two_visit_turns.py` | 공개 대화·업무 기록·판독 결과 |
   | 이관 | `scripts/analyze_retail_handoff_factors.py` | 공개 대화·업무 기록 |
   | 비용 | 실험별 비용 원장 | 요청별 예약·청구 |

   점수기는 읽는 자료의 출처를 선언한다. 채점 정답과 분석 주석은 분석자 전용 파일에 두고 해시로 참조한다. 이 파일이 에이전트 입력에 들어가지 않는지는 테스트로 확인한다. 의미 판정이 필요한 점수기는 규칙이 제안한 후보와 판독 결과를 구분해 기록한다.
4. **짝비교 통계.** 다음 계산을 한 모듈로 모은다.
   - 고객 단위 평균과 짝지은 차이
   - 개선·동률·악화
   - 양측 정확 부호검정
   - 재표집 구간
   - 결측에 0·1을 대입한 범위
   - 층별 차이의 차이

   각 결과에 가중 방식(과제 또는 고객 동일 가중), 재표집 단위(고객 또는 은행·반복 블록), 조건(은행 고정 여부)을 적는다. 재표집 횟수와 seed는 실험 사양에서 받고, 기존 결과는 당시 설정으로 다시 계산한다.
5. **점수 타당성 점검.** 실험에서 찾은 점수 문제를 다음 실험의 사전 점검 항목으로 만든다.
   - **천장과 바닥:** 대조 조건의 점수 분포를 과거 자료로 보고, 지정한 지표가 조건 차이를 드러낼 수 있는지 실행 전에 표시한다.
   - **채점기 탐침:** 두 번 방문 실험의 통제 대화 다섯 개를 과제군별 탐침 묶음으로 일반화한다. 다섯 개는 승인 후 취소, 답변 없는 취소, 거절 뒤 취소, 다른 주문 취소, 취소 없는 종료다.
   - **환경 결함:** 확인된 결함을 어댑터 점검 항목으로 둔다. 예를 들어 고정 τ²의 `modify_pending_order_items`는 여러 품목을 바꿀 때 가격·옵션을 잘못 기록한다.
   - **시뮬레이터 이탈:** 고객 시뮬레이터가 지시와 다른 사실을 말한 사례를 따로 표시한다. 이번 실험에서는 주문 상품을 부인해 취소 없이 이관된 1건이 있다.
   - **반복 변동.** 같은 과제·조건을 반복한 배정에서 성패가 바뀌는 비율과 분모를 낸다. 해당 반복이 없으면 ‘해당 없음’으로 표시한다. 무기억 세 반복에서는 57과제 중 20과제의 성패가 바뀌었다(`README.md`). 이전의 27.3%·29.7%는 서로 다른 두 대조 사이의 관측값이다.

**1단계 완료 기준.** 공통 점수기로 아래 네 대상의 공개 분자·분모와 해당 구간·p값을 다시 계산한다. 새 기억 경로 점수는 현재 입력만으로도 맞힐 수 있는 사례와 기억 노출 없이 맞힌 사례에서 관측과 대조 효과를 구별하는지도 확인한다. 값이 다르면 원인을 해당 배정까지 추적해 정정 기록을 남긴다.

- 주문 선택 140회
- 두 번 방문 실험의 첫 판단·전체 상담·결측·복구. [배정별 기대값과 짝비교 분모](#두-번-방문-실험의-검증-기준)를 모두 대조한다.
- 소매 세 실험을 합친 2회차 상담 2,012건
- 항공 두 회차의 공식 채점 234건과 무기억 대비 149쌍(개선 18·악화 16, [개발 계획](roadmap.md)의 첫 검증 기준)

### 2단계 · 판독 계층

판독에 필요한 단계를 공용화한다.

- 조건을 가린 자료 생성
- 분석자 키 봉인
- 판정 기준의 버전 관리
- 근거 인용의 원문 대조
- 판독 결과 결합
- 일치도 계산

판독 규칙을 만들 때 쓴 사례와 규칙을 평가할 사례를 구분해 기록하고, 결과를 본 뒤 정한 규칙은 탐색적 분석으로 표시한다. 독립 판정은 사람이나 다른 모델이 보는 표본으로 둔다. 같은 에이전트가 다시 읽은 것은 독립 판정으로 세지 않는다. 다른 모델을 판정자로 쓰려면 비용 승인과 별도 프로토콜이 필요하다.

완료 기준: 공개된 판독 파일을 새 모듈로 다시 결합해 같은 수치가 나오고, 독립 판정 표본의 프로토콜 초안이 준비된다.

### 3단계 · 실행 계층

1. **실험 사양과 단계 실행기.** 두 번 방문 실행기의 기능을 실험과 무관한 실행기로 일반화한다.
   - 대상 기능: 단계 진행, 배정 등록, 단계별 영수증, 누적 승인, 중복 전송 방지, 재개
   - 기준 실험: 두 번 방문 실험 하나만 보지 않고, 전체 상담형 소매 실험(예: 전이 재실험)과 항공 두 회차 실험도 함께 본다.
   - 단계 구성: 단계는 사양에 선언한 순서로 둔다. 그래야 `continual`·`checkpoint_probe`·`write_read_cross`와 수행 중 작성 같은 연구 범위의 설계를, 아직 실행하지 않더라도 표현할 수 있다.
   - 일시 장애: 재시도 간격, 시도할 묶음 수, 결측으로 남길 조건을 사양의 사전 등록 항목으로 둔다. 이번 [복구 프로토콜](../../protocols/pilots/tau2-retail-two-visit-recovery-v1.json)의 규칙을 첫 기본안으로 쓸 수 있다. 120초·600초·1,800초 간격으로 기다리고, 이미 보낸 첫 판단은 다시 보내지 않는 규칙이다.
2. **비용 원장.** 공통 인터페이스 아래 기존 동작을 이름 붙인 버전으로 유지한다. 11월 16일 계획대로, 한도 판정 차이를 통일해 숨기지 않는다. 새 실행은 사용할 버전을 명시한다.
3. **기억 정책 계층.** 조건 이름을 실험마다 해석하지 않는다. 상세 설계 5절의 정책 필드와 은행 변형(실제 은행·빈 은행)의 조합으로 표현한다. 정책 필드는 기억 제공 여부, 작성 시점, 표현, 읽기 방식, 가공, 피드백, 한도다. `policy_for`의 대응표가 출발점이다. 외부 기억 시스템도 같은 인터페이스의 선택적 구현으로 붙일 수 있게 하되, 코어 필수 조건으로 두지 않는다.
4. **사용성.**
   - 상세 설계 14절의 명령(`plan validate`·`plan resolve`·`run`·`resume`·`analyze`)을 구현한다.
   - 계획 해석기는 [인수인계](../handoff/next-session.md)에 적힌 대로 미정 값과, 해당 없음·무제한을 구분한다.
   - 실행에 필요한 스키마를 패키지 자원으로 넣어, 설치한 패키지가 저장소 없이 동작하는지 확인한다.

완료 기준:
- 두 번 방문 실험, 주문 선택 실험, 전체 상담형 실험 하나를 새 사양으로 다시 쓴다.
- 이때 정규화한 배정 내용(배정 목록·순서·입력 해시)이 [두 번 방문 실험의 사전 배정](../../artifacts/analyses/20261122-retail-two-visit-preflight.json) 같은 공개된 사전 배정과 같아야 한다.
- 가짜 모델로 모든 단계와 중단·재개·장애 묶음을 통과한다.
- 설치한 패키지로 저장소 밖에서 모의 실험을 실행한다.

### 4단계 · 일반성

동일 과제 비교의 첫 판단은 공통 코드로 연결했다. τ²에서 첫 고객 발화를 복원하고 BFCL의 고정 과제에서는 공개 질문·함수 정의를 다시 구성한다. 새 어댑터의 검증은 첫 업무 입력의 일치, 메모 노출과 다음 행동, 공식 결과와 비용까지 순서대로 확장한다. [구현 범위와 재현 명령](../design/architecture.md#동일-과제의-첫-판단)

어댑터가 지원 범위를 선언하게 한다. 대상은 초기화·행동·종료·공식 채점, snapshot과 재생이다. 그다음 가짜 환경을 하나 더 붙여 τ²에 묶인 가정을 찾는다. 실제 AppWorld·BFCL 연결은 패키지 고정과 사용자 승인이 필요한 별도 결정이다.

11월 23일 오프라인 점검에서 AppWorld의 공식 요구사항 판정과 BFCL의 공식 답 채점·기억 복원을 재현했다. BFCL 고유 호출은 공통 라우터가 기억 허용 조건에서도 거절한다. 다음 어댑터의 완료 판정에는 허용한 기억의 반환이 다음 행동 입력에 기록되는지, 무기억 대조에서는 접근이 차단되는지, 공식 채점 대조가 보존되는지를 함께 확인한다. [벤치별 확인 범위와 반복 명령](../reports/20261123-framework-portability.md)

### 5단계 · 정리와 규칙

- 이번 실행과 분석이 끝나면 `.local/`의 판독 절차·단계 감시 스크립트를 저장소로 옮긴다. 머신별 실행 셸만 남긴다.
- 인수인계에 규칙을 적는다.
  - 새 실험은 사양과 플러그인으로 추가한다.
  - 실험 전용 함수가 두 번째 실험에서 쓰이면 공용 코드로 옮긴다.
  - 탐색 진단은 스크립트로 둘 수 있지만 탐색이라고 표시한다.

## 하지 않는 것

- 원본 실행·과거 실험·과거 lock 해시·`historical-v1.json`을 고치지 않는다.
- 옛 수치에 맞추려고 점수기를 조정하지 않는다. 불일치는 정정 기록으로 남긴다.
- 기존 비용 guard의 의미를 하나로 합쳐 숨기지 않는다.
- 공용화와 호환 감사는 도구의 검증이다. 기억 효과의 실증으로 보고하지 않는다.
- BM25나 임의의 2k 배분을 기본값으로 넣지 않는다. 필터·Jev를 필수 코어로 두지 않는다. 저장·조회·전이·누적·득실·비용의 연구 범위를 줄이지 않는다.
- 이 계획은 새 모델 호출·예산·패키지 설치를 승인하지 않는다.

## 사용자가 정할 것

- 정리 작업을 이 세션과 다른 세션 중 누가 맡을지, 별도 worktree에서 할지
- 1단계 이후 실험이 새 측정 계층을 쓰도록 할지, 정리 기간 동안 유료 실험을 멈출지
- 독립 판정을 사람 표본으로 할지 다른 모델로 할지(다른 모델이면 비용 발생)
- 두 번째 환경을 AppWorld와 BFCL 중 무엇으로 시작할지
