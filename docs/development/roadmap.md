# 개발 계획과 완료 기준

2026-11-14 · 구현 의존성에 따른 순서

현재는 파일 기록자·기억 서비스·입력 구성·도구 라우터와 가짜 두 회차 실행/재계산이 동작한다. [오프라인 코어](offline-core.md)에 사용법과 행동 검증 범위를 정리했다. [무기억 연결](tau2-connection.md)에 이어 [native 기억/두 회차 연결](tau2-memory.md)을 구현했다. 연구용 계획 준비 검사·일반 정책 비교 실행·다른 벤치·효과/통계 분석은 후속이다. 아래 순서는 연구 범위를 좁히는 결정이 아니다.

새 세션의 시작은 [인수인계](../handoff/next-session.md), 첫 개발의 구체적인 산출물·행동 검증은 [오프라인 코어 작업](first-implementation.md)을 따른다. 과거 데이터 보관과 그 무결성 검사 코드는 런타임 구현 완료에 포함하지 않는다.

첫 구현의 저장·입력·혼합 호출 기준은 [코어 계약](../design/core-contracts.md)이다. 단일 원본 로그와 순차 쓰기로 가볍게 시작하고 복잡한 동시 쓰기나 전체 세션 자동 복구는 후속으로 둔다. 연구 범위는 유지한다.

## 같은 저장 형식에서 작성 프롬프트 비교

새 고객의 1회차부터 수집하는 경로에서는 네 형식과 두 대조를 같은 시작 제공 방식으로 비교한다. 보고서는 1회차 성적에 따라 전환을 나누고, 실제 본문이 들어간 요청·고객 대화·도구 인수·최종 DB를 같은 배정으로 연결한다. 503 중단 뒤에는 원본에 없는 배정만 이어서 실행하고 청구 미확인액을 같은 비용 상한에 반영했다. [실행 및 재검증 방법](../research/new-customer-forms.md) · [실제 비교 결과](../reports/20261118-new-customer-forms-results.md)

아래 세 단계의 구현과 첫 항공 실험은 [실행 방법](prompt-comparison.md)과 [실측 보고서](../reports/20261118-fact-recheck-results.md)에 있다. 보고서 생성기는 과거 234개 공식 점수, 무기억과 함께 채점된 149쌍, 기존 가림 판정 42쌍의 인용을 원본에서 재검증했다.

2026-11-18 기준으로 권하는 첫 사용 시나리오는 실험자가 한 설정에 같은 저장 형식의 작성 프롬프트 두 개를 넣고, 2회차 공식 결과와 그 판단의 원문을 함께 확인하는 것이다. 기존 항공 실행기는 네 형태의 이름과 두 반복을 배정에 사용하고, 작성할 때 공통 지침 뒤에 형태별 한 줄을 붙인다. 새 비교에서는 실험 조건 이름, 저장 형식, 작성 지침의 버전, 조회 방식을 각각 식별할 수 있게 한다. [현재 배정 코드](../../src/agent_memory_eval/experiments/forms_batch.py) · [작성 지침 구성](../../src/agent_memory_eval/experiments/forms_write.py)

1. **기존 기록을 첫 검증 자료로 쓴다.** 같은 보고서로 봉인된 항공 실행을 열었을 때, 모델을 다시 호출하지 않고 공식 채점 234건과 무기억 대비 149쌍의 개선 18·악화 16이 일치해야 한다. 한 쌍을 선택하면 원천 경험, 실제 작성물, 각 작업자 입력에 전달된 내용, 처음 달라진 판단의 대화·도구 기록과 최종 성적을 따라갈 수 있어야 한다. 빈 작성과 미채점도 원래 배정에 남긴다. [기준 결과](../reports/20261118-two-pass-memory-forms-final-results.md) · [성공 사례](../reports/20261118-two-pass-memory-success-factors.md) · [실패 사례](../reports/20261118-two-pass-memory-failure-factors.md)
2. **첫 새 실험은 단순 정보 작성 프롬프트만 바꾼다.** A는 현행 사실 기록 지침, B는 같은 지침에 ‘이번 사례에서 관찰한 값 중 다음 수행 때 다시 확인해야 할 값은 표시하라’는 문장을 더하는 조건이다. 기존 공통 지침에는 이미 불확실성과 적용 조건 보존이 들어 있다. 두 조건은 같은 1회차 공개 경험·모델·작성 한도·2회차 본문 시작 제공을 사용하고 각자 독립적으로 기억을 작성한다. 과제·반복을 짝지어 전체 2회차 공식 성공과 양방향 성적 변화를 비교한다. 같은 반복의 무기억·빈 메모 대조, 1회차 성적, 실제 작성·노출, 비용·결측도 함께 기록한다. 20번의 연도 판단과 17번의 정확한 날짜 메모는 개발 사례로 삼고, 효과를 확인할 고객 그룹·과제와 반복은 실행 전에 정한다. 각 확인 과제도 자기 1회차 경험을 사용한다. [현행 공통 작성 지침](../../protocols/instructions/optional-experience-writer-v1.txt)
3. **다음 비교에서 조회 방식을 바꾼다.** A와 B가 작성한 기억 은행을 각각 고정해 본문 시작 제공과 작업 중 자율 조회에 배정한다. 같은 은행에서 어떤 기억이 요청·반환됐고 어느 판단 전에 실제 입력에 들어갔는지 확인한다. 두 조회 조건의 전체 과제 결과와 조회 비용을 비교하면 어느 작성 방식에서 전달 방법이 중요했는지도 볼 수 있다.

## 공통 계약과 오프라인 실행

| 구현할 기능 | 완료 근거 |
| --- | --- |
| 설정·배정·준비 검사 | draft 차단, 필수 설정·의미·source group·조건/짝·capability 검증 |
| 기억 서비스 | 제목·본문 저장/갱신, 불변 버전, 은행 소유권, snapshot·fork·compose |
| 도구 라우터 | 단계별 허용, 목록·본문, 오류, 읽기 보기와 페이지, 업무 단계와 분리 |
| 기록 | 요청 시작/종료, 반환/입력 포함, 실제 설정·사용량·결측, 원자적 사건과 export |
| 가짜 환경 | 두 세션·은행 복제·중단 감지·확정 기억 재읽기·합성 결과를 연결하고 원본에서 재계산 |

기존 v1.1 fixture는 읽기 전용 계약 예시로 보존한다. 새 서비스와 가짜 환경의 실제 파일·요청·도구 행동은 별도 테스트로 검증한다. 기본 예제는 2원천·8 run이며 성능 실증이 아니다.

## τ² 연결

제한된 무기억 1과제에서 실제 OpenRouter 요청·사용자 시뮬레이터·도구 왕복·native 채점을 확인했다. 이후 [기억 연결 진단](tau2-memory.md)에 외부 기억 routing·업무 projection·사후 작성·새 probe를 구현했다. 기존 무기억 binding의 capability는 false로 유지하며 기억 binding과 별도다. 두 진단 프로필은 연구 계획과 구분한다.

같은 기억 binding에서 [자율 조회 세 조건 파일럿](tau2-autonomy-pilot.md)을 구현·실행했다. 닫힌 준비 검사·고정 source 가져오기·블록 배정·조건별 기록 재계산을 지원하며, 한 과제의 미조회 관측을 일반 정책 효과로 확장하지 않는다.

[고정 은행 전달 비교](tau2-delivery.md)는 본문 시작 제공·과제/조건/반복 배정·로컬 준비 검사·원본 audit를 추가한다. native mock 검증과 실제 전달 정책 실험은 구분하며, 실제 실행 프로필의 미정 값을 임의로 채우지 않는다.

이후 별도 동결 프로토콜로 [세 과제·네 조건 48회](../reports/20261114-tau2-delivery-development-results.md)를 완료했다. 다음은 설명/시나리오 판정 보완·정보 차이가 분명한 과제 검증·같은 경험의 기억 표현 비교 준비다. 상태 사본의 보관량·검증 시간도 확대 전에 계측한다. 개발 순서는 [갱신한 2주 계획](../reports/20261114-progress-and-two-week-plan.md)을 따른다.

모델 요청 지점·공개 대화·기억 도구 왕복·업무 도구·사용자 시뮬레이터·종료·공식 채점까지 연결한다. 업무 호출만 원래 환경으로 전달하고 기억 호출로 사용자나 업무 단계가 자동 진행되지 않게 한다.

같은 초기 상태, 세션 간 이력 차단, 실제 입력 기록, 종료 후 작성의 업무 결과 고정, 환경/채점 오류 처리를 검증한다. 벤치 commit과 프롬프트·정책·DB·과제·사용자 설정을 고정한다. 실제 모델 연결 점검은 별도 계획과 비용 기록으로 수행한다.

첫 실증 후보는 [동일 경험의 요약/적용 조건 기억 파일럿](../research/condition-sensitive-pilot.md)이다. 고정된 조회의 저장 진단 후 조회 정책 교차로 이어갈 수 있다. 항공 변형의 일관성·행동 판정은 별도 검증하고 표본/비용 설정은 실행 전에 확정한다. 적용 가능성 필터와 Jev는 선택적인 후속 비교이며 코어 완료 조건이 아니다.

## 비교 절차와 분석

두 회차·자기 경험/혼합 풀·자연 누적·동일 경험·저장/조회 교차·체크포인트·개입을 설정으로 표현하고 검증한다. 무기억 반복·원기록·단순 요약 기준선의 실제 정보·연산·비용을 기록한다.

먼저 결과 짝·공식 성적·배정/결측 수·노출·비용을 원본에서 재계산한다. 이후 근거·적용 조건·행동 오류·진척 주석과 불일치 처리를 연결한다. 마지막으로 독립 은행·순서·과제의 의존성을 반영한 통계와 원본 근거 사례를 만든다.

## AppWorld와 BFCL 확장

각 어댑터는 초기화·행동·종료·공식 채점과 snapshot·replay·진척의 지원 범위를 선언한다. DB만 복원한 것을 완전한 세션 복원으로 표시하지 않는다.

AppWorld는 업무 코드/API·DB·실행 변수·대화 상태를 구분한다. BFCL은 우리 기억을 추가하는 변형과 고유 Memory 절차를 관측하는 모드를 구분한다. 고유 기억 API를 강제 치환하거나 변경한 절차를 공식 leaderboard와 동일하게 표시하지 않는다.

## 첫 기능 구현의 경계

공통 패키지의 소유 경계는 다음과 같다.

```text
src/agent_memory_eval/
  contracts/    # 계획·식별·메시지·결과 타입
  runner/       # 배정·수집·평가·누적·개입
  memory/       # 은행·버전·snapshot·복제·연산
  policies/     # 저장·조회·가공·피드백 지침
  adapters/     # 벤치 환경·공식 채점
  models/       # 요청·응답·제공 경로·사용량
  recording/    # 사건·노출·원본
  analysis/     # 지표·주석·통계·보고서
```

현재 구현 파일과 후속 책임은 [패키지 안내](../../src/agent_memory_eval/README.md)에 구분했다. 실제 벤치/API를 성공한 것처럼 반환하는 stub을 제공하지 않는다. 모델·벤치의 큰 의존성은 실제 어댑터를 연결할 때 선택·잠근다.

## 검증 기준

세션 이력 차단, 미래 정보·정답 차단, 은행·반복·평가 복제본 격리, 동일 기억의 풀 구성, 버전·멱등성, 한도 초과의 원자성, 제목·본문·가공·재노출, 종료 후 작성, 채점 결측, 복원 가능 범위, 기록 장애, 비용·집계 중복을 검증한다.

설계에 있는 표준 대조식이나 모듈 개수 자체를 성과로 보고하지 않는다. 기능 완료·공식 채점 의미의 보존·측정 타당성·실증 발견을 구분한다. 구체적인 계약은 [상세 설계](../design/architecture.md), 비교는 [프로토콜](../research/experiment-protocol.md), 지표는 [측정 문서](../research/metrics.md)를 따른다.
