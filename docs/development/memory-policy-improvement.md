# 업무별 기억 정책을 개선하는 하네스

한 업무군에서 같은 모델이 **무엇을 저장하고, 언제 찾고, 현재 업무에서 무엇을 재확인해야 전체 과제의 성공률이 올라가는지** 반복해서 시험한다. 각 고객의 메모는 그 경험에 속한다. 여러 고객에게 옮길 수 있는 결과물은 근거와 적용 조건을 포함한 작성·조회 정책의 버전이다.

다른 벤치를 연결할 때는 어댑터가 공개 경험, 업무 행동과 그 대상, 공식 채점 결과를 제공한다. 예를 들어 항공은 어느 예약의 어떤 결제 수단을 선택했는지, 소매는 어떤 주문을 고객 확인 후 취소했는지를 읽어 낸다. 하네스는 같은 방식으로 원천에서 메모, 판단 전 입력, 실제 행동, 최종 성패까지 추적하고 후보 정책을 평가한다. 성공률 차이는 각 벤치와 업무군별로 보고한다.

## 한 번의 개선 과정

| 담당 | 할 일 | 남길 근거 |
| --- | --- | --- |
| 실험자·실행기 | 업무군, 초기 상태, 채점기, 모델, 개발·검증 고객, 예산과 채택 기준을 고정한다. | 1회차 무기억 원천, 배정, 기준 정책과 버전 |
| 작성자·작업자 LLM | 같은 공개 경험에서 무엇을 저장·갱신·생략할지 정한다. 2회차에는 새 세션에서 필요할 때 목록·본문을 열고, 현재 조회나 고객 확인을 거쳐 업무 행동을 고른다. 시작 제공 조건도 같은 기록으로 평가한다. | 저장된 제목·본문의 버전, 조회 호출·반환, 해당 판단을 만든 실제 요청과 업무 도구 인수 |
| 개선안을 만드는 LLM | 개발 사례에서 성공을 얻거나 잃은 판단을 찾고 원문을 인용한다. 바꿀 지침 하나, 예상 행동, 그 예측이 틀렸다고 볼 관측을 제안한다. | 이전 정책, 제안 내용, 인용 위치, 가설과 확인할 행동 |
| 실행기·채점기 | 같은 원천과 2회차 과제에 기존 메모 정책과 후보를 배정한다. 작성 변경은 읽기 방식을 고정하고, 조회 변경은 같은 작성물 버전을 재사용한다. | 최근접 행동 차이, 공식 성공, 성공을 잃은 경우, 결측, 작성·조회·전체 수행 비용 |

개발에서는 후보와 기존 정책이 처음 갈라질 만한 공개 상태부터 적은 비용으로 시험할 수 있다. 예를 들어 같은 업무 요청에서 이미 카드 잔액이 드러난 경우와 새로 확인해야 하는 경우를 모두 본다. 여기서 기대한 행동이 나타난 후보를 전체 상담에서 평가한다. 실행 기록을 읽어 프롬프트 수정을 제안하고 후보를 평가하는 방법은 GEPA에서도 사용한다. 여기서는 각 제안을 기억의 저장·노출·업무 행동·공식 결과와 연결한다. [GEPA 연구](https://arxiv.org/abs/2507.19457) · [판단 재생 범위](decision-replay.md) · [메모 문장과 득실의 근거](../research/metrics.md#메모-문장과-득실을-연결하는-근거)

**LLM이 점검할 행동.** 원천에 근거가 있는데 저장에서 빠졌다면 작성 지침을 바꿔 본다. 저장됐지만 판단 전 요청에 없었다면 조회 시점이나 제목 선택을 바꿔 본다. 본문이 입력에 들어갔는데 과거 값을 그대로 사용했다면 현재 적용 조건을 확인하는 규칙을 시험한다. 현재 입력만으로 충분한 성공 사례도 같이 본다. 목록을 여는 데 토큰을 쓰거나 이미 받은 값을 다시 묻는 손해가 있기 때문이다. 각 진단은 원인 후보이며, 해당 요인만 바꾼 비교가 행동과 결과를 뒷받침하는지 확인한다. [조회 경로와 실제 행동의 대조](../reports/20261123-memory-claim-evidence.md)

## 정책을 채택하는 기준

- 같은 과제의 **1회차 무기억 대비 변화**와 **같은 2회차에서 기존 메모 정책 대비 후보의 차이**를 각각 보고한다. 새 2회차 무기억 배정은 0건이다. 형식·반복이 같은 원천을 쓰므로 과제·고객을 묶어 불확실성을 계산하고 미시작·미채점도 남긴다. 여러 후보는 개발에서 비교하되, 마지막 후보의 정책 버전과 판정 기준은 확인 평가 전에 고정한다.
- 개발 자료와 고객·원천·파생 과제가 겹치지 않는 확인 집합에서 전체 과제를 끝까지 수행한다. 과거에 상세 검토한 고객은 개발 사례로 표시한다. 개선안 작성자에게는 개발용 공개 기록과 허용된 개발 피드백을 제공한다. 확인 집합의 상담·점수·정답 행동은 후보를 고치는 입력에서 제외한다. 확인 결과로 다시 수정했다면 그 자료는 다음 라운드부터 개발 자료다.
- 주 지표는 해당 업무의 **공식 과제 성공률**이다. 각 비교에서 기대하는 최소 개선, 기존 성공 과제의 허용 악화, 비용 한도와 불확실성의 판정 방법은 배정 전에 정한다. 동일 조건에서의 정책 간 차이, 업무에 맞는 실제 행동·상태 변화까지 부합하면 새 버전을 채택한다. 표본이 작거나 결측으로 판정이 달라질 수 있으면 기존 정책을 유지하고 보류 사유를 남긴다.
- 단계별 득실은 별도로 활용한다. 소매에서는 지난 주문을 더 빨리 찾아도 끝까지 관측한 153쌍의 목표 주문 취소는 양쪽 모두 성공했다. 항공에서는 평가 네 자리의 공식 성공이 3건에서 4건이 됐지만 차이가 난 한 자리는 같은 수를 영단어와 숫자 중 무엇으로 표기했느냐에 달렸다. 각각 처리 효율과 채점 민감도의 증거다. [소매 전체 상담](../reports/20261122-retail-two-visit-results.md) · [항공 공식 점수 대조](../reports/20261118-fact-recheck-results.md)

## 현재 실행할 수 있는 개발 단계

2026-11-24부터 실제 효과를 다시 측정할 때는 공식 과제에서 새 무기억 원천을 수집한다. 아래 보관 원천과 결제 작성 후보는 당시 개발 경로를 재현하는 예시로 보존한다. [현재 계열의 사전 배정](../research/fresh-matched-series.md)

첫 예시는 **항공 결제 수단 선택**이다. 개발 과제 21번에서 고객은 잔액이 가장 적은 기프트카드를 요청했고, 23번에서는 예약을 나눠 서로 다른 결제 방식을 지정했다. 후보 작성 지침은 고객의 선택 기준과 그 거래에서만 유효한 값·승인을 나누어 기록하게 한다. 예측하는 변화는 다음 작업자가 결제 전에 현재 거래의 조건과 값을 확인하는 것이다. 특정 카드 ID나 금액을 공용 지침에 넣을 필요가 없다. 이미 살펴본 두 과제는 개발에만 쓴다. [작성 비교 초안](../../protocols/drafts/tau2-airline-payment-memory-v2.json) · [원문을 인용한 제안 예시](../../tests/fixtures/airline-payment-writer-proposal.json)

23번에서는 두 승객에게 같은 금액의 증서를 다르게 배정하면 총 청구액이 같아도 최종 점수가 갈린다. 이 사례의 개발 실험은 같은 1회차에서 정보·경험 일기·절차·교훈·자유 구성으로 각각 작성한다. 자유 구성에서는 한 작성자가 내용을 섞거나 여러 항목을 저장할 수 있다. 각 방식의 기본 지침과 같은 보완 문장을 더한 지침을 지난 배분 지칭·현재 동일·현재 변경의 세 요청에 비교한다. [형식별 원천 기록·배정·채점기 점검](../research/airline-payment-allocation-pilot.md)

```bash
study=protocols/drafts/tau2-airline-payment-memory-v2.json
trial_dir=$(mktemp -d)
uv run python -m scripts.prepare_memory_candidate "$study" --development-packet --output "$trial_dir/development.json"
uv run python -m scripts.prepare_memory_candidate "$study" \
  --proposal tests/fixtures/airline-payment-writer-proposal.json --output "$trial_dir/candidate.json"
uv run python scripts/run_prompt_comparison.py "$trial_dir/candidate.json" --preflight
```

첫 명령은 개발 과제의 공개 대화·도구 기록, 해당 1회차의 성패와 기존 작성 지침을 개선안 작성자용 파일에 담는다. 두 번째 명령은 부모 설정 해시와 공개 필드의 정확한 인용을 대조한다. 제안자는 작성 문구·가설·예상 행동과 인용을 낸다. 실행기는 부모 설정에서 개발 과제만 가져오고 기존 정책, 모델 설정과 읽기 방식을 유지한 새 초안을 만든다. 확인 과제는 부모 설정에 남고 새 초안의 예산은 미정이다. 가설·성패·인용 메타데이터는 상담원과 메모 작성자에게 보내지 않는다. 정확한 인용은 출처의 증거이며 제안의 일반성은 확인 집합에서 평가한다.

세 번째 명령은 보관 원천 2건에서 작성 4건·2회차 4건·2회차 무기억 0건의 배정을 검산한다. 실제 모델 전송은 세 명령 모두 0건이다. 결과 보고서는 원천 실행 ID와 각 정책의 1회차 대비 전환, 2회차 정책 간 짝비교를 제공한다. 이미 쓰인 메모를 시작 제공과 자율 조회로 교차하는 기존 경로도 사용할 수 있다. [쓰기·조회 실행 경로](prompt-comparison.md) · [v2 계약](../../schemas/prompt-comparison-v2.schema.json)

동일 과제에서 의도적으로 달라지는 입력은 배정한 메모, 그 사용 안내와 메모 도구다. v2 사전 검사는 원천별로 고정한 1회차 저널에서 고객 시나리오를 포함한 과제·정답, 기본 업무 정책과 도구 스키마, 역할별 모델·공급자·시드, 초기 DB와 채점·종료 설정을 다시 대조한다. 원천 21·23의 상담원 시드는 모두 0이다. 항공 1회차의 요청당 64,000바이트·45초, 상담당 200요청·600초·$0.10을 2회차 상담에도 적용한다. 새 실험 전체 비용은 그 실험의 승인 한도로 제약한다. 작성자는 같은 공개 경험만 받고, 해결자는 독립된 세션·DB에서 지정된 은행만 받는다. 시작 제공 안내에는 메모 사용법만 둔다. 해결 중에도 고객 첫 요청이 1회차와 완전히 같은지, 모든 모델 요청이 원래 설정·업무 도구와 현재 세션의 대화로 구성되는지 전송 전에 확인한다. 메모를 제거하고 대조하는 부분은 등록한 안내·도구·본문뿐이다. 이후 고객과 상담원이 주고받는 실제 답은 각자 행동에 따라 달라진다. [항공 21·23 원천별 검증 기록](../../artifacts/pilots/20261124-airline-payment-first-pass-match.json) · [원천 대조와 전송 검사](../../src/agent_memory_eval/experiments/first_pass_match.py) · [기존 15건의 비교 조건 정정](../reports/20261124-airline-allocation-forms.md#1회차와-메모리만-달랐는가)

v2 결과에서 각 판단을 열면 그때의 고객 요청·업무 도구 결과, 조회 안내, 표시된 후보의 제목·순서와 버전, 실제 조회한 항목과 다음 업무 응답을 확인할 수 있다. 같은 과제에서 양쪽 모두 성공했어도 고객 발화·업무 호출·메모 조회·모델 요청·토큰·요금의 변화를 각각 계산한다. 1회차 기준과 같은 2회차 정책 간 비교가 모두 있다. 원천 보관본이나 사용량이 빠진 지표에는 관측 범위를 표시한다. [실제 선택 분포와 같은 성공의 효율](../reports/20261123-memory-selection-efficiency.md)

자동 반복을 완성할 다음 연결은 **개발용 2회차의 선택 근거·업무 결과·효율을 다음 제안 입력으로 돌려주는 것**이다. 예를 들어 서로 다른 제목이 보여도 맨 위 항목에 선택이 집중되면, 같은 은행의 순서만 바꿨을 때 모델이 같은 메모를 찾는지 검증할 수 있다. 개발 사례만 제안에 쓰고, 확인 집합은 정책 채택 평가에 보관한다. 현재 제안 입력은 1회차 공개 기록에서 만들고, 제안 JSON은 외부에서 받는다. 별도 LLM이 스스로 다음 라운드를 기동하거나 성적에 따라 정책을 승격한 실측은 아직 없다.

## 탐구 에이전트가 두 번째 후보를 고르는 경로

현재는 이 저장소에서 일하는 세션이 탐구를 맡는다. 개발 결과에서 판단 근거를 검산하고, 바꿀 작성·조회 규칙과 반증 기준을 기록해 다음 비교에 쓴다. 별도 에이전트 연결은 후속 단계다. 이때 외부 에이전트가 허용된 조작과 개발 근거를 확인하고, 다음 정책이나 보류 사유를 제출하고, 비교 결과를 다시 읽을 수 있어야 한다. 사람은 연구 질문, 개발·확인 분할, 허용한 변경과 총예산을 정한다. 아래는 그 연결의 설계다. [현재 쓸 수 있는 공용 판독](trajectory-outcomes.md#한-판단에서-단서의-출처를-검산하기)

첫 연결은 기존 제안 검사기와 두 벤치의 결과 판독기에 버전이 있는 JSON 입출력을 붙이는 것이다. 탐구 에이전트는 같은 명령으로 사용 가능한 조작과 개발 근거를 요청하고, 제안의 접수·거부 사유와 다음에 읽을 결과 참조를 받는다. 벤치가 제공하지 않는 측정값과 실행 중 놓친 관측을 구분해야 한다. 예를 들어 BFCL 함수 선택 과제는 호출을 채점하고, 은행은 실제 도구 반환과 DB 변화도 기록한다.

| 탐구 에이전트가 할 일 | 프레임워크가 제공하거나 검증할 것 |
| --- | --- |
| 무엇을 바꿀 수 있는지 확인한다 | 벤치 어댑터가 지원하는 저장 시점·표현 형식, 조회 시점·선택 방법과 버전, 관측 가능한 업무 결과를 반환한다. 다섯 형식은 출발 정책이다. 새 형식과 도구 설명은 선언으로 추가하고, 새 검색 알고리즘이 필요하면 버전을 부여한 플러그인으로 같은 자리에 연결한다. |
| 개발 결과에서 다음 가설의 근거를 찾는다 | 등록한 개발 사례만 내보낸다. 원천의 공개 구절, 저장한 항목·버전, 선택 당시의 입력과 목록 순서, 판단 전 실제로 들어간 제목·본문, 업무 호출과 결과를 연결한다. 공식 성패와 행동 지표, 공동 성공 쌍의 효율, 전체 배정 비용·결측·반복 변동을 함께 준다. 각 근거에는 다시 열 수 있는 참조를 붙이고, 공식 채점 세부와 확인 고객의 기록은 별도로 보관한다. [두 벤치에서 확보한 근거](trajectory-outcomes.md) |
| 다음 정책이나 보류 사유를 제출한다 | 부모 정책·개발 결과의 버전, 인용한 근거, 바꿀 내용, 예상 행동과 그 예측을 기각할 관측을 한 기록에 묶는다. 변경 없이 보류하는 경우에도 근거를 남긴다. 실행기는 인용 출처·개발 분할·잔여 한도를 점검한다. 탐구 결과와 의견은 작업자 입력에서 분리하고, 기억 작성자에게는 배정한 공개 경험과 등록된 피드백만 전달한다. [기존 제안과 인용 검증](../../scripts/prepare_memory_candidate.py) |
| 비교를 실행하고 다음 판단에 쓴다 | 작성 정책 비교는 조회 조건을 고정하고, 조회 정책 비교는 같은 작성물 버전을 쓴다. 동일 과제에서는 1회차의 업무 시작점을 재사용하고 2회차 무기억 배정은 0건이다. 결과에는 부모·후보·배정·원장 참조와 누적 지출을 남겨 새 프로세스에서도 이어 읽게 한다. 탐구 모델을 쓰면 제안 비용도 작성·조회·업무 비용과 구분해 총예산에 합산한다. 후보와 채택 기준을 고정한 뒤 확인 집합을 연다. |

보관 자료에서 두 가지 판단을 연습할 수 있다. BFCL 공연 검색의 같은 공개 경험에는 함수 호출 시도만 있었다. 기존 사실 기억은 공연을 찾았다고 적었고, 이 기억이 입력에 들어간 2회차는 검색을 생략했다. 후보 기억에서는 세부 정보를 미확인으로 남겼고 2회차가 다시 검색했지만, 후보 본문에도 성공했다는 표현이 남았다. 다음 작성 후보는 **완료를 주장한 문장이 실제 도구 반환을 인용하는가**를 시험할 수 있다. 은행에서는 요청 상품의 개설 결과가 공개 1회차 19건 중 0건이었다. 이 자료에 대해 **경험한 개설 결과를 더 잘 보존하는 작성법**을 비교하자는 제안에는 보류 근거가 있다. 두 판단은 어떤 관측을 보고 무엇을 시험하거나 멈출지 보여 주는 개발 예시다. [BFCL 작성물·판단 원문](../../artifacts/analyses/20261126-bfcl-writer-pairs.json) · [은행 원천 단서와 관측 분모](../../artifacts/analyses/20261126-banking-trajectory-summary.json)

**후속 연결의 완료 기준.** 은행과 BFCL의 보관 원장·모의 실행에서 같은 정책 선언과 같은 호출 절차로 두 라운드를 잇는다. 새 세션의 제안자에게 첫 라운드의 개발 자료와 허용 조작만 주고, 제안 또는 보류가 인용한 근거와 연결되는지, 그 기록에서 다음 배정을 복원할 수 있는지 확인한다. 확인 사례를 인용한 제안과 기억 외 조건을 바꾼 배정은 실행 전에 거부되어야 한다. 고정 응답으로 이 경로를 검증한 뒤, 실제 탐구 에이전트가 같은 인터페이스에서 사람의 후보 지정 없이 다음 결정을 내리는 것을 별도로 확인한다. 독립 고객·문항에서 나타나는 정책의 이득과 손해는 그 뒤의 확인 실험에서 측정한다.
