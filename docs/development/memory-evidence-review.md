# 메모 작성 때의 성패 피드백과 행동 근거 판독

은행 실험에서 과제 008은 이관이 공식 요구 행동이었고 1회차에 성공했다. 과제 010도 도구가 이관 성공을 반환했다. 하지만 공식 채점에서 본인확인은 일치했고 고객의 추천 제출은 일치하지 않아 1회차는 실패했다. 작성자가 공개 대화에서 확인할 수 있는 개별 행동의 결과와 과제 전체의 결과는 서로 다른 정보다. [은행 필수 작성 결과 원본](../../artifacts/analyses/20261124-banking-required-results.json)

## 작성자에게 제공할 정보

무기억 1회차가 끝나고 공식 채점이 확정되면, 등록된 작성 정책이 피드백 범위를 정한다. 같은 공개 대화와 도구 기록으로 사실·경험·절차·교훈·자유 메모를 각각 독립된 세션에서 작성한다. 필수 저장에서는 각 형식에 비어 있지 않은 봉인 메모가 있어야 그 원천의 2회차를 시작할 수 있다.

| 작성 조건 | 작성자가 받는 마지막 사용자 메시지 | 원장에 남기는 근거 |
|---|---|---|
| `none` | `{"kind":"evaluation_feedback","level":"none"}` | 1회차 실행·공개 궤적 해시, 작성 요청과 실제 저장본 |
| `result_only` | `{"kind":"evaluation_feedback","level":"result_only","success":false}` 또는 `true` | 위 근거와 함께 1회차의 공식 채점 이벤트 ID와 그 불리언 값 |

다섯 형식 모두 같은 성패를 받는다. 공식 결과가 아직 없으면 `result_only` 작성은 결측으로 남겨야 한다. 도구의 성공, 고객의 만족 표현, 작성자의 추측을 실패나 성공으로 대신 입력하면 비교가 달라진다. 결과의 열람 권한은 사후 작성자에게 있다. 공식 정답·누락 행동·채점 사유·최종 DB는 작성 요청에서 제외한다. 2회차 풀이 입력에는 기존에 허용된 메모 내용만 전달할 수 있다. 작성자가 성패를 실제 메모에 적었다면 그 문장은 메모의 일부로 추적한다.

공통 실행 설정의 `writer_feedback_level`로 조건을 정한다. 생략한 과거 등록은 `none`을 사용한다. `result_only`를 사용하는 등록은 원천 로그, 채점 이벤트, 성공 여부를 묶는다. 모의 작성기로 양쪽 성패와 다섯 형식 모두에서 작성 요청·저장본·재열기를 확인했다. 과거 은행 파일럿의 실제 작성은 20건 모두 `none`이었다. 이 요청의 역할·지침·경험·모델 설정·도구를 그대로 보존하고 성패만 바꾼 입력 20건의 해시를 오프라인으로 만들었다. 원천은 성공 1건과 실패 3건으로, 형식별 배정을 합치면 각각 5건과 15건이다. 11월 25일 이 해시와 일치하는 실제 작성 20건과 새 상담 40건을 확인했다. [공식 결과 수신 계약](../../schemas/form-result-feedback-v2.schema.json) · [은행 원기록 대조](../../artifacts/analyses/20261124-banking-evidence-review.json) · [실제 응답과 후속 성적](../reports/20261125-banking-result-feedback.md)

다음 비교의 단위는 **같은 원천 × 같은 메모 형식**이다. 두 작성 조건의 예산·모델·시드·저장 규칙을 맞춘다. 실패 원천에서는 실패한 전략을 무조건 권하는 문장이 줄었는지, 성공 원천에서는 한 번의 성공을 모든 단계의 정당성으로 확대하는 문장이 늘었는지도 본다. 성패 하나로 원인을 알 수 없으므로 이유를 지어내지 말라는 안내를 추가한다면 두 조건에 똑같이 적용한다. 후속 행동이나 효율은 2회차의 같은 전달 방식끼리 비교한다. 무기억 기준은 원래 1회차다.

Reflexion은 과제 결과 신호를 받은 에이전트가 경험을 글로 정리하고 다음 시도에 활용하는 방식을 실험했다. 여기서는 같은 궤적과 작성 형식을 짝지어 공식 성패 한 가지가 주는 추가 정보를 측정할 수 있다. [Reflexion, NeurIPS 2023](https://papers.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)

## 어떤 판단을 사람이 읽거나 모델에 맡길 수 있는가

공식 성패와 근거는 별도로 기록한다. 노출 여부는 제출된 요청의 메모 구간과 응답을 검사하고, 호출·인수·비용은 실행 기록으로 확인한다. 성공 여부는 벤치의 채점 이벤트와 공식 산출물을 대조한다. 사람이나 LLM은 **메모의 한 문장과 한 시점의 행동 사이의 의미 관계**를 판독할 수 있다.

| 판독 항목 | 허용하는 근거 |
|---|---|
| 과거 경험이 이 주장을 지지하거나 반박하는가 | 작성자에게 공개된 1회차 대화·도구 응답 |
| 주장에 적힌 조건이 현재 상황에 해당하는가 | 해당 업무 판단 **직전**까지의 일반 입력 |
| 같은 결론을 이미 현재 입력만으로 얻을 수 있는가 | 당시 보인 정책·고객 발화·도구 정의·업무 도구 결과 |
| 실제 응답이 그 절차·교훈과 일치하거나 충돌하는가 | 그 시점의 공개 발화 또는 업무 호출·인수 |

확정 판독마다 해당 구역의 JSON 경로와 원문 인용이 필요하다. 가져올 때 경로, 고유한 인용 일치와 문자 위치를 검사한다. 판단이 이르거나 기록이 모호하면 `unclear`를 허용한다. 인용의 존재는 프로그램이 검증하며, 그것이 결론을 충분히 뒷받침하는지는 독립 판독으로 점검한다.

판독자는 후보 문장, 과거 공개 경험, 현재의 일반 입력, 관측 행동을 받는다. 조건명, 실제 메모 노출, 공식 성패, 반대 조건 결과는 분석용 대응표에 보관한다. 판독 뒤에 노출 여부·동일 입력 비교 가능성·공식 결과를 연결한다. 메모를 보지 않아도 행동이 주장과 일치할 수 있다. 한 건의 의미 일치로 메모를 사용한 동기나 최종 성공 원인을 결정할 수 없다.

은행 사례는 결과를 본 뒤 선택한 **판독 경로 검증용 표본**이다. 네 과제의 절차·교훈 각 한 문장, 두 전달 방식, 첫째·셋째 공개 업무 판단을 포함한다. 선택한 32개 지점 모두에 응답이 있었다. 두 배정의 입력이 같아 중복을 제거하면 서로 다른 판독 입력은 31개다. 여러 판단이 같은 과제와 메모를 공유한다. 첫 판단 16건은 1회차와 일반 입력이 같았고 이 중 8건에서 메모 본문이 보였다. 셋째 판단 16건은 모두 1회차와 일반 입력이 이미 달랐다. 이 사례에서 절차·교훈의 평균 효과를 추정하지 않는다. [문장·시점 선택 목록](../../protocols/diagnostics/banking-semantic-review-v1.json)

LLM을 도입하면 먼저 사람이 조건을 가린 채 같은 입력을 독립 판독한다. 작성·풀이 모델과 독립된 판정 모델의 버전과 설정을 고정하고, 별도 과제에서 항목별 일치·불일치·판단 보류를 공개한다. 같은 입력의 중복 배정은 한 판독으로 센다. 둘 다 보류한 것을 정답 일치율로 해석하지 않도록 양쪽이 확정한 건의 일치 수도 낸다. 근거가 엇갈리는 사례는 원문을 사람이 재검토한다. G-Eval은 기준을 명시한 과제별 모델 평가를 검증했고, MT-Bench 연구는 답변 순서·장황함·자기 선호가 판정에 영향을 줄 수 있음을 보였다. 이 은행 기록에서의 일치도는 별도 측정이 필요하다. [G-Eval](https://aclanthology.org/2023.emnlp-main.153/) · [Judging LLM-as-a-Judge](https://papers.nips.cc/paper_files/paper/2023/hash/91f18a1287b398d378ef22505bf41832-Abstract-Datasets_and_Benchmarks.html)

## 오프라인 재현

봉인된 두 은행 실행 디렉터리가 있는 작업 공간에서 실행한다.

```bash
uv run python -m scripts.review_banking_evidence --output outputs/banking-evidence-review
uv run python -m scripts.analyze_banking_memory --exposure-coverage
```

판독자에게는 `blinded-inputs.json`만 전달한다. `analyst-key.json`은 원천·작성 로그, 항목 버전·문장 위치, 각 판단의 요청·응답 및 공식 결과에 연결된다. `writer-feedback-pairs.json`은 기존 요청과 성패를 제공하는 요청의 해시를 보존한다. 노출 보고는 미채점 상담도 배정 분모에 두고, 확인된 노출·확인된 미시작·불확실한 전송을 구분한다.

아래 명령은 제출된 판독을 원래 봉인된 기록에 대조한다. 사람 기준 파일을 지정하면 항목별 혼동표와 재검토 대상이 나온다. 모델 판독에는 모델·버전·공급자·설정, 원응답 ID와 원문, 실제 판독 입력 해시가 필요하다. 이 도구에서 모델 호출이나 비용은 발생하지 않는다. [판독 제출 형식](../../schemas/semantic-memory-ratings-v1.schema.json) · [합성 입력·판독 예시](../../tests/fixtures/semantic-memory-review-v1.json)

```bash
uv run python -m scripts.review_banking_evidence --output outputs/banking-evidence-assessed \
  --ratings judge-submission.json --human-reference human-submission.json
```
