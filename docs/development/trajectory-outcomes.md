# 원천 경험과 첫 업무 판단을 원기록에서 비교하기

아래 두 판독 명령에 `--policy-evidence`를 추가하면 같은 원장을 정책 비교용으로 읽는다. 함수 호출 없는 정답, 미관측 판단, 공개 단서의 저장·노출·행동 일치, 1회차 대비 회복·악화, 두 정책의 공동 성공 효율과 작성 비용까지 확인할 수 있다. `--summary`를 함께 주면 전체 행과 작성 기록의 해시를 보존한 집계표가 나온다. [공통 정책 실행과 집계의 해석](../reports/20261126-evidence-foundation-plan.md) · [재현한 두 표](../../artifacts/analyses/20261126-policy-evidence-summary.json)

같은 결과 형식으로 τ³ 은행 계좌 개설과 BFCL 함수 선택을 분석할 수 있다. 한 행은 등록된 1회차 과제 또는 2회차 배정 하나다. 조건·기억 형식·전달 방법·작성 반복·상담 반복, 원천과 작성 실행 ID, 작성자가 저장한 스냅숏을 함께 둔다. 은행의 독립 단위는 고객, BFCL의 단위는 공개 질문이다. 같은 기억으로 여러 번 받은 응답은 하나의 반복 묶음이다. [결과 계약](../../schemas/trajectory-outcomes-v1.schema.json) · [공용 집계 코드](../../src/agent_memory_eval/analysis/trajectory.py)

## 1회차만으로 후속 실험의 기회를 확인하기

`--sources-only`로 1회차의 공개 궤적과 상담원의 첫 업무 입력을 읽는다. 은행에서는 원천 단계가 닫힌 직후, 작성과 후속 상담을 배정하기 전에 실행할 수 있다. 단서별로 원천에 있는 값, 첫 입력에도 있는 값, 원천에서만 관측한 값을 집계한다. 누락된 관측은 `null`, 확인 결과가 빈 집합이면 `[]`다. 중단 시점까지의 1회차 전체와 작성에 쓸 수 있는 공식 채점 원천의 분모를 함께 표시한다. [은행 원천 판독](../../src/agent_memory_eval/adapters/banking_trajectories.py) · [BFCL 원천 판독](../../src/agent_memory_eval/adapters/bfcl_trajectories.py)

은행 v3 실측에서는 과제 메타데이터가 지정한 필수 문서 ID가 1회차 검색 결과에 등장한 과제가 18/19개였다. 채점 원천으로 좁히면 11/12개, 고객 9명이었다. 해당 ID는 첫 업무 입력에 없었다. 검색 결과의 등장만으로 본문을 이해했거나 그 내용을 기억에 저장했다는 결론까지 낼 수는 없다. 요청 상품의 개설·거절 등 실제 도구 반환은 0/19개였다. 따라서 이번 원천으로는 경험한 개설 결과를 두 작성법이 얼마나 잘 보존하는지 비교할 수 없다. [은행 실측](../../artifacts/analyses/20261126-banking-trajectory-summary.json)

새 은행 프로토콜은 `source_opportunity_requirement`를 선택적으로 등록할 수 있다. 예를 들어 과거의 요청 상품 개설 결과를 보존하는 실험이라면 다음과 같이 쓴다. 최소 고객 수는 가설과 설계자가 정한다. 이 예시는 설정 문법을 보여 준다.

```json
{"source_opportunity_requirement": {"cue": "target_opening_return", "evidence": "source_only", "minimum_clusters": 1}}
```

`source`는 공개 원천에서 확인한 단서를, `source_only`는 첫 입력과 대조해 과거에만 있었던 단서를 센다. 은행 실행기는 해당 단서가 있는 **채점 원천의 서로 다른 고객 수**를 확인한다. 후속 실행 폴더의 `source-opportunity.json`에 진행·중단과 근거 해시를 기록한다. 중단이면 등록된 모든 후속 상담을 미시작으로 읽을 수 있다. 통과하면 같은 판정을 후속 등록에 묶는다. 과거 은행 등록에는 이 조건이 없으며 BFCL 판독기는 동일한 단서 집계를 제공한다. [은행 실행 경로](../../scripts/run_banking_policy_cycle.py) · [판정의 회귀 검사](../../tests/test_trajectory_report.py)

## 행동·진척·효율을 읽는 법

| 질문 | 근거와 분모 |
| --- | --- |
| 판단 전에 무엇을 봤나 | 메모리 목록·본문 요청과 도구 반환을 각각 세고, 첫 업무 응답을 만든 요청에 실제로 포함된 제목·본문과 항목 버전을 검증한다. 반환된 응답에는 오류도 들어갈 수 있다. 본문 노출은 입력의 해당 구간에서 확인한다. |
| 무엇을 선택했나 | 첫 업무 응답의 함수 이름과 인수를 기록한다. 텍스트만 보냈으면 호출 목록은 비어 있다. 완전한 업무 응답이 없으면 판단은 미관측이다. BFCL은 함수 호출 여부를 공식 채점하며 함수의 실행 결과는 제공하지 않는다. |
| 어디까지 진행했나 | 은행은 고객과 상담원의 기록된 행동을 네이티브 DB에서 재생해 종료 해시와 계좌 행을 대조한다. `graded`, `ungraded`, `not_started`마다 대상·대상 외·전체 개설을 집계한다. 각 지표에는 관측 분모, 양수인 상담 수, 값의 합이 있다. 분모가 0이면 합도 `null`이다. |
| 같은 기억으로도 판단이 달라지나 | 같은 과제·작성 조건·형식·작성 반복·전달 방식에서 작성 실행, 스냅숏, 첫 요청 바이트가 같은 묶음만 비교한다. 전송용 호출 ID는 제외하고 함수 순서와 인수 변화를 센다. 은행의 첫 검색 적중은 첫 업무 응답이 검색 하나이고 실제 반환에서 문서 순위를 읽을 수 있는 경우에 측정한다. |
| 비용과 토큰은 얼마나 들었나 | 각 상담의 전체 역할에서 기록된 요청·전송 수, 토큰 보고가 있는 요청 수, 보고 토큰·금액, 금액 미확정 요청 수를 제시한다. 로컬 결과를 재사용한 요청 수도 보여 준다. BFCL 원천 8건은 기존 생성 결과를 재사용했으며 토큰 합에는 그 입력·출력이 들어간다. 조건별 합은 채점·중단으로 나눈다. 작성 비용까지 포함한 실험 총액과 공동 성공 쌍의 효율은 기존 짝비교 결과에서 확인한다. |

은행에서는 220개 기억 각각의 세 상담이 같은 첫 요청을 받았다. 217묶음에서 첫 함수 또는 인수가 달랐다. 세 상담 모두 첫 검색을 비교할 수 있었던 198묶음 중 49묶음은 필수 문서를 찾았는지도 갈렸다. 이것은 같은 기억 아래의 반복 변동이다. 기존·후보의 공식 양쪽 채점 210쌍은 모두 실패였고, 현재 자료에서 두 작성 규칙의 성공률 우열을 가릴 수 없다. [계좌 행과 공식 채점](../reports/20261126-banking-opening-model-results.md) · [반복 집계](../../artifacts/analyses/20261126-banking-trajectory-summary.json)

BFCL 질문 8개의 2회차에서 자동 제공은 40/40건에 본문이 들어갔고 첫 업무 함수 호출은 23/40건이었다. 자율 조회는 목록과 본문 호출이 모두 0건이었고 첫 업무 함수 호출은 25/40건이었다. 해당 질문에는 함수 호출을 삼가야 하는 경우도 있다. 함수 호출 여부를 올바르게 고른 횟수는 각각 33/40건, 35/40건이었다. [BFCL 실측](../../artifacts/analyses/20261126-bfcl-trajectory-summary.json)

별도 BFCL 대조에서 목록을 먼저 여는 행동만 지정하고 다음 행동을 모델에 맡겼을 때, 같은 판독기가 8/8건에서 목록·본문 반환과 다음 업무 입력의 본문을 확인했다. [대조 원장의 해시](../../artifacts/analyses/20261126-bfcl-read-path/initiation-list_only.json)

은행의 `request_error_summary`는 전송 영수증을 단계·상담 반복·담당 모델·오류별로 묶는다. 고객 모델의 503 응답 130건은 모두 첫 반복, 429 응답 2건은 모두 세 번째 반복에 몰렸고 132건 모두 재시도 시점을 담고 있었다. 작성 요청 20건은 142,390∼142,651바이트로 로컬 상한에서 전송 전에 중단됐다. 새 등록에서 재시도 범위 및 역할별 입력 상한을 정할 때 이 분포를 사용할 수 있다. ## 한 판단에서 단서의 출처를 검산하기

조사할 작업자 요청 ID와 표현을 지정하면 같은 판독기로 여러 벤치의 실제 원장을 읽을 수 있다. 아래 명령은 BFCL의 공연 검색에서 도시명이 어디에 있었는지를 재현한다. 무기억 1회차는 작업자 원장만 지정한다. 작성과 풀이가 서로 다른 원장에 있으면 `--writer`로 원래 작성 폴더를 지정한다. 기억을 모아서 제공한 경우 각 작성 폴더를 같은 옵션으로 추가한다. 배정된 항목마다 원래 저장 호출과 버전이 맞아야 한다. [명령 구현](../../src/agent_memory_eval/analysis/decision_cues.py) · [결과 형식](../../schemas/decision-cue-v1.schema.json)

```bash
uv run --offline python -m agent_memory_eval.analysis.decision_cues \
  --worker runs/bfcl-relevance-two-pass-01-decoded/live_relevance_8-8-0 \
  --request request_3ea05b67cc484267bb5cd7a64a22f873 --literal 'Cape Town'
```

결과에는 작성자에게 실제로 주어진 공개 경험의 인용 위치가 남고, 작성 지침·피드백에 있던 표현도 따로 표시한다. 저장된 버전, 조회 직전 보였던 제목과 순서, 요청·반환, 판단 입력의 제목·본문 위치를 대조한다. 현재 고객의 말·업무 도구 결과·앞선 작업자 발화·도구 설명은 실제 입력의 출처별로 찾아낸다. 업무 응답과 해당 요청의 토큰·비용, 세션의 공식 채점 상태도 함께 보관한다. 반환을 받은 뒤 어느 요청에 본문이 들어갔는지 두 요청의 ID로 구별할 수 있다. 전송 전 중단되면 판단의 노출과 행동은 미관측으로 남고, 응답이 잘렸다면 확인된 입력과 불완전한 행동을 구별한다.

| 보관 기록 | 판단에서 확인된 근거 | 현재 가능한 해석 |
| --- | --- | --- |
| BFCL 공연 검색, 무기억 1회차와 같은 사실 기억을 배정한 2회차 두 건 | `Cape Town`은 모든 현재 질문에 있었다. 1회차는 도시명을 넣어 검색했다. 2회차 자동 제공은 제목·본문을 보고 텍스트로 답했고, 자율 조회는 기억을 열지 않고 검색했다. 함수 호출 여부의 공식 결과는 각각 정답·오답·정답이었다. | 도시명 사용에는 현재 질문이라는 대체 출처가 있다. |
| τ³ 은행 058, 첫 업무 검색 | `EcoCard`는 작성자가 본 공개 경험과 저장한 제목·본문에 있었고, 이 본문을 받은 작업자가 쓴 첫 검색 인수에도 있었다. 그 요청의 다른 입력 문자열에서는 일치가 0건이었다. 상담은 미채점이었다. | 과거 상품명이 검색어 선택에 기여했을 가능성을 같은 판단에서 시험할 수 있다. 최종 성공에 대한 관측은 없다. |
| τ² 소매 주문 조회, 연속한 두 요청 | 네 작성자의 은행에서 항목 세 개가 배정됐다. 본문 조회를 요청할 때 주문번호는 앞선 업무 도구 결과에 있었다. 다음 업무 요청에서 선택한 본문에도 번호가 들어갔고 실제 주문 조회 인수에 쓰였다. | 읽은 시각은 확인됐다. 해당 번호를 얻을 수 있던 경로는 두 개였다. |

여섯 요청의 입력 경로와 원본 해시를 함께 보관했다. 판독은 대소문자를 구분해 각 공개 문자열 값에서 첫 일치 위치를 남긴다. 표현이 다른 주장에는 기존 문장 추적기로 각 단계의 원문을 별도로 인용할 수 있다. BFCL 사례에서 1회차의 검색 함수명, 기억의 “Successfully found a Theater event”, 후속 답변의 “I have found a Theater event”를 같은 요청에 대조했다. 공식 채점과 별도로, 공연 발견을 확인하는 도구 반환이 원천에 있었는지를 판단할 수 있다.
