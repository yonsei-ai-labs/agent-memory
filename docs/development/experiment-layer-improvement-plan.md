# 실험 계층 개선과 다음 기억 실험의 연결

2026-11-16 · P0·schema/blob 캐시·작은 버그 수정·작업자 작성 기억의 mock 연결

기억·기록 코어를 유지하고, 과거 재현을 현재 작업 트리에서 분리한 뒤 공통 실험 실행·기록 비용을 개선한다. 다음 연구 목표는 공개 경험에서 작업자가 작성한 기억이 새 세션의 행동과 최종 결과에 미치는 영향이다. 이름·폴더 재배치보다 그 비교를 반복해서 안전하게 실행할 수 있는 공통 기능을 먼저 만든다. SQLite 도입은 필요하지 않다.

## 확인한 상태와 리뷰의 보정

최초 검토 기준 HEAD는 `efd019d`이며 당시 작업 트리는 깨끗했다. [연구 계획](../research/plan.md)·[설계](../design/architecture.md)·코드·과거 동결 기록을 대조해 계획과 Git 객체 대조 자료를 추가했다. 이어 사용자의 구현 요청으로 [P0 재현 실행기](historical-reproduction.md)를 추가했다. 기존 실행 코드·원본·동결 기록은 유지한다. 리뷰가 보고한 151개 테스트 통과·약 9분은 제공받은 검증 이력이며 새 행동 검증·과거 재현은 별도 기록한다.

- 과거 검토 스크립트가 현재 트리의 광범위한 해시를 강제하는 문제는 실제로 있다. 최근 `review_decision_replay_120.py`도 같은 제약을 추가했다. 공용 수정 대신 새 실험 파일을 덧붙이게 만드는 요인이다.
- `Journal.append`는 누적 메모리 바이트 `self.data + line`을 매번 다시 파싱한다. `validated_prefix`는 과거 줄의 스키마 검사만 건너뛰고 해시·연결·사건 검사는 다시 한다. 매 append마다 디스크 전체를 다시 읽는다는 뜻은 아니다. 누적 bytes 연결도 복사 비용을 만든다.
- 모든 commit에 `state_ref`가 있고 현재 상태 전체를 직렬화한다. 동일 내용은 이미 blob 해시로 중복 제거되므로, 같은 state 참조를 재사용하는 것 자체에 새 계약 버전이 반드시 필요한 것은 아니다. provenance가 계속 변하면서 커지는 부분을 따로 해결해야 한다.
- `contracts.core`가 `validation`의 JSON 기본 함수를 가져오고, 런타임 검증은 저장소 `schemas/`·fixture 경로와 연결돼 있다. 단순 import 전체가 반드시 실패한다는 뜻보다, checkout 밖 런타임·검증 경로의 패키징이 완결되지 않았다는 뜻으로 본다.
- 어댑터→실행기, 분석↔실행기, 실행기끼리의 공통 함수 의존과 기억 도구 스키마 중복을 확인했다. `PlanCompiler`의 범용 의미/준비 검사는 구현 전이며, 다음 정리에서 구현 완료로 표시하지 않는다.

## 1. 먼저 과거 재현 경로를 고정한다

**실행 구현 commit과 분석 재현 commit을 구별한다.** 분석 스크립트·결과 주석은 실행 이후 추가되므로 `implementation_commit`만 checkout하면 분석 명령이 없거나 프로필 문서가 빠진다. 현재 main 이력의 Git blob을 SHA-256으로 대조해 아래 후보를 찾았다. [기계적 대조 자료](../../artifacts/analyses/20261116-reproduction-commit-candidates.json)에 전체 commit·lock 해시·검증 범위를 남겼다.

| 실험 | 실행 구현 파일이 처음 일치한 commit | 전체 동결 참조가 처음 일치한 commit | 검토 스크립트가 있고 동결 참조가 일치하는 재현 후보 |
| --- | --- | --- | --- |
| 전달 비교 | `65a757f` | `65a757f` · 64개 | `65a757f` |
| 무기억 기준선 | `1edc6d0` | `086eb6f` · 85개 | `7243fef` |
| 결정 재전송 | `8a33939` | `0bd1acc` · 133개 | `c51165b` |

전달 비교 lock의 `head_commit=c89e34b`는 커밋 전 구현을 포함한다고 명시돼 있다. 원본 lock을 고치는 대신 64개 참조가 일치하는 `65a757f`를 보충 기록으로 사용한다. 이 표는 **코드·스크립트 존재의 후보 검증**이며 새 worktree에서 세 명령을 모두 실행했다는 뜻은 아니다.

새 재현 launcher는 다음 책임만 가진다.

1. 보충 registry로 분석 재현 commit·실행 구현/분석 해시·원본 및 의존 자료를 찾는다. detached worktree를 만들고 현재 main과 사용자의 변경을 건드리지 않는다.
2. 해당 버전의 환경과 실제 Python import 경로를 확인한다. 현재 venv의 editable install이 main의 코드를 가져오면 거부한다. Python·잠금 파일·실행 명령·실제 코드 위치를 재현 receipt에 기록한다.
3. 검증한 원본을 별도 경로에 준비한다. 기존 함수는 symlink 경로를 거부하므로 raw symlink로 우회하지 않는다. 원본에 쓰기가 전파되는 hardlink도 쓰지 않는다. 독립 복사 또는 검증한 copy-on-write 사본을 사용하고 입력 해시를 전후 대조한다.
4. 실험별 누락 자료를 명시한다. 전달 비교의 기존 review는 고정 τ² 소스와 guided 기억 원천 raw도 확인한다. baseline·재전송의 저장 결과 감사와 필요한 입력이 같다거나 모두 자동 복원 가능하다고 가정하지 않는다.
5. 고정한 읽기 전용 분석 명령만 실행하고 성공·실패를 별도 receipt에 남긴다. 과거 receipt·주석을 덮어쓰지 않는다. 모델 호출·live 실행·결측 대체·자동 재시도는 재현 작업에 포함하지 않는다.

두 검증 책임을 유지한다. **과거 재현**은 지정한 코드·주석·원본으로 당시 결과를 재계산한다. **최신 코드 호환 감사**는 옛 로그의 해시·격리·비용·채점·노출을 읽고 의미가 유지되는지 확인한다. 전자는 고정된 코드 해시를 엄격히 검사하고, 후자는 현재 코드가 과거 파일과 같을 것을 요구하지 않는다. 기존 assert를 단순히 끄는 방식으로 해결하지 않는다.

완료 기준은 세 재현 후보에서 필요한 원본·의존 자료를 준비해 기존 검토 명령을 통과하고, 모의 저장소에서 main의 코드를 변경해도 재현이 고정 commit을 사용하는지 확인하는 것이다. 잘못된 commit·원본 변조·다른 경로의 import·불완전 입력을 거절하는 행동 검사도 필요하다. 이후 원인 진단 `c31a9d6`까지 추가해 네 명령을 실제 통과했다. [검증 자료](../../artifacts/analyses/20261116-historical-reproduction-results.json)·[반영 보고서](../reports/20261116-reproduction-and-review-update.md)를 따른다.

## 2. journal은 v1.1/v1.2 형식을 유지하며 먼저 개선한다

추가 리뷰가 제공한 프로파일링은 120요청 감사 51.3초 중 schema validator 재생성이 45.9초, 테스트에서 schema 약 48%·blob 재검증/읽기 약 25%·journal 재파싱 약 6%였다. 이 수치를 여기서 독립 재측정한 것은 아니다. 코드를 대조해 `validate_manifest(checks=None)`의 매 요청 schema 재컴파일과 `Journal.append`의 새 `seen` 집합으로 인한 전체 참조 blob 재검증을 확인했다. **P1a는 schema 재사용 → blob 검증 캐시 → 증분 journal/인덱스 순서로 분리 측정한다.**

schema 캐시는 계약 버전·schema 자원 범위를 명확히 하며 공유 객체의 뜻하지 않은 변경을 막는다. writer의 blob 캐시는 불변 참조에 대한 최적화로 한정하고, 새 참조·변조/재개·예외 뒤의 캐시 상태를 검사한다. 새 writer와 독립 감사의 전체 해시 검증은 유지한다. 같은 writer에서 외부 변경을 어디까지 감지할지도 명시하고 테스트한다.

첫 schema 캐시는 적용했다. 같은 120요청을 프로파일링한 새 프로세스에서 감사 49.80→5.87초, `validators()` 누적 44.45→0.39초였고 감사 결과 SHA-256은 같았다. [측정 자료](../../artifacts/analyses/20261116-schema-validation-performance.json)는 버전별 한 번의 관측과 실행 코드를 보존한다. blob 캐시·증분 journal은 이 성능 수치에 포함하지 않는다.

이어 [writer blob 검증 캐시](blob-verification-cache.md)를 적용했다. 하위 참조까지 파일 정보를 확인하고 새 writer·독립 감사는 전체 해시 검증을 유지한다. 별도 사본의 3회 append에서 반복 검증 읽기 23.9MB→0, 전체 관측 중앙값 약 389→271ms였다. [보존 원본 10개 전체 감사](preserved-run-audits.md)의 출력도 유지했다. 증분 journal은 아직 구현하지 않았으며, native 환경 복사 비용과 전체 테스트 시간은 별도로 판단한다.

열 때 전체 검증을 한 번 수행하고, 이후 새 commit을 기존 검증 상태에 적용하는 증분 검증기를 둔다. 열린 writer의 정상 기록 경로와 파일 전체의 독립 검증 경로를 구별한다. append 실패 뒤 poisoned 상태·새 writer의 전체 검사·tail 보존·blob 선기록→log fsync 순서는 유지한다.

- 새 행의 해시 연결·순서·실험/세션 ID·인과 관계·중복 연산·run 시작/종료·미완료 요청 규칙을 이전 상태에 대해 검사한다. 기존 접두부를 매번 파싱하거나 누적 bytes 전체를 연결하지 않는다.
- 이미 있는 event ID map을 재사용하고, run별 사건·요청 수·request ID→완료 사건·공개 대화 항목 인덱스를 추가한다. 인덱스는 로그에서 다시 만들 수 있는 파생물이며 새 원본이 아니다.
- 검증·fsync가 성공한 뒤 인덱스와 현재 state를 확정한다. 중간 예외로 확정 전 정보가 다음 요청에 노출되지 않게 한다.
- 같은 row들을 전체 검사와 증분 검사에 넣고 결과를 대조한다. 손상·중복·미래 인과·세션 재사용·종료 후 사건·tail·짧은 write/fsync 실패도 포함한다. 과거 raw는 독립 전체 검사로 검증한다.

성능은 임시 합성 로그에서 commit 증가에 따른 새 행 검증 시간·전체 append 시간·fsync·blob 직렬화·감사 시간을 분리해 측정한다. 동일 장비·사건 크기·실행 조건을 남긴다. 상태가 커지는 비용은 이 단계 뒤에도 남을 수 있으므로 전체 append가 상수 시간이 됐다고 보고하지 않는다. 9분 테스트의 원인을 프로파일링 없이 전부 journal로 돌리지 않는다.

## 3. 공통 기능을 두 실험에서 먼저 사용한다

처음부터 여섯 실행기를 새 프레임워크로 전부 옮기지 않는다. 기존 baseline·delivery를 먼저 공통 기능으로 옮겨 재사용 경계가 맞는지 확인하고, 다음 작업자 작성 기억 실험이 같은 기능을 사용하게 한다.

| 책임 | 옮기거나 추출할 내용 | 유지할 구분 |
| --- | --- | --- |
| contracts | JSON 직렬화·해시·pointer·기본 타입을 검증 I/O에서 분리 | 저장소 fixture 검사는 개발 도구에 남김. 런타임 스키마는 패키지 자원 또는 명시한 resolver로 제공 |
| recording | journal 검증 상태·사건 인덱스·공통 참조 조회 | 원본 사건과 재생성 가능한 인덱스, 옛 계약 읽기 |
| memory | 도구 스키마 한 벌·ToolRouter | 기억 왕복이 업무·사용자 턴을 진행시키지 않는 기존 의미 |
| models | SpendGuard·ScopedGuard·전송 제약·종료 판정 | 예산 예약/관측·미확인 비용·오류/배정 생략의 의미 |
| τ² 어댑터 | 고정 checkout·patch 지점·지원 capability | native 혼합 호출·종료 도구·사용자 projection. 도메인 업무 루프는 어댑터에 남김 |
| experiments | asset 로딩·배정·실행 전 검사·수명주기·CLI 공통 기능 | 과제 선정·조건·피드백·메모 작성·채점 기준은 실험별 plan에 남김 |
| analysis | 한 번 만든 audit 인덱스·공통 비용/노출 추출 | 실험별 판정과 분석 버전·주석 출처 |

분석이 실행 루프를 import하지 않도록 계획 해석·배정 함수를 부작용 없는 모듈로 분리한다. 실행도 분석 함수를 뒤에서 import하지 않고, CLI/상위 조합이 실행 종료 후 감사를 호출한다. 어댑터는 `memory` router에 의존하고 `runner`를 import하지 않는다. 공통 코드를 하나의 거대한 `common.py`에 다시 몰지 않는다. 기존 import 경로의 얇은 호환 진입점은 이관 중 유지할 수 있다.

배정과 guard 우선순위는 실험의 일부다. 같은 seed의 순서가 유지되는지 골든 배정으로 확인하며, 시간/비용 한도 동시 도달의 판정 차이를 숨겨서 통일하지 않는다. 과거 해석은 고정 버전을 유지하고 신규 실행에서는 정책을 명시한다. 전송 64,000 bytes·45초 등의 값도 새 실행 설정으로 받아 요청 기록에 남기되, 단순 추출 과정에서 과거 한도를 바꾸지 않는다.

완료 기준은 baseline·delivery의 모의 실행에서 배정·세션/은행 분리·업무/기억 순서·원본/실제 요청·거부/오류·비용·생략·최종 점수가 유지되는 것이다. wheel을 임시 환경에 설치해 저장소 `tests/` 없이 핵심 기록·검증이 동작하는지도 확인한다. 공용 정리 자체를 기억 효과의 실증으로 보고하지 않는다.

## 4. 다음 연구는 실제 기억 경로를 사용한다

### 유료 기억 비교 전에 정할 한도와 결측

기존 프로필의 `RecordingGateway` 경로는 actor 구분 없이 같은 run의 요청을 합산하고, 요청 한도 예외가 나면 baseline은 미채점으로 남긴다. [설계 §6.3](../design/architecture.md#63-오류와-한도)의 정책 측 요청 한도·도달 상태 채점 방향과 다르며, 기존 테스트가 현 동작을 고정한다. 다음 프로토콜은 worker/writer/조회 가공과 사용자 시뮬레이터의 한도를 구분하고, 한도로 종료된 업무의 DB/통신 채점 가능 여부와 종료 사유를 정해야 한다. 인프라 오류·사용자 상태 불완전·평가 불가는 별도 결측으로 남긴다. 과거 실행·테스트의 의미를 소급 변경하지 않고 신규 실행 계약과 행동 테스트로 반영한다.

추가 [실행 보완](runtime-hardening.md)에서 새 `ExecutionLimits` API에 역할별 한도와 입력 bytes를 연결했다. 위 합산 동작은 기존 프로필의 legacy 경로이며 새 API는 명시적 계약을 선택한다. worker 한도 뒤의 도달 DB/substring COMMUNICATE는 별도 진단으로 계산하고 공식 성공·불완전 상태는 유지한다. writer의 추론 필드 재입력·전체 대화/비용 감사·중복 ID 부분 쓰기·비정상 응답 보존도 수정했다. 깨끗한 구현 동결 검사 도구는 생겼으며 새 유료 진입점의 호출 연결은 후속이다.

64,000 bytes는 현재 전송 코드의 운영 한도다. 추가 리뷰의 최대 47,358B·상위 5% 약 40KB는 제공받은 측정이며 새 은행에도 충분하다는 뜻이 아니다. 신규 프로토콜에 입력 한도 값·snapshot 크기·실제 직렬화 요청의 사전 점검·대화 진행 중 초과·한도 종료의 집계 방식을 명시한다. 새 기억을 자동 절단하거나 입력 한도 오류를 성공/일반 실패로 숨기지 않는다. 모델 context 값만 근거로 운영 한도를 임의로 높이지 않는다.

### 실제 기억과 전체 회차

추가 연구 리뷰에 따라 첫 주장 후보를 **작성 시 피드백이 오류의 기억·교정·재적용을 어떻게 바꾸는가**로 좁혀 검토한다. 피드백 없음, 검증된 성공/실패 결과만, 짧은 비평을 같은 공개 경험에서 구분한다. 14·17처럼 사용자가 잘못된 처리를 수용한 기록에 자동으로 올바른 교훈이 들어갈 것을 전제하지 않는다. 결과 피드백의 채점 정합성을 먼저 확인하고 7·39 제외 기준을 유지한다. 비평 작성자가 결과·정답을 보았는지, 비평에 어떤 근거를 공개했는지 별도 기록하며 숨은 정답을 무심코 writer 입력에 추가하지 않는다. 연구자 메모는 참고 조건이며 성능의 이론적 상한으로 부르지 않는다.

작성한 기억은 결정 지점 재전송에서 무기억·일반 메모, 원래 틀린/옳은 상태와 먼저 비교한다. 같은 상태에서 특정 규칙을 고치는지·새 오류를 만드는지·행동을 보류하는지를 본다. 그 개발 관측으로 고른 조합은 조정하지 않은 확인용 출처·상태에서 전체 회차로 검증한다. 같은 원천의 기억 생성 변동과 평가 반복을 구분하며, 유리한 기억만 골라 전체 작성 정책의 효과로 보고하지 않는다.

airline의 기존 규칙·절차 상기와 실제 과거에만 있는 정보의 가치를 구별한다. 23의 승객별 분할 예약이 정책으로도 유도 가능한 전략인지 확인하기 전에는 새 정보형으로 확정하지 않는다. 일반 주의 환기만으로 차이를 설명할 수 있는 비교도 포함한다.

자율 조회를 평가할 별도 과제 묶음은 이전 세션의 선호·약속을 현재 과제에서 재사용하는 변형으로 준비할 수 있다. 현재 사용자 입력·정책·DB에 같은 정보가 이미 노출되지 않는지 검사하고 공식 원본과 변형 채점을 구분한다. 무기억 에이전트의 정당한 추가 질문을 오답으로 강제하지 않는다. 필요한 정보의 조회·적용과 해로운/부적합 기억의 선택성을 각각 측정한다. AppWorld의 재사용 정보·도구 비용을 점검하는 준비도 병행 후보로 유지한다. 자율 저장 0·조회 0의 기존 관측은 삭제하거나 강제 제공 결과로 대체하지 않는다.

표본 계획은 1차 비교·분석 단위·효과 크기·기억/원천/과제 군집을 정한 뒤 계산한다. 추가 리뷰의 조건당 90~380회는 독립 집단의 대략적 가정이지 현재 쌍 설계의 확정 표본이 아니다. 기존 요청당 비용으로 작성·전체 에피소드 비용을 보장하지 않는다. 의미 판정은 조건을 가린 독립 사람 또는 별도 모델 검토를 일부 포함하는 안을 준비하고, 주석 일치도와 불일치 해결을 기록한다. 같은 분석 에이전트의 재독해를 독립 판정으로 세지 않는다.

탐색은 동결 과정을 자동화·축소하되 실제 입력 출처·사용량/비용·오류·배정·실행 설정은 항상 남긴다. 확인 비교의 1차 기준·배정·표본/중단·가림은 실행 전에 고정한다. 탐색이라는 이유로 API 한도나 과거 보존을 생략하지 않는다. 병렬 실행은 journal별 단일 writer 외에 native 전역 patch의 프로세스 격리와 전체 예산의 예약/관측 조정이 필요하다. 각 프로세스에 전체 예산을 중복 부여하지 않는다. 실제 병렬 모델 실행·새 예산은 아직 준비/승인된 실행이 아니다.

[120요청 결과](../reports/20261116-decision-replay-results.md)는 연구자 메모를 system에 추가한 진단이었다. 14의 수하물 인수 변화·17의 새 날짜 오류·21의 보류를 후속 후보로 사용하지만 개발 사례에서 고른 사실을 유지한다.

다음 세로 흐름은 **공개 경험 → 작업자 작성 → 불변 기억 버전/snapshot → 새 세션 → 실제 제공/조회 출처 → 업무 도구·사용자 승인 → 최종 결과**다. 분석 주석·채점 정답·실패 진단을 writer 입력으로 넘기지 않고, 피드백은 새 프로토콜에서 허용한 것만 제공한다. 기억 작성 0개도 결과로 보존한다.

첫 비교는 시작 제공을 고정해 내용의 활용 가능성을 본다. 무기억·일반 주의 환기·작업자 작성 기억의 비교와, 수하물이 없는/필요한 상황을 후보로 준비한다. 문맥 위치·역할이 달라 생기는 효과를 섞지 않도록 제공 경로를 맞추고, 시스템 지침으로 넣은 연구자 메모는 별도 진단 조건으로 표시한다. 이후 같은 기억을 자율 조회와 교차한다. 제목·반환·실제 입력 포함·업무 호출은 각각 기록한다.

전체 회차는 공식 초기 상태의 새 세션에서 끝까지 수행하는 흐름부터 준비한다. 기존 요청 스냅샷만으로 업무 DB·사용자 시뮬레이터 상태·대화·난수가 복원된다고 가정하지 않는다. 중간 상태 이어가기는 별도 capability와 복원 검증 뒤에 다룬다. Luna low·DeepSeek 1017과 전체 연구 범위는 유지한다. 새 과제 수·반복·표본 크기·금액을 여기서 실행 승인으로 확정하지 않는다.

[작업자 작성 기억 API와 mock 연결](worker-written-memory.md)을 구현했다. 같은 종료 경험에서 피드백 없음·결과만·비평을 분리하고, 새 writer 은행의 snapshot을 기존 native probe에 전달한다. 공통 요청 감사와 memory 계층의 라우터를 재사용한다. task 40의 합성 응답으로 업무 DB 변경·채점까지 검증했으며 실제 기억 효과는 아직 측정하지 않았다. [task 14 설계 초안](../../protocols/drafts/tau2-worker-written-memory-study-v1.json)은 실행 불가 자료다.

새 비교의 메모는 과거 기록이라는 system 안내와 user 역할 JSON items를 같은 위치에 둔다. 메모 속 ID를 현재 고객의 확인으로 세지 않도록 명시하고, native 대화의 첫 데이터 조회 전 ID 등장·질문을 별도 과정 판정으로 남긴다. 재전송과 에피소드의 새 renderer를 공유하며 과거 system 메모 결과와 합산하지 않는다. 7을 포함한 전이 후보는 과정 판정에만 쓰고 에피소드 주 비교의 제외 기준을 유지한다.

## 5. 저장 형식 변경과 정리는 뒤에 둔다

P0 뒤의 별도 수정 `319780a`에서 시각 `01:30:00+1`의 일수 오프셋, `usage: null`의 미확인 비용과 원응답 보존, 배정을 모두 소진한 정상 완료의 `stop_reason=null`을 반영했다. 실제 오류·미확인 비용 중단 사유는 유지하며 동결본과 기존 결과도 보존한다. 행동 검사·원천 시각 300개 점검·과거 세 실험 호환·고정 코드 재현의 근거는 [버그 수정 기록](runtime-edge-fixes.md)에 모았다.

인프라 재개는 예전 raw에 이어 쓰는 기능이 아니라, 부모 배정·오류 run·미시작 allocation ID·남은 예산/미확인 비용을 연결한 새 실행 묶음으로 준비한다. 오류 run을 성공할 때까지 대체하지 않고 미시작 배정만 사전에 정한 규칙으로 실행한다. 비용 미확인이 해소되지 않으면 가능한 청구액을 보수적으로 반영하거나 별도 승인된 예산이 있어야 하며, 자동으로 예산에서 제외하지 않는다. 사용자 시뮬레이터·DB 중간 상태의 완전 복원과는 별도 기능이다.

공통 audit 인덱스와 변경 없는 state 참조 재사용으로 얻는 효과를 먼저 측정한다. 요청 출처를 state에서 사건으로 옮기는 등의 변경이 실제로 필요하면 journal 차기 버전을 설계한다. **v1.3은 이 계획으로 확정하지 않는다.** 상태 참조·부분 상태·checkpoint/delta를 무엇으로 읽고 독립 감사할지 정하고, 스키마·fixture·문서·구버전 reader를 함께 제공한다. 과거 raw나 주석을 새 형식으로 덮어쓰지 않는다.

포매터·린터 설정, 낡은 `__init__`/README, 빠른 단위 테스트와 native 통합 테스트 구분, 날짜별 분석 스크립트 위치는 작은 후속 변경으로 정리한다. 포맷 일괄 적용은 동작 변경과 별도 commit에 둔다. 새 도구 버전은 도입 시 확인·고정하며 이번 계획에서는 패키지를 설치하지 않는다.
