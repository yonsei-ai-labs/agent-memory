# Writer의 blob 검증 재사용

2026-11-16 · 파일 형식·원본 보존 · 새 모델 호출 없음

`Journal`은 writer가 열린 동안 이미 해시 검증한 blob의 파일 정보와 하위 참조 목록을 재사용한다. 파일 전체 bytes나 파싱한 전체 state를 캐시에 보관하지 않는다. 별도 `BlobStore`·`read_experiment`·감사는 기본적으로 이 캐시를 사용하지 않는다.

매 append에서 참조 그래프를 다시 순회하고 경로·symlink와 각 파일의 device·inode·mode·크기·mtime_ns·ctime_ns를 확인한다. 정보가 같으면 그 파일의 재읽기·재파싱·재해시만 생략한다. 부모가 그대로여도 자식의 변경·삭제를 확인한다. 변경된 파일은 다시 해시하고, 검증에 실패한 새 항목은 성공한 캐시로 등록하지 않는다. writer를 닫으면 캐시를 비우고 새 writer는 전체 검증부터 시작한다.

같은 길이로 내용을 바꾸고 mtime을 되돌린 경우도 ctime으로 다시 검사한다. 파일 교체·삭제·하위 참조 변조·symlink·검증 실패 후 수리·로그 기록 실패 후 poisoned 상태와 재열기를 행동 테스트 8개로 확인했다. 이는 단일 writer와 신뢰하는 로컬 파일시스템에서의 최적화다. 파일 메타데이터를 위조하는 적대적 파일시스템이나 동시 외부 쓰기 전체를 방어하는 보장은 아니다. 독립 감사는 저장 bytes의 해시를 다시 검사한다.

5,002 commit인 무기억 원본의 **독립 사본 두 개**에서 상태를 바꾸지 않는 append를 각각 3번 측정했다. 재검증의 `BlobStore.get` 읽기는 27회·23,920,647 bytes에서 0회로 줄었고, 전체 append의 관측 중앙값은 약 389ms에서 271ms였다. 캐시를 끈 측정도 같은 현재 코드에서 독립 `BlobStore.verify`를 사용한다. 파일 캐시·순서·다른 로컬 작업을 통제한 통계적 벤치마크는 아니다.

0 bytes는 **반복 blob 검증의 읽기**만 뜻한다. state 직렬화·기존 blob 일치 확인·로그 재파싱·fsync는 남아 있다. 전체 append가 상수 시간이 됐거나 테스트 전체가 같은 비율로 빨라졌다는 뜻이 아니다. 최신 추가 리뷰에서 τ² DB 깊은 복사가 native 테스트의 큰 비용이라는 관측도 받았으며, 이 비율은 독립 재측정하지 않았다.
