# 실험 프레임워크 방향 논의 노트

2026-11-14 · 구성 스케치와 재검토 결과

**첫 구현은 SQLite 없이 JSON·JSONL 파일로 가볍게 시작하고, 과제별 세션·기억 접근·연구용 기록의 경계를 분리한다.** 사용자는 당장 DB 설치·도입까지 진행하는 것을 원하지 않으며 가벼운 시작을 우선한다. 큰 연구 방향을 유지하면서 파일 형식·모듈 분할·세부 실험 조건은 논의와 구현 근거에 맞춰 조정한다.

## 유지하는 연구 방향

- 같은 Luna 작업자의 가중치를 고정하고 저장·선택·조회 정책에 따른 후속 수행의 차이를 본다. 초기 연결 대상은 τ²-bench이며 AppWorld·BFCL 확장 목표를 유지한다.
- 저장 시점·형태·조회 방식, 같은 과제 재시도·새 과제 전이·누적 변화·저장과 조회의 교차·내용 개입·이득과 손해·전체 비용을 연구 범위에 둔다.
- 모델이 허용된 시점에 저장 여부·내용·개수와 조회 시점을 결정하게 한다. BM25·고정 2k 배분·자동 정리·적용 가능성 필터를 공통 기본값으로 추가하지 않는다.

## 현재 구성안

| 구성 | 맡을 일 |
| --- | --- |
| 실험 제어 | 계획·조건·과제·순서·반복을 배정하고 세션과 시작 기억을 준비 |
| 작업자 실행 | 현재 과제의 공개 정보와 허용된 지침으로 모델 요청을 구성하고 기억 도구를 처리 |
| 벤치 어댑터 | 원래 업무 행동·사용자 시뮬레이션·종료·공식 채점을 연결 |
| 기억 관리 | 항목·버전·은행·고정 스냅샷과 평가별 변경을 관리 |
| 기록과 분석 | 실제 요청·응답·도구·기억 노출·공식 결과·비용을 보존하고 별도 분석 |

첫 안에서는 실행기가 파일을 관리하고 모델은 `memory_store`·`memory_list`·`memory_get`으로 접근한다. 역할 분리가 각각의 별도 서버를 뜻하지는 않는다. 실제 전송 입력과 연구용 내부 자료를 구분할 수 있는 작은 모듈 구성을 우선 검토한다.

단일 프로세스·순차 쓰기부터 시작한다. 원본 버전 보존·평가별 격리·기억과 기록의 일치·중단 감지는 첫 흐름에서 챙기고, 복잡한 동시 쓰기와 전체 세션 자동 복구는 후속으로 둔다. 불명확한 중단은 배정·실패/결측 기록을 보존하고 새 run으로 시작한다. 구현 범위의 순서이며 누적·전이·비용 등 연구 범위를 줄이는 선택은 아니다.

첫 흐름은 경험 수집 → 기억 고정 → 평가별 복제 → 새 세션 평가 → 분석이다. 저장 정책별로 원천 과제의 기억을 작성하고, 자기 경험·혼합 풀 비교에는 그 정책에서 작성한 동일 버전을 사용한다. 합치는 과정에서 기억을 재작성하지 않는다. 평가 중 쓰기가 허용되면 해당 복제본만 갱신한다.

이 두 회차 흐름은 첫 절차다. 누적 실험에서는 과제 사이에 은행을 이어가고, 체크포인트 평가에서는 고정한 은행의 복제본을 사용한다. 실행기를 두 회차와 평가 후 변경 폐기에만 고정하지 않는다.

## 비교 질문을 구분하는 방법

| 비교 | 경험과 기억의 관계 | 결과의 해석 |
| --- | --- | --- |
| 자연 실행의 정책 비교 | 정책별로 실제 수행하며 경험과 기억을 생성 | 행동·경험 수집·저장·조회·비용을 포함한 전체 정책 효과 |
| 동일 경험의 저장 비교 | 같은 공개 경험에서 작성 방식별로 기억을 생성 | 주어진 경험에서 저장 표현·작성 방식이 만드는 차이 |

수행 중 저장·읽기는 1회차 행동과 수집 경험도 바꿀 수 있다. 따라서 자연 실행에서 나온 2회차 성적 차이를 저장 내용만의 효과로 해석하지 않는다. 동일 경험 비교의 수행 중 작성에는 해당 시점까지의 경험만 제공한다.

무기억 반복·원경험 접근·단순 요약 기준선을 유지한다. 무기억도 동일한 과제 배정과 재시도 기회를 갖도록 설계한다. 같은 은행에서 나온 여러 호출·기억·평가를 독립 저장 표본으로 세지 않고, 과제 출처·은행·순서·반복의 연결을 보존한다. 구체적인 표본 수와 예산은 아직 정하지 않는다.

## 선행연구를 활용하는 탐색 방향

**선행연구와 겹치는 부분도 우리 조건에서 재현하며 진행하고, 그 과정에서 추가로 설명할 차이를 찾는다.** 겹침 자체를 진행의 장애물로 삼지 않는다. 기존 결과와 우리 관측을 구분하고, 실증 결과에 맞춰 기여 주장을 구체화한다.

| 참고 연구 | 실험에 가져올 관점 |
| --- | --- |
| [BASM](https://arxiv.org/html/2608.22339v1) | 조건을 담은 기억, 조건 구간 attention 차단 개입과 길이·형식 대조 |
| [The Memory Trap](https://arxiv.org/html/2611.07554v1) | 기억 작성 단계의 범위 확대와 재사용 단계의 과잉 일반화 구분 |
| [When Continual Learning Moves to Memory](https://arxiv.org/html/2604.27003v1#A3) | 표현·조회 빈도·전이 비교. 은행 내용 차이와 평가 시 조회 효과가 함께 달라질 수 있음을 유의 |
| [MemUse — Delivered, Not Used](https://arxiv.org/html/2611.01718v1) | 실제 노출·기존 문맥·후속 행동의 연결. 기록 기반 관찰적 귀속과 재실행의 인과 효과 구분 |
| [The Compliance Trap](https://arxiv.org/html/2607.10608v1) | 최초 행동 변화·전파·회복, 해로운 영향과 도움 되는 영향이 함께 줄어드는지 확인 |
| [What Eviction Destroys](https://arxiv.org/html/2609.08279v1) | 정답 근거 복원과 재응답 진단. 원문 근거 라벨을 자율 생성 요약에 그대로 대응시키지 않음 |

우리 실험에서 우선 살펴볼 질문은 다음과 같다.

- 조건을 기억에 남겼어도 자율 조회에서 선택·노출되지 않으면 시작 시 제공과 효과가 달라지는가?
- 적용 조건을 강조하면 금지된 행동 시도를 줄이면서 변경 가능한 업무의 완료는 유지하는가?
- 원경험의 조건이 저장·선택·입력 포함 중 어디에서 빠졌는지에 따라 조건 복원 개입의 결과가 달라지는가?

용어는 주제·절차의 **관련성**, 현재 상태의 **적용 가능성**, 제공했을 때의 **실제 득실**로 구분한다. 단계별 기록은 설명의 근거이며 각 단계의 고유한 인과 기여율로 더하지 않는다.

첫 실증 후보는 같은 공개 경험의 일반 요약과 조건·절차 기억을 시작 시 제공해 비교한 뒤, 같은 버전에 자율 조회를 교차하는 흐름이다. 항공 과제쌍에서는 등급 외 조건과 채점의 정합성을 검증하고, 함수 이름뿐 아니라 직전 상태·인수·승인으로 행동을 판정한다. 금지 행동 감소와 허용 업무 완료를 함께 보고 다른 출처의 업무로 확인 범위를 넓힌다. 이 파일럿이 전체 연구를 대체하지는 않는다.

조건 복원은 원경험에 있던 조건만 최초 노출 전에 되살리는 연구자 개입으로 둔다. 길이·위치의 영향을 통제하고 현재 과제의 정답·숨은 상태를 보충하지 않는다. 처음에는 세션 시작의 최초 노출 전부터 비교해 중간 상태 전체 복구를 선행 조건으로 두지 않는다. 이 진단을 자율 정책 점수나 유일한 실패 원인의 증명으로 합치지 않는다. 표본·반복·예산은 별도 실행 계획에서 정한다.

## 세션과 기억의 정보 경계

새 세션은 현재 과제의 정상 초기 상태에서 시작한다. 과제가 기본으로 제공하는 초기 대화·정책·도구·관측은 유지하고, 이전 실험 회차의 대화·provider 연결·작업 상태가 추가로 넘어오는 경로를 차단한다. τ²는 `initial_state.message_history`를 초기 입력으로 사용할 수 있다. [확인한 초기화 코드](https://github.com/sierra-research/tau2-bench/blob/c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4/src/tau2/orchestrator/orchestrator.py#L500-L565)

모델 입력은 허용된 자료에서 구성한다. 개발 대화·이 논의 노트·저장소 지침·채점 정답·미래 관측·분석 라벨·다른 조건의 출력을 자동으로 붙이지 않는다. 조건명이나 정답 역할이 파일 이름·항목 ID·도구 설명·오류 문구를 통해 힌트가 되지 않는지도 확인한다. 내부 출처 정보는 연구용 기록에 보존한다.

목록 제목도 기억 노출이다. 제목·본문·가공본·이력 재전송에 대해 반환, 입력 포함, 전송 상태를 구분한다. 기억을 읽었다는 사실만으로 올바르게 활용했다고 판단하지 않는다. 입력 구성기가 삽입한 구간의 출처와 기록을 대조하며, 모델이 재서술한 문장의 의미적 출처·활용은 별도 분석으로 다룬다.

혼합 은행의 방해 후보와 모델이 작성한 오류는 평가 대상이다. 실험기가 임의로 수정·필터·요약·병합·잘라내기하지 않는다. 현재 과제의 정상 정보는 충분히 제공하면서 실행기가 덧붙이는 불필요한 힌트를 줄인다.

`same_episode_read=false`여도 모델이 쓴 저장 인수가 현재 대화에 남을 수 있다. 이를 몰래 지우거나 금지 조회로 집계하지 않는다. 자기 작성 내용은 v1.1에서 `self_authored` 출처로 표현하며, 구체적인 입력 구성과 기록의 대조는 런타임에서 검증한다.

## 기억 도구와 업무 진행

기억 도구 왕복은 작업자의 내부 흐름에서 처리하고, 업무 결정이 나왔을 때 벤치의 정상 전이로 전달하는 안을 검토한다. 기억을 여러 번 조회했다는 이유로 사용자 대화나 업무 단계를 자동 진행시키지 않는다. 모델 요청 수·기억 연산·업무 단계·사용자 턴과 전체 경과 시간은 구분해 기록한다.

τ²의 일반 실행 경로는 역할 간 메시지를 전달하고 단계 수를 증가시킨다. 기억 도구를 그대로 이 경로에 추가하면 원래 종료 한도와 실행 의미에 영향을 줄 수 있으므로 연결 시 검증한다. 한 응답에 기억·업무 호출이 섞인 경우의 순서와 호출/결과 대응도 보존한다. [확인한 실행 코드](https://github.com/sierra-research/tau2-bench/blob/c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4/src/tau2/orchestrator/orchestrator.py#L840-L949)

업무 종료 시 도달 상태와 채점 입력을 고정하고, 종료 후 기억 작성의 실패나 중단이 그 업무 결과를 바꾸지 않도록 한다. writer에는 허용된 경험과 피드백만 제공한다.

위 τ² 참조 commit은 소스 검토의 근거이며 실제 실험 버전의 확정값은 아니다.

## 리뷰에서 채택한 구현 기준

파일 연산별 확정 기록을 모든 사건의 단일 journal로 단순화했다. 요청 출처 manifest와 자기 작성 노출을 v1.1에 추가하고, 은행 revision은 공개 반환에서 제외한다. 혼합 호출은 결과 순서뿐 아니라 부작용 순서와 종료 batch의 사전 거절도 보존한다.

상세 결정과 근거는 [코어 계약](core-contracts.md)에 모았고, 스키마·draft·fixture는 v1.0을 보존한 별도 v1.1로 추가했다. 실제 기록자·입력 구성기·라우터 구현 전이며 단일 프로세스·순차 쓰기로 시작한다. 문서와 합성 검증의 통과를 런타임 완료로 해석하지 않는다.

실험 절차의 추가안은 [보정 실행과 비교 계획](../research/experiment-protocol.md#보정-실행과-비교-계획)에 정리했다. 빈 은행·지침 문구 반복·목록 순열·결과 피드백은 질문에 맞춰 선택하는 진단이며 첫 코어에 모두 강제하지 않는다.

## 먼저 확인할 동작과 남은 논점

작은 가짜 환경에서 정상 과제 초기화, 세션 분리, 기억 버전 보존, 평가 복제본 격리, 기억/업무 도구 분리와 실제 요청 기록을 연결한다. 허용 정보가 도달하는 경우와 비공개 정보가 차단되는 경우를 함께 검증한다. 이 검증을 실제 Luna·τ² 성능 결과로 보고하지 않는다.

| 남은 논점 | 논의할 내용 |
| --- | --- |
| 파일 구현의 검증 | journal 계약에 따른 실제 동기화·장애 주입·재읽기의 지원 범위 |
| 기억 표현과 접근 | 항목 단위·본문 형식, 모델 공개 도구, 제목·메타데이터·목록 순서·페이지 |

현재 v1.1은 과거 검사에서 빠졌던 의미 검증을 합성 자료에 추가한 상태다. 이전 점검 이력과 현재 한계는 [검증 범위](core-contracts.md#5-합성-검증의-범위와-남은-구현)에 있다. 실제 세션 초기화·wrapper 계측·벤치 행동은 구현 후 확인한다.

비교의 자세한 정의는 [실험 프로토콜](../research/experiment-protocol.md), 지표는 [측정과 분석](../research/metrics.md), 초기 구현안은 [첫 구현 작업](../development/first-implementation.md), 세션 재개 시 현재 상태는 [인수인계](../handoff/next-session.md)에서 확인한다.
