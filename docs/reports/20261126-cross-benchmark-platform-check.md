## 실험 조건

BFCL V4의 단일 질문 8개를 응답을 생성하기 전에 골랐다. 4개는 업무 함수를 호출해야 하고 4개는 호출을 삼가야 한다. 각 질문을 로컬 Qwen3.5-4B가 먼저 무기억으로 풀었다. 같은 모델이 같은 공개 질문·함수 명세·자신의 응답과 1회차 성패 한 비트를 보고 사실·경험·절차·교훈·자유 메모를 하나씩 썼다. 작성 시 저장 함수 이름만 지정했고 제목과 본문은 모델이 생성했다. 작성자에게 함수의 실제 반환값, 정답, 범주 이름을 제공하지 않았다. [사전등록](../../protocols/diagnostics/bfcl-relevance-two-pass-v1.json)

같은 형식의 두 후속 세션은 동일한 봉인 메모를 받았다. 하나는 시작 입력에 본문을 넣고 다른 하나는 목록과 본문 조회 도구를 제공했다. 1·2회차의 공개 질문과 업무 도구, 모델·생성 설정이 일치하는지 전송 전에 검사했다. 2회차 무기억은 0건이다. 첫 업무 판단이 끝나면 중단하며 업무 함수는 실행하지 않는다. 범주 점수는 BFCL의 호출 여부 규칙을 따른다. 설명의 사실성, 인수 전체의 의미, 업무 완료는 별개의 측정 대상이다. 독립 단위는 질문 8개이며 다섯 형식과 두 전달 방식은 같은 1회차를 공유한다.

## 자율 조회 0/40을 원문과 실제 도구로 검증한 결과

40개 세션 모두 각자 작성한 비어 있지 않은 메모 버전에 연결돼 있었고, 모델이 받은 실제 입력에는 목록·본문 도구가 모두 선언돼 있었다. 첫 요청에는 제목·본문·메모 ID가 없었다. 원래 안내는 이전 메모를 사용할 수 있으며 메모가 틀릴 수 있다는 두 문장이었다. 목록을 요청해야 제목과 ID가 보이고, 그 ID로 본문을 요청해야 다음 판단 입력에 본문이 들어간다. 업무 함수 호출이나 일반 답변이 먼저 나오면 이 단일 판단 실험은 끝난다.

원래 모델은 25회에 곧바로 업무 함수를 호출했고, 15회에는 텍스트로 답했다. 40회 모두 생성 토큰과 원문에서 기억 도구 이름조차 나오지 않았고 도구 거절·응답 잘림도 0건이었다. 메모가 열리기 전에는 같은 질문의 다섯 조건에서 렌더링된 입력이 바이트 단위로 같았고 생성 토큰까지 같았다. 따라서 35/40은 서로 다른 8개 첫 판단 중 7개 정답을 다섯 은행에서 관측한 수치다. 이 조건에서 메모 형식별 효과를 구할 수 없다. ## 목록을 본 뒤에는 스스로 본문을 여는가

같은 로컬 Qwen3.5-4B에 원래 질문 8개와 각 질문의 봉인된 사실 메모를 사용했다. 메모 안내에 ‘바로 이 질문을 이전에 풀고 남긴 메모 한 건이 있다’는 사실을 덧붙이는 경우와, 첫 호출만 목록 도구로 지정하는 경우를 교차했다. 목록 도구가 성공하면 모델은 제목과 ID를 본다. 다음 응답에서는 업무 함수를 호출하거나, 바로 답하거나, 그 ID로 본문을 요청할 수 있다. 아래 네 조건에서 본문 호출은 모두 자유 선택이었다. 첫 행은 인터페이스 보완 후의 기존 기록이며, 나머지 24개 판단은 실행 전에 등록했다. ## 원기록으로 검증하기

사전등록 구현은 `04bcd4f`, 실제 후속 판단을 수집한 구현은 `30c2d90`이다. 첫 시도는 로컬 GPU의 Python 헤더 누락으로 응답을 받기 전에 중단됐다. 일치하는 헤더를 별도 경로에 둔 뒤, 최초 디코더가 Qwen의 종료 표식을 함수 본문으로 읽는 결함을 발견했다. 이 단계의 23개 모델 응답과 미시작 배정을 보존했다. 디코더 수정 뒤에는 모델 버전·런타임·전체 요청이 같은 원응답을 각각 한 번만 재사용했다. 사용한 원응답의 프롬프트, 생성 토큰, 사용량, 원래 요청·응답 해시를 재대조한다. 수집한 데이터로 과제·메모 지침·배정·채점 규칙을 바꾼 항목은 없다.
