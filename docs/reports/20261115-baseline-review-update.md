# 추가 리뷰 반영: 실패 분류와 다음 진행 범위

2026-11-15 · 기존 진단의 해석 정정·구현 보완 · 새 유료 호출 0

**14번은 Luna의 절차 오류, 11번은 사용자 시뮬레이터 이탈로 정정한다.** 과제 정의 충돌은 7·39로 좁히고, 이후 에피소드 주 비교에서는 두 과제 전체를 제외하는 기준을 남긴다. 기존 [측정](20261115-tau2-baseline-screening-results.md)의 공식 44/55와 원본·오류·결측을 유지하며 새 주 분석 점수로 바꾸지 않는다.

## 실패 11회의 분류

| 분류 | 건수 | 과제·반복 |
| --- | --- | --- |
| Luna의 판단·절차·목표 확인 오류 | 8 | 17·1, 23·2, 14·2, 42·1, 42·2, 39·2, 21·1, 20·1 |
| 사용자 시뮬레이터 이탈 | 1 | 11·2 |
| 과제 정의와 실현된 정책 조건의 충돌 | 2 | 7·1, 39·1 |

이는 공개 행동의 주된 문제 위치를 정리한 개발 분류다. 예를 들어 20에는 Luna의 잘못된 날짜 판단 뒤 사용자 연도 변경이 이어졌고, 42·1의 잘못된 타인 예약 취소 제안은 실행 전에 정정됐다. 원인 하나가 모든 후속 현상을 독점적으로 설명한다고 가정하지 않는다. 단일 검토자의 최초 진단에 사용자가 전달한 검증 의견과 원천 정책·대화를 다시 대조했다. 의견 작성자가 모든 결정 요청을 독립 확인했다고 확대해 기록하지 않는다.

## 14·11 정정의 이유

**14·2:** 정책에는 “Do not add checked bags that the user does not need.”가 있다. Luna는 무료 허용량 6개를 제시했지만 실제 6개가 필요하다는 요청을 받지 않았고, 최종 예약 전 확인에도 6개를 명시하지 않았다. 사용자의 ‘no extra bags’라는 표현이 다의적일 수 있다는 점이 필요하지 않은 수량을 추가한 절차를 정당화하지 않는다. 원래 시나리오의 수하물 없음과 참조 0개도 정책과 일치한다. 14를 과제·채점 정합성 수정의 선행 목록에서 빼고 **필요 수량 확인·명시적 승인 절차 후보**로 옮긴다. 숨은 0개를 메모에 정답으로 넣지는 않는다.

**11·2:** 원래 결제수단은 gift card이며 Luna는 이를 정확히 안내했다. 사용자가 gift card를 거부하고 다른 카드·계좌·수표 예외를 요구한 것은 원래 시나리오에 없는 제약이었다. 이관을 명백한 Luna 실패나 채점 오류로 다루지 않는다. 원래 과제와 사용자 모델은 유지하고 반복에 따른 요동과 이탈을 함께 관찰한다. 반복하면 이탈이 반드시 상쇄된다고 가정하거나 성공할 때까지 해당 실행만 다시 돌리지 않는다.

## 7·39 처리와 병행 진행

7은 ‘other reservations’의 대상과 고정 합계 1,628이 맞지 않고, 39는 자리 양보라는 사유에 보험 취소를 요구한다. 이후 에피소드 주 분석에서는 **7·39 전체 과제**를 제외하는 개발 범위 결정을 남긴다. train 30개 중 후보 범위는 28개가 되며 11·14는 유지한다. 이전 55회에서 유리한 실행만 남기거나 이를 사전 등록된 제외였다고 보고하지 않는다.

39·2의 실제 잘못된 취소 판단은 별도 결정 지점 진단에 그대로 쓸 수 있다. ‘과제 전체의 고정 정답이 주 분석에 부적합하다’와 ‘그 안의 특정 행동에 관측 가능한 오류가 있다’는 서로 다른 판단이다. 공식 과제의 정답·시나리오·정책을 수정하는 작업은 이번 구현의 필수 선행 조건으로 두지 않는다.

## 추론 강도와 입력 길이 재확인

- worker 565개 응답에서 제공자 보고 reasoning tokens는 **0인 337개·양수인 228개**였다. 선택한 오류 8개 중 0은 4개다. 추론 토큰 필드 누락을 0으로 센 결과가 아니다.
- 선택 지점의 prompt tokens는 **3,440~9,841**이었다. 이번 기록에서 긴 문맥 또는 reasoning low가 오류의 원인이라고 단정할 근거는 없다. 토큰 수가 작다는 사실만으로 관측의 선택·적용 실패까지 배제하지 않는다.
- 503 요청은 Fireworks 한 경로·fallback 끔이었다. 장애 후보는 그 경로의 Fireworks 또는 OpenRouter 측으로 좁힐 수 있지만, 보존된 code 503·routing_reason provider만으로 둘 중 어디서 발생했는지는 특정하지 못한다.

## 이번에 구현한 다음 비교

[결정 지점 재전송 실행기](../development/decision-replay.md)는 저장된 요청 8개를 원본·medium·연구자 메모 세 조건으로 한 응답씩 비교할 수 있다. 업무 도구 호출은 실행하지 않는다. 원본 조건의 요청 동일성, 조건별 변경 범위, 출처 manifest, 요청/응답·사용량·비용·실패와 전체 중단을 기록하고 읽기 전용으로 재계산한다.

준비한 8×20×3=480요청은 제안이다. 비용·요청·시간 한도와 배정 seed가 미정인 draft라 유료 실행을 차단한다. 기존 예산을 새 실험에 자동 전용하지 않았다. 새로 반복한 원본 조건을 기준으로 비교하며 역사적 오류를 새 응답들의 기준 오류율로 쓰지 않는다.

현재 지점의 실제 출력 형태는 **도구 호출 3개·설명/계획 5개**다. 39·2·20·1도 현재 선택 위치는 텍스트이므로 8개 전부를 호출 인수로 자동 판정하지 않는다. 추가 조회·확인 질문·보류를 자동 성공과 분리하고, 세 호출 검사도 전체 업무 정답의 판정으로 확대하지 않는다.

현재 메모는 **결과를 본 연구자가 정리한 절차 메모**다. 작업자가 실패 피드백을 받아 작성한 기억은 별도로 준비하고 다른 조건으로 구분해야 한다. 여기에서 메모가 영향을 보여도 자율 생성 기억·조회·전체 에피소드 성공의 효과를 측정했다고 보고하지 않는다.

[준비 기록](../../artifacts/analyses/20261115-decision-replay-preparation.json)에 분류·이후 주 비교 범위·과거 토큰 관측·원본 스냅샷과 구현/프로필 참조를 연결한다. 정합성 결정을 짧게 기록하면서 이 진단과 후속 기억 비교를 병행하는 순서로 조정했다.

다른 세션이 작성한 [추가 검토 노트](../research/baseline-failure-review-note.md)는 일반 메모·원래 옳았던 상태·최초 제안 지점의 대조를 후속으로 제안한다. 현재 3조건·8지점은 그런 대조가 없는 개발 진단이라는 범위를 유지한다. 분할 예약은 이전 대화에서 관측한 재사용 절차이지만 현재 정책·도구로도 추론할 수 있으므로 과거에만 존재하는 정보라고 단정하지 않는다. 같은 seed의 응답 변동은 독립성의 보증이 아니다.
