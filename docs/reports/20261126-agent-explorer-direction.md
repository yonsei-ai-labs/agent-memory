# 궁극적 방향: 에이전트가 기억 방식을 스스로 탐구하는 프레임워크

2026-11-26 · 사용자가 밝힌 최종 방향을 정리한 노트 · 확인에 쓴 모델 호출 0건. 이 문서는 커밋·push·모델 호출·예산을 승인하지 않는다.

**이 프레임워크의 최종 사용자는 사람이 아니라 에이전트다. 에이전트가 벤치 과제를 바탕으로 기억을 남기는 방식과 꺼내는 방식을 스스로 바꿔 가며 더 나은 방식을 찾고, 사람은 그 탐구가 가능한 환경과 규칙을 제공한다. 지금의 1회차→2회차 실험과 다섯 형식은 그 환경에서 돌릴 수 있는 예시다.**

## 사용자 원문

> 1회차의 경험을 남기는건 어떻게 보면 지금은 예시지, 추후 그런 기억을 이 프래임워크를 llm이나 에이전트에게 연결해서 에이전트가 계속 특정 타스크 벤치들을 기반으로 좋은 메모리 저장방식과 조회 방식을 스스로 찾게끔하고 싶은거야. … 결국 이건 사람이 뭔가 작업을 하는게 아니라 에이전트가 탐구할 수 있는 프레임워크로 제공해줘서 개선하는 포인트를 찾도록 하는거야.

> 그래서 기억을 남기는 방식, 기억을 조회하는 방식은 이 프레임워크로 실험하는 에이전트가 자유롭게 개선하도록 하게 하고 싶은거지.

> 이게 궁극적으로 내가 하고자 하는 방향이야.

앞선 지시와 같은 방향이다. 11월 18일에는 플랫폼이 실행·진단을 맡고 이용자가 저장·조회 방식을 조정한다고 했다. 11월 23일에는 메모리를 개선해 성공률을 올리는 하네스를, 11월 25일에는 프레임워크가 주 목적임을 밝혔다. 달라진 점은 그 이용자가 사람이 아니라 에이전트라는 것이다.

## 무엇이 고정이고 무엇이 탐구 대상인가

| 구분 | 내용 |
| --- | --- |
| 프레임워크가 고정하고 보장 | 각 기준·후보 비교 안에서 과제와 시작 상태, 업무 입력·도구, 작업자와 환경, 공식 채점 기준을 고정한다. 고객 시뮬레이터가 있는 벤치는 그 설정도 고정한다. 배정한 기억 개입, 실제 입력, 성패·비용과 중단을 기록한다. |
| 탐구 에이전트가 자유롭게 바꿈 | 기억을 남기는 방식(무엇을, 어떤 형태로, 언제, 어떤 지침으로, 갱신과 삭제)과 꺼내는 방식(시작 제공, 도구 조회, 선택과 순서, 도구 설명) |
| 사람 | 탐구 환경과 규칙을 제공하고, 예산과 범위를 승인하고, 결과를 검토 |

## 지금 실험의 위치

- 현재 탐구는 이 저장소에서 일하는 에이전트가 맡는다. 지금은 여러 벤치에서 기억이 선택·노출된 근거와 실제 행동·성패·비용을 대조할 수 있게 하고, 개선 가설을 다음 비교에 남긴다. 별도 탐구 에이전트의 연결은 후속 작업이다. [현재 판독기와 세 벤치 사례](../development/trajectory-outcomes.md#한-판단에서-단서의-출처를-검산하기)
- 1회차 무기억 → 같은 LLM의 작성 → 2회차라는 구성, 다섯 형식, 시작 제공과 자율 조회는 사람이 고른 예시 정책이다. 탐구 에이전트가 출발점으로 쓸 기준 정책으로 남긴다.
- 이 예시를 돌리며 만든 격리 검증, 원기록 재생, 1회차 중단 규칙, 비용 원장은 탐구 환경의 바닥이 된다.
- 기존 [기억 정책 개선 하네스 설계](../development/memory-policy-improvement.md)는 이 방향의 첫 형태다. 개발·확인 집합 분리, 확인 전에 고정하는 채택 기준, 원문 인용과 반증 관측은 그대로 유지한다. 다만 그 설계의 제안은 지침 하나의 변경으로 한정된다. 제안 JSON은 외부에서 받고, LLM이 스스로 다음 라운드를 기동한 실측은 아직 없다고 같은 문서에 적혀 있다. 이 범위를 작성·조회 방식 전체로, 그리고 에이전트가 스스로 도는 반복으로 넓힌다.

## 탐구 에이전트의 한 바퀴

1. 기준 정책과 지난 결과를 읽고 가설을 세운다.
2. 새 작성·조회 방식을 선언한다.
3. 개발용 과제에서 예산 안에서 실행한다.
4. 성패 전환, 같은 성공의 효율, 기억 노출, 판단 변화, 반복 변동을 읽는다.
5. 다음 방식을 고르거나, 후보를 고정해 확인용 과제에서 평가한다.
6. 무엇을 왜 시도했고 무엇을 배웠는지 남긴다.

각 단계는 새 스크립트가 아니라 프레임워크 호출이어야 한다.

정책 선언에는 작성 지침·기억 구조·조회 시점과 사용할 선택 방법의 버전을 담는다. 등록된 선택 방법의 순서나 조건을 바꾸는 실험은 설정으로 표현할 수 있다. 기존 선택 방법으로 표현할 수 없는 검색 알고리즘은 같은 정책 인터페이스에 플러그인으로 등록하는 구조를 제안한다. 어느 경우에도 벤치별 실행·채점 코드를 다시 쓸 필요가 없어야 한다. 에이전트가 직접 작성한 플러그인의 실행 권한과 예산 단위는 열린 결정이다.

점수 쪽에는 세 가지가 더 필요하다. 반복 변동 범위가 점수와 함께 나와야 한다. 개발·확인 집합 분리를 실행기가 강제해야 한다. 기억이 과제의 답을 담아서 오른 것인지, 절차나 단서를 담아서 오른 것인지 판정해야 한다. 작성 방식이 자유로우면 탐구 에이전트는 잡음과 허점까지 최적화하기 때문이다.

**기존 경로를 다시 확인한 범위.** 보관된 항공 개발 과제 2개의 공개 기록, 부모 정책 해시와 원문 인용을 사용해 예산 미정인 작성 후보와 작성 4건·후속 상담 4건·2회차 무기억 0건의 배정을 재현했다. 제안은 미리 작성된 JSON이었다. 이 경로는 개발·확인 고객이 겹치면 거부하며, 제안 입력은 개발 사례로 한정한다. 다음 연결은 개발용 2회차의 노출·행동·결과·비용을 탐구 에이전트에 돌려주고, 그 근거로 다음 후보를 만들거나 탐구를 끝낸 이유를 남기는 것이다. [재현 명령과 현재 범위](../development/memory-policy-improvement.md#현재-실행할-수-있는-개발-단계) · [개발·확인 분할 검사](../../src/agent_memory_eval/experiments/prompt_comparison.py)

**정답과 일치한 기억의 판독.** 이전 고객이 직접 알려 준 주문번호를 기억해 맞는 주문을 조회한 경우에는 그 공개 발화, 저장한 번호, 판단 직전 입력과 실제 조회 인수를 연결한다. 현재 고객이나 업무 도구도 같은 번호를 이미 줬다면 두 출처를 모두 표시한다. 숨은 채점 정답이나 확인용 사례가 정책 지침에 들어간 경우는 오염으로 기록한다. 공개 근거가 여러 개면 내용 제거 등 같은 판단의 대조를 거친 범위에서 기여를 해석한다. [기억 문장과 득실을 연결하는 기준](../research/metrics.md#메모-문장과-득실을-연결하는-근거)

**여러 라운드의 확인 자료.** 지금 검증된 분리는 제안자에게 내보내는 개발 입력의 범위다. 탐구 에이전트를 연결할 때는 제안 도구가 개발 근거를 반환하고 확인용 고객의 개별 기록과 비공개 정답 요청은 거부하는지 시험한다. 확인 전에 정책 버전과 채택 기준을 고정하고, 확인 결과를 보고 후보를 바꿨다면 다음 확인에는 아직 쓰지 않은 집합을 쓴다. [정책 채택과 확인 집합](../development/memory-policy-improvement.md#정책을-채택하는-기준)

## 다음 순서 (추천)

0. 탐구 에이전트와 프레임워크의 역할을 연구 계획과 인수인계에 반영했다. [연구 계획](../research/plan.md#실험자와-플랫폼의-역할) · [인수인계](../handoff/next-session.md)
1. 저녁 변경을 작업 브랜치에 커밋한다([보완 점검](20261126-next-step-order-check.md)의 1번).
2. **최소 탐구 경로를 만든다.** 다섯 형식에 없는 작성 방식 하나와 새 조회 방식 하나를 선언하고, 같은 정책 버전을 은행과 BFCL의 모의 실행에서 재사용한다. 작성 방식을 비교할 때는 조회 조건을 고정하고, 조회 방식을 비교할 때는 해당 벤치에서 같은 기억 버전을 배정한다. 두 벤치의 결과에는 같은 형식으로 근거·비용·결측을 담고 공식 점수의 의미와 분모는 각각 표시한다. 새 실험 스크립트 없이 선언·실행·판독까지 연결하는 것이 이 단계의 완료 기준이다.
3. 점수의 신뢰 장치를 넣는다. 반복 변동, 벤치별 독립 단위에 맞춘 개발·확인 분할, 기억 내용이 나온 출처를 보고한다.
4. 예산과 중단을 공용 실행기로 옮긴다. 중단 규칙 필수화, 재시도, 입력 상한 처리가 여기에 들어간다(보완 점검의 2·5번).
5. 탐구 에이전트를 연결한다. 모의 실행에서 한 후보의 개발 결과를 다음 제안 입력으로 되돌리고, 새 후보 또는 보류 결정이 어느 관측에 근거했는지 확인한다. 실제 모델이 독립 확인 집합에서 정책을 개선하는지는 후속 실증으로 평가한다.

개발 결과를 다음 라운드에 넘기는 입력, 에이전트가 제출하는 근거와 정책 변경, 은행·BFCL에서 확인할 첫 완료 기준은 [탐구 에이전트가 두 번째 후보를 고르는 경로](../development/memory-policy-improvement.md#탐구-에이전트가-두-번째-후보를-고르는-경로)에 정리했다.

공용 탐구 경로의 모의 검증에는 기존 원장을 쓸 수 있다. 별도로 유료 확인을 설계할 때는 보완 점검의 과제별 표와 단서 정의로 개발·확인 집합을 정하고, 연구 질문에 맞는 중단 기준과 입력 상한·재시도·누적 지출 처리를 등록한다. 채점 가능한 1회차가 하나도 없는 경우도 중단 사유에서 구별할 필요가 있다. [20시 점검의 원장·중단 사유 재검산](20261126-next-step-order.md#20시-점검-노트-재검산)

## 하지 않을 것

- 다섯 형식과 시작 제공·자율 조회를 프레임워크의 고정 선택지로 만들지 않는다. 예시 정책으로 둔다.
- 사람이 고른 조건마다 새 실행 스크립트를 만드는 방식을 늘리지 않는다.
- 한 벤치의 점수를 목표로 삼지 않는다.
- BM25나 임의의 배분 같은 조회 방식을 기본값으로 넣지 않는다. 에이전트가 고를 수 있는 선택지로만 둔다.
- 격리 규칙, 채점, 예산을 탐구 에이전트가 바꿀 수 있게 하지 않는다.

## 사용자가 정할 것

1. '자유롭게'의 범위: 프롬프트·기억 구조·도구 설명까지인지, 에이전트가 조회 코드(검색·정렬)까지 직접 짜는지
2. 탐구 에이전트에게 맡길 예산 단위와 사람이 승인하는 시점
3. 최소 탐구 경로(2번)가 생길 때까지 새 유료 연구를 멈출지
