# 자율 기억 조회 0회와 실험 설계 점검

2026-11-14 · 기존 원본 재검사·오프라인 행동 검증 · 새 모델 호출 0

**기억 도구의 전송 누락이나 생성된 호출의 라우팅 유실은 발견하지 못했다. 최신 자율 조회 조건의 88개 worker 요청에 list/get이 모두 있었고 선택은 전부 `auto`였다. 원응답 자체에 기억 호출이 없었다. 다만 이 기록만으로 τ² 문맥·과제의 정보 필요·기억 내용·지침·모델 특성 중 무엇이 미조회를 일으켰는지는 분리할 수 없다.**

이번 결과는 [48회 결과](20261114-tau2-delivery-development-results.md)에 대한 기계적 재검사다. 연구 가설을 바꾼 새 모델 실험이나 기존 실패의 재시도가 아니다. [검사 코드](../../scripts/audit_tau2_memory_visibility.py)와 [전체 근거 JSON](../../artifacts/analyses/20261114-memory-tool-visibility.json)에 원본 로그·요청/응답 blob 해시와 run별 첫 요청을 연결했다.

## 실제 요청과 원응답에서 확인한 것

| 실행·조건 | 평가 run | worker 요청 | 두 기억 도구가 있는 요청 | 선택 방식 | 원응답의 기억 호출 |
| --- | --- | --- | --- | --- | --- |
| 최신 전달 비교 · 무기억 | 12 | 84 | 0 | auto, 업무 도구만 | 0 |
| 최신 전달 비교 · 빈 은행 | 12 | 90 | 90 | auto | 0 |
| 최신 전달 비교 · 자율 조회 | 12 | 88 | 88 | auto | 0 |
| 최신 전달 비교 · 본문 제공 | 12 | 83 | 83 | auto | 0 |
| 이전 자율 파일럿 · 고정 은행 | 3 | 16 | 16 | auto | 0 |
| 이전 guided 연결 · 새 회차 조회 | 1 | 6 | 6 | auto | list 1회·get 1회 |

네 원본 폴더의 요청 744개를 검사했다. 최신 48회의 기억 조건은 모두 업무 도구 14개 뒤에 `memory_list`·`memory_get`이 15·16번째로 추가됐다. 매 worker 요청에 다시 포함됐으며, `none`이나 업무 도구만의 강제 선택으로 막힌 경우도 없었다. 사용자 시뮬레이터에는 기억 도구를 제공하지 않았다.

최신 자율 조회 12회와 이전 고정 은행 3회는 시작 은행에 각각 기억 1개가 있었다. 이 15회의 104개 worker 요청에서 두 읽기 도구가 제공됐지만 기억 호출은 생성되지 않았다. 목록이 빈 은행이라서 조회가 실패한 상황과 구분된다. 본문 제공의 list/get 0회는 이미 본문을 받은 뒤의 추가 조회가 없었다는 관측이다.

guided 연결에서는 같은 모델 ID·OpenRouter 제공자 경로에서 저장 1회·list 1회·get 1회의 원응답과 반환이 모두 대응했다. 호출 ID·run·연산 종류·순서를 대조했고, 기록 누락·짝이 없는 반환은 없었다. guided는 명시적으로 읽도록 지시한 연결 검사여서 자율 조회율의 근거로 합치지 않는다.

이전 자율 작성 0개 사례도 writer 요청에 `memory_store` 스키마와 `auto`가 있었다. 작성 기회가 누락된 증거는 없지만 저장하지 않은 이유는 확인되지 않았다.

## 전송·파싱·벤치 라우팅 점검

- `Tau2MemoryBridge.invoke`가 native 업무 도구에 허용된 기억 스키마를 추가한다. native 변환 뒤 실제 전송 요청과 승인 입력의 일치를 검사한다.
- `OpenRouterClient.respond`는 승인한 요청의 canonical JSON을 HTTP body로 전송한다. 새 모의 전송 검사에서 기억 스키마·auto 선택·원응답의 memory call이 보존됨을 확인했다.
- 모델 원응답과 journal의 기억 반환을 직접 대응했다. 최신·이전 자율 파일럿은 원응답에 호출 자체가 없었고, guided의 세 기억 연산은 반환까지 연결됐다. 파싱 과정에서 생성된 기억 호출이 사라진 사례는 찾지 못했다.
- 현재 delivery native mock에서 on-demand list/get과 본문 입력 도달을 재검증했다. 다른 native mock은 잘못된 기억 조회도 업무 단계·오류 한도를 소모하지 않는지 확인했다. 둘 다 통과했다. 이는 설계된 가짜 응답의 라우팅 검사이며 새 Luna 행동 관측은 아니다.

고정 τ² checkout은 `c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4`이고 수정되지 않았다. agent 소스는 해당 공개 revision과 바이트도 일치했다. [native agent](https://github.com/sierra-research/tau2-bench/blob/c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4/src/tau2/agent/llm_agent.py)는 메시지와 도구를 모델에 전달한다. 기억 왕복은 우리 worker bridge가 내부에서 처리한다. 현재 경로에서 벤치가 기억 도구를 일괄 차단한다는 증거는 없다.

`auto`는 모델에게 호출 여부를 맡기는 설정이다. 도구를 제공했다는 사실만으로 사용을 기대할 수는 없다. [OpenRouter 공식 안내](https://openrouter.ai/docs/guides/features/tool-calling#tool-choice-configuration)

위 검사는 저장된 전송·응답 경계에 대한 것이다. 제공자 내부의 문맥 처리나 모델의 주관적 판단 이유를 직접 관측한 것은 아니다. 읽지 않은 이유를 모델에게 사후 질문한 답변으로 대체하지 않았다.

## 설계에서 중요한 한계와 가설

| 항목 | 확인된 사실 | 현재 해석 |
| --- | --- | --- |
| 정보의 추가 가치 | 은행은 현행 취소 조건과 이전 예약 사례를 담은 1개 기억. 현행 정책에도 일반 조건이 있음 | 현재 정보만으로 충분하다고 선택했을 가능성. 과거 기억이 항상 쓸모없다는 결론은 아님 |
| 조회 전의 진입 정보 | 제목·본문은 list/get 전에는 제공하지 않음. 빈 은행과 고정 은행의 지침·도구는 같음 | 기억 내용의 유용성을 알려주는 단서가 적음. 숨긴 은행의 유무가 조회 전 행동에 직접 영향을 주도록 설계한 것은 아님 |
| 지침 | 도움이 될 때 선택적으로 읽도록 하고, 현재 정책·현재 관측을 우선하도록 함 | 원하는 결과를 얻으려고 명시적 조회 지시로 바꾸면 정책 자체가 달라짐. 진단 조건으로 분리해야 함 |
| 내부 설정 JSON | system에 `same_episode_read:false`·`write_timing:none` 등이 공개됨 | 해석 혼동 가능성이 있는 인터페이스 요인. 효과는 미검증 |
| 도구 위치 | 기억 두 개가 16개 중 마지막에 있음 | 위치나 도구 수의 영향은 미검증. 발견한 버그로 간주하지 않음 |
| 채점 | 취소 과제는 DB 유지로 성공 가능하고, 요구한 상황 일부가 실제 대화에 제시되지 않음 | 기억의 적합성·설명 품질을 공식 점수 하나로 검증하기 어려움 |
| 일반화 | airline 과제 0·40·47·49와 한 고정 은행, 한 worker 모델 | τ² 전체 또는 다른 벤치·모델에서의 자율 조회 성향은 미확정 |

`same_episode_read:false`의 코드 의미는 **이번 run에서 새로 쓴 값 대신 시작 snapshot을 읽기**다. 과거 은행 읽기를 금지하는 플래그가 아니다. 이번 on-demand 은행에는 시작 항목이 1개 있었고 `read_mode=on_demand`도 제공됐다. 이 플래그의 실제 권한 문제와 모델에게 보여주는 문구의 모호함을 구분한다.

최신 12개 블록 중 7개는 빈 은행과 on-demand의 첫 worker 전송 요청 해시도 같았다. 해당 블록은 1·4·5·7·9·10·11이다. 이는 조회 전 입력을 맞춘 대조의 성질이다. 미노출 은행 내용으로 그 시점의 행동 차이를 설명하지 않는다. 요청·응답의 후속 분기는 별도로 남긴다.

과제 40은 허용된 승객 수정을 유지하는지 보는 대조로 적절하다. 취소 기억이 이 과제의 성과를 높여야 한다고 가정하지 않는다. 필요한 정보가 이미 있었는데 사용하지 못한 두 실패도 유효한 업무 관측이며, 그 자체가 실험 실행 오류를 뜻하지 않는다.

## 무엇을 분리해서 더 확인할까

아래는 후속 진단 제안이다. 아직 실행하지 않았으며 유료 호출 수·반복·예산을 확정한 프로토콜이 아니다.

| 진단 | 고정하거나 바꿀 것 | 답할 수 있는 범위 |
| --- | --- | --- |
| 짧은 문맥에서 조회의 추가 가치 확인 | 같은 모델·16개 도구·같은 은행. 현재 입력에는 없고 기억에서만 확인할 수 있는 검증 가능한 사실을 둠 | 자율 조회가 가능한 최소 조건. 합성 긍정 대조이며 실제 업무 전이 성능은 아님 |
| 같은 과제에 τ² 정책 문맥 추가 | 위 사실·도구·질문을 유지하고 system 정책 문맥만 바꿈 | 정책 문맥의 영향. native 벤치 전체 효과와 구분 |
| 허용 여부를 명료하게 설명 | 같은 권한과 auto를 유지하고 내부 JSON 대신 읽기 가능·쓰기 불가를 사람이 읽는 문장으로 제시 | 인터페이스·지침 표현의 영향 |
| guided 긍정 대조 | 같은 조건에서만 명시적으로 조회를 지시해 호출/반환 확인 | 도구 사용 가능성. 자율 조회 결과로 합치지 않음 |

실제 업무 평가에서는 현재 문맥과 경험의 정보 차이, 기억이 적용 가능한 경우와 보류해야 하는 경우, 실제 상황 제시·필요 변경·금지 시도·설명을 함께 검증한다. 제목을 먼저 제공하면 이미 노출 조건이 달라지므로 새 조건으로 기록한다. 원래 0회 결과·프로토콜은 보존하고 조회할 때까지 지침을 바꿔 반복하지 않는다.

자율 저장 전체 정책은 저장 0개도 후속 빈 은행 실행으로 이어지는 절차가 필요하다. 기존 source-empty 생략은 고정 은행 진단의 기록으로 유지한다. 앞선 48회가 자율 작성 전체 정책을 평가했다고 해석하지 않는다.
