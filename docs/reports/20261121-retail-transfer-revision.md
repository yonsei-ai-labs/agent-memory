## 같은 경험에서 무엇이 달라졌나

## 후속 상담에서 무엇을 비교하는가

과거 상담과 같은 고객·주문을 다루는 24개 과제에 22개 원천이 32쌍으로 연결된다. 각 쌍에서 두 지침으로 쓴 네 형식의 메모를 새 상담 시작 때 제공한다. 빈 메모 조건에는 같은 메모 취급·본인확인 안내와 빈 목록을 준다. 무노트 조건은 새 세션·초기 주문 DB에서 메모 안내와 목록 없이 고객을 상대한다. 과제·반복마다 대조 상담을 한 번씩 실행해 같은 과제·반복의 메모 조건들이 공유한다.

목표마다 두 번의 반복에서 기존 본인확인 안내와 소매 정책을 따르도록 고친 안내를 번갈아 쓴다. 각 안내를 먼저 받는 과제는 12개씩이다. 두 반복의 고객 발화는 독립적으로 생성한다. 주 비교는 보완 작성·보완 안내를 함께 쓴 메모와 같은 과제·반복의 무노트다. 두 작성 지침끼리는 같은 안내에서, 두 안내끼리는 같은 작성본에서 비교한다. 24개 목표는 이전 실험에서 이미 관측했다. [사전 배정과 분석 계획](../../protocols/pilots/tau2-retail-transfer-revision-v1.json)

## 공급자 요청량 제한과 전송 간격

첫 상담 묶음에서 고객 시뮬레이터가 HTTP 429를 반복 반환했다. 11월 21일 11시 35분 51초(KST)부터 새 상담 접수를 15분간 늦췄고, 재개 후 한 건만 수행해도 그 상담의 아홉 번째 고객 요청에서 429가 돌아왔다. 당시 실행 중이던 여섯 과제 묶음은 원래 실행기가 끝까지 기록한다.

후속 묶음에는 같은 고객 시뮬레이터로 향하는 요청에 공통 전송 간격을 둔다. 최초 간격은 4초다. 429를 받으면 해당 공급자가 안내한 대기 시간을 지키고 간격을 최대 10초까지 두 배로 늘린다. 정상 응답 64건이 연속되면 간격을 4분의 3으로 줄이며 최소 간격은 1.5초다. 동시에 진행하는 과제는 최대 세 개다. 이 규칙에는 상담 점수나 실험 조건이 들어가지 않는다. 기존 묶음의 원본·비용, 원천과 메모, 과제별 배정 순서, 열리는 세션, 모델 요청 본문, 미채점 처리와 총 $3.50 한도를 유지한다. [전송 간격과 재개 검증 코드](../../scripts/pace_retail_transfer_revision.py)

이 여섯 과제의 첫 반복 84개 배정에서 20개가 채점됐고 51개는 고객 시뮬레이터의 429로 끝났다. 두 과제에서 각각 열 번째 미확정 요청이 발생해 과제별 예산을 전액 보류했고 13개는 시작 전에 멈췄다. 작성까지 공급자가 보고한 비용은 $0.295904077, 등록된 보류액은 $1.151444107이었다. 다음 묶음의 사용 가능액은 $2.052651816이다. 이 시점의 보충 계획에서는 원래 배정 중 요청 전송·세션 생성 이력이 없는 위치만 별도 장부에서 시도하고, 과제 예산 전체를 계속 보류하기로 했다. [미시작 배정의 실행·합산 규칙](../../protocols/pilots/tau2-retail-transfer-revision-pending-v1.json)


첫 반복의 18개 과제 묶음이 닫혔을 때 공급자 확인 비용은 $0.850017352였고, 당시 규칙은 $1.178493907을 보류했다. 미확정 62개 모두 고객 시뮬레이터의 429 응답이었다. 요청 원문·출력 상한·고정 단가에서 각 요청의 최대액을 재계산한 합계는 $0.1484328이었다. 사용자는 **총한도 $3.50을 유지하면서 보충 실행에는 요청별 검증 최대액을 보류**하도록 승인했다. 최초 실행의 비용 장부를 보존하고, 별도 보충 장부에서 원래 과제 단위 보류액과 요청마다 검증한 금액을 대조한다. 개별 최대액을 확인할 수 없는 전송은 과제 단위 보류를 유지한다.
