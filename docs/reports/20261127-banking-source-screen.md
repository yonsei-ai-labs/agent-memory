# 은행에서 기억을 쓸 판단을 고르는 1회차 실험

2026-11-27 · 개발 과제 46개, 독립 세션으로 과제당 3회 · 무기억 1회차 138건 사전 배정

이 실험의 질문은 **같은 과제를 재시도할 때 과거 경험에서 가져올 단서가 있고, 실제 상담에서는 성공과 실패가 모두 발생하는가**이다. 결과를 보기 전에 과제와 선별 기준을 고정했다. [등록 규칙](../../protocols/pilots/tau-banking-source-screen-v1.json) · [고객 분할과 배정 해시](../../artifacts/pilots/20261127-banking-source-screen-preflight.json)

개발 과제 14개는 기본 DB의 고객 4명과 연결된다. 과제 적용 후 DB의 사용자와 본인 확인 대상을 연결하면 24개 과제에서 고객 23명을 추가로 확인할 수 있다. 080·081은 같은 고객이다. 남은 8개는 신원이 미확정이다. 후보 수와 식별한 고유 고객 수를 각각 집계한다. [이전 과제 분모 검산](20261127-banking-task-room.md)

1. 세 번 모두 새 세션에서 원래 과제를 시작한다. 작업자와 고객 모델, 시드, 도구, 초기화 및 채점 설정은 같은 과제의 반복 사이에 고정된다. 29개 과제의 DB 패치는 별도 환경에 먼저 적용하고, 실제 환경의 작업자·고객 DB 해시를 첫 모델 요청 전에 검증한다. 고객의 첫 발화는 각 1회차에서 새로 생성되며 원문을 보관한다.
2. 세 건 모두 공식 성적이 있고 성공과 실패가 섞인 과제에서, 한 번이라도 원래 과제가 지정한 문서 ID가 상담원의 공개 검색 반환으로 들어왔는지 확인한다. 그 ID는 해당 회차의 상담원 첫 요청 전체에서 부재해야 한다. 확인한 상담 원장, 공개 경험, 첫 요청, 도구 반환을 해시로 연결한다. 이는 후속 판단에 제공할 수 있는 검색 단서다. 문서의 내용 이해와 기억의 인과 효과는 후속 비교에서 측정한다.
3. 세 번 모두 성공, 세 번 모두 실패, 미채점을 별도로 센다. 과거 계좌 개설에서 원천 19건 중 7건이 160,000바이트 입력 제한에 걸려 이번에는 320,000바이트로 등록했다. 모든 1회차에 같은 제한을 적용한다. 해당 원천을 쓰는 후속 실험도 같은 설정을 재현해야 한다. [기존 입력 제한과 결측](20261126-banking-opening-model-results.md)

## 재현 명령

사전 점검은 고정된 은행 체크아웃을 사용한다. 결과 판독은 해당 실행의 원장과 공식 결과를 읽는다.

```bash
uv run --offline python -m scripts.run_banking_memory preflight --series source-screen
uv run --offline python -m scripts.run_banking_memory results --series source-screen
```
