# 과거 재현 분리와 추가 리뷰 반영

2026-11-16 · P0 실제 검증·첫 성능 개선 · 새 모델 호출 없음

**과거 세 실험의 결과 검토와 원인 진단, 네 명령을 각자의 고정 코드 환경에서 재현했다. 이어 최신 코드의 schema validator 재생성을 줄여 동일한 120요청 감사 시간이 49.8초에서 5.87초로 감소했고 감사 결과 해시는 같았다.**

## 과거 재현을 현재 코드에서 분리

[P0 실행기](../development/historical-reproduction.md)는 [registry](../../protocols/reproductions/historical-v1.json)의 분석 commit으로 detached worktree를 만들고, 잠금 파일 기반 전용 환경과 독립 입력 사본을 준비한다. API 역할 키를 제거하고 Python audit hook으로 네트워크·입력 쓰기를 차단한다. 원본·복사 입력·코드를 전후 대조하고 임시 사본은 기본 정리한다.

| 재현 대상 | 분석 코드 | 결과 | 관측한 전체 소요 시간 |
| --- | --- | --- | --- |
| 48회 전달 비교 | `65a757f` | 통과 | 약 173초 |
| 55회 채점 무기억 기준선 | `7243fef` | 통과 | 약 191초 |
| 결정 지점 120요청 | `c51165b` | 통과 | 약 29초 |
| 실패 11회 원인 진단·로컬 재생 | `c31a9d6` | 통과 | 별도 receipt 참조 |

시간은 환경·입력 준비·검증·정리를 포함한 각 실행의 관측치다. 앞의 세 작업은 일부 시간이 겹쳐 독립 성능 비교에 사용하지 않는다. [검증 자료](../../artifacts/analyses/20261116-historical-reproduction-results.json)에 실행 구현/분석 commit·입력 manifest·환경·출력 해시·원본 보존·정리 결과를 연결했다.

네 작업 모두 금지된 네트워크·프로세스·입력 쓰기 시도가 0이었다. 원인 진단은 등록한 native clone의 정확한 Git 신원/상태 읽기만 허용했고, 자체 로컬 도구·DB 재생은 사본에서 수행했다. 과거 원인 분류를 재현한 것이며 이후 11·14 재분류를 되돌리지 않는다. 의미 주석을 독립 재판정하거나 새 모델 성능을 측정한 작업은 아니다.

진단의 첫 준비 시도에서는 partial native clone의 과거 객체가 없어 실패했다. 원본을 유지하고 작업 사본을 정리했으며, 검증한 HEAD만 로컬 shallow clone으로 준비하도록 수정한 뒤 새 출력 폴더에서 통과했다. 실패 receipt도 검증 자료에 보존했다. 과거 모델 오류 run을 재시도한 것은 아니다.

## 첫 병목 개선: schema 컴파일 재사용

추가 리뷰가 지적한 매 요청 schema 재컴파일을 실제 코드와 프로파일로 확인했다. `validators()`는 계약 자원 경로별로 컴파일 결과를 재사용하고, 호출자에게 별도 mapping을 반환한다. 한 호출에서 mapping을 바꿔도 다른 호출에 전파되지 않는다. 다른 schema root는 다른 캐시를 사용한다. schema 자원과 validator는 프로세스 안에서 불변으로 취급하며 schema를 고치면 새 프로세스를 사용한다.

| 같은 120요청의 저장 결과 감사 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 전체 시간 | 49.80초 | 5.87초 |
| `validators()` 누적 시간 | 44.45초 | 0.39초 |
| `validators()` 호출 수 | 121 | 121 |
| 정상 응답·보고 비용 | 120·$0.043359345 | 동일 |
| 감사 결과 SHA-256 | `923bf64219ff2e5eca5d8f9d685d696ab394c0461689ad5944b28375ea15ebd1` | 동일 |

프로파일링을 켠 새 프로세스를 버전별로 한 번씩 실행한 관측이며 약 8.5배·시간 약 88% 감소다. 장비·파일 캐시·다른 작업의 영향을 완전히 통제한 통계적 성능 주장은 아니다. [측정 자료와 실행 코드](../../artifacts/analyses/20261116-schema-validation-performance.json)를 남겼다. 원본 로그 해시와 과거 비용·판정은 유지했다. journal 재파싱·writer의 blob 재검증은 아직 별도 개선 대상이다.

## 추가 리뷰에서 확인한 문제와 후속 순서

- `usage: null`에서 `SpendGuard.after`가 `AttributeError`를 내고 미확인 비용을 표시하지 않는 현상을 재현했다. `+1` 일수 표기의 시각이 파싱 불가로 되는 것도 재현했으며 원천 항공편 300개 중 36개가 해당 형식이다. 정상 완료 때 남는 `call_limit`도 별도 수정 대상이다. **이번 성능 변경으로 이 세 버그를 고쳤다고 보고하지 않는다.**
- 현재 정책 측 요청 수는 사용자 시뮬레이터까지 합산하고, 한도 종료는 미채점으로 남는다. 다음 기억 비교에서 역할별 한도·도달 상태의 채점 가능성·결측 처리를 설계와 맞춰야 한다. 세 원본의 runtime 오류를 대조했을 때 한도 오류는 없었고 baseline HTTP 503 한 건만 있었다.
- 64,000 bytes는 현 전송 코드의 운영 한도다. 새 은행의 크기·실제 입력 사전 점검·대화 중 초과·배정 전체의 집계 기준을 다음 프로토콜에 정한다. 수치를 임의로 높이거나 기억을 조용히 절단하지 않는다.
- 인프라 재개는 오류 run을 유지하고 미시작 배정·남은 예산·미확인 비용을 연결하는 새 실행 묶음으로 준비한다. 과거 raw에 이어 쓰거나 유리한 결과를 얻을 때까지 대체하지 않는다.

연구 쪽 첫 주장 후보는 **작성 시 피드백이 오류의 기억·교정·재적용에 미치는 영향**이다. 피드백 없음·결과만·짧은 비평, 일반 메모 대조, 원래 옳았던 상태와 적용 조건을 분리한다. 23의 분할 예약은 정책에서도 유도 가능한지 확인하기 전에는 과거에만 있는 정보형으로 확정하지 않는다. 과거 선호/약속이 필요한 자율 조회 과제·독립 의미 판정·군집을 반영한 표본 계획을 병행 준비한다.

탐색 절차는 자동화하되 입력 출처·배정·비용·오류를 유지한다. 병렬 실행은 journal 분리뿐 아니라 native 전역 patch의 프로세스 격리와 전체 예산의 예약/관측 조정이 필요하다. 이 보고서로 새 유료 프로토콜·표본 수·예산·병렬 모델 실행을 확정하지 않는다. [개선 계획](../development/experiment-layer-improvement-plan.md)에 세부 책임과 완료 기준을 모았다.

## 검증 범위

P0의 실제 작은 Git worktree·격리 Python 행동 테스트 18개와 schema 캐시 테스트 3개가 각각 통과했고, 이어 **전체 172개가 373.041초에 통과**했다. native 통합을 포함한 mock HTTP 테스트이며 실제 모델 호출은 없다. 기본 설계·저장소·보관본 검사 3개와 diff 공백 검사도 통과했다. 기존 전체 151개 통과는 추가 리뷰가 제공한 이전 이력과 구분한다. 현재 코드 변경 뒤 고정 코드 재현은 별도 최종 확인으로 남긴다. 과거 동결 기록·v1.1/v1.2 wire 형식·원본 실행은 보존한다.
