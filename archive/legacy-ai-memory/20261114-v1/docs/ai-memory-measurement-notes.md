# 메모리의 득실을 무엇으로 측정할 것인가

2026-11-04 · 야간 실험에서 드러난 측정 문제를 정리한 작업 노트

현재 실험의 효과는 **정해진 과제·모델·기억·제공 정책에서 관측한 성과와 비용의 차이**다. 메모리 일반의 효능, 모든 사실과 모든 행동 안내의 우열, 개별 실행의 확정된 인과 원인으로 확대하지 않는다. 원본과 회차별 계획은 [야간 실험 보고서](reports/2026-11-04-overnight-research.md)에 있다.

## 2026-11-05 연구 초점: 기억의 어느 부분이 얼마만큼 기여하는가

사용자가 확인하고 싶은 것은 기억 전체의 평균 성능뿐 아니라, **기억 안의 어떤 내용·성질이 어느 조건에서 이득 또는 손해를 만들고 그 크기가 얼마인지**다. 현재 방향은 제공 방식의 우열보다 구성요소의 기여를 먼저 측정하는 것이다. 아래는 새 설계이며 야간 결과에서 이 기여를 이미 측정했다는 뜻이 아니다.

이후 한 카드·한 과제에서 다섯 조건을 두 번씩 실행한 [기능 검증](reports/2026-11-05-component-measurement-feasibility.md)을 완료했다. 실제 입력의 부분별 개입과 성과·비용 대비 계산은 확인했지만, 모두 2/2 성공했고 표본이 작아 유익·유해 방향은 판정하지 못했다. 아래 가상 수치와 새로 얻은 실측 결과를 구분한다.

추가 연구 축으로 [동일 본문의 사용 안내 비교](ai-memory-content-and-framing.md)를 둔다. `p(지침형)−p(정보형)`은 본문을 유지하고 사용 안내를 바꾼 기여이며, 본문에서 절차 구간을 삭제한 기여와 다르다. 내용 유형·권고 강도·체크리스트 배치·적용 조건의 명시 여부를 구분하고, 지침에만 새 사실이나 조건을 추가하지 않는다. 현재 예시는 검토용이며 새 효과를 관측한 결과가 아니다.

### 비교 단위와 효과의 정의

기억의 득실은 대상 문제·수신 모델·예산·다른 기억과의 조합에 조건부다. 처음에는 모델·환경·전달 위치·시점을 고정하고, 대상 문제와 출처 카드의 쌍을 비교 단위로 둔다. 같은 카드가 여러 대상에 쓰이면 그 의존성을 보존하며 독립 카드로 세지 않는다.

고정된 대상 `i`에 구성요소 집합 `S`를 제공했을 때 예산 내 공식 해결물을 제출할 확률을 `p_i(S)`, 배정된 전체 실행의 평균 비용을 `c_i(S)`로 둔다. 같은 문제의 독립 실행을 반복해 이를 추정한다. 다른 사람의 사후 평가로 유익/유해를 정답 라벨링하는 것이 아니다.

```text
전체 기억 M의 순효과 = p_i(M) − p_i(∅)

전체 기억 안에서 부분 j의 기여 = p_i(M) − p_i(M \ {j})
같은 부분의 추가 비용 = c_i(M) − c_i(M \ {j})
```

성과 기여가 음수이면 그 조합에서 그 부분을 넣는 것이 평균 성과를 낮춘다는 뜻이다. 기억 전체가 무메모리보다 나쁘다는 뜻도, 그 부분이 모든 과제에서 나쁘다는 뜻도 아니다. 비용의 양수는 비용 증가를 뜻한다. 이 정의에서 미제출은 예산 내 전달 실패로 세되 원래 공식 채점 필드의 빈 값은 유지한다.

### 두 부분을 나누는 최소 비교

처음부터 많은 문장을 모두 조합하지 않고, 출처가 있는 사실 묶음 `F`와 과거 경험에서 나온 행동 지침 묶음 `P`부터 정의할 수 있다. 이는 운영상 분류이며 모든 지침도 정보를 포함하므로 순수한 정보와 순수한 행동의 분리라고 부르지 않는다. 각 부분이 단독으로도 이해 가능해야 한다. P가 F를 가리키는 생략 표현뿐이라면 억지로 P 단독 조건을 만들지 말고, 사실을 공통으로 둔 지침 추가 비교부터 한다.

다음 숫자는 **설계 설명을 위한 가상의 성공 확률이며 실제 실행 결과가 아니다.**

| 제공 내용 | 가상 성공 확률 |
| --- | ---: |
| 없음 | 40% |
| 사실 F | 60% |
| 지침 P | 35% |
| 사실 F + 지침 P | 50% |

이 예시에서 전체 기억은 +10%p다. 사실만 추가하면 +20%p지만, 사실이 있는 상태에 지침을 추가하면 −10%p다. 따라서 전체가 유익해도 일부 내용이 그 이득을 깎을 수 있다. 반대로 지침이 있는 상태에서 사실을 추가하는 효과는 +15%p다. 같은 부분의 기여는 다른 부분의 존재에 따라 달라진다.

두 부분의 조합 효과를 다음처럼 별도로 남긴다.

```text
I = p_i(F+P) − p_i(F) − p_i(P) + p_i(∅)
```

위 예시의 I는 −5%p다. 이는 이진 성과의 확률 차이 척도에서 정의한 상호작용이며, 실패 사건이 정확히 5% 늘었다는 개별 반사실 판정이 아니다. 전체 기억에서 각 부분을 한 번씩 삭제해 얻은 기여는 단순히 더해 전체 효과와 같다고 가정할 수 없다. 요소의 유무를 교차해 비교하는 설계 원리는 [NIST의 요인 실험 안내](https://www.itl.nist.gov/div898/handbook/pri/section3/pri3331.htm)를 참고하며, 여기서 이를 기억 입력의 개입으로 적용하는 것은 우리의 설계 제안이다.

하나의 합계로 반드시 배분해야 한다면 여러 조합에서의 추가 기여를 평균내는 Shapley 계열의 규칙도 검토할 수 있다. 그러나 선택한 기여 배분 규칙이 유일한 물리적 원인을 찾아 주는 것은 아니고, 조합 수·분산·계산 비용이 늘어난다. 처음에는 위의 조건부 기여와 상호작용을 직접 제시한다. 특성 간 상호작용을 별도로 다루는 방법론은 [The Shapley Taylor Interaction Index](https://proceedings.mlr.press/v119/sundararajan20a.html)에 있다. 그 논문의 모델 특성 기여를 우리 에이전트 메모리의 검증된 방법으로 동일시하지 않는다.

### '어떤 부분'에서 '어떤 성질'로 확장하기

구성요소는 사실, 절차, 적용 조건, 실패 경고처럼 출처 근거에 따라 나눌 수 있다. 성질은 현재 버전과의 일치, 조건의 명시 여부, 근거 대비 단정 강도, 중복·분량 등이다. 구성요소 전체의 기여와 특정 성질의 효과는 다른 비교다. 예를 들어 P 전체 삭제가 좋아졌다는 사실만으로 그 원인이 '단정적인 어조'였다고 판정하지 않는다. 그 어조만 바꾼 새 비교가 필요하다.

데이터 제작은 새로운 벤치 문제 작성보다 실제 출처 궤적의 근거 있는 문장 구분과 제한된 편집에 집중한다. 분할·편집 규칙과 적용성 판단은 대상 결과를 보기 전에 정한다. 대상의 숨겨진 정답으로 카드를 교정하지 않는다. 자동 분할은 후보를 만드는 데 쓰고 출처 충실성·의미 보존·잘못된 참조는 표본 검토한다. 자연 발생 기억의 편집과 일부러 틀린 정보를 넣은 진단 자료는 따로 표시하며, 진단 결과의 비율을 자연 기억의 피해 발생률로 쓰지 않는다.

삭제하면 길이·문맥 구조도 달라진다. 처음에는 그 삭제 정책 전체의 효과를 보고한다. 내용의 의미나 지시 강도만 원인이라고 주장할 경우, 비슷한 길이의 다른 문구·일반 조언·비교 가능한 편집을 추가해 대안 설명을 검사한다. 어떤 문장도 완전히 무효한 중립 대조라고 가정하지 않는다. 지침이 새 사실까지 추가한다면 그 사실을 비교 조건에도 맞추거나, 주장 범위를 '그 지침 묶음의 추가 효과'로 제한한다.

### 수치로 보고할 산출물

| 측정 대상 | 보고할 숫자 | 해석 |
| --- | --- | --- |
| 과제 성과 | 부분 추가 전후의 예산 내 해결률 차이, %p | 조합·대상 분포에 조건부인 평균 기여 |
| 회귀 | 공식 유지 테스트에서 새 회귀가 생긴 과제 비율의 차이 | 공통 대조의 기존 실패와 구분 |
| 비용 | 전체 배정 실행의 평균 달러·입출력 토큰 차이 | 실패 조기 종료·캐시·수집/작성 비용의 귀속 포함 |
| 행동 | 사전에 정한 명령·오류 반복·코드 경로 선택 빈도의 차이 | 작용 경로의 단서이며 성과상의 득실과 별도 |
| 조합 | 두 요소의 조건부 효과와 I | 일부 요소를 더했을 때 다른 요소의 효과가 달라지는지 |

효과는 추정치와 불확실성, 과제·카드 수, 모델·예산을 함께 표시한다. 실제 연구 표의 행은 `부분 또는 성질 × 대상 조건 × 선언한 편집`으로 두고, 성과 기여·비용 변화·확인 상태를 연결한다. 최종적으로 '사실은 좋고 지침은 나쁘다' 같은 보편 라벨보다 '어느 조건에서 이 지침을 추가하면 성과가 얼마나 바뀌는가'를 보고한다.

무작위 배정 또는 사전에 고정한 균형 순서, 새 환경, 반복 실행과 별도 과제 확인이 필요하다. 정책 간 인과 효과는 조건 외 차이를 통제하고 배정이 적절하다는 가정에 의존한다. 과제 평균을 주 분석으로 하고 실행·테스트·API 호출 수를 독립 과제 수로 바꾸어 세지 않는다. 과제와 출처를 공유하는 반복의 의존성을 분석에 반영한다. 여러 후보에서 유리한 것만 고르는 탐색과 최종 확인은 분리하고, 애매한 추정치는 미확정으로 남긴다. 표본 규모는 원하는 최소 차이와 실제 변동성에 맞춰 정한다. 관련 방법론은 [Empirical Design in Reinforcement Learning](https://jmlr.org/papers/v25/23-0183.html)을 참고한다.

전체 평균 순효과만으로 모든 개별 실행의 '도움을 받은 비율'과 '피해를 받은 비율'을 각각 알 수는 없다. 아래 3절의 한계는 그대로 유지된다. 여기서 측정 가능한 것은 **정의한 부분의 조건부 평균 기여와 그 변동**이다. 한 번 성공한 실행에서 특정 문장이 정확히 얼마의 공헌을 했는지를 확정하는 수치가 아니다.

## 1. 먼저 구분해야 하는 효과

| 물음 | 필요한 비교 | 현재 데이터의 한계 |
| --- | --- | --- |
| 이 제공 정책이 도움이 되는가? | 같은 과제 분포에서 정책별 전체 배정 결과 | 조회한 실행만 고르면 선택 편향이 생긴다 |
| 이 카드 내용을 읽게 하면 도움이 되는가? | 같은 시점·형식으로 고정한 카드와 대조 내용 제공 | 자율 조회 0인 실행은 읽은 카드의 효과를 말하지 못한다 |
| 특정 정보나 절차가 도움이 되는가? | 원문과 해당 부분 삭제·교체 조건 | 길이·표현·출처 판정이 함께 달라지면 순수한 단일 요인의 효과가 아니다 |
| 검색기가 좋은 카드를 골랐는가? | 같은 은행에서 선택 규칙을 바꾸고 후속 성과를 측정 | 어휘 관련성과 실제 과제 효용은 같지 않다 |
| 필요할 때 읽는 편이 좋은가? | 같은 카드의 시작 제공·선택적 읽기·정해진 시점 제공 | 조회 선택·추가 단계·노출 시점이 함께 바뀔 수 있다 |
| 실패 경험은 해로운가? | 출처 실패 여부와 미래 효용을 별도로 측정 | 출처 실패는 미래에 도움이 되는 경고·조사 절차를 포함할 수 있다 |

R02에서 실패 출처의 카드가 Django의 이득 후보였고, 자율 조회 조건의 일부 실패에는 카드 본문 노출이 없었다. 따라서 `출처 실패=유해 기억`, `조회 조건 실패=읽은 기억의 피해`라는 자동 라벨은 부적절하다.

또한 현재 `none`은 외부 경험 카드가 없는 조건이다. 저장소의 Git 이력은 접근 가능하며 R05의 DeepSeek 실행에서 과거 커밋을 실제 읽었다. 따라서 과거 정보 자체의 총효과와 외부 기억을 추가하는 한계 효과를 구분한다. [접근 감사와 실제 사례](reports/2026-11-04-overnight-research.md#중간-감사에서-확인한-또-다른-과거-정보-경로).

## 2. 최종 성공과 회귀를 함께 남긴다

주 지표는 공식 해결 여부다. 보조 지표는 목표 테스트 통과 수(F2P), 기존 통과 테스트의 회귀 수(P2P 실패), 요청 수·실제 API 비용, 패치·행동 기록이다. 테스트 개수는 독립 과제 수가 아니며 서로 다른 과제의 F2P 분모를 그대로 합쳐 대표 성공률로 삼지 않는다.

R02의 Sphinx 10451에서는 모든 정책이 목표 테스트 2/2를 고쳤지만 유지 테스트 세 개를 깨뜨렸다. 원본 대조에서 이 유지 테스트들이 통과했음을 확인했다. 이것은 패치의 회귀지만, 무메모리에서도 나타났으므로 아직 **메모리 때문에 추가된 회귀**라고 할 수는 없다. 기억 조건의 회귀율·개수와 같은 과제의 기준 조건을 비교해야 한다.

가능하면 각 과제에서 다음을 함께 보고한다.

- 해결률 차이: `평균 해결(memory) − 평균 해결(baseline)`.
- 추가 회귀: `평균 P2P 실패 수(memory) − 평균 P2P 실패 수(baseline)`.
- 비용 차이: `평균 총 API 비용(memory) − 평균 총 API 비용(baseline)`.
- 관측 경로: 요청 여부 → 반환·빈 결과 → 실제 입력 노출 → 행동 → 패치·평가.

입력 노출은 주의·이해·채택의 증거가 아니다. 함수명을 검색했다는 사실은 그 이름을 활용한 행동의 증거지만, 그 행동이 최종 성공을 만들었다는 증거는 아니다. 모델의 자기 설명도 독립적인 인과 증명이 아니다.

## 3. 반복 실행의 차이와 개별 득실 라벨은 다르다

이번 OpenRouter 실행은 공통 난수나 결정론적 재생을 보장하지 않는다. 같은 과제·반복 번호로 짝을 지어도 동일한 숨은 난수를 공유하는 실험이 아니다. 한 쌍에서 기준 성공·메모리 실패가 나왔다는 사실만으로 그 기억에 확정된 `harmful` 라벨을 붙이지 않는다.

가상의 동일 대상에 대한 이진 잠재 결과를 `Y0`(기준), `Y1`(메모리)로 정의하면 이득 비율 `B=P(Y0=0,Y1=1)`, 손해 비율 `H=P(Y0=1,Y1=0)`이고 순효과는 `P(Y1=1)−P(Y0=1)=B−H`다. 두 조건의 주변 성공률만 알아서는 B와 H를 각각 식별할 수 없다. 예를 들어 두 성공률이 모두 50%여도 항상 같은 대상을 해결하는 경우와 서로 다른 절반을 해결하는 경우가 모두 가능하다.

진짜 주변 확률을 안다고 가정하더라도 가능한 범위는 다음과 같다.

`max(0, p1−p0) ≤ B ≤ min(p1, 1−p0)`

`max(0, p0−p1) ≤ H ≤ min(p0, 1−p1)`

이는 사건의 교집합에 대한 대수적 범위이며, 작은 표본의 관측 비율을 넣는다고 곧바로 신뢰구간이 되는 것은 아니다. 확률적인 에이전트에서는 어떤 난수 결합을 잠재 결과의 대상으로 삼을지도 먼저 정의해야 한다.

이 연구에서는 우선 **과제·카드·정책 조합의 평균 효과**를 대상으로 삼는 편이 실험 가능하다. 같은 조합을 새 실행으로 반복하고, 발견에 쓴 실행과 확인 실행을 분리한다. 그 후 충분한 서로 다른 과제에서 효과의 분포를 본다. 개별 기억의 유해성 특징을 학습하려면 불확실한 효과 추정치를 확정 라벨처럼 쓰지 않도록 별도 확인 세트·불확실성·적용 범위를 보존해야 한다.

## 4. 비용 하나로 득실을 결정하지 않는다

평균 비용은 성공 실행만이 아니라 배정된 모든 실행에서 계산한다. 성공한 실행끼리의 비용 비교는 성공이라는 정책 이후 변수로 선별된 비교다. 보조 설명으로는 쓸 수 있지만 주 비용 효과로 대체하지 않는다.

성공률이 높고 비용이 낮으면 그 두 지표의 관측 평균에서는 유리하다. 성공률과 비용이 모두 높으면 비용과 품질의 교환 관계다. 작은 표본에서는 둘 모두 변동하므로 점추정의 우열을 확정 정책으로 받아들이지 않는다. 과제 해결의 금전적 가치를 임의로 정해 단일 점수로 숨기지 않는다.

가치를 정할 필요가 있다면 `V×Δ해결률 − Δ비용`을 V의 여러 값에서 보여준다. 이 식은 사람의 확인 비용·추가 회귀의 피해·인프라 비용을 포함하지 않았음을 명시해야 한다. 여러 과제에서 재사용할 때의 손익분기점도 먼저 성과 조건과 수집 비용의 귀속을 정해야 한다.

- 실제 업무에서 이미 발생한 경험을 재사용: 카드 작성·검색·추가 입력이 주 증분 비용이다.
- 연구용으로 경험을 별도 수집: 출처 실행 비용도 포함한다.
- 과금 사후 조회는 동일 요청 비용의 확인이며 응답 비용과 다시 합산하지 않는다.
- 카드가 대화에 반복 포함되는 비용은 실제 API 입력·캐시 사용량에 이미 들어 있다.

실제 청구에는 캐시 상태도 영향을 준다. R06에서는 무메모리·기존 검색 카드의 첫 요청이 이미 캐시 적중을 보인 반면, 다른 카드의 첫 반복은 캐시 쓰기로 기록됐다. 현재 비용 차이는 이 실행 순서와 서비스 상태에서의 실제 지출 차이다. 의미만의 비용 효과나 모두 처음 읽는 상황의 비용으로 바꾸어 해석하지 않는다. 후속 비교에서는 입력·출력 비용, 읽기·쓰기 토큰, 첫 요청의 상태를 남기고, 캐시를 통제할 수 없는 경우 그 제한을 명시한다. 가격을 임의로 적용해 관측된 청구를 덮어쓰지 않는다.

## 5. 중간 패치로 볼 수 있는 것과 볼 수 없는 것

후속 회차에서는 실행 전 정한 API 요청 단계의 패치를 수동 개입 없이 저장하고, 전체 실행이 끝난 뒤 공식 평가한다. 중간 평가 결과·테스트 내용을 에이전트 입력에 넣지 않는다. 저장 명령·시간·오류·패치 해시도 보존한다.

이 자료는 정해진 관측 격자에서의 해결 여부, 최초로 **관측된** 통과 단계와 그때까지의 비용, 통과 후 다시 실패한 경우를 보여준다. 격자 사이의 정확한 최초 통과 시점을 안다고 주장하지 않는다. 같은 패치의 채점 재사용은 그 사실을 표시한다. 마지막 제출 패치와 저장 패치가 다르면 자동으로 같다고 처리하지 않는다.

최초 관측 통과 시점은 사후 공식 채점으로 알아내는 값이다. 에이전트가 온라인으로 그 시점을 알아서 멈출 수 있다는 뜻은 아니며, 그 뒤의 검증·수정을 모두 불필요한 비용으로 부르지 않는다. 실제 조기 종료 절감을 주장하려면 에이전트가 사용할 수 있는 별도의 중단 규칙과 그 품질을 검증해야 한다.

이는 일반 실행 경로의 중간 상태를 보는 측정이다. 에이전트에게 처음부터 짧은 예산을 알리고 실행한 실험과 다르다. 실제 시간·비용 예산별 정책 효과를 주장하려면 그 예산을 사전에 고정한 새 비교가 필요하다.

R05에서 이 구분이 실제로 필요했다. DeepSeek 무메모리 실행의 20번째 저장 패치는 통과했지만 32회 한도에 도달할 때까지 제출하지 못했다. 공식 최종 판정은 미제출로 비워 두고, 작업 트리의 사후 성공을 별도로 기록했다. 주 지표가 ‘예산 내 공식 해결물 제출’이라면 미제출은 전달 실패이고, ‘수정 경로가 통과 코드에 도달했는가’는 보조 지표다. 둘 중 유리한 쪽만 골라 기억 효과를 주장하지 않는다.

R07에서는 중간에 공식 통과였지만 최종 실패인 실행이 네 번 있었다. 대표 사례의 추가 대조에서는 공식 정답 패치조차 수정 전 로컬 테스트 하나를 실패했다. 공식 테스트 패치가 그 기대값을 바꾸기 때문이다. 따라서 ‘통과 후 실패’는 어느 평가 버전에서의 판정인지 반드시 붙여야 하며, 뒤의 변경을 무조건 품질 저하·쓸데없는 검증으로 해석하지 않는다. [원본·정답·중간·최종의 테스트 버전 대조](reports/data/2026-11-04-django-test-version-diagnostic.json).

## 6. 다음 단계의 검증 단위

현재처럼 몇 과제에서 다양한 개입을 하는 탐색은 실패 원인 후보와 측정 장치를 찾는 데 적합하다. 일반적인 효과를 검증하려면 탐색에 쓰지 않은 과제와 출처를 늘리고, 주요 대비·표본 수·중단 기준을 미리 고정해야 한다. 같은 과제의 반복 수를 늘리는 것과 새로운 과제 수를 늘리는 것은 다른 문제를 해결한다.

우선 순서는 **환경 대조 → 새 기준을 포함한 재현 → 한 요소의 삭제·교정 → 새 과제에서 재검증**이다. 원본 실패, 무조회, 빈 검색, 평가 불완전을 모두 유지한다. 선택된 흥미로운 사례만으로 전체 득실을 추정하지 않는다.

## 7. 선행 연구와 비교할 때 전달 경로를 맞춘다

2026-11-04에 원문을 다시 확인했다. ReasoningBank의 일반 방법은 검색된 기억을 시스템 지시에 추가한다. 웹 에이전트 구현을 설명하는 부록 A.2는 과제 임베딩으로 경험을 고른 뒤 본문을 넣고, 매 단계에 기억을 사용할지 검토하도록 안내한다. 이는 우리의 선택적인 별도 조회 도구와 같은 처리가 아니다. 웹 부록의 상세 문구가 SWE 구현에도 그대로 쓰였다고 여기서 가정하지 않는다. [ReasoningBank §3.1, Appendix A.2](https://arxiv.org/html/2509.25140v1)

MemDev-Bench의 부록 G에서도 방식이 다르다. A-Mem은 훅이 조회를 권하고 에이전트가 검색·본문 읽기를 선택한다. Mem0는 첫 실질적 사용자 입력에 검색을 시작하며 이후 직접 검색도 가능하다. Supermemory는 시작과 입력 훅에서 문맥을 제공하고, Claude-Mem은 시작 개요와 선택적 세부 조회를 함께 사용한다. [MemDev-Bench Appendix G](https://arxiv.org/html/2610.27524v1)

이로부터의 연구 설계 판단은 **시작 제공, 자율 조회, 사용 여부 검토를 유도하는 안내**를 서로 다른 개입으로 기록해야 한다는 것이다. 우리의 어휘 검색·짧은 고정 은행·32요청 예산·선택적 안내는 위 방법의 충실한 재현 구현이 아니다. 따라서 무조회 관측은 이 설정의 채택 문제를 보여주며 다른 방법의 내용 효용을 반박하지 않는다. 후속 안내 비교에서도 본문을 자동 노출했는지, 선택을 권했는지, 호출을 의무화했는지를 구분한다.
