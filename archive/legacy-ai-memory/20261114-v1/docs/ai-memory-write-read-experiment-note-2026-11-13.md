# 에이전트 기억의 저장과 활용 실험 논의

2026-11-13. 연구 목적은 **LLM이 작업 경험을 어떻게 저장하고 불러오느냐에 따라, 다음 작업의 성공·실패·행동·비용이 어떻게 달라지는지 측정하는 것**이다. 기존의 기억 제공에 따른 이득·손해를 유지하면서, 분석 범위를 기억의 생성과 활용 과정까지 넓힌다.

[평가 프레임워크 설계 검토안](ai-memory-evaluation-framework-design-2026-11-13.md)에 기능·도구 계약·비교 조건·실행 절차·측정·원본 기록·기여 검토와 미정 사항을 구체화했다. 실험 시작 전 검토용 제안이며 아래 논의의 연구 범위를 유지한다.

τ²-bench 같은 실제 도구 사용 환경을 본실험 후보로 두고, 현재 데이터셋은 통제된 진단에 활용하는 방향을 논의했다. **저장 시점·형태·자율 선택·조회·반복·전이·득실·비용을 연구 범위로 유지한다.** 벤치·도메인·모델·실행 규모는 아직 정하지 않았으며, 아래 내용은 새 실험 결과가 아닌 설계 노트다.

재검토에서는 실험 방향은 적절하지만, 관찰할 현상과 원인을 검증할 비교가 더 구체적으로 연결돼야 한다고 판단했다. 가까운 선행연구와 겹치는 질문도 있어 현재 구상만으로 독창성이 확보된 것은 아니다. 한 도메인부터 실행하거나 저장 시점부터 순차 비교하는 것은 개발 순서의 선택이며, 연구 범위를 제한하거나 실험 타당성을 보장하는 조건으로 삼지 않는다.

## 연구 질문과 기존 목표의 관계

핵심 질문은 다음과 같다.

> LLM이 경험을 어떤 시점과 형태로 저장하고 어떻게 불러오느냐에 따라, 후속 작업의 성공·실패·행동·비용이 어떻게 달라지며 그 차이는 어떤 정보의 보존·누락·변형·조회에서 생기는가?

LLM에게 기억 도구를 주고 저장·조회를 맡겨도 원래의 득실 측정은 가능하다. 다만 비교에 따라 측정 대상이 달라진다.

| 비교 | 측정하는 효과 |
| --- | --- |
| 기억 도구 사용 가능 대 사용 불가 | 저장·조회·적용을 포함한 기억 정책 전체의 효과 |
| 같은 경험에서 만든 기억 A와 B를 같은 후속 작업에 제공 | 저장 방식의 효과 |
| 같은 기억 은행에서 조회 정책을 변경 | 불러오는 방식의 효과 |
| 같은 노출 직전 상태에서 기억을 제공하거나 보류 | 그 상태에서의 국소적인 제공 효과 |

전체 정책의 효과와 개별 기억의 효과는 별도로 해석한다. 자유 실행에서 성능이 개선됐다는 결과만으로 특정 기억 하나가 원인이라고 단정할 수는 없다.

## 현재 데이터셋과 실제 작업 벤치의 역할

현재 여행·대화 기반 자료는 사실의 보존, 현재 상황과 과거 기억의 관계, 잘못된 기억 적용을 통제해서 점검하는 데 적합하다. 그러나 사전에 만든 기록을 제공하는 평가는 LLM이 실제 경험에서 무엇을 기록할지 결정하는 능력이나 도구 사용 경로의 개선을 직접 보여주지 않는다. 기존 기록의 필요·무효 라벨을 LLM이 새로 쓴 기억에 그대로 붙일 수도 없다.

본실험 후보는 τ²-bench 같은 실제 도구 사용 벤치다. 개발은 이 저장소에서 하고, 작업 환경과 채점에 벤치 어댑터를 연결하는 방향이다. 벤치·도메인·모델에 따라 효과가 달라지는지도 검증할 수 있도록 설계하며, 구체적인 구성은 미정이다.

τ²-bench는 설정된 평가 기준에 따라 실행 후 데이터베이스 상태와 필요한 응답 등을 채점한다. 행동 경로 변화는 별도로 분석하며, 정답 예시의 호출 순서와 일치하는지를 성공 기준으로 삼지 않는다. 공식 채점이 모든 절차상의 문제를 자동으로 검출하는 것은 아니므로, 실제 과제의 평가 항목과 채점 버전을 기록하고 반복 오류·중복 처리·불필요한 호출 등의 과정 지표를 함께 본다. [공식 평가 문서](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)

기존 오프라인 세션 패킷(`datasets/memory_context_session/20261113-offline-v2/README.md`, 로컬 개발 자료)은 입력 구성·노출·예산 검사에 사용할 자료다. 그 준비 완료를 자율 기억 실험의 성능 검증으로 해석하지 않는다.

## 기억 도구의 최소 구성

첫 단계에서는 별도 검색 모델이나 학습 선택기를 필수 요소로 추가하지 않고, LLM이 다음 도구로 여러 기억을 저장하고 선택하게 한다.

| 도구 | 역할 |
| --- | --- |
| `store` | 현재까지 관찰한 경험에서 기억을 작성해 저장 |
| `list` | 저장된 기억의 ID와 제목 등 탐색 정보를 조회 |
| `get` | 선택한 기억의 본문을 조회 |

`list`에서 제목이나 요약을 보여주는 것 자체도 기억의 노출이다. 본문 조회만 기록하면 실제로 모델이 받은 정보를 놓칠 수 있으므로 목록 응답도 보존한다. 수정·삭제가 필요하면 후속 도구로 검토하고, 변경 전후 내용을 추적할 수 있게 한다.

BM25는 기존 입력 준비에서 사용한 임시 검색 기준선이며 새 실험의 필수 조건이 아니다. **기억 2k 또는 최근 대화 2k와 기억 2k의 배분도 기본 연구 가정으로 채택하지 않는다.** 실제 모델의 문맥 한도는 지키고 저장·조회·추론 비용을 기록한다. 별도의 저장 한도를 둘지는 연구 질문과 실행 비용에 맞춰 결정하며, 저장 한도와 한 번에 읽는 분량을 구분한다.

## 저장 시점과 형태 및 조회 방식의 교차 비교

저장 시점·형태·조회 방식을 각각 구분하여 교차 비교한다. 한 조건에서 여러 요인을 함께 바꾼 결과만으로 원인을 분리할 수는 없지만, 요인별 조합을 비교하면 각 효과와 상호작용을 검증할 수 있다. 예를 들어 같은 저장 형태가 종료 후 정리에는 유리하고 수행 중 기록에는 불리한지도 연구 대상이다.

저장 시점의 비교 조건은 다음 네 가지다.

| 조건 | 저장 규칙 |
| --- | --- |
| 기억 없음 | 기억을 이어받지 않고 매 시도를 새로 시작 |
| 종료 후 저장 | 작업이 끝난 뒤 경험을 정리해 저장 |
| 수행 중 저장 | 작업 중 필요할 때 저장하며 별도의 종료 후 정리 단계는 두지 않음 |
| 수행 중 저장과 종료 후 정리 | 작업 중 필요할 때 저장하고 종료 후 수정·추가 허용 |

수행 중에만 저장하는 조건을 포함해야 중간 기록 자체의 효과와 종료 후 정리의 추가 효과를 구분할 수 있다. 저장 형태는 자유 형식, 사건 기록, 요약, 절차·전략, 실패 원인·주의사항 등이 후보이며, 조회 방식은 작업 시작 시 제공, 필요할 때 목록과 본문 조회, 현재 과제에 맞춘 조회 시 재가공 등이 후보다. 실제 비교할 수준과 조합은 후속 명세에서 정한다.

특정 효과를 비교할 때는 나머지 지침·도구·작업자·후속 과제 조건을 맞춘다. 자율 작성 조건에서는 실제 저장 내용과 선택을 LLM에 맡기고, 배정한 지침과 실제 수행한 저장·조회 행동을 모두 기록한다. 어떤 형태나 조합이 우수한지는 검증할 가설이다.

수행 중에는 그 시점까지의 관측만 저장에 사용할 수 있다. 종료 후 저장은 전체 수행 기록을 볼 수 있으므로 두 정책의 정보 차이도 효과에 포함된다. 수행 중 쓴 기억을 같은 작업에서 다시 읽도록 허용하면 첫 작업의 행동과 경험까지 달라진다. 이 경우의 결과는 저장 시점만의 독립 효과가 아니라 정책 전체의 효과로 보고한다.

## 기준선과 정보 및 연산 조건

무기억 조건도 같은 횟수만큼 재시도한다. 여기에 **동일 경험의 원기록에 그대로 접근하는 조건과 단순 요약을 활용하는 조건**을 두어, 과거 정보에 접근하는 효과와 새 기억 표현의 추가 효과를 비교한다. 원기록의 접근 경로와 노출 정보도 기록하며, 문맥에 전부 넣을 수 없는 경우의 조회·생략 규칙을 명시한다.

정책에 따라 종료 후 추론, 저장 횟수, 읽기·재가공 횟수와 정보량이 달라질 수 있다. 자연 실행에서는 그 차이를 포함한 성능과 전체 비용을 보고한다. 저장 표현 자체의 우위나 비용 효율을 주장할 때는 동일 경험·정보 접근 조건의 비교와 성능 대비 비용 분석이 필요하다. 이를 위해 임의의 2k 제한을 도입하지 않는다.

저장 단계에는 실제 관찰한 경험과 사전에 정한 피드백만 제공한다. 숨겨진 정답·기준 행동·채점기 내부 설명이 기억에 들어가지 않도록 하고, 성공·실패 피드백을 제공하는 실험이라면 조건 간 정보 제공 규칙을 맞춘다. 종료 후 저장에 필요한 추가 모델 호출도 비용에 포함한다.

## 반복 실행과 경험 전이

기본 흐름은 **첫 작업 수행 → 정책에 따른 기억 저장 → 업무 환경과 대화 초기화 → 기억만 유지한 다음 작업 수행**이다. 매 시도의 업무 데이터베이스, 에이전트 대화, 사용자 시뮬레이터 상태를 초기화하고, 기억 저장소는 업무 데이터베이스와 분리한다. 이전 작업의 처리 결과가 남아서 성공하는 경우를 막기 위한 조건이다.

후속 작업은 다음 세 경우를 구분하면 해석에 도움이 된다.

- **같은 과제 재시도:** 원래 실패를 복구하거나 더 효율적으로 해결하는지 측정한다.
- **관련된 새 과제:** 과거 경험에서 얻은 절차나 전략이 전이되는지 측정한다.
- **중요 조건이 다른 과제:** 과거 절차를 재사용하면 안 되는 상황을 알아보는지 측정한다.

조건이 다른 과제를 별도로 구성한다면 기본 벤치와 구분해 보고한다. 같은 과제의 재시도 개선도 유효한 결과지만, 새로운 과제에 대한 일반화와는 별개의 주장이다.

기억 없는 조건도 같은 횟수만큼 재시도한다. 각 기억 정책은 독립된 저장소에서 시작한다. 본실험의 연속 작업에서는 기억을 누적할 수 있지만, 전이 확인용으로 따로 남긴 과제의 경험은 기억 갱신이나 이후 학습에 사용하지 않는다. 모델·벤치 버전·사용자 시뮬레이터 설정·초기 상태·반복 시드를 기록한다. 같은 시드라도 에이전트 행동이 달라지면 사용자 응답까지 같아진다고 가정하지 않는다.

두 번째 시도의 변화와 여러 작업을 거친 뒤의 변화는 구분한다. 기억 은행을 시점별로 보존하고, 사전에 정한 평가 시점에서 새 과제의 성공과 이전에 풀던 과제의 회귀를 함께 측정한다. 확인용 평가에서는 같은 시작 은행을 과제별로 복제해 설정된 저장·조회 정책을 수행하고, 평가 경험·피드백·기억 변경을 원은행이나 다른 확인 과제에 반영하지 않는다. 저장을 중지한 고정 은행 진단은 이 정책 평가와 별도 조건으로 둔다.

작업 순서도 결과에 영향을 줄 수 있으므로 독립된 저장소에서 작업 스트림을 반복하고 순서에 따른 차이를 기록한다. 같은 은행으로 많은 과제를 평가한 횟수와 독립된 은행·작업 스트림의 반복 수를 구분한다.

메모리를 이어받는 반복은 일반 τ²-bench 반복 평가와 다른 설정이다. 공식 `pass^k`와 섞지 않고 **τ²-bench 기반 메모리 적응 실험**으로 보고한다. [공식 반복 평가 설명](https://github.com/sierra-research/tau2-bench/blob/main/docs/glossary.md)

| 측정 대상 | 주요 관측 |
| --- | --- |
| 작업 성공 | 조건별 성공률, 시도별 변화, 같은 과제와 새 과제의 차이 |
| 이득과 손해 | 같은 후속 과제의 관측된 결과 반전과 반복 실행에서 추정한 성공 확률 차이 |

| 저장과 조회 | 작성 내용·시점·버전·당시 관측, 목록에서 노출한 정보, 조회한 본문과 시점 |
| 누적 변화 | 기억 갱신 전후의 성능, 이전 과제 회귀, 새 과제 전이, 작업 순서에 따른 차이 |
| 비용 | 첫 경험 수집과 기억 작성부터 후속 조회·작업 수행까지의 토큰·호출·지연·금액 |

득실은 같은 초기 상태와 후속 과제를 맞춘 비교에서 집계한다. 관측한 개선은 무기억 실패·기억 성공이고, 악화는 무기억 성공·기억 실패다. 양쪽 성공과 양쪽 실패도 남긴다. 첫 시도에 실패한 과제나 기억이 도움이 된 사례만 골라 전체 효과를 보고하지 않는다.

**관측된 결과 반전과 성공 확률의 변화는 구분한다.** 예를 들어 두 조건의 성공 확률이 모두 70%로 같아도, 독립 실행을 짝지으면 실패→성공과 성공→실패는 각각 약 21% 발생할 수 있다. 이는 실행 변동을 설명하는 가정 예시이며, 실험에서 측정한 기억 효과가 아니다.

조건별 반복 실행으로 성공 확률 차이와 불확실성을 추정하고, 무기억 대 무기억의 반복 비교로도 결과 반전의 변동 수준을 확인한다. 반전 집계의 짝짓기 규칙을 명시하며, 변동 수준을 단순 차감해 개별 기억의 인과적 득실로 해석하지 않는다. 같은 원천 과제의 표현 변형·재시도·여러 기억 파일은 독립 경험 수와 구분하고, 독립된 과제와 기억 은행·작업 스트림의 구조를 반영해 집계한다.

도구 로그는 기억이 제공됐다는 증거다. 모델이 그것을 활용해 성공했다는 주장에는 통제 비교가 필요하다. LLM의 사후 설명만으로 성공 원인이나 실패 원인을 판정하지 않는다. 저장이 부정확했는지, 필요한 기록을 못 찾았는지, 제공된 내용을 잘못 적용했는지 나누어 진단하되, 로그만으로 구분하기 어려운 경우는 별도 개입으로 확인한다.

자율적으로 선택한 행동과 배정한 정책의 효과를 구분한다. 어려운 과제일수록 기억을 더 많이 작성할 수 있으므로, 저장량과 실패율의 상관관계만으로 저장의 인과 효과를 판단하지 않는다. 조건별로 배정한 저장 기회·형식 지침·조회 방식의 효과와, 그 안에서 LLM이 실제로 선택한 행동을 나누어 분석한다.

## 저장과 조회의 원인을 구분하는 보조 실험

자유롭게 저장·조회하는 본실험은 정책 전체의 실용적 효과를 측정한다. 원인을 확인할 때는 다음 비교를 추가할 수 있다.

1. **같은 경험에서 다른 기억을 만든다.** 동일한 첫 수행 기록을 사용해 저장 정책 A와 B로 기억을 만들고, 같은 작업자·조회 정책·후속 과제에 적용한다. 수행 중 저장을 재현할 때는 해당 시점의 기록 접두부만 보여준다.
2. **같은 기억에서 조회 방식을 바꾼다.** 기억 은행을 고정하고 자유 조회, 정해진 제공 방식, 현재 과제에 맞춘 재가공 등을 비교한다. 저장 정책 A와 B에서 만든 은행을 각각 조회 정책 X와 Y에 적용하면 저장과 조회의 조합 효과도 검증할 수 있다.
3. **특정 노출의 영향을 확인한다.** 목록·제목·본문에서 정보가 처음 노출되기 직전의 같은 상태에서 제공·보류 분기를 비교한다. 앞서 제목으로 이미 제공된 정보는 본문 보류만으로 제거되지 않는다.
4. **내용을 바꾸어 판단의 변화를 확인한다.** 적용 조건·관찰 사실·잠정 추측 등 검증할 내용을 교체하거나 일부만 제거하고, 다른 조건을 맞춘 후속 실행에서 행동과 성공 여부를 비교한다. 단순히 기억을 조회한 뒤 행동이 바뀌었다는 관찰과 구분하며, 편집에 따른 분량·표현·노출의 차이도 기록한다.

은행을 고정하는 것은 이런 원인 진단을 위한 조건이다. 본실험에서는 작업이 이어지며 기억을 추가·수정하는 동작을 허용할 수 있다. 여러 기억이 함께 작용하므로 한 기록을 뺀 효과를 각 기억의 고유한 가치로 일반화하지 않는다.

## 연구기여 후보와 선행연구의 범위

기여 후보는 **경험이 기억으로 기록되고 조회되어 행동에 반영되는 과정에서 무엇이 보존·누락·변형되며, 그 차이가 후속 작업의 성공·손해·효율을 어떻게 만드는지 밝히는 것**이다. 저장·조회·누적·전이를 함께 연구하면서 각 주장에 필요한 비교를 연결한다. 새 알고리즘을 만들지 않아도 새로운 설명과 반복 검증되는 행동 증거, 재현 가능한 평가 절차가 있으면 실증 연구로 발전시킬 수 있다.

예를 들어 이전 주문에서 성공한 처리 순서를 저장한 뒤, 주문 상태가 달라진 후속 과제에서도 그대로 적용하는지 볼 수 있다. 순서만 저장한 기억과 적용 조건·확인 근거까지 저장한 기억을 비교하면 저장 내용과 오용의 관계를 검증할 수 있다. 적용 조건을 적으면 반드시 좋아진다는 결론은 실험 전에 가정하지 않는다.

또 다른 가설은 수행 중의 잠정적 추측을 종료 후 정리가 수정하거나, 오히려 확정된 규칙처럼 강화할 수 있다는 것이다. 최초 작성·후속 정정·종료 후 정리·다음 작업의 조회와 판단을 연결해 기록하고, 해당 내용을 바꾼 개입으로 결과 변화를 확인할 수 있다. 성공을 돕는 정보의 보존과 잘못된 추론의 지속을 모두 검증한다.

저장·활용 자체, 저장 방식별 성능 차이, 기억의 손해, τ²-bench 적용만으로 새로움을 주장하기는 어렵다. 기존 노트의 문헌에 더 가까운 연구를 추가해 대조했다. 다음 표에는 정식 게재 논문, 사전 공개 논문과 연구 글이 함께 포함된다.

| 선행연구 | 이미 다루는 범위와 이번 설계의 관계 |
| --- | --- |
| [ReasoningBank](https://arxiv.org/html/2509.25140v2) | 성공·실패 경험에서 전략을 추출하고 후속 작업에 활용한다. 경험을 기억으로 만들어 성능을 높이는 것 자체는 기존 연구 범위다. |
| [AgeMem](https://aclanthology.org/2026.acl-long.981/) | 저장·조회·수정·요약·삭제를 도구 행동으로 다룬다. LLM에게 기억 도구를 제공하는 것 자체의 새로움은 제한적이다. |
| [When Continual Learning Moves to Memory](https://arxiv.org/html/2604.27003) | 경험 표현, 저장 단위, 조회 빈도와 긍정·부정 전이를 분석한다. 저장과 조회의 관계를 묻는 것만으로 독창성을 주장하기 어렵다. |
| [JitMem](https://arxiv.org/html/2609.27334) | 원경험을 저장하고 현재 과제에 맞춰 조회 시 가공하며 τ²-bench도 평가한다. 수행 중·종료 후 작성 시점과는 다른 축이지만, 표현·조회 비교의 가까운 선행연구다. |
| [MemGym](https://arxiv.org/html/2605.20833) | τ²-bench 등을 포함한 기억 평가와 동일 작업자에서의 비교를 다룬다. 주로 수행 중 문맥 압축을 평가하므로 후속 작업으로 이어지는 자율 저장·조회와 구분해 대조한다. |
| [Useful Memories Become Faulty When Continuously Updated by LLMs](https://arxiv.org/html/2605.12978) | 동일 경험의 갱신 방식에 따른 기억 차이와 누적 정리 후 성능 악화를 분석한다. 누적 회귀를 관찰하는 것 자체는 새 기여가 아니다. |
| [MemTrim](https://arxiv.org/html/2610.07311) | 현재 과제와 일부만 맞는 기억이 손해를 주는 현상과 저장·조회 단계의 제어를 다룬다. 기억의 오용이나 손해만으로 차별화하기 어렵다. |
| [Self Evolving Agents Can Repair Failures but Struggle to Generalize from Them](https://arxiv.org/html/2610.22984v1) | 실패 경험을 통한 원래 과제 복구와 새 과제로의 전이를 구분한다. 재시도와 전이를 나누는 것만으로 독창성을 주장할 수는 없다. |
| [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory) | 기억 작성·표현·조회와 작성 시점의 문제를 다룬 연구 글이다. 수행 중 저장과 사후 정리의 비교 역시 구체적인 검증 조건과 추가 근거가 필요하다. |

이 선행연구들이 전체 실험을 이미 수행했다는 결론은 아니다. 기여를 평가할 때에는 단순한 측정 항목의 추가보다 **기존 결과로 설명하지 못한 정책 간 차이와 그 원인을 어떤 교차 비교·내용 개입·후속 검증으로 설명했는지**를 확인한다. 현재는 타당한 실험 골격과 기여 후보를 정리한 단계이며 독창성은 미확정이다. 기존 [문헌 조사 자료](reports/data/agent-memory-literature-20261113/review.json)는 앞선 조사 범위이며, 위 추가 자료까지 모두 포함한 목록으로 해석하지 않는다.

## 다음 설계에서 정할 사항

다음 설계에서는 전체 연구 범위를 유지하면서 주장과 비교 조건을 구체적으로 연결한다.

1. 저장 시점 네 조건, 저장 형태, 조회 정책, 같은 과제 재시도·전이·누적 평가의 조합을 명세한다. 벤치·도메인·모델과 실행 순서는 검증하려는 적용 범위에 맞춰 정한다.
2. `store/list/get`의 노출 내용, 수정 방식, 피드백과 환경 초기화 규칙을 정한다.
3. 무기억 반복·원기록 접근·단순 요약 기준선과 조건별 정보·연산·전체 비용의 기록 규칙을 정한다.
4. 동일 경험에서의 기억 생성, 은행 교환과 조회 정책 교차, 내용 개입을 연결해 관찰과 원인 검증을 구분한다.
5. 독립된 기억 은행·작업 스트림·과제와 반복 시드·작업 순서를 정하고, 관측된 결과 반전·성공 확률 차이·누적 회귀를 구분할 집계 방법을 명세한다.
6. 각 기여 주장에 해당하는 선행연구의 비교 조건과 필요한 새 증거를 연결한다.

구체적인 벤치·도메인·모델 구성, 저장 형식, 피드백 제공 여부, 저장 한도, 과제 수와 반복 수, 비용 규모는 미정이다. 이번 보완은 설계 정리이며 벤치 통합이나 모델 실행의 착수는 아니다.
