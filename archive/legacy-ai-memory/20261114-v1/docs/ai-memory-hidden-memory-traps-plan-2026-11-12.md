# 사람처럼 기억을 쓰는가: 숨은 함정과 긴 맥락의 기억 득실 자료 설계

**후속 상태 안내(2026-11-12):** 아래는 제작 전 설계 기록임. 현재는 4세션 패킷의 제작·별도 검산까지 완료함. 데이터 버전·UNKNOWN 해석·전달 예산의 정정과 다음 누적 실험은 [최신 통합안](ai-memory-data-cleanup-and-context-stream-plan-2026-11-12.md)을 따름. 고정 정답 과거와 모델 답변 이력이 쌓이는 세션을 구분함.

2026-11-12. 작성: Claude. 사용자와의 설계 대화를 정리한 실행 전 설계안이다. 아직 아무것도 만들거나 실행하지 않았다. 숫자는 저장된 자료에서 다시 계산한 것이다.

## 1. 왜 만드나

연구 질문은 "에이전트 기억의 득과 실을 판단할 수 있는가"이다. 지금까지 확인한 것은 세 가지다.
- 득실은 측정된다.
- 직접 만든 자료의 손해는 단순 규칙으로 풀린다. 변경·취소가 "Recorded cancellation…"처럼 드러나 있기 때문이다.
- 공개 자료에는 손해 상황이 드물다.

그래서 **같은 기억이 맥락에 따라 득도 되고 실도 되는 상황을, 사람의 기억 실험처럼 설계한 자료**를 만든다. 문제(함정)는 자연스러운 말 속에 숨기고, 정답 라벨은 구조화된 대본에서 나오게 한다. 그래야 득실을 다시 계산해 확인할 수 있다.

발표에서 전할 한 문장: **"에이전트가 사람처럼 기억을 쓰는지, 여러 맥락에서 득과 실을 짝지어 확인할 수 있는 자료를 만들었다."**

**역할 분담 ([Codex 인계 노트](ai-memory-data-augmentation-handoff-2026-11-12.md) 반영):**
- Claude: 새 원천 자료(세션, 대본, 겉말, 관계 라벨)를 만든다.
- Codex: 학습용 관계 증강, 출처·분할 확인, 독립 검산을 맡는다.
- 첫 납품은 작업자를 실행하기 전에 검토할 수 있는 데이터 패킷이다(6절 7번).

## 2. 지금 자료의 한계 (배달 경로 실험의 여행 세션)

| 한계 | 확인한 숫자 |
|---|---|
| 문제가 드러나 있음 | 바뀐 참조는 "최신 기록만" 규칙으로 9B 38 → 59/60까지 풀린다 |
| 맥락이 짧음 | 세션 마지막(요청 35–40)에 대화 전체를 넣어도 입력 중앙값 5,359토큰(최대 5,763). 기록 목록 2,856(최대 3,096). 무기억 입력 1,110 |
| 틀이 하나 | 요청 문장 틀 1개, 본 실험 20세션 + 파일럿 8세션 |

- 요청이 아무리 많아도 요청 하나가 짧아서 맥락은 길어지지 않는다. 그래서 기억을 다 넣는 것이 늘 가능하다.
- 그런데도 9B는 이 짧은 길이에서 기록 목록으로 64건을 잃었다. 지금의 손해는 길이가 아니라 **비슷한 기록끼리의 간섭**에서 나온 것이다.
- 새 자료는 간섭과 길이를 따로 조절할 수 있어야 한다.

## 3. 목표 · 비목표 · 피할 것

**목표**
1. 사람 기억의 능력 하나씩에 대응하는 함정 7종을 자연스러운 말 속에 숨기고, 라벨은 대본에서 계산한다.
2. 실제 에이전트 작업처럼 맥락이 길어지게 한다. 길이를 단계로 바꿔 길이의 효과를 따로 잰다.
3. 같은 대본을 "드러낸 겉말"과 "숨긴 겉말"로 만들어 숨김의 효과를 짝지어 잰다.
4. 정답을 장소 ID나 UNKNOWN으로 정확히 채점하고, 손해의 원인(어떤 기록을 따랐는지)을 남긴다.

**비목표**
- 새 기억 시스템 구조를 만드는 것
- 이번 회차에 새 선택기를 학습하는 것. 이 자료는 나중에 평가에 쓴다.
- 여행 이외의 영역으로 넓히는 것

**피할 것 (만들어도 실패인 경우)**
- 키워드나 단순 규칙으로 풀리는 "숨김"
- 의미 없는 채우기로 늘린 길이. 소설 붙이기 같은 것은 안 되고, 실제 작업에서 생기는 내용이어야 한다.
- LLM 채점이 필요한 라벨
- 평가할 작업자나 비교 정책의 실패를 보고 문항을 고르거나 버리는 것. 자료의 타당성은 의미 검사로만 판단한다.
- 꼼꼼한 사람이 봐도 정답이 둘로 갈리는 함정

## 4. 함정 7종

여행 카탈로그에는 식당 종류(Seafood, BBQ, Bakery 등 15종)와 숙소 규칙(No pets, No children under 10, No smoking 등), 가격이 있다. 조건 함정은 이 속성으로 정답 집합을 정확히 계산할 수 있다.

| 함정 | 사람이 잘하는 일 | 대응하는 기억 개념 | 숨긴 겉말 (예) | 정답 | 지는 단순 정책 | 손해 방향 |
|---|---|---|---|---|---|---|
| ① 숨은 무효화 | 말하지 않아도 바뀐 걸 알아차림 | 순행 간섭 피하기 | "리버 호텔에서 연락이 왔는데, 민수가 묵기로 한 날 공사라 그 방을 못 쓴대." ("취소"라는 말 없음) | 무효가 된 예약을 빼고, 대본이 정한 대체 상태 | 다 주기, 관련성 검색, 드러난 표시 규칙 | 무효 기억을 따름 |
| ② 변경처럼 보이는 보완 | 덧붙인 것과 바꾼 것을 구분 | 역행 간섭 피하기 | "민수 1일차에 디저트 카페도 하나 넣어 줘." | 기존 저녁과 카페 둘 다 유효 | 최신만 남기기 | 유효 기억을 버림 |
| ③ 일시적 예외 | 한 번의 예외를 습관으로 착각하지 않음 | 일화와 의미 기억의 구분 | "지수는 해산물을 안 먹는데, 2일차 저녁만 친구가 해산물집을 잡아 둬서 거기 가." | 다른 날 저녁은 Seafood 제외 | 최신 날짜 우선 | 오래 유지되는 선호를 덮어씀 |
| ④ 숨은 관련성 | 한 번 들은 중요한 것을 필요할 때 떠올림 | 미래 기억 | 초반에 한 번 "민수는 이번에도 콩이(강아지) 데려간대." 나중에 "민수 3일차 숙소 잡아 줘." | No pets 숙소 제외 | 관련성 검색, 최신성·망각 | 필요한 기억을 놓침 |
| ⑤ 과거를 묻는 질문 | 바뀐 것도 "예전엔 그랬다"로 간직 | 일화 기억 | "민수 숙소, 원래는 어디로 하려고 했지?" | 무효가 된 원래 기록 | 덮어쓰기, 무효 기록 삭제 | 이력을 잃음 |
| ⑥ 닮은 남의 기억 | 누구 일이었는지 구분 | 출처 기억 | 같은 날 Ana와 Anna, 이름이 비슷한 식당 | 그 사람의 기록만 | 관련성 검색 | 남의 기록을 따름 |
| ⑦ 없는 것을 묻기 | 모르는 건 모른다고 함 | 거짓 기억 피하기 | 계획한 적 없는 사람·날을 물음 | UNKNOWN | 다 주기 | 지어냄 |

**섞는 원칙**
- 세션마다 7종이 각각 2번 이상 나오고, 위치는 무작위다.
- 함정이 아닌 평범한 요청도 절반쯤 둔다. 그래야 "모든 요청이 함정"이라는 단서가 생기지 않는다.
- 어떤 단순 정책도 모든 함정에서 이기지 못하도록 함정 수를 맞춘다.

**무효화 뒤의 상태:** 올바른 상태는 언제나 대본이 정한다. 대체(다른 기록이 유효해짐)이거나 빈 상태(그 칸을 물으면 정답은 UNKNOWN)이다. 작업자가 그 턴에 어떻게 답했는지는 정답을 바꾸지 않는다. 다만 작업자가 직접 고른 장소가 이후 참조의 정답이 되는 지금 방식은 유지한다.

## 5. 맥락 길이 설계

실제 에이전트의 맥락은 요청이 아니라 **도구 결과, 여러 날에 걸친 작업, 다른 일과 잡담** 때문에 길어진다. 그 세 가지를 넣는다.

1. **검색 결과:**
   - 예약 요청마다 하네스가 카탈로그 검색 결과(후보 10–30개와 속성·가격)를 대화에 넣는다. 작업자가 도구를 고르지 않고 결과는 결정적으로 생성한다.
   - 후보 목록 자체가 닮은 이름과 비슷한 속성의 방해물이 된다.
2. **여러 날:**
   - 한 세션을 여러 "날"로 나누고, 날이 바뀌면 새 맥락에서 시작한다.
   - 지난 날의 내용은 기억(기록 목록·검색·대화 원문)을 통해서만 볼 수 있다. 그래서 기억이 "있으면 좋은 것"이 아니라 꼭 필요한 것이 된다.
3. **다른 일과 잡담:**
   - 날씨, 짐 목록, 다른 여행자의 일정 같은 요청을 섞는다.
   - 일부에는 닮은 인물·장소를 넣는다. 사실이 서로 충돌하지 않는지는 생성 후 검사한다.

**길이 단계:** 같은 대본과 함정을 세 길이로 만든다. 사실과 함정은 같고 주변 내용만 늘린다.

| 단계 | 구성 | 세션 끝 대략 길이 |
|---|---|---|
| S | 지금과 같음 (검색 결과·잡음 없음) | 약 6천 토큰 |
| M | 검색 결과 요약 + 일부 잡음 | 약 3만 토큰 |
| L | 검색 결과 전체 + 여러 날 + 잡음 | 약 10만 토큰 |

**기억 예산:**
- 기록·선택 조건에는 전달 예산을 둔다. 제안은 2천·8천 토큰이다.
- M과 L에서는 기록을 다 줄 수 없으므로 고르는 판단이 필요해진다.
- "전체 이력을 맥락에 넣기"는 모델 창에 들어가는 범위에서 따로 참고 조건으로 잰다. 지난 LongMemEval 전체 길이 실행에서 9B는 최대 113,294토큰 입력을 처리했다.

## 6. 만드는 방법

1. **대본:** 지금 생성기(`experiments/delivery_path/validity_specs.py` 계열)에 함정 7종의 사건을 더한다. 필요한 기록, 무효 기록, 정답 집합(속성 조건 포함), UNKNOWN은 대본에서 계산한다.
2. **겉말:**
   - 드러낸 겉말은 지금 같은 틀 문장이다.
   - 숨긴 겉말은 함정별로 쓴 자연스러운 문장이다. 첫 패킷은 아래 5번의 문장 은행 방식으로 만든다.
   - 함정마다 금지어를 둔다. 예를 들어 ①에는 cancel, changed, 취소, 변경을 쓰지 않는다. 문장 틀은 3가지 이상 쓴다.
3. **검색 결과와 잡음:** 검색 결과는 카탈로그에서 결정적으로 만든다. 잡담은 LLM이 쓰고, 대본의 사실과 충돌하지 않는지 검사한다.
4. **확정 전 검사:**
   - **숨김 검사:** 금지어가 없는지만 본다. 단순 규칙이 숨긴 함정에서 실제로 틀리는지는 결과로 보고하고, 자료를 고르거나 고치는 기준으로 쓰지 않는다. 그렇게 하면 결과가 설계로 미리 정해진다.
   - **모호성:** 숨긴 문장의 함축이 대본보다 약하면 고쳐 쓴다. 고칠 수 없으면 모호로 표시해 남긴다.
   - **복원 검사:** 작성자(Claude)와도, 작업자와도 다른 모델이 숨긴 문장만 읽고 대본의 사건을 구조로 다시 적는다. Codex의 독립 검증에서 맡는다. 95% 이상 일치해야 한다. 어긋난 문장은 다시 쓰고 버리지 않는다.
   - **사람 검토:** 숨긴 문장 40개를 무작위로 뽑아 "이 문장이 대본의 사건을 분명히 뜻하는가"를 본다. 38/40 이상이어야 한다.
5. **대본이 새지 않게 하는 규칙 (제 판단):**
   - **기록 목록에 들어가는 기록:** 사용자 발화 원문과, 작업자가 실제로 고른 예약 확인으로만 쓴다. 대본의 사건(무효화 등)을 구조로 적어 넣지 않는다. 그렇지 않으면 숨긴 무효화가 기록에서 드러나 버린다.
   - **단순 규칙 기준선:** "최신 기록만"과 "드러난 표시"는 겉말에 드러난 단서만 쓴다. 단서는 사람·날짜 이름, 취소·변경 같은 말이다. 대본에는 접근하지 않는다.
   - **생성·검사 모델:** 숨긴 겉말을 쓰는 모델과 복원 검사를 하는 모델은 평가할 작업자(9B·27B)와 다른 모델로 한다. 작업자가 자기 문체를 알아보는 이점과, 작업자가 읽을 수 있는 문장만 남는 치우침을 피하기 위해서다.
   - **정답 형식:** 지금처럼 칸별 장소 ID로 유지한다. 보완(②)은 같은 칸을 덮지 않고 새 칸(예: 디저트)을 더하는 사건으로 정의한다.
   - **선택기 입력에서 판정 가능해야 함:** 판단 시점마다 사례에 공개된 진행·관측을 넣고, 무효·필요의 근거가 실제 입력의 어디에 있는지 연결한다. 그 입력만으로 판정할 수 없으면 "정보 부족"으로 표시한다. 그 시점 이후의 사건은 판정에 쓰지 않는다.
   - **효용은 비워 둔다:** 작업자 실행 전 효용 라벨은 null이다. 기존 결과를 새 문장이나 다른 상태에 복사하지 않는다.
   - **첫 패킷의 숨긴 겉말:** Claude가 함정별 문장 은행(유형마다 여러 표현)을 직접 쓰고 사례에 채워 넣는다.
     - 작업자와 다른 모델이 쓴 문장이 된다.
     - 외부 API·GPU 비용이 없다.
     - 표현마다 의미를 한 번씩 검사할 수 있다.
     - 다양성이 부족하면 다음 버전에서 사례별 LLM 생성을 더한다.
6. **고정:**
   - 해시를 기록한다.
   - 파일럿은 기존 첫 자료 가족에서 만든다.
   - 본 자료는 여행 세션에 아직 쓰지 않은 new-a 24가족으로 만든다. 이 가족들은 1단계 실험에서 다른 형식으로 쓰인 이력이 있다. 그래서 실제 manifest로 수와 이력을 확인해 `source-inventory`에 적는다.
   - 봉인된 new-b 40가족은 마지막 확인용으로 남긴다.
7. **첫 납품 (작업자 실행 전 패킷):** 인계 노트의 형식을 따른다.

   | 파일 | 내용 |
   |---|---|
   | `source-inventory.jsonl` | 가족, 부모 출처, 사용 이력, 분할 |
   | `events.jsonl` | 대본 사건. 모델 입력에서는 제외 |
   | `cases.jsonl` | 판단 시점, 공개 진행·관측, 후보 은행, 실제 모델 입력 |
   | `relations.jsonl` | 필요 기록, 조건, 근거 위치, 정보 부족, 모호. 효용은 null |
   | `contrasts.jsonl` | 드러낸/숨긴 겉말, 길이 단계, 상태 변경의 짝 |
   | `review-packet` / `review-key` | 정답을 가린 검토표와 별도의 정답 |
   | `protocol.json`, `manifest.json` | 생성 기준, 분할, 해시 |

   작업자 실행 결과(`outcomes`)는 패킷을 고정한 뒤에 따로 더한다.

## 7. 실행 조건과 측정

**작업자:** Qwen3.5-9B, 27B (지금과 같음)

**조건**

| 조건 | 대응하는 실제 시스템 방식 |
|---|---|
| 무기억 | — |
| 전체 이력을 맥락에 | 원문 보존 |
| 기록 목록 | 계속 쌓기(Mem0 현재 문서) |
| 최신 기록만 | 덮어쓰기(Mem0 논문) |
| 드러난 표시 | 무효 표시(Zep) |
| 관련성 검색 (예산 안 상위) | 표준 검색 |
| 무효 기록만 뺀 기록 (정답 라벨) | 이상적 무효 판정. 재예약·보완 때문에 "최신 기록만"과 실제로 다를 때만 실행하고, CPU로 먼저 확인 |
| 필요한 기록만 (정답 라벨) | 이상적 선택 |

**같은 과거 비교:** 두 작업자가 각자 진행한 세션과 따로, 대본이 정한 하나의 고정 과거를 두 작업자가 함께 읽는 비교를 넣는다. 모델 차이를 과거 차이와 분리하기 위해서다.

**지표**
- 함정 × 겉말 × 길이 단계별 성공
- 같은 상태끼리 짝지은 득실: 무기억 대비, 필요한 기록만 대비. 개선·악화·둘 다 성공·둘 다 실패의 네 유형을 모두 남긴다
- 틀린 답이 일치한 것: 무효 기록 / 남의 기록 / UNKNOWN / 이전 결정과 일치하는 조합 없음. 여러 기록과 동시에 일치하면 모호로 표시하며, 원인 확정 라벨이 아니다
- 옛 기억 사용률, 필요한 기억 누락률, 쓰이지 않은 전달 토큰, 입력 토큰
- 세션 단위 부호 검정

**미리 적는 가설 (자료 채택 기준이 아님)**
- **숨김:** ①번에서 "드러난 표시" 조건의 손해가, 드러낸 겉말보다 숨긴 겉말에서 세션 단위로 커진다.
- **단순 정책:** 각 단순 정책이 적어도 한 함정에서 가장 나쁜 결과를 낸다.
- **길이:** 기록·선택 조건의 손해가 S → L로 커진다.
- 성립하지 않아도 자료를 고치거나 문항을 고르지 않는다. 결과를 그대로 보고한다. 자료의 타당성은 의미 검사(복원 검사, 사람 검토)로만 판단한다.

**멈춤 기준 (자료 품질만):** 파일럿에서 복원 검사가 90% 미만이거나 사람 검토가 38/40에 못 미치면, 본 실행 전에 생성 방법을 고친다.

## 8. 규모 · 비용 · 일정 (추정)

- **파일럿:** 4세션 × 겉말 2 × 길이 S·L, 9B만. 생성기와 검사를 확인하는 단계다.
- **본 실행 기본안:**
  - 24세션 × 겉말 2 × 길이 3.
  - 27B는 S·M만, L은 12세션만, L의 조건은 줄인다.
- **비용 근거:**
  - 지난 20세션 짧은 실행은 9B 6.6 GPU시간(L4), 27B 3.6 GPU시간(G4)이었다.
  - LongMemEval 전체 길이 실행(입력 중앙값 21,021토큰)은 9B 500회에 1.44 GPU시간(G4)이었다.
  - 이를 바탕으로 기본안은 수십 GPU시간 수준으로 예상한다. 파일럿에서 실측한 뒤 규모를 확정한다.
- **일정 (발표 약 11/27 기준):**
  - 생성기·검사 2일, 파일럿 1일, 본 실행 2–3일, 분석 2일.
  - 남는 기간은 발표 준비다.
