# 숨은 함정 기억 자료: 파일럿 패킷 인계 (2026-11-12)

[데이터 보강 인계 노트](ai-memory-data-augmentation-handoff-2026-11-12.md)가 요청한 "작업자 실행 전 검토 가능한 데이터 패킷"의 첫 납품임. 역할 분담(2026-11-12)에 따라 새 원천 데이터는 Claude가 만들었고, 증강과 독립 검증을 Codex에 부탁함.

**검토 후 갱신(2026-11-12):** [92판단·실제 입력 검산](reports/2026-11-12-hidden-memory-traps-pilot-review.md)을 완료함. 모델 내용 검토는 사람 주석과 구분함. UNKNOWN·부가 메시지의 설명을 아래에서 정정했으며, 예산 계산과 작은 선택기의 실제 입력 계약은 수정 대기임. 현재 역할과 누적 세션의 다음 순서는 [통합안](ai-memory-data-cleanup-and-context-stream-plan-2026-11-12.md)을 따름. 원본 데이터·protocol·다른 작업 트리는 변경하지 않음.

## 1. 넘기는 것

- **자료:** [`datasets/hidden_memory_traps/pilot-20261112-v1/`](../datasets/hidden_memory_traps/pilot-20261112-v1/README.md). 14개 파일에 README를 더해 30MB임. 파일과 열의 뜻은 그 README에 있음.
- **생성 코드:** 브랜치 `hidden-traps-data`의 `experiments/hidden_traps/`(커밋 `953217b`, 테스트 71개). 배달 경로 자료처럼 main에는 자료만 넣었음.
- **설계와 구현 계획:** [설계](ai-memory-hidden-memory-traps-plan-2026-11-12.md), [구현 계획](ai-memory-hidden-memory-traps-build-plan-2026-11-12.md). 둘 다 작업 트리에만 있고 미커밋임.
- **규모:** 4세션(Dallas, Buffalo, Seattle, San Diego), 결정 92개, 사례 552개(겉말 2 × 길이 3), 서로 다른 모델 입력 3,468개, 블라인드 검토 문항 58개.
- **검토 완료:** 별도 장부의 92정답, 고유 입력 3,468개, 해시·시점·전달 본문을 확인함. 설계에 이미 노출된 Codex 모델의 숨긴 문장 42개·판단 16개 검토도 일치함.
- **아직 안 한 것:** 독립 인간 검토, 본 자료(20세션) 생성, 실제 작업자 실행. 아래 4절은 최초 인계 시 요청한 검사 목록이며 사람 검토는 계속 미완료임.

## 2. 인계 노트의 요구와 패킷의 대응

| 인계 노트의 요구 | 패킷에서 |
| --- | --- |
| 출처별 원 ID·사용 이력·역할, 원천 가족을 먼저 나눔 | `source-inventory.jsonl` 120행. 파일럿 4·본 20은 travel v2가 쓰지 않은 new-a 24가족이며, Codex 인수 후보 24개와 같은 집합임. 24개 모두 stage1에 쓰인 이력이 `prior_use`에 있음. new-b 40은 sealed, 첫 자료 24가족(증강 11 포함)은 not_used |
| 대본과 공개 문장 분리, 판단 시점까지의 사건만 사용 | `events.jsonl`은 생성 구조이고 모델 입력이 아님. 라벨과 S 입력은 대본을 결정 시점에서 잘라도 같음(1,840개 확인) |
| 무효의 근거가 실제 입력 어디에 있는지 연결 | `relations.jsonl`의 `candidate_relations[*].judge_with` |
| 선택기 입력만으로 판정 가능, 아니면 정보 부족 표시 | 후보 은행은 `cases.jsonl`의 기록 ID에 `records.jsonl` 본문을 이은 것. 예외 요청 원문은 보완됨. 다만 다른 기록을 함께 봐야 하는 주석 20개가 있어, 작은 선택기에 실제로 주는 입력·보조 근거·정보 부족 규칙은 별도 정의가 필요함. 전달 ID만의 확보와 의미적 충분성을 구분함 |
| 같은 실제 입력에 반대 정답이 붙지 않음 | `validate_packet`이 입력 해시마다 정답 충돌을 검사함(통과) |
| 간접 서술의 함축이 대본보다 약하면 모호 | 사람 검토 전이라 `ambiguous`는 null. 최종 검토에서 약하다고 지적된 문장 틀은 다시 썼음(아래 3절) |
| 관계와 효용 분리 | `utility`는 모두 null |
| 같은 조건을 다시 호출하지 않음 | `protocol.json`의 `identical_inputs`(겉말·단계·조건 쌍별로 같은 입력의 수). `invalid_removed`가 `latest_surface`와 같은 것은 겉말·단계마다 92개 중 12개뿐임 |
| 대본 정답을 쓴 삭제는 진단용으로 표시 | `needed_only`, `invalid_removed`는 라벨 기반 진단 조건이라고 README와 protocol에 적었음 |
| 같은 고정 과거를 읽는 비교 | 앞선 턴의 답은 대본 정답으로 고정했음. 두 작업자가 같은 과거를 읽음 |
| 실제 입력에 넣지 않을 필드, 원문·코드 해시 | `protocol.json`의 `never_model_input`, `source_sha256`(원천 6개), `code_sha256`(코드 27개 파일), `tokenizer_sha256`, 그리고 `manifest.json` |

## 3. 최종 검토와 수정

구현을 마친 뒤 새 검토자(opus, 읽기 전용)가 브랜치 전체를 검토했음. 판정은 "수정 후 병합 가능"이었고, 지적을 모두 고친 다음 패킷을 다시 만들었음.

- 열린 예약("그 사람에게 맞는 아무 곳")의 답을 그 사람의 이전 예약에서 베낄 수 있었음(파일럿 제약 8/8, 예외 5/8). 선호를 가진 사람의 다른 예약을 열린 예약 뒤로 옮겼음. 이제 파일럿과 본 20가족 모두 0건임.
- 조건부 참조가 언제나 대체 예약으로 풀렸음. 이제 절반은 첫 예약이 유지됨(대조군, 본 20가족 40 대 40).
- 숨긴 무효화 문장이 과제 문장의 "will not be used"를 되풀이했음. 다시 쓰고, 그 단어들을 금지어에 넣었음.
- 선호 문장 일부가 라벨보다 약했음("어느 하루 저녁 파티", "대부분의 밤" 등). 여행 내내 유지되는 필요로 다시 썼음.
- 부가 메시지가 기록에서 한 줄 요약이 되어, 기록 조건은 길이 단계와 함께 길어지지 않았음. 원문 그대로 넣었고, 이제 L 기록 목록이 7.9만~8.1만 토큰임.
- 예외 예약 기록에 요청 원문이 없었음. 넣었음.
- 닮은 이름 상대의 같은 날 예약이 닮은 이름 함정 밖에서는 '무관'이었음. 이제 모든 요청에서 방해 기록임.
- 검토 결정 문항에 카탈로그와 과제가 없어 정답을 낼 수 없었음. 넣었음.
- 해시와 제외 필드 목록이 없었음. protocol에 넣었음.
- 그 밖에 고친 것: ref_void의 `needs_memory`, 같은 입력이 되는 조건 쌍의 선언, 드러낸 보완 문장과 숨긴 보완 문장의 사건 불일치.

다시 만든 패킷에서 확인한 것:
- 두 번 빌드한 결과의 모든 파일이 같음.
- `validate_packet` 통과.
- 모든 입력에 결정 시점 이후의 요청 번호가 없음.
- 숨긴 겉말의 표시 243개는 모두 변경 기록의 "replaces"에서 나옴. 숨긴 무효화에 붙은 표시는 없음.

## 4. 부탁하는 검사

1. **출처:** `source-inventory.jsonl`과 `protocol.json`의 원천 해시를 Codex 쪽 사용 이력 목록과 대조함.
2. **복원 검사(설계 §6):**
   - `review-packet.jsonl`의 statement 문항 42개(숨긴 문장 틀 전부)만 읽고, 대본의 사건을 구조로 다시 적음. `review-key.jsonl`의 `implies`가 의도한 뜻임.
   - 작성자(Claude)와도, 작업자(Qwen3.5-9B·27B)와도 다른 모델로 함.
   - 목표는 95% 이상 일치임. 파일럿에서 90% 미만이면 본 생성 전에 문장 만드는 방법을 고침. 어긋난 문장은 다시 쓰고 버리지 않음.
3. **입력:** 중복, 상충 정답, 길이, 누락, 미래 정보를 봄. 모델 입력은 `inputs-*.jsonl.gz`의 메시지뿐이어야 함. `never_model_input`에 적은 파일과 필드가 그 안에 섞이지 않았는지 확인함.
4. **포함 여부:** 세션마다 함정 7종이 각 2번 이상 있는지, 대조군이 있는지, UNKNOWN 정답(ref_void, absent)이 있는지 확인함.
5. **사람 검토:** 58문항을 정답 없이 풀고 `review-key.jsonl`과 대조함. 숨긴 문장 42개에는 설계 §6의 기준(무작위 40개 중 38개 이상, 곧 95% 이상이 사건을 분명히 뜻함)을 적용함. 그 결과로 `ambiguous`를 채움.
6. **증강할 때(인계 노트의 규칙):**
   - 같은 가족의 변형은 같은 분할에 둠.
   - new-b는 쓰지 않음.
   - 작업자나 비교 정책의 성패를 자료 채택 기준으로 쓰지 않음.
   - 증강본은 별도 버전으로 둠.

## 5. 알고 써야 할 것

- **설계상 성립하는 것:**
  - 답이 UNKNOWN인 곳에서는 상수 UNKNOWN 출력이 맞음. 실제 무기억 작업자의 성공이나 기억의 손해만을 보장하지 않음. `needs_memory=false`를 실제 제공 정답으로 쓰지 않음.
  - `latest_surface`는 숨긴 무효화에서 무효 예약을 주지 않고, 보완에서는 필요한 예약을 버림.
  - `marked_surface`는 숨긴 무효화를 표시하지 않음.

  각 단순 정책이 어떤 함정에서는 이기고 어떤 함정에서는 지게 만든 구성이므로, 결과를 읽을 때 함정별로 봐야 함.
- **기록 형식:** 기록은 예약 확인, 변경 확인("this replaces …"), 드러낸 취소, 사용자 원문(사건 턴, 예외 예약의 요청, 부가 메시지)으로만 씀. 대본에만 있는 사실은 쓰지 않았음.
- **부가 메시지와 검색 결과:**
  - 부가 메시지는 코드로 만든 표이며 닮은 이름이 포함된 부가 기록 108행이 있음. 새 예약 사실은 추가하지 않음.
  - 검색 결과는 매번 같은 메뉴 목록임.
- **카탈로그:** 원천 카탈로그의 깨진 이름과 이상한 요리 태그가 그대로 있음.
- **설계와 달라진 점:**
  - 예약자는 6명임. 함정 역할에 필요한 예약(사람·날짜) 24개를 채우려면 6명이 필요했음.
  - 가격 상한은 세 번째로 싼 숙소 가격임(설계는 중앙값). 중앙값은 메뉴의 절반을 허용해서, 찍어서 맞힐 확률이 가장 높아짐.
  - 파일럿에 M 단계도 넣었음(설계는 S·L). 상위 집합이라 나중에 빼면 됨.
- **독립 단위**는 세션임.
