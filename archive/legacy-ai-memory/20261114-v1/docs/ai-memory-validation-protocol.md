# 메모리 내용의 이득·손해를 검증하는 다음 프로토콜

2026-11-07 · 최초 설계 제안. 이 제안을 토대로 후속 [32회 파일럿](reports/2026-11-07-prescription-validation.md)을 완료했다. 아래는 당시의 제안이며 실제 범위와 결과는 보고서를 따른다. 문헌의 실험 설계 원리를 현재 데이터의 한계에 적용한 제안이며, 아래 조건·가설은 아직 검증 결과가 아니다.

주 질문은 **같은 대상 문제에서 기억의 특정 부분을 추가했을 때 예산 내 해결률·회귀·비용이 어떻게 달라지는가**다. 전체 기억의 유무와 한 부분의 기여를 나누고, 관측 차이와 원인에 대한 주장을 구분한다.

## 현재 결과에서 출발할 점

- 최근 24회는 세 조건 모두 6/8 해결이었다. 앞선 Sphinx의 개선 후보와 Django의 악화 후보도 조건별 두 반복이라 확정된 효과가 아니다.
- R08에서는 오래된 이름의 검색이 3/4→0/4로 줄었지만 공식 해결은 2/4→1/4였다. 행동 변화는 최종 효용의 증명이 아니었다.
- 기존 부분 삭제 기능 검증은 다섯 조건 모두 2/2 성공이었다. 입력 개입은 확인했지만 이득·손해 방향을 구별하지 못했다.
- 최근 카드의 직접 처방은 현재 과제와 맞는 정도가 낮았다. 같은 저장소·기능군이라는 이유만으로 적합한 평가 쌍이 되지는 않는다.

따라서 다음 실행은 카드 수·반복만 늘리는 것보다, **어떤 부분을 바꾸는가와 그 차이가 드러날 평가 쌍을 먼저 점검**해야 한다. [내용 분석](reports/2026-11-06-memory-content-analysis.md), [R08](reports/2026-11-04-overnight-research.md), [기존 구성요소 검증](reports/2026-11-05-component-measurement-feasibility.md).

## 1. 첫 주 대비는 ‘구체적 처방의 추가 기여’로 좁힌다

출처에 근거한 관측·검증 맥락을 `F`, 과거의 구체적 수정 처방을 `P`, 그 처방의 적용 조건을 구체화한 안내를 `A`로 둔다. source의 공식 판정과 로컬 검증 한계는 모든 메모리 변형에서 유지한다. 원문에 없는 일반 원리를 새로 만들었다면 그것은 별도의 표현 개입으로 기록한다.

| 조건 | 제공하는 내용 | 확인할 물음 |
| --- | --- | --- |
| N | 외부 경험 없음 | 기준 성과·비용 |
| F | 출처 관측과 검증 맥락 | 이 경험 정보를 제공하는 패키지의 전체 효과 |
| F+P | 같은 F에 과거 수정 처방 추가 | F가 있는 상태에서 이 처방을 더하는 기여 |
| F+P+A | 같은 F+P에 구체적 적용 조건 추가 | 처방이 있는 상태에서 적용 안내를 구체화하는 기여 |

```text
주 대비: 처방 추가 효과 = p(F+P) − p(F)
보조 대비: 경험 정보 패키지 효과 = p(F) − p(N)
보조 대비: 적용 조건 구체화 효과 = p(F+P+A) − p(F+P)

같은 대비를 전체 배정의 평균 비용과 회귀 위험에도 적용한다.
```

`p`는 고정된 모델·예산 아래 공식 해결물을 제출할 확률이다. 음의 처방 효과는 **이 F·대상·프로토콜에서 P를 추가하는 것이 평균 해결률을 낮췄다**는 뜻이다. 모든 처방이 해롭다는 뜻이나 매 실행에서 손해가 났다는 뜻은 아니다.

이 대비는 처방 구간의 내용·구체성·길이를 함께 더하는 효과다. 순수한 명령형 말투의 효과라고 부르지 않는다. 같은 정보의 말투·사용 안내 효과는 기존 본문 고정 비교 또는 명제 대응표를 갖춘 별도 재작성 비교로 검증한다.

네 조건은 비용을 줄이기 위한 순차 추가 설계이며 완전 요인 설계가 아니다. A가 P에 특별히 작용하는 상호작용까지 주장하려면 `F+A`를 더해 다음 차이를 확인해야 한다. 지금 네 조건만으로 그 상호작용을 계산하지 않는다.

```text
P×A 상호작용 = [p(F+P+A) − p(F+A)] − [p(F+P) − p(F)]
```

주 효과와 상호작용을 구분하는 설계 원리는 [NIST의 요인 실험 안내](https://www.itl.nist.gov/div898/handbook/pri/section3/pri3331.htm)를 참고한다. 여기서 F/P/A를 정하고 네 조건부터 시작하는 것은 이 프로젝트의 제안이다.

## 2. 효과를 재기 전에 적용성을 점검한다

대상 결과를 보기 전에 공개 문제·초기 코드와 source 근거로 아래를 기록한다. target 정답이나 숨겨진 테스트를 기억 작성·관련성 판단에 넣지 않는다.

| 확인 항목 | 기록할 내용 |
| --- | --- |
| 오류 조건 | 빈 입력·문자열 자료형·문맥 의존 캐시 등 source 처방의 전제가 현재 재현에도 있는가 |
| 코드 경로 | 해당 API·기능이 현재 문제의 경로인가. 이름이 있다는 사실만으로 적합하다고 하지 않음 |
| 버전·표현 | 내부 함수·상태 표현·데이터 형식이 양립하는가 |
| 새로 더하는 정보 | 공개 문제에 이미 같은 원리나 수정 위치가 제시되어 있는가 |
| 근거 범위 | source에서 직접 검증된 관측인가, 추정인가, 공식 미해결 원인은 알려졌는가 |

현재 LabelEncoder 카드의 예로, ‘빈 입력의 반환’이라는 처방은 공개 재현 입력이 비어 있지 않은 OneHotEncoder·군집 지표 문제의 직접 해결책이 아니었다. 이런 쌍만 늘려 놓고 기억의 일반적 효능을 검증했다고 할 수 없다.

먼저 **적용성이 명확한 쌍·약한 쌍·판단 불명**을 구분한다. 명확한 쌍을 확보하지 못하면 source나 평가 질문을 바꾸고, 대량 실행을 먼저 하지 않는다. 각 쌍 안에서는 모든 조건을 비교한다. 적용성이 좋은 문제의 메모리 실행과 나쁜 문제의 무메모리 실행을 직접 비교하지 않는다.

적용성 집단 간 효과 차이는 조절 관계의 단서다. 그 집단들은 난이도 등도 다르므로 적용성 자체 하나의 인과 효과라고 주장하지 않는다. 특정 성질의 원인을 확인하려면 같은 카드의 그 성질을 조작한 대조가 필요하다.

## 3. 측정 체계와 과제의 민감도를 먼저 확인한다

기존 SWE-bench의 문제·환경·테스트를 재사용한다. 새 과제를 전부 사람이 작성할 필요는 없다. 사람의 주요 검토 대상은 source 근거, F/P 경계, 적용 조건과 source/target 관계다.

원본 미해결·정답 패치 해결, 기대 테스트 누락 여부를 먼저 검사한다. 추가 회귀 검사는 실행 전에 범위를 정하고 원본·정답에서도 실행한다. pytest 8906처럼 정답 변경이 기존 로컬 기대값과 충돌하는 사례는 선정 단계에서 기록한다. 사전에 정한 기준으로 제외하거나 별도 층으로 보고하며, 관측한 메모리 성과를 보고 제외하지 않는다. 이 선택을 한 평가 집합은 전체 공식 벤치 점수와 구분한다.

관측상 모든 조건이 성공하거나 모두 실패하는 사례만으로는 성공률 차이에 대한 정보가 약하다. 이미 결과를 분석한 탐색 과제에서 모델·예산·계측을 교정하고, 설정을 고정한 뒤 프로젝트에서 사용하지 않은 확인 과제에 적용한다. 확인 과제의 결과를 보며 예산을 조정하지 않는다. 기준 실행으로 난이도를 선별한다면 모집단이 ‘선별한 과제’임을 밝히고 선별에 쓴 기준 실행을 본 비교의 대조군으로 재사용하지 않는다.

예산별 효용은 에이전트에 예산을 고지한 실제 실행으로 검증할 수 있다. 중간 패치 채점은 언제 정답 상태를 거쳤는지의 진단이다. 긴 실행의 중간 통과를 짧은 예산에서 제출한 성공으로 바꾸어 세지 않는다.

## 4. 최종 득실과 작용 경로를 따로 측정한다

| 층 | 지표 | 주장할 수 있는 범위 |
| --- | --- | --- |
| 최종 성과 | 같은 예산에서 공식 해결물 제출률 차이, %p | 과제·source·모델·예산에 조건부인 평균 성과 기여 |
| 회귀 | 공식 유지 테스트 실패 위험·사전 지정 공통 추가 검사의 변화 | 기준과 비교한 추가 피해. 관측된 테스트 범위 안에서 해석 |
| 자원 | 전체 배정의 API 비용·입출력 토큰·요청 수 | 비용 차이. 성공한 실행만 고르지 않음 |
| 행동 | 실제 적용 조건 확인, 특정 경로 조사, 처방에 해당하는 수정·검사 | 경로의 단서. 그 행동이 최종 성과의 원인이라는 증명은 아님 |

기억이 입력에 들어간 것, 기억과 연결되는 행동을 한 것, 최종 효용이 달라진 것을 구분한다. ‘없는 이름을 한 번 검색’은 현재성을 확인하는 합리적 행동일 수도 있다. 반복된 동일 탐색을 보려면 query·검색 범위·이전 반환 결과·API call ID까지 남긴다. 단순 문자열 부재나 모델의 자기 설명을 손해 라벨로 쓰지 않는다.

행동 기준은 결과 전에 구체화한다. 예컨대 P가 빈 입력 처방이면 빈 입력 분기 수정 여부와 기존 검증 순서 보존 여부를 읽고, cache 처방이면 문맥을 바꾼 재현·키 의존성 조사를 본다. `rg`/`grep`뿐 아니라 읽은 파일·Python 재현·테스트 실행·패치도 포함한다. 해석이 필요한 표본은 조건·최종 결과를 가능한 범위에서 가리고 코드로 판정하며, 불명은 불명으로 남긴다.

코드 메시지 과제의 부분 요구사항이나 중간 진척도도 보조로 기록할 수 있다. 평가 기준을 먼저 정하고 공식 최종 점수와 분리한다. 결과를 본 뒤 통과하는 부분 지표를 골라 주 점수로 교체하지 않는다.

실패를 줄이면서 비용을 더 쓰는 경우와 비용을 줄이면서 실패가 늘어나는 경우는 교환 관계다. 처음에는 하나의 임의 합산 점수로 숨기지 않는다. 실용적 판단이 필요하면 허용할 성과 하락과 추가 비용 기준을 결과 전에 정한다. source 수집·카드 작성 비용과 재사용 횟수, 호스트 평가·검토 비용도 별도 기록한다.

## 5. 배정·통계·확인 절차

각 대상의 조건·반복을 새 환경에서 수행하고 순서를 무작위화한다. 모델·제공자·추론 설정·도구·이미지·기억 위치·예산·source 메타데이터를 고정한다. 조건명·해시 같은 불필요한 단서를 모델 입력에 넣지 않는다. 실제 첫 요청이 선언한 P·A 차이 외에는 같은지 검사한다. 자동 수정·재시도·과제 교체 규칙도 미리 정한다.

주 대비 하나와 의미 있는 최소 차이를 먼저 정하고, 필요한 서로 다른 과제·source 수와 반복 수를 민감도 계산으로 산정한다. 파일럿은 구성과 계측 확인용이다. 세 번·네 번 반복했다는 이유만으로 확증 규모가 되지는 않는다. 같은 source를 공유하는 대상의 의존성과 과제 난이도를 반영하고, API 요청·테스트 개수를 독립 과제 수로 세지 않는다. 실험 설정·변동성·baseline·실험자 선택 편향을 명시하는 원칙은 [Empirical Design in Reinforcement Learning](https://jmlr.org/papers/v25/23-0183.html)과도 일치한다.

효과의 추정치와 불확실성을 함께 보고한다. 성공률 차이가 양수인 점추정만으로 이득을 확정하지 않으며, 넓은 구간이 0을 포함하면 미확정으로 둔다. ‘차이가 유의하지 않음’은 동등성이나 손해 부재의 증거가 아니다. 무해성을 말하려면 허용할 성과 하락 폭을 먼저 정한 비열등성·동등성 질문이 별도로 필요하다.

전체 평균 0도 일부 대상의 이득과 다른 대상의 손해가 상쇄된 것일 수 있다. 대상별 평균 효과의 분포를 함께 본다. 그러나 한 stochastic 실행의 기준 성공·메모리 실패를 확정 유해 라벨로 만들지 않는다. 주변 성공률만으로 개별 실행의 잠재적인 ‘도움받은 비율’과 ‘피해받은 비율’을 각각 복원할 수 없다는 한계는 [측정 노트](ai-memory-measurement-notes.md)를 따른다.

탐색에서 고른 편집·행동 기준·가설은 새로운 확인 문제에서 고정해 검증한다. 카드의 공통 성질로 새 카드의 효용을 예측하려면 source까지 분리한 확인이 필요하다. 최종 실용 검증은 그 예측으로 기억을 제공·보류하는 정책을 항상 제공·미제공과 비교하는 것이다.

## 검증 순서와 완료 기준

1. **내용 감사:** F/P/A 경계와 source 근거를 기록한다. 현재 결과를 보고 만든 부분 구분임을 표시한다.
2. **평가 쌍 감사:** 실제 적용 전제·추가 정보·검사 충돌을 결과 전에 정리한다. 적합한 사례가 없으면 실행보다 source 선정부터 보완한다.
3. **작은 계측 점검:** 실제 입력·행동·제출·채점·비용 연결이 작동하는지 확인한다. 성과 방향의 입증으로 쓰지 않는다.
4. **고정 확인 실험:** 새 문제와 필요한 source 수·반복 수에서 주 대비를 검증한다. 결과에 따른 반복 확대·조건 변경은 별도 회차다.

이 순서에서 기술적 입력·채점·과금 검증은 이미 상당 부분 갖춰졌다. 다음에 해결할 가장 큰 미확정 항목은 적합한 source/target 쌍과 처방 구간의 실제 기여다.

[LabelEncoder 카드로 만든 네 조건 예시](design-data/content-validation-example-20261107.json)는 원문 구간 보존을 확인한 검토용 자료다. 이미 분석한 source를 쓴 **설계 예시**이며 새로운 확인 데이터·실행 은행·실험 계획이 아니다. 이 LabelEncoder 예시를 실행 은행으로 사용한 유료 호출은 하지 않았다. 후속 파일럿은 새로운 SymPy 소스 카드를 사용했다.
