# 메모리 데이터 수집·증강·분류의 통합 방향

2026-11-08. 동료 공유용 현재 설계. [기존 데이터 계약](ai-memory-next-data-contract-2026-11-08.md), [다른 에이전트의 수집 제안](ai-memory-data-collection-and-augmentation-plan-2026-11-08.md), [새 출처 19쌍](design-data/memory-evidence-discovery-20261108-v1/README.md)을 함께 검토했다. 아래 규모는 앞으로의 작업 목표다. 이번에는 문헌 확인·기존 자료 재집계·분류만 했으며 새 원본 수집·효용 측정·학습·GPU 할당·유료 호출은 없다.

**추천 방향은 자연 경험의 폭을 넓히고, 같은 경험이 통하는 조건과 통하지 않는 조건을 실행으로 확인한 뒤, 실제 제공 효과를 작은 선택기의 학습으로 연결하는 것이다.** 바꿔쓰기만 늘리거나 소수 API 사례를 계속 변형하는 것으로 일반화를 주장하지 않는다. 분류는 수집에서 빠진 부분을 찾는 도구이며 최종 연구 목표는 작업자의 성공·악화·비용이다.

## 1. 이번에 합의할 것

| 쟁점 | 통합한 방향 |
| --- | --- |
| 무엇을 수집하는가 | 개별 로그보다 **과거의 어떤 관측이 현재의 어떤 판단에 필요한지 연결된 사례**를 수집한다. 같은 저장소·API 이름은 검색 단서이며 정답이 아니다. |
| 무엇을 늘리는가 | 서로 다른 과거 경험 가족과 현재 문제를 우선 늘린다. 같은 원리가 여러 출처에서 반복되는지 확인하고, 그 안에서 조건 대조를 만든다. |
| 무엇을 학습시키는가 | 관계·적용 전제는 보조 감독, 고정 작업자의 실제 제공 효과는 선택 정책의 감독으로 구분한다. 출처의 성공 여부로 기억의 이득을 대신하지 않는다. |
| 처음 무엇을 비교하는가 | 기존 계약의 **N / P / P+E / P+G**를 내용 보존의 주 비교로 유지한다. 다른 제안의 N/G/F/FP는 별도 질문을 위한 보조 설계다. |
| 무엇을 일반화하는가 | 먼저 **알려진 기억 은행 → 새 현재 문제**를 평가한다. 새 기억·새 저장소·새 버전으로의 전이는 따로 표시하고 추가한다. |
| 파일럿은 어디까지인가 | 작은 묶음은 재현·주석·분기 실행·비용 확인용이다. 그 뒤에도 12묶음 수준에 머무르며 구조 비교를 반복하지 않는다. |

다른 에이전트의 “재사용 관계 확보 → 조건 증강 → 제공 효과 측정”과 두 층의 라벨 생성에 동의한다. 추가로 **현재 입력에 이미 있는 정보**, **직접 복사할 수 없지만 원리를 활용할 수 있는 기억**, **후보가 여러 개일 때의 선택**을 명시적으로 남긴다.

## 2. 현재 자료가 말해 주는 것

- 640쌍 자료는 40개 현재 이슈와 16개 기억의 조합이다. 학습 긍정 18쌍은 기억 10개에 분산돼 각 1–3쌍이고, 여러 현재 저장소에 긍정이 있는 기억은 5개다. 이번에 [재집계 코드와 결과](design-data/collection-augmentation-20261108/coverage.json)를 다시 확인했다. 여기서 긍정은 기존 단일 작성자의 **진단 단서 관련성**이며 실제 도움을 뜻하지 않는다. 효용 라벨은 0개다.
- 새로운 발견 자료는 기억 12개·현재 문제 18개·관계 19쌍이다. 직접 재사용 조건 검토는 조건 불일치 10쌍, 과거 처리가 다른 경로에 이미 존재함 4쌍, 수정 활용 후보 5쌍이었다. 다섯 후보도 실제 도움 사례가 아니다.
- 이번 [분류표](design-data/memory-taxonomy-20261108-v1/README.md)에서 12개 카드의 주된 내용은 입력·출력·API 계약 10개, 수정 절차·순서 2개다. 환경, 실패 복구, 검사 결과도 카드에 있지만 주된 재사용 대상으로 균형 있게 수집된 것은 아니다.
- 기존 학습 실패를 전부 데이터 부족으로 확정할 수 없다. [통합 리뷰](../training/memory_selector/reviews/2026-11-08-integrated/README.md)에서 실제 평가 checkpoint의 사례별 노출은 1–3회였고, 마지막 128 update의 4–5회와 달랐다. 새 데이터와 함께 학습 적합·checkpoint 선택도 고쳐야 한다.

새 발견 자료에서 같은 저장소의 오래된 문제와 나중 문제를 연결하자 다른 작동 원리의 문제가 많이 나왔다. 따라서 다음 수집은 **저장소 수 확대와 재사용 관계의 반복 확보를 함께** 해야 한다. 그렇다고 실제 효과가 좋아 보이는 문제만 골라서는 안 된다.

## 3. 분류는 세 층으로 나눈다

### A. 기억에 남기는 정보

아래는 코드 작업 경험을 위한 실용적인 분류다. 기억 시스템 전체의 표준 분류라고 주장하지 않는다. 한 경험에 여러 종류가 함께 있을 수 있다.

| 코드 | 종류 | 보존할 정보의 예 | 다음에 확보할 대조 |
| --- | --- | --- | --- |
| M1 | 환경·도구 전제 | 도구 부재, 의존성, 초기화, 실제 import 대상 | 필요한 환경 조치 / 이미 충족 / 설치해도 남는 다른 원인 |
| M2 | 입력·출력·API 계약 | 반환값, 원본 변경, None, 버전·플랫폼·형식 | 같은 API지만 반환 위치·옵션·요구가 다른 경우 |
| M3 | 진단·위치 찾기 | 어떤 관측으로 원인과 실패 단계를 좁혔는가 | 같은 오류 문구·다른 원인 / 다른 문구·같은 원리 |
| M4 | 수정 절차·순서 | 캡처와 위임의 순서, 여러 등록·렌더링 경로 갱신 | 선행 작업 필요 / 이미 수행 / 다른 분기만 수정 필요 |
| M5 | 검사 범위·완료 상태 | 무엇을 검사했고 무엇이 미실행·부분 통과인가 | 좁은 검사와 전체 요구 / 다른 환경·선택 범위 |
| M6 | 실패·회피·복구 | 실패한 시도, 그때의 조건, 복구 방법 | 같은 실패 반복 / 원인이 바뀌어 과거 회피가 불필요 |

일화 형태, 요약 형태, 절차 카드 형태는 **표현 형식**으로 따로 적는다. 예를 들어 같은 API 계약을 원문 로그·짧은 사실·지시형 절차로 표현할 수 있다. 내용 종류와 형식을 한 범주로 섞으면 무엇이 개선됐는지 구분하기 어렵다.

### B. 현재 문제에서 무엇을 판단해야 하는가

| 코드 | 선택의 어려움 | 실제 근거 또는 확보해야 할 자료 |
| --- | --- | --- |
| S1 | 표면적으로만 비슷한가 | 같은 structlog라도 문맥 복사와 None 비교 오류는 다른 원리다. |
| S2 | 전제·버전·범위가 달라졌는가 | fsspec의 실제 URI 인식과 콜론이 있는 로컬 파일 오인식은 입력 계약이 다르다. |
| S3 | 이미 알거나 끝낸 일인가 | 과거 처리가 현재 코드에 있거나 문제 본문에 같은 단서가 있다. 현재 문제 전체가 해결됐다는 뜻은 아니다. |
| S4 | 판단에 필요한 관측이 있는가 | wheel 출력 문제에서 로그 handler 스트림을 아직 안 읽었거나, 요청한 날짜 형식이 미정일 수 있다. |
| S5 | 처방 대신 원리를 옮겨야 하는가 | numpydoc 섹션 추가 경험을 내용이 어느 단계에서 사라지는지 찾는 힌트로 활용할 후보가 있다. |
| S6 | 요약하며 근거를 잃거나 과장했는가 | 검사 범위·실패한 대안·전제의 삭제와 복원. 부분 통과를 전체 해결로 쓰지 않는다. |
| S7 | 후보가 중복·충돌하거나 예산을 넘는가 | 여러 기억의 순서·중복·모순·길이를 통제한 별도 자료가 필요하다. |
| S8 | 확인 비용이 작업을 방해하는가 | 확인·수정·검증·제출 시간과 비용을 실제 실행에서 나누어 기록해야 한다. |

기존 19쌍의 잠정 태그는 S1 14, S2 3, S3 7, S4 3, S5 5다. 중복 태그이므로 합산하지 않는다. S6–S8은 이 묶음에서 검증한 자료가 없으며, 현상이 없다는 음성 정답이 아니다. 분류표는 원래 관계 주석과 효용 `null`을 그대로 보존한다.

실제 주석에서는 “전제가 맞음/틀림/부분적으로 맞음/모름”, “현재 관측에 새 정보인가”, “직접 적용/수정 활용/진단 후보인가”를 각각 기록한다. 태그 S1–S8은 수집·오류 분석의 축이지, 그대로 예측할 단일 정답 클래스가 아니다. 특히 **전제 미확인과 전제 불일치, 이미 알려진 정보와 가치 없는 정보는 다르다.**

### C. 제공한 뒤 실제로 무엇이 달라졌는가

같은 초기 상태에서 N과 특정 기억 행동을 실행했을 때 **개선 / 악화 / 둘 다 성공 / 둘 다 실패**를 구분한다. 성공이 같아도 비용 차이가 있으므로 토큰·지연·검사·제출을 별도로 기록한다. 미실행은 `null`이지 중립 0이 아니다.

관계 주석은 효과를 설명하거나 예측하는 감독이다. 실제 작업자는 부적합한 기억을 무시하거나 수정할 수 있으므로, 적용 불가를 자동으로 피해 라벨로 바꾸지 않는다. 한 번의 행동 쌍은 관측 차이이고 기대 효과를 확정하는 정답이 아니다.

## 4. 새 출처를 모으는 경로와 선별 규칙

주 수집원은 이미 사용하는 [SWE-rebench 실행 로그](https://huggingface.co/datasets/nebius/SWE-rebench-openhands-trajectories)로 유지한다. 여러 parquet 구간의 **메타데이터부터** 넓히고 필요한 원문만 읽는다. 공개 로그에는 행동·관측·패치·종료 정보가 있지만 동일 현재 상태에서 기억 제공/보류한 효과는 따로 측정해야 한다.

보조 경로는 과거 이슈·PR·문서 이력과 [SWE-smith의 검증 가능한 코드 변형](https://swesmith.com/guides/create_instances/)이다. PR만 있으면 “PR 기반 사실 기억”으로 표시한다. 실제 로그가 없는 실행 경험을 만들지 않는다. SWE-smith 방식의 결함은 자연 발생 이슈와 구분한다.

수집 단위는 다음 연결이다.

> 과거의 관측·행동·검사 범위 → 보존한 정보 조각 → 현재 선택 전에 볼 수 있는 전제 → 그 전제를 쓰는 판단 → 실제 행동별 결과

1. 먼저 출처 경험에서 기억과 적용 전제를 작성하고 해시를 고정한다. 현재 대상의 미래 풀이를 보고 과거 기억에 정답 단서를 추가하지 않는다.
2. 현재 문제 설명과 base 코드의 API·설정·관측 가능한 오류로 후보를 찾는다. BM25·임베딩은 후보 제안 도구이며 유익성 판정기가 아니다. 같은 저장소의 일치와 저장소를 넘는 원리 재사용을 둘 다 허용한다.
3. 각 연결에 **어느 원문 관측이 현재의 어느 판단을 돕는지 한 문장과 근거 위치**를 남긴다. “둘 다 파싱 버그” 수준이면 미확인 또는 제외 후보로 남긴다.
4. 직접 조건이 맞는 사례, 같은 주제 안의 가까운 불일치, 이미 완료·이미 알려짐, 관측 부족을 함께 찾는다. 모든 출처에 모든 유형을 억지로 만들지 않는다. 무관한 음성만 대량 생성하지 않는다.
5. 같은 이슈 반복, 포맷 복제, 공통 코드·결함 가족을 표시한다. merge 이력과 현재 base의 관계, 경험 로그의 생성 시점은 별도 기록한다. PR이 먼저 생겼다는 사실만으로 그 에이전트 경험이 당시에 이용 가능했다고 쓰지 않는다.
6. 원문 후보 → 실제로 읽은 근거 → 관계 검토 → 재현 가능 → 효용 측정을 각각 집계하고 제외 이유를 남긴다. 제목만 읽은 후보는 음성 라벨이 아니다.

현재 12개 기억과 18개 문제는 이 절차의 설계 자료다. 다음에는 **동일한 기억이 직접 성립하는 자연 사례와 가까운 조건 불일치가 함께 있는 관계**를 우선 찾는다. 현재의 수정 활용 후보만 계속 늘리면 “언제 그대로 쓸 수 있는가”가 또 비게 된다.

## 5. 증강은 바뀌는 대상과 정답을 함께 적는다

| 방식 | 예시 | 관계 라벨 | 실제 효용 라벨 |
| --- | --- | --- | --- |
| 표현만 변경 | 어순·문장·동일한 사실의 서술형/지시형 | 사실·수량·범위·부정·식별자를 검사한 뒤 유지 여부 결정 | 작업자가 받는 표현이 달라지므로 기존 결과를 새 관측처럼 복사하지 않음 |
| 현재 전제 변경 | 실제 버전·옵션·반환 계약·원본 보존 요구 변경 | 실제 코드·환경을 확인하고 다시 판정 | 새 상태에서 다시 측정 |
| 관측 가림 | 반환값이나 설치 상태에 대한 선택기 관측 일부 제거 | 다른 단서로 판단 가능한지 확인; 자동으로 미확인 처리하지 않음 | 선택기만 가렸는지 작업자도 바꿨는지 명시; 후자면 재측정 |
| 기억 조각 삭제·복원 | 동일 출처의 조건 E·실패한 시도·검사 범위 추가/제거 | 근거가 남은 범위를 다시 판정 | 동일 snapshot에서 내용 개입 실행 |
| 가까운 후보·충돌 추가 | 같은 함수의 다른 버전 기억, 중복 요약, 무관한 기억 | 각 후보와 후보 사이의 관계 검토 | 후보 집합·순서·제공량을 고정한 별도 정책 평가 |
| 새 자연 출처 | 같은 반환 계약이나 검사 경계가 다른 저장소에 등장 | 새 근거로 판정 | 새 문제에서 측정; 이는 표현 증강이 아니라 출처 확대 |

선택기만 보는 관측을 가리고 작업자의 정확한 입력·상태·행동이 변하지 않는 진단에서는 기존 작업자 결과를 참조할 수 있다. 이때도 **같은 결과를 참조하는 파생 행**으로 기록하고 독립 실행으로 세지 않는다. 작업자 입력, 기억 문구, 실행 상태 중 하나라도 바뀌면 효과가 유지된다고 가정하지 않는다.

조건 변형은 문장 속 버전 숫자를 바꾸는 것으로 끝내지 않는다. 환경·코드·기대 동작을 실제로 맞추고, 결함이 존재하는지와 수정 가능한지를 검사한다. 일부 관측 삭제는 정보 제한 진단이지 자연적으로 발생한 새 작업이라고 쓰지 않는다.

[CheckList](https://aclanthology.org/2020.acl-main.442/)의 능력×검사 유형 구성, [Contrast Sets](https://aclanthology.org/2020.findings-emnlp.117/)의 작은 의미 변화, [Counterfactually-Augmented Data](https://arxiv.org/abs/1909.12434)의 최소 수정·내부 일관성을 참고했다. 이 연구들이 코드 기억 효용의 개선을 보장하는 것은 아니다. 여기서는 검증 가능한 변형을 만드는 원칙을 가져온다.

첫 배치에서는 원형 하나에 소수의 검증된 변형만 붙이고, 학습 시 부모 가족 단위의 표집·가중치를 둔다. 증강 자식이 많은 한 경험이 학습을 독점하지 않게 한다. 숫자·길이·기억 ID만으로 정답을 맞힐 수 있는지 현재 입력만/기억만/단순 규칙 기준선도 확인한다.

## 6. 작은 파일럿에서 실제 규모의 자료로 넘어간다

| 단계 | 작업 목표 | 완료 기준 |
| --- | --- | --- |
| 준비 확인 | 기존 후보 중 4–8개 현재 문제, 필요하면 최대 12개 연결 묶음 | 요구·채점 계약, 환경, 무기억 공통 조사, 복원 가능한 snapshot, 네 행동 분기와 비용 기록이 작동함 |
| 첫 확대 | 서로 다른 현재 문제 약 100개와 30–50개 과거 경험 가족을 향해 수집 | 유형별 근거와 주석 수율, 실제 실행 가능 비율, 고정 정책 대비 선택 여지를 보고 |
| 본 수집 목표 | 서로 다른 현재 문제 300–500개와 여러 저장소에 걸친 경험 가족 | 자연 사례·재구성·변형·반복을 따로 집계하고 고정 개발 자료에서 학습 곡선 확인 |
| 독립 확인 | 방법을 고를 때 보지 않은 현재 문제·가족 | 최소 관심 효과와 파일럿의 변동·군집 구조에 맞춰 표본 수·반복·분석 계획을 먼저 고정 |

준비 확인에는 이미 검토한 후보를 먼저 사용한다. 별도의 12묶음을 처음부터 다시 만들어야 한다는 뜻은 아니다. 요구·환경·채점 계약이 성립하지 않는 후보는 이유를 남기고 교체하며, 교체를 실제 기억 효과의 좋고 나쁨으로 결정하지 않는다.

**위 수는 작업량 목표이지 일반화나 통계적 충분성의 보장이 아니다.** 같은 저장소의 서로 다른 이슈도 완전히 독립이라고 가정하지 않는다. 18개 문제에 대한 수천 조합보다 서로 다른 문제와 경험 가족의 폭이 먼저다. 표본 수는 원하는 효과와 변동에 좌우되며 작은 표본의 한계를 정확도 하나로 해결할 수 없다. [검정력 논의](https://aclanthology.org/2020.emnlp-main.745/).

최초 세 집중 영역은 다른 제안과 맞춰 동작·데이터 보존, 버전·설정 전제, 검증 범위로 둔다. 다만 M3 진단과 M6 실패 복구를 영구히 배제하지 않는다. 한 유형이 한 저장소나 한 문구에만 묶이지 않도록 출처를 배치하고 부족한 칸을 공개한다.

자료는 **조건을 고르게 채운 진단 집합**과 **정한 수집 범위의 연속·층화 표집으로 만든 자연 문제 평가 집합**을 구분한다. 학습 후보는 불일치·희귀 관계를 우선 검토할 수 있으나, 그 비율을 실제 배포 빈도로 해석하지 않는다. 최종 확인은 효과가 난 사례만 남겨 구성하지 않는다.

예산은 원본 수집 비용과 작업자 실행 비용을 나눈다. 한 후보의 N/P/P+E/P+G를 300–500개 상태에서 한 번씩 실행하면 1,200–2,000개 작업자 실행이며 초기 조사·반복·실패 재준비는 별도다. API 요청 수나 확정 비용과 같지 않다. 첫 배치에서 실제 실행당 비용을 재고 다음 배치 규모를 정한다. 이 문서는 그 실행을 이미 시작했거나 자원을 예약했다는 뜻이 아니다.

## 7. 제공 조건과 후보 선택의 역할을 구분한다

현재 내용 보존 질문의 주 비교는 다음과 같다. P와 E는 같은 출처에서 작성한다.

| 행동 | 내용 | 주 비교 |
| --- | --- | --- |
| N | 무기억 | 작업자의 기본 성과와 비용 |
| P | 구체적인 과거 절차 | 절차 제공 효과 |
| P+E | 같은 P + 전제·관측·검사 범위 | 생략된 정보를 보존한 묶음 효과 |
| P+G | 같은 P + 길이를 맞춘 일반 안내 | 단순한 추가 안내·길이와 비교 |

P+G는 일반 안내만 제공하는 G와 다르며, G도 무효한 위약이 아니다. 길이·위치·절단 규칙을 고정한다. 원문 근거를 제공하는 별도 진단은 원문량과 처리 비용을 함께 기록한다.

다른 제안의 N/G/F/FP는 “사실 F에 절차 P를 추가하면 어떤가”를 보는 보조 설계로 남긴다. F가 이 문서의 E와 정확히 같다면 FP는 P+E와 대응할 수 있지만 **이름만으로 동일 조건이라고 간주하지 않는다.** 첫 주 비교와 합쳐 여덟 조건을 무조건 실행하지 않는다.

첫 준비 확인 이후에는 **여러 후보 가운데 선택하는 실험을 별도로 고정해 이어간다.** 같은 기억 한 개의 제공/보류만으로 여러 기억을 잘 고르는 모델이라고 주장할 수 없기 때문이다.

- 알려진 은행에서 현재 정보만으로 검색한 후보 K개를 고정한다. 처음에는 K=3 정도의 제한된 후보로 시작할 수 있다. 후보 누락과 선택 실패를 분리한다.
- 여러 후보 비교의 초기 행동은 N 또는 각 후보의 P+E 하나 제공으로 단순화할 수 있다. 이 확장은 기존 N/P/P+E 행동 공간과 다른 버전의 프로토콜로 고정한다. 내용 비교는 미리 정한 부분 집합에서 이어간다.
- N, 검색 1위 항상 제공, 유사도 문턱, 전제 규칙, 학습 선택기를 같은 은행·후보·비용 한도에서 비교한다. 작업자 직접 선택 기준선에는 그 판단 비용도 더한다.
- 관측한 후보 중 최선은 **그 후보 안에서의 관측 상한**이다. 은행 전체 최선이라고 쓰지 않는다. 개발에서 고른 고정 기억이 후보에 없으면 별도 실행을 확보해야 그 기준선과 비교할 수 있다.
- 모든 기억 제공은 예산 안에 들어갈 때만 비교한다. 은행 크기, 검색 후보 수 K, 실제 제공 토큰을 따로 기록한다. 후보 조합·순서·충돌은 S7의 후속 패널이며 첫 실험에 모두 섞지 않는다.

관계 라벨로 계산한 후보 재현율은 유익한 기억의 재현율과 다르다. 검색을 개선해도 선택 정책의 실제 이득이 자동으로 입증되지는 않는다.

## 8. 주석·분할·학습에 필요한 최소 계약

기존 기록에 다음 필드를 연결한다. 아직 실행되지 않은 필드는 비워 두고 준비 완료로 표시하지 않는다.

- 계보: source episode, memory version, target issue/base commit, parent family, 파생 방식, 실제/재구성 구분, 원문·코드 해시.
- 정보 경계: 공통 무기억 조사 명령·관측·비용, 선택 시점의 전체 snapshot, 선택기와 작업자에게 각각 보이는 정보, 기억 은행·검색 버전.
- 주석: 정보 종류, 전제별 근거 위치와 충족/충돌/미확인, 현재에 이미 있는 단서, 직접/수정/진단 활용 후보, 작성자·검토자·이견.
- 결과: 작업자·모델 revision·프롬프트·예산·행동·반복, 성공·회귀·제출, 단계별 비용, 중단·환경 오류, 실제 실행 artifact.

기존 긍정 18쌍과 논쟁적인 근접 사례는 독립 검토의 우선순위로 삼는다. 새 핵심 조건 대조도 두 번째 검토와 실행 근거를 확보하고, 나머지는 유형별 무작위 품질 검토를 더한다. 독립 검토자가 아직 참여하지 않았으면 잠정 라벨로 남긴다. 분류표 19쌍 역시 이번 한 에이전트의 재분류다.

출처와 부모 가족을 정한 뒤 증강한다. 같은 문제·코드 결함의 자식, 표현 변경, 반복 실행은 같은 분할에 둔다. 알려진 은행 실험에서 공유 기억 하나가 연결됐다는 이유만으로 모든 현재 문제를 한 그룹으로 합치지는 않는다. 대신 은행 공유를 명시하고 현재 문제·공통 결함 가족의 누출을 막는다. 새 기억 전이 실험은 출처 은행까지 분리한다.

공식 target 정답·미래 명령·기억 제공 뒤의 상태를 선택기 입력이나 검색 키로 쓰지 않는다. 과거 시점 복원에 못 미친 자료는 “과거에 실제 이용 가능한 기억”이라고 주장하지 않는다. 현재 연구자가 읽은 코드는 실제 작업자가 공통 조사에서 보았다는 근거를 대신하지 않는다.

학습은 먼저 일관된 학습 부분을 충분히 맞추는지 확인하고, 전체 정확도 외에 조건별 판독·기억별 선택·보류율을 본다. 증강 비교는 원자료만 / 표현 변형 / 조건 대조 / 새 출처 추가를 구분하고 계산량·가족별 노출·선택 checkpoint의 적합을 함께 기록한다. 50→100→200 문제 등의 학습 곡선은 고정 개발 자료에서 본다. 최종 확인 집합으로 반복 선택하지 않는다.

## 9. 연구와 연결되는 지점

[Memory Tax](https://arxiv.org/html/2610.34073v1)는 보존된 정보와 그 정보에 접근하는 과정 등을 구분해 분석한다. 따라서 소실된 근거 복원과 검색 실패를 다른 문제로 둔다. [BASM](https://arxiv.org/html/2608.22339v1)은 절차와 적용 조건·위험·회피·복구 정보를 구조화한다. 이번 M1–M6와 S2·S6는 이런 구조를 코드 경험의 관측 근거에 연결하려는 설계다.

[MemHarness](https://arxiv.org/html/2607.28272v1)는 현재 상태에 맞춘 기억의 수정·거절과 최소 상태 변화 진단을 다룬다. 그 아이디어는 S5와 조건 변형에 참고하되, 텍스트 진단을 실제 SWE 환경·작업자 효과와 동일시하지 않는다. [SWE-smith](https://arxiv.org/abs/2504.21798)는 실행 가능한 결함 합성의 선례이며 기억 선택의 효용 정답을 제공하는 선례는 아니다.

우리가 만들 수 있는 구체적인 기여 후보는 **출처의 어떤 정보가 현재 조건에서 어떻게 쓰이고, 실제 성공·비용에 무엇을 더하는지 연결한 자료와 평가**다. 분류표 자체나 선택기를 붙였다는 사실만으로 새로움을 주장하지 않는다. 단순 고정 제공·검색·규칙보다 학습 선택기가 나아지는지는 이 자료에서 검증할 질문이다.
