# AI 메모리 득실을 검증하는 실험 설계

2026-11-02 · 제안 단계 · 이 문서의 실행 수와 예시는 실험 결과가 아님

2026-11-04 실행 후 보완: 실제 작은 비교와 재현 결과는 [야간 보고서](reports/2026-11-04-overnight-research.md), 해석상의 구분은 [측정 노트](ai-memory-measurement-notes.md)에 기록한다. 아래 독립 실행의 관측 전환 `H=p0(1−p1)`와 측정 노트에서 정의한 동일 대상의 잠재 결과 피해 비율 `H=P(Y0=1,Y1=0)`는 서로 다른 양이다. 전자는 관측 빈도를 기술하며 후자는 주변 성공률만으로 식별되지 않는다. 같은 기호를 같은 인과 지표로 합쳐 쓰지 않는다.

2026-11-03 재검토 및 전달 방식 추가: 현재의 첫 실행 권고는 [연구 방향 재검토와 첫 실험 실행안](ai-memory-pilot-reassessment.md)이다. 과제 연결 가능성과 Lite–Verified 중복을 먼저 점검하고, 첫 비교는 **무메모리 / 시작 시 제공 / 에이전트의 자율 검색**으로 갱신했다. 기존 재배정 대조와 아래 3절의 원본·요약 비교는 후속 진단으로 활용한다. 같은 카드의 지연 조회 대조와 전체 배정 실행을 분석하는 규칙은 현재 실행안 4절을 따른다. 효과의 정의와 개입·통계·비용에 관한 원칙은 유지한다.

**첫 목표는 작은 재현 실험으로 효과와 사례를 확보하고, 그중 한 현상을 개입으로 확인하는 것이다.** 전체 벤치 성능, 모든 실패 원인, 정보와 행동 지침의 차이, 장기 축적 효과를 한 실험에서 동시에 결론내리지 않는다. [문헌 검토](ai-memory-benefit-harm-review.md)의 근거를 바탕으로, 기존 [스케치](ai-memory-research-sketch.md)를 실행 가능한 비교와 판단 기준으로 구체화했다.

**1. 무엇의 효과인지 먼저 명시한다.** 첫 실험의 대상은 ‘고정된 과거 경험을 새 과제에 시작부터 제공하거나, 에이전트가 필요할 때 찾아보도록 하는 정책’이다. 자율 검색과 시작 제공의 차이에는 시점·조회 여부·내용 선택·비용이 함께 들어 있다. 같은 카드 대조로 내용 차이를 제거해도 자율 조회 여부와 호출 비용은 남는다. 모델 가중치 학습, 같은 문제의 정답 피드백을 받은 재시도, 평가 중 기억이 계속 바뀌는 온라인 학습은 별도 단계로 둔다.

과제 `i`, 조건 `a`, 반복 `r`의 공식 채점 결과를 `Y[i,a,r] ∈ {0,1}`로 둔다. 고정된 모델·환경·예산에서 실행의 변동성을 평균낸 성공 확률은 `p[i,a]`다. 과제별로 같은 가중치를 주는 주 효과는 다음과 같다.

```text
Δsuccess = (1/N) × Σ_i {p[i, memory] − p[i, no_memory]}

추정값 = (1/N) × Σ_i {조건별 반복 성공률의 차이}
```

이 값이 양수면 지정한 평가 집합에서 평균적으로 이득이다. 고정된 저장소 하나로 얻은 결과는 **그 저장소에 조건부인 효과**다. 기억 생성 방법 일반의 우수성을 주장하려면 다른 경험 수집 집합이나 저장소에서도 확인해야 한다. 같은 저장소에서 모든 실행이 손해를 보는 것은 아니어도 평균 손해는 측정할 수 있다.

실용적 효과와 통제된 효과도 구분한다. 실제 시스템처럼 요약하면 짧아지는 효과까지 포함한 비교는 의미가 있다. 그러나 “지침의 의미가 좋아서 개선됐다”는 주장은 입력 길이, 추가 모델 호출, 검색 결과와 적용 시점까지 통제한 후속 비교가 필요하다.

**2. ‘관측된 득/실 전환’과 ‘기억이 유발한 피해’를 구분한다.** 메모리 없이 성공할 확률이 `p0`, 메모리와 함께 성공할 확률이 `p1`이고 두 실행이 독립이라면 다음과 같다.

```text
관측되는 실패→성공 확률 R = (1 − p0) × p1
관측되는 성공→실패 확률 H = p0 × (1 − p1)
R − H = p1 − p0

p0 = p1 = 0.5이면 R = 0.25, H = 0.25, 순효과 = 0
```

즉 `H` 자체는 인과적 피해율이 아니다. 같은 API seed를 사용해도 서로 다른 프롬프트의 실행이 동일한 우연성을 공유한다고 보장할 수 없다. 한 실행의 ‘기억이 없었을 때 실제로 어떻게 됐을지’와 ‘있었을 때 실제로 어떻게 됐을지’를 동시에 관측할 수 없다는 문제도 남는다.

MemDev-Bench는 과제별 두 조건의 3회 실행에서 가능한 9개 조합으로 rescue/harm을 계산한다. 무메모리 성공 수가 `k`, 메모리 성공 수가 `m`이면 각각 `(3−k)m/9`, `k(3−m)/9`다. 이는 관측 전환을 기술하고 순성공률 차이를 분해하는 데 유용하다. **9개 조합이 9개의 독립 실험이 되는 것은 아니다.** [논문 Appendix H](https://arxiv.org/html/2610.27524v1)

주 결과는 성공률 차이와 불확실성으로 보고하고, 전환은 사례를 찾는 보조 지표로 쓴다. 과제별 기대 효과 `Δi = p[i,memory] − p[i,no_memory]`를 알 수 있다면 다음 분해도 가능하다.

```text
기대 이득의 크기 G = mean_i max(Δi, 0)
기대 손해의 크기 L = mean_i max(−Δi, 0)
평균 효과 Δ = G − L
```

그러나 반복이 적을 때 관측 성공률을 그대로 대입하면 우연한 흔들림만으로 `G`와 `L`이 모두 부풀려진다. 첫 파일럿의 확정 지표로 사용하지 않는다. 개별 과제를 ‘해로운 기억의 정답 사례’로 선언하기 전에 추가 실행, 독립적인 확인, 필요하면 계층모형에 의한 추정이 필요하다.

**3. 원본·요약의 후속 비교는 다음처럼 구성할 수 있다.** 아래는 초기 설계에서 남긴 표현 방식 비교안이며 현재의 첫 실행 조건은 아니다. 수량은 효과를 입증하기 위한 표본 수 계산이 아니라 실행 부담을 확인하기 위한 예시다.

| 구성 | 예시 규모 | 목적 |
| --- | --- | --- |
| 환경 점검 과제 | 별도 2–3개 | 실행·저장·채점이 되는지 확인 |
| 경험 수집 과제 | 10개 × 1회 | 실제 성공·실패 이력 확보 |
| 평가 과제 | 다른 10개 | 고정된 기억의 전이 관찰 |
| 평가 조건 | 무메모리 / 원본 경험 / 요약 기억 | 경험 접근과 정리 방식 비교 |
| 평가 반복 | 조건별 3회 | 우연한 전환과 변동성 관찰 |
| 기본 실행 수 | `10 + 10×3×3 = 100회` | 점검·요약 생성·재채점 비용은 별도 |

반복 3회는 강한 통계적 입증에 충분하다는 의미가 아니다. 이 규모에서 얻을 것은 파이프라인, 대략적인 효과, 개입해 볼 후보 사례다. 모델·벤치 선택 후 실제 과제당 비용을 재어 다음 단계의 표본 수를 정한다.

이 표현 방식 실험의 세 조건 차이는 아래처럼 제한한다. A/B/C 표기는 이 절 안에서만 사용한다.

| 조건 | 에이전트가 받는 과거 경험 | 해석 |
| --- | --- | --- |
| A: 무메모리 | 없음 | 현재 과제의 원래 정보와 기본 에이전트의 기준점 |
| B: 원본 경험 | 선택된 과거 실행 기록 | 과거 경험에 접근하도록 하는 정책의 효과 `B−A` |
| C: 요약 기억 | B와 같은 출처를 정리한 기억 | 표현·압축·추출 정책의 효과 `C−B`, 전체 효과 `C−A` |

표현 방식만 비교하는 이 후속 실험에서는 시작할 때 한 번 제공하고 동일한 출처를 쓰도록 과제별 검색 결과 ID를 미리 고정한다. 자율 검색의 비교는 현재 실행안에서 별도로 수행한다. 검색 쿼리는 현재 문제 설명과 허용된 현재 환경 정보만 사용하며, 정답 패치나 미래 실행 결과는 쓰지 않는다.

이용 가능한 과거 경험이 없는 과제에 미래의 기록을 배정하지 않는다. 그런 과제의 빈 기억 처리와 집계 방식을 미리 정하고, 전체 과제 중 실제로 기억을 제공한 비율도 보고한다. 관련 과거 경험이 있는 과제만 고른 실험이라면 그 조건을 명시한다.

B와 C의 토큰 수가 다르면 첫 비교는 자연스러운 길이 차이를 포함한 정책 비교로 해석한다. 원본이 너무 길면 사전에 정한 절단 규칙을 적용하고, 실제 전달된 부분을 보존한다. 모든 조건의 모델·도구·계산 상한을 맞추되, 같은 행동 수가 같은 토큰 비용을 뜻하지는 않으므로 실제 사용량도 기록한다.

**4. 새 문제를 만드는 대신 실제 기록에서 기억을 만든다.** 최소 단위는 ‘정답처럼 보이는 교훈’이 아니라 **출처가 있는 관측과 그로부터 추정한 규칙**이다.

| 필드 | 내용 |
| --- | --- |
| 출처 | 과제 ID, 저장소·커밋·환경, 실행 ID, 원본 로그 위치 |
| 관측 | 실제 명령, 도구 반환값, 발견한 파일·사실 |
| 시도와 결과 | 어떤 접근을 했는지, 어디까지 확인됐는지 |
| 최종 결과 | 공식 성공/실패, 시간 초과·환경 오류 등 별도 상태 |
| 추출한 교훈 | 관측에서 도출한 재사용 후보 규칙 |
| 적용 조건 | 어느 버전·상태·목표에서 성립하는지 |
| 불확실성과 반증 | 확인하지 못한 부분, 적용을 중단할 관측 |

관측과 추정을 구분하는 추출 프롬프트를 하나 고정하고, 모든 기억에 원본 근거를 연결한다. 시작부터 사람이 모든 기억을 ‘좋음/나쁨’으로 판단하지 않는다. 출처 충실성에 대한 작은 표본 검토와, 실제 행동에 영향을 준 후보의 정밀 검토에 시간을 쓴다.

실패 기록에서는 “마지막 패치가 채점을 통과하지 못했다”와 “특정 명령이 실패의 원인이었다”를 구분한다. 환경 장애나 예산 소진도 문제 해결 전략의 오류로 자동 번역하지 않는다. 성공 기록에서도 모든 중간 행동을 성공 원인으로 간주하지 않는다.

수집용 과제의 최종 공식 결과를 기억 추출에 사용할지는 미리 정한다. 사용하면 ‘검증기 피드백이 있는 과거 경험’ 설정이다. 운영에서 그러한 피드백을 얻을 수 없는 경우와는 다르다. 평가 과제의 숨겨진 테스트·정답 패치·최종 채점 결과는 실행 종료 전 에이전트나 기억 생성기에 주지 않는다.

**평가 누출을 막는 분리 규칙도 데이터 제작의 일부다.**

1. 수집·탐색 평가·최종 확인용 문제 ID를 분리하고, 같은 해결책의 중복 문제도 점검한다.
2. SWE의 저장소별 과거 경험은 평가 코드 시점에 이용 가능했어야 한다. 이슈 날짜만 보지 말고 관련 커밋의 선후관계와 분기를 확인한다.
3. 평가 동안 기억 저장소와 검색 결과를 고정한다. 한 조건의 패치·로그·캐시가 다른 조건으로 넘어가지 않게 한다.
4. 난이도 선정을 위해 무메모리 결과를 보았다면 평가용 기준 실행은 새로 수행하고, 선정된 집단의 결과임을 밝힌다.
5. 실패한 문제만 고르면 원래 풀던 문제의 회귀를 볼 수 없으므로, 첫 결과를 보고 평가 집합에서 성공 문제를 제거하지 않는다.

동일 과제를 다시 푸는 실험도 가능하지만, 그것은 별도로 ‘동일 과제 재시도’라고 부른다. 다른 과제로의 기억 전이와 섞어 성과를 보고하지 않는다.

**5. 특정 기억이 손해를 만들었다는 주장은 단계적으로 확인한다.** 먼저 전체 실행을 반복하고, 가능할 때 중간 상태 실험을 추가한다.

| 단계 | 비교 | 확인하려는 것 |
| --- | --- | --- |
| 후보 발견 | 무메모리 / 원래 기억 | 평균 차이와 의심되는 행동 발견 |
| 항목 제거 | 원래 기억 M / 의심 항목을 뺀 M | 해당 항목이 있는 것이 결과를 악화시키는지 |
| 내용 교정 | M / 조건·사실 한 부분만 고친 M | 단순히 적게 읽어서가 아니라 내용 때문에 달라지는지 |
| 제거 대조 | 의심 항목 삭제 / 비슷한 길이의 다른 항목 삭제 | 길이·위치·일반적인 부담 감소로 설명되는지 |
| 재제공 | 삭제한 항목을 다시 제공 | 같은 방향의 행동·성과 변화가 돌아오는지 |
| 별도 확인 | 새로운 실행·유사한 별도 과제 | 발견에 사용한 우연한 사례에만 맞춘 설명인지 |

모든 조건은 같은 초기 환경에서 새 실행으로 비교하고 순서를 무작위화한다. 한 번의 삭제 후 성공은 후보 증거다. 정밀 확인에 사용할 조건과 반복 수는 확인 실행 전에 고정한다. 중립적인 문장으로 길이를 맞추더라도 완전히 영향이 없는 입력이라고 가정하지 않으며, 원본 삭제와 길이 대조를 함께 해석한다.

예를 들어 실제 로그에서 과거 환경의 명령 옵션을 현재 환경에도 계속 쓰는 현상이 발견됐다고 하자. 다음은 **설계 설명용 가상 예시**다.

```text
과거 관측: 환경 v1에서 tool build --fast가 실행됐다.
의심 지침: 빌드할 때 tool build --fast를 사용하라.
조건 복구: 현재 버전에서 --fast 지원을 확인한 경우에 사용하라.
대조 수정: 비슷한 길이의 일반적인 ‘출력을 확인하라’ 조언을 추가한다.

측정: 옵션 확인 → 명령 선택 → 지원 오류 이후 반복 여부 → 최종 성공·비용
```

조건 복구로 지원 확인이 늘고, 잘못된 반복이 줄고, 성공률이나 비용도 개선되면 설명이 강해진다. 행동만 달라지고 최종 성과가 같다면 행동 영향까지만 주장한다. 일반 조언도 같은 정도로 개선되면 기억의 특수한 내용보다 추가 검토를 유도한 효과일 수 있다. 정답을 보고 만든 교정 문구라면 실용 정책이 아니라 진단용 상한 실험으로 표시한다.

**같은 중간 상태에서 분기하면 행동의 영향을 더 좁힐 수 있다.** 공통의 메모리 없는 실행 또는 미리 정한 공통 실행에서, 의심되는 결정 직전 상태를 보존한다. 대화뿐 아니라 파일, 프로세스·서비스, 작업 디렉터리, 데이터베이스 등 이후 행동에 영향을 주는 상태도 같아야 한다. 그 상태에서 기억 조건만 바꾸고 다음 행동과 종료 시 채점까지 비교한다.

이 설계는 “이미 특정 경로로 이동한 결과”와 “그 순간 기억의 영향”을 구분하는 데 도움이 된다. 그러나 분기 상태를 메모리 실행에서만 골랐다면 메모리가 도달하게 한 상태에 조건부인 실험이다. 전체 정책 효과는 처음부터 실행한 비교로 별도 측정한다. 환경 상태를 충실하게 복제할 수 없다면 동일 상태 실험이라고 부르지 않는다.

메모리의 영향을 설명하는 모델의 발언, 주의 가중치, 검색되었다는 로그만으로 행동 원인이 확인되지는 않는다. 실제 입력 개입과 명령·파일 수정 등 관측 가능한 행동을 중심으로 본다. 여러 기억의 조합이 의심되면 `M / M−m1 / M−m2 / M−{m1,m2}`를 비교할 수 있지만, 첫 실험에서 모든 조합의 기여도를 계산할 필요는 없다.

**6. 사실 정보와 행동 지침은 같은 근거에서 파생시켜 비교한다.** 초기 세 조건에서 현상이 나온 뒤 확장하는 실험이다. 모든 지침도 정보라는 점을 인정하고, ‘과거 관측을 기술하는 방식’과 ‘현재 행동을 권고하는 방식’의 효과를 측정한다.

| 조건 | 입력 | 핵심 비교 |
| --- | --- | --- |
| A | 과거 경험 없음 | 기준 |
| B | 과거 경험의 사실 F | `B−A`: 사실에 접근시키는 정책의 효과 |
| C | F + 일반적 조언 G | 추가적인 주의·검토를 유도하는 대조 |
| D | F + 해당 경험에서 나온 지침 P | `D−C`: 경험 특이적인 지침의 추가 효과 |

G와 P의 토큰 예산, 어조, 위치를 맞춘다. P가 새로운 사실을 알려주면 그 사실을 B·C의 F에도 넣는다. 출처, 적용 범위, 불확실성도 비교 조건 사이에 맞춘다. `D−B`만 보면 분량 증가와 행동 권고가 함께 변하므로, 지침의 의미만 분리한 효과라고 주장하지 않는다. G 자체가 유용할 수 있다는 점도 결과의 일부다.

두 번째 진단은 `사실형/지침형 × 적용 가능/적용 불가능`의 비교다. 적용 가능성은 현재 과제에서 관찰 가능한 버전·상태·도구 지원으로 판정한다. 최종 성공 여부나 숨겨진 정답으로 사후 판정하지 않는다. 같은 사실을 서술형과 명령형으로 바꿔도 의미가 완전히 동일해지는 것은 아니므로, 이를 ‘순수한 정보와 순수한 행동의 분리’라고 부르지 않는다.

자연 발생 사례와 일부러 환경 조건을 틀리게 바꾼 진단 사례는 분리한다. 진단 사례는 부적절한 전이가 일어나는지를 시험하기 좋지만, 그 비율로 실제 운영의 유해 기억 발생률을 추정할 수는 없다.

**7. 해로운 기억의 공통점은 대조 집단과 개입으로 확인한다.** 실패 로그만 모아 공통 단어를 찾으면 어떤 기억에도 흔한 특징을 원인으로 오해하기 쉽다. 성공·실패·변화 없음의 전체 노출 사례에서 먼저 비교한다.

| 실행 전에 판정할 후보 특징 | 판정에 사용할 정보 | 검증용 편집 |
| --- | --- | --- |
| 적용 조건 누락 | 기억과 원본 경험 | 원본에서 확인되는 조건만 추가 |
| 현재 환경 불일치 | 버전·도구·현재 관측 | 해당 정보만 교정하거나 사용 보류 |
| 과도한 확정성 | 원본의 증거 강도와 기억의 표현 | 단정 강도만 낮춤 |
| 관측을 넘은 일반화 | 시도 횟수·범위와 추출 규칙 | 주장 범위를 근거에 맞게 제한 |
| 오래되거나 중복된 내용 | 생성 시점, 동일 근거의 반복 | 최신성 확인·중복 제거 |
| 한 행동을 강하게 우선시 | 지침의 구체성·반복·위치 | 선택 조건과 대안만 추가 |

이 표는 아직 검증되지 않은 특성 목록이다. 특징을 표시하는 사람이나 판정기는 가능하면 최종 성공 결과를 보지 않는다. 반면 ‘모순이 나왔는데도 반복했다’ 같은 항목은 실행 후 행동 유형이므로 사전 위험 특징과 다른 열에 기록한다. LLM 판정은 후보 정리 도구로 쓰되, 표본을 사람이 확인하고 불명확·불일치 사례를 남긴다.

첫 분석에서는 특징별 노출 수, 과제·환경 분포와 성공률 차이를 보고한다. 어려운 과제에만 특정 기억이 검색된 경우를 고려해야 한다. 이후 의심 특징 하나를 편집해 비교하고, 별도 과제에서 같은 방향인지 확인한다. 작은 파일럿의 몇 개 회귀를 ‘유해 기억’의 확정 라벨로 학습시키지 않는다.

실용적 검증은 **실행 전에 관찰 가능한 특징으로 기억 사용 여부를 결정하는 정책**이다. 예를 들어 환경 불일치가 확인되면 지침 사용을 보류하는 규칙을 탐색 집합에서 정하고, 별도 집합에서 항상 사용·항상 미사용·선택적 사용을 비교한다. 선택적 사용이 이득을 유지하면서 손해나 비용을 줄이면, 공통점 분석이 설명을 넘어 유용한 정책으로 이어진다.

**8. 성공, 부작용, 비용, 행동을 함께 기록한다.** 공식 채점은 주 지표로 유지하고, 설명에 필요한 관측을 덧붙인다.

| 구분 | 기록할 지표 | 주의할 해석 |
| --- | --- | --- |
| 주 성과 | 과제 평균 성공률과 조건 간 차이, 불확실성 | 테스트 통과는 해당 채점기의 기준 충족 |
| SWE 회귀 | 원래 통과하던 P2P 테스트가 실패한 과제 비율 | 테스트 수를 독립 과제 수처럼 세지 않음 |
| 부분 진전 | F2P 테스트 결과 등 | 보조 지표이며 공식 과제 해결을 대체하지 않음 |
| 효율 | 전체 토큰·비용·벽시계 시간·행동 수 | 성공률과 함께 보고; 실패 조기 종료 구분 |
| 행동 | 첫 탐색 위치, 지원되지 않는 명령, 같은 오류 반복, 모순 이후 전환 | 사전 정의한 계산 규칙과 원본 로그 보존 |
| 변경 부작용 | 수정 파일 수, 범위 확장과 검증 결과 | 작은 패치가 항상 옳거나 큰 패치가 항상 나쁜 것은 아님 |
| 운영 상태 | 인프라 장애, 시간·비용 상한 도달, 실행 중단 | 패치 실패와 환경 실패를 구분 |

정답 패치와의 줄 단위 일치는 참고 지표일 뿐이다. 다른 방식의 올바른 수정도 있을 수 있다. 성공한 실행끼리의 비용 비교 역시 조건마다 성공한 과제가 달라질 수 있어 선택 편향이 있다. 전체 실행의 성공률·비용 분포를 먼저 보고하고, 동일 과제의 공통 성공 집합 분석은 보조적으로 제시한다.

메모리가 개선한 성공을 별도 피해가 상쇄하는 경우도 있으므로 하나의 가중 점수로 바로 합치지 않는다. 필요하면 성공 가치와 비용 가중치를 명시한 효용을 추가하되, 가중치를 바꿨을 때 결론이 달라지는지도 확인한다.

**9. 불확실성은 과제 단위와 실행 단위를 구분한다.** 통계적 검정은 설계와 독립 단위에 맞춰야 한다. 반복이 적은 성능 비교에서 점 추정만으로 순위를 매기는 문제는 NLP·강화학습 평가 문헌에서도 다룬다. 여기의 세부 절차는 우리 실험에 맞춘 제안이다. [Dror 등, ACL 2018](https://aclanthology.org/P18-1128/), [Agarwal 등, NeurIPS 2021](https://arxiv.org/abs/2108.13264)

- **탐색 파일럿:** 과제별 모든 결과를 공개하고 조건별 평균 차이를 계산한다. 반복 3회로 과제마다 신뢰할 만한 성공 확률을 알아냈다고 해석하지 않는다.
- **새 과제로의 일반화:** 과제를 묶음으로 재표집하는 paired bootstrap 등을 사용한다. 같은 과제의 모든 조건과 반복을 함께 유지한다. 같은 저장소·문제군에 강하게 묶여 있으면 그 계층도 반영하거나, 저장소별 결과와 제한된 일반화 범위를 보고한다.
- **고정된 벤치에서 실행 변동성만 측정:** 과제는 고정하고 반복 실행의 변동성을 별도로 평가한다. 새 과제 모집단에 대한 신뢰구간과 혼동하지 않는다.
- **작은 표본의 한계:** 관측 결과가 전부 0 또는 1인 경우 단순 재표집이 지나치게 좁은 구간을 만들 수 있다. 설계에 맞는 검정·모형 등과 함께 해석하고, 작은 표본에 강한 결론을 부여하지 않는다. 조건별 성공 비율의 이항 구간만으로 두 조건 차이의 신뢰구간을 대신하지 않는다.
- **확인 실험:** 주 비교, 실질적으로 중요한 효과 크기, 반복 수·중단 규칙을 미리 정한다. 탐색한 여러 가설은 탐색 결과로 표시하고, 고른 가설은 새 데이터에서 확인한다.

‘유의하지 않음’은 ‘효과 없음’이나 ‘해롭지 않음’을 증명하지 않는다. 실질적으로 무시할 수 있는 차이라고 주장하려면 허용 오차를 사전에 정하고, 충분한 정밀도의 동등성·비열등성 평가가 필요하다. 확인에 사용한 데이터를 다시 방법 선택에 쓰면 최종 검증용 데이터는 새로 남겨야 한다.

규모 감각을 위한 **단순 근사 예시**도 도움이 된다. 과제당 한 쌍의 이진 결과, 독립적인 과제 쌍, 양측 5% 유의수준과 80% 검정력의 정규근사를 가정하면 다음 정도다.

```text
N ≈ (1.96 + 0.84)² × q / δ²
q: 두 조건 결과가 다른 과제 쌍의 예상 비율
δ: 검출하려는 성공률 차이

q = 0.20, δ = 0.05이면 약 628개 과제 쌍
q = 0.20, δ = 0.10이면 약 157개 과제 쌍
```

이는 실제 예산 산정이나 권장 표본 수가 아니다. 반복 실행·과제 상관·정확 검정·실제 분산을 반영하지 않은 근사다. 의미는 **10개 과제로 작은 평균 개선을 확정하기는 어렵다**는 것이다. 파일럿 이후 관측 분산으로 설계하고, 몇 과제의 반복 횟수만 계속 늘리기보다 새로운 과제에서도 성립하는지를 확인해야 한다. 작은 규모에서는 큰 국소 행동 효과를 확인하는 개입 실험이 먼저 생산적일 수 있다.

**10. 기억을 만드는 비용까지 포함해야 ‘정말 이득인지’ 판단할 수 있다.** 다음 항목을 분리해 보고한다.

```text
생애주기 비용 = 경험 수집 비용 + 기억 생성 비용
               + Σ(검색 비용 + 과제 실행 비용) + 갱신 비용
```

실제 운영에서 과거 과제는 원래 수행했을 업무일 수 있다. 이 경우 경험 수집 비용을 이미 발생한 비용으로 보는 관점과, 연구를 위해 새로 만든 비용으로 보는 관점을 둘 다 제시한다. 기억 생성에 쓴 추가 모델 호출을 숨기거나, 검색·재검토 비용을 실행 비용에서 누락하지 않는다.

성공 품질이 동등하고 재사용당 비용이 `c0`에서 `cm`으로 줄어든다는 조건에서, 구축 비용 `Cb`의 단순 손익분기는 `사용 횟수 ≥ Cb / (c0−cm)`다. `c0≤cm`이면 비용 절감만으로는 회수되지 않는다. 성공률이 달라지면 이 식만으로 경제적 이득을 결론낼 수 없다.

같은 최대 예산에서 성공률을 비교한 결과와, 여러 예산에서 그린 성공률–비용 곡선을 구분한다. API 가격·캐시 할인·실제 청구량은 실행 시점의 값을 기록하며, 행동 횟수 감소를 곧바로 금전 절감으로 번역하지 않는다.

**11. 환경과 평가기를 통제하지 않으면 기억의 효과를 잘못 읽을 수 있다.** 아래는 이 실험에 직접 필요한 재현 조건이다.

| 항목 | 고정·기록할 내용 |
| --- | --- |
| 실행체 | 모델 정확한 식별자와 날짜, 에이전트·하네스 커밋, 프롬프트·도구 설정 |
| 환경 | 컨테이너·저장소 커밋, CPU·RAM·시간 상한, 네트워크·캐시 정책 |
| 실행 순서 | 조건을 시간 블록 안에서 섞어 실행; 동시 실행 수와 자원 경쟁 관리 |
| 기억 제공 | 실제 전달한 텍스트, 역할·위치, 검색 ID, 절단·압축 여부 |
| 초기화 | 조건마다 새 환경과 대화, 숨은 대화 기록·파일·온라인 기억 공유 차단 |
| 예산 | 최대 비용·토큰·행동 수와 종료 조건, 실제 사용량 |
| 채점 | 공식 테스트·정답 자료는 평가기에 격리; 채점 버전과 원본 결과 보존 |

메모리는 일반적인 과거 증거로 제공하고, 이를 따르도록 기본 프롬프트까지 바꾸는 경우 그 변경도 실험 처리의 일부로 기록한다. 무메모리 조건에는 없는 ‘항상 반성하라’ 같은 지시를 메모리 조건에만 추가하면 추가 지시의 효과가 섞인다.

SWE 평가기는 `run_id`와 `instance_id`를 기준으로 결과를 캐시하므로, 조건·반복·패치별로 고유한 `run_id`를 쓴다. 그렇지 않으면 다른 패치에 이전 결과를 재사용할 수 있다. [공식 평가 문서](https://www.swebench.com/SWE-bench/guides/evaluation/)

Terminal-Bench는 버전 변경 때 과제와 자원 설정이 바뀔 수 있으므로 데이터셋 버전과 해시를 고정한다. [Terminal-Bench 4.0 변경 안내](https://www.tbench.ai/news/terminal-bench-4-0)

인프라 오류의 재시도 규칙은 결과를 보기 전에 정하고 모든 조건에 동일하게 적용한다. 실행이 실패한 뒤 유리한 조건만 재시도하거나, 어려운 과제를 환경 오류라는 이유로 사후 제거하지 않는다. 실행 가용성과 정상 채점된 실행의 성능을 나누어 보고하고, 제외·재시도 건수와 원인을 남긴다.

**12. 로그는 다음 정도면 분석을 시작할 수 있다.** 첫 단계부터 복잡한 데이터베이스가 필요한 것은 아니다. 실행별 JSON/JSONL, 기억 원문, 채점 결과, 패치와 도구 로그를 연결하면 된다.

| 묶음 | 최소 기록 |
| --- | --- |
| 과제 | 과제 ID, split, 저장소·base commit, 환경 이미지 |
| 조건 | 조건 ID, 반복 ID, 기억 저장소 해시, 검색된 출처·항목 ID |
| 입력 | 실제 기억 텍스트·해시, 프롬프트 버전, 입력 위치와 토큰 수 |
| 실행 | 모델·에이전트·하네스 버전, seed 설정 여부, 시간 블록, 예산 |
| 궤적 | 명령·관측·수정, 기억 조회 이벤트, 종료 이유 |
| 결과 | 공식 점수, F2P/P2P, 인프라 상태, 시간·토큰·비용 |
| 분석 | 사전 특징, 판정자·불확실성, 실행 후 실패 유형 |
| 개입 | 원본 기억 ID, 바꾼 문구, 개입 유형, 비교 실행 ID |

전달 방식 비교에는 조회 0회·빈 결과·검색 오류, 최초 조회 시점, 검색어·카드·입력 위치, 실제 다음 API 입력에 노출됐는지를 추가한다. [기록 규약](experiment-recording.md)의 후속 구현 필드를 따른다. 조회 실행만 추려 비교하면 에이전트의 과제 난도 판단 등이 섞일 수 있어 주 정책 효과로 해석하지 않는다.

최종 보고에는 조건별 성공률·비용 표, 과제별 반복 결과, 출처가 있는 사례 카드, 불확실성과 제외 내역을 포함한다. 사례 카드는 ‘원본 경험 → 제공한 기억 → 실제 행동 → 최종 결과 → 개입 결과’가 연결되게 만든다. 이 기록이 이후 정량 분석과 실패 사례 논의를 동시에 가능하게 한다.

**13. 단계별로 무엇을 얻으면 다음으로 갈지 정한다.**

| 단계 | 산출물 | 다음 판단 |
| --- | --- | --- |
| 환경 점검 | 실행·채점·로그 저장의 재현 확인 | 유료 대량 실행 전에 환경 문제 해결 |
| 작은 재현 | 세 조건의 반복 결과와 비용, 후보 사례 | 메모리가 실제로 읽히고 행동에 영향을 주는지 |
| 한 현상 검증 | 삭제·교정·대조·재실행 결과 | 특정 내용이 행동과 성과에 기여하는지 |
| 별도 과제 확인 | 고정된 가설·정책의 새 데이터 결과 | 과적합된 설명인지, 실용적 개선인지 |
| 규모 확장 | 더 많은 과제·다른 저장소 또는 모델 | 효과 범위와 불확실성, 총비용 |
| 지속 축적 | 여러 과제 순서·고정 시점 평가 | 저장·검색·갱신에 따른 장기 변화 |

파일럿에서 효과가 없으면 곧바로 ‘메모리는 무용하다’고 결론내리지 않는다. 검색된 경험의 관련성, 실제 노출 여부, 기준 성능의 천장·바닥, 요약의 출처 충실성을 진단한다. 그 결과를 보고 설계를 바꾸면 새로운 탐색 실험으로 표시한다. 반대로 효과가 클 때도 조건을 계속 바꾸며 가장 좋아 보이는 결과만 고르지 않는다.

지속 축적 단계에서는 과제 순서를 여러 번 바꾸고, 같은 경험 스트림에서 저장·갱신 정책을 비교한다. 고정된 평가 과제의 실행은 기억에 다시 쓰지 않도록 분리한다. 그래야 기억이 많아지는 효과, 표현이 바뀌는 효과, 검색이 어려워지는 효과를 구분하기 쉬워진다. 고정 저장소 파일럿만으로 장기 축적의 이득을 증명했다고 주장하지 않는다.

**현재 제안하는 첫 확인 실험은 ‘적용 조건의 복구’다.** 먼저 자연 발생한 부적절한 전이 사례가 있는지 보고, 있다면 같은 원본 근거에서 적용 조건 한 부분만 복구한다. 원래 기억, 수정 기억, 일반 조언 대조, 무메모리를 반복 비교한다. 행동 변화와 최종 성공·비용이 함께 움직이는지 확인하고, 규칙을 고정해 별도 과제로 넘어간다. 후보가 발견되지 않으면 그 결과를 받아들이고 다른 관측에서 가설을 고른다.

이 경로라면 새 벤치나 대규모 유해 기억 정답셋을 먼저 만들 필요가 없다. 처음에는 기존 벤치의 경험을 모으고 비교하고, 정밀한 데이터 제작은 실제로 확인할 가치가 있는 작은 개입 집합에 집중할 수 있다.
