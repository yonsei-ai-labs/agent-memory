# 연구 방향 재검토와 첫 실험 실행안

2026-11-03 · 문헌·공개 데이터 메타데이터·에이전트 코드 확인 · 메모리 효과 실험 전

2026-11-04 진행 상태: 아래는 제안 당시의 설계다. 실제 경험 수집·전달·반복 비교는 [야간 실험 보고서](reports/2026-11-04-overnight-research.md)에 회차별로 기록한다. 후속 `scope_index` 조건은 시작에 짧은 기억 범위 정보가 보이므로, 본문 미조회와 정보가 전혀 없는 조건을 구분한다. 작은 최초 이득의 재현 여부·중간 패치 측정·개별 득실 라벨의 한계는 [측정 노트](ai-memory-measurement-notes.md)를 따른다.

OpenRouter 단일 과제 실행기와 기록 경로를 구현했다. 환경 점검의 실제 결과는 [진행 기록](experiment-log.md)과 [첫 보고서](reports/2026-11-03-openrouter-smoke.md)를 따른다. 아래 표본 수와 본 실험 과제 구성은 아직 설계안이다.

**2026-11-03 전달 방식 비교 추가:** 사용자의 요청에 따라 첫 주 비교를 `none / preload / agent_search`로 갱신했다. 세 정책과 진단용 `deferred_same`을 구현하고, 별도의 출처 1과제·평가 2과제를 사용하는 전달 기능 점검에 착수했다. 고정 계획과 환경 변경은 [기능 점검 계획](../experiments/swe_memory/plans/delivery-smoke-v1.json), [환경 변경 기록](../experiments/swe_memory/plans/delivery-smoke-v1-environment-amendment.json)을 따른다. 아래 134회 규모의 주 실험은 아직 설계안이다.

모델·비용에 관한 현재 권고는 [Luna·DeepSeek 선정과 저비용 진행안](ai-memory-model-selection.md)을 따른다. 사용자 비용 선호를 반영해 두 모델을 같은 별도 과제에서 짧게 점검하고, 하나로 주 실험을 마친 뒤 다른 모델로 확인한다.

**판단: 연구 방향은 적절하다. 첫 실험은 ‘실제 과거 경험을 제공했을 때 새 과제의 수행이 어떻게 변하는가’에 집중하는 편이 좋다.** 기존 설계의 핵심인 별도 과제로의 전이, 고정된 기억, 반복 실행, 항목 개입은 유지한다. 보완할 부분은 과제 연결 가능성, 평가 집합의 중복, 대조군의 우선순위다. 작은 표본에서 평균 점수의 개선부터 확정하려 하기보다, 효과의 크기와 변동성을 보고 재검증할 현상을 찾는다.

이 문서는 [문헌 검토](ai-memory-benefit-harm-review.md)와 [상세 검증 설계](ai-memory-causal-evaluation-plan.md)를 다시 검토한 현재 실행 권고다. 수량과 기준은 제안이며, 실제 벤치 성능을 측정한 결과는 아니다.

**1. 타당성은 네 가지로 나눠 판단한다.**

| 질문 | 현재 판단 | 아직 확인해야 할 것 |
| --- | --- | --- |
| 연구할 가치가 있는가? | 있다. 평균 이득과 별개로 적용 실패·회귀·비용을 설명할 필요가 있다. | 새 기여는 재현 후 발견한 현상으로 구체화 |
| 효과를 측정할 수 있는가? | 같은 과제에서 기억 제공 정책의 성공률·비용 차이를 측정할 수 있다. | 작은 표본의 불확실성, 과제·모델에 따른 효과 차이 |
| 원인을 확인할 수 있는가? | 기억의 삭제·교정과 행동 변화를 함께 비교할 수 있다. | 한 번의 성공→실패 전환만으로 원인 확정 불가 |
| 구현 가능한가? | 컨테이너·모델·채점·시작 제공·자율 조회와 기록 경로를 구현하고 로컬 검증했다. | 충분한 경험 관계와 과제 수, 자율 조회가 일어나는 조건, 반복 결과 |

성공·실패 경험을 활용하는 [ReasoningBank](https://github.com/google-research/reasoning-bank)와 저장소 이력의 득실을 다루는 [MemDev-Bench](https://arxiv.org/html/2610.27524v1)는 가까운 출발점이다. 기존 연구와 비슷하게 시작하는 것은 현재 목표에 맞는다. 다만 ‘때로 득이고 때로 실’이라는 관측에서 나아가 적용 조건이나 행동 전환에 대한 검증을 확보하는 것이 후속 목표다.

**2. 공개 데이터에서 실제로 확인한 분할 문제.** Hugging Face의 Lite dev 23개, Lite test 300개, Verified test 500개 행을 조회하고 `instance_id`와 `repo`를 비교했다. 문제 설명과 공개 메타데이터만 분석 대상으로 보존했으며 정답 패치·테스트·힌트는 분석에서 제외했다. [Lite 데이터](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Lite), [Verified 데이터](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified)

| 직접 계산한 항목 | 결과 | 실험에 주는 의미 |
| --- | --- | --- |
| Lite dev와 test의 공통 저장소 | 0개 | dev 경험을 test에 쓰면 저장소 간 전이다. 같은 저장소의 경험 전이를 검증하는 기본 분할로는 맞지 않는다. |
| Lite test와 Verified의 공통 문제 ID | 93개 | Lite에서 탐색한 뒤 Verified 전체를 모두 처음 보는 확인 집합이라고 부를 수 없다. |
| Lite test에서 Verified 중복 ID를 뺀 후보 | 207개 | Verified를 이후 확인용으로 남길 때 사용할 초기 후보군이다. |

207개에는 Django 71개, SymPy 55개, matplotlib 16개, pytest 15개, scikit-learn 14개, Sphinx 13개 등이 있다. 이는 후보 수이며, 이 과제들이 유용한 경험 쌍을 이룬다고 확인한 것은 아니다. 세부 집계와 조회 방법은 [메타데이터 점검 기록](swe-bench-metadata-check-2026-11-03.json)에 남겼다. 조회 시점의 데이터이며 실제 실행 시에는 버전을 고정해야 한다.

따라서 **Lite의 Verified 비중복 후보 안에서 먼저 작은 경험 수집·평가 집합을 만든다.** ID가 다르더라도 같은 수정의 중복·백포트일 수 있으므로 추가 점검이 필요하다. 나중에 Verified로 확장할 때도 각 과제 시점에 이용 가능했던 기억만 허용한다. 날짜가 늦은 수집 경험을 오래된 평가 과제에 소급해서 제공하지 않는다.

**3. 가장 먼저 할 일은 경험을 재사용할 여지가 있는 과제를 찾는 것이다.** 무작위 수집 10개와 평가 10개로는 전이할 내용이 거의 없을 수 있다. 이때 무효과는 기억 자체의 한계인지, 경험 구성이 맞지 않은 것인지 해석하기 어렵다.

1. 위 207개에서 2–3개 저장소를 후보로 삼는다. Django·pytest·Sphinx 등은 조사 후보이며 확정된 선택은 아니다.
2. 같은 저장소에서 시간상 앞선 수집 후보와 뒤의 평가 후보를 연결한다. `created_at`은 1차 정렬에만 쓰고, 원래 사례의 해결·종료 시점과 평가 `base_commit`의 코드 이력·분기를 확인한다. 현재 수행하는 벤치 실행의 날짜와 원사례의 역사적 시점을 혼동하지 않는다.
3. 현재 문제 설명에 나타나는 하위 시스템, API, 증상·도구를 기준으로 경험 후보를 찾는다. 정답 패치가 수정한 파일을 검색 키로 쓰지 않는다.
4. 관계가 있을 법한 출처와 덜 관련된 출처를 모두 확보한다. 과제별 선택 근거를 한두 문장으로 기록하되, 도움이 될 것이라는 정답 라벨을 붙이지 않는다.
5. 수집 후보와 평가 후보를 먼저 고정하고 수집을 시작한다. 평가 결과를 본 뒤 유리한 과제 쌍으로 바꾸지 않는다.

관계가 있는 과제를 의도적으로 고른 첫 실험은 ‘전이 기회가 있는 과제군’에 대한 진단이다. SWE-bench 전체 분포의 평균 효과와 구분해서 보고한다. 조건에 맞는 과제 쌍이 부족하면 같은 원래 SWE 데이터 안에서 수집 후보를 넓히거나, 반복되는 도구·절차를 가진 Terminal-Bench 과제군으로 전환한다. 아직 존재를 확인하지 않은 10쌍을 확보했다고 가정하고 실행하지 않는다.

MemDev-Bench는 과거 이력을 구성할 때 평가 PR의 변경 파일과 diff도 활용한다. 이는 벤치 제작의 관계 선정을 위한 정보다. 그 관계 목록을 그대로 사용하는 진단과, 실제 실행 때 이용 가능한 정보만으로 검색하는 성능은 구분해야 한다. 우리의 첫 검색 규칙은 현재 문제 설명과 허용된 과거 경험만 사용한다. [구축 방법 §2.1](https://arxiv.org/html/2610.27524v1)

**4. 첫 비교는 기억을 전달하는 세 정책이다.** 기억 저장소·작성 규칙·검색기를 고정하고, 무메모리·시작 시 제공·자율 검색을 비교한다. 실제로 조회하지 않는 선택까지 포함해 각 방식의 성공률·비용을 평가한다. 원본 경험과 이전 설계의 재배정 대조는 후속 진단에 사용할 수 있도록 보존한다.

| 조건 ID | 제공하는 내용 | 비교가 답하는 질문 |
| --- | --- | --- |
| `none` | 현재 과제와 기존 에이전트 입력, 과거 기억 접근 없음 | 기준 성공률·비용 |
| `preload` | 문제 설명으로 사전 검색한 카드 최대 1개를 시작 입력에 제공 | `preload−none`: 자동 제공 정책의 총효과 |
| `agent_search` | 시작 시 내용 없이 조회 방법만 안내. 에이전트가 필요할 때 쿼리를 작성해 검색 | `agent_search−none`: 자율 검색 정책의 총효과; `agent_search−preload`: 두 정책의 차이 |

`preload`와 `agent_search`에는 같은 고정 저장소, 과제별로 시간상 이용 가능한 후보, 같은 검색기·정렬 규칙을 사용한다. 시작 검색은 현재 문제 설명만, 자율 검색은 그 시점까지 실제로 관측한 문제·코드·도구 결과만 사용한다. 평가 정답·숨겨진 테스트·미래 궤적은 사용하지 않는다. 사전 검색 카드와 자율 검색 카드가 같을 것이라고 가정하지 않는다.

첫 파일럿은 검색 최대 1회·반환 최대 1카드로 제한한다. `preload`의 자동 검색도 이 한도와 비용에 포함한다. 검색 결과가 비어 있으면 그대로 실행하고, `agent_search`에서 검색하지 않아도 실행을 유지한다. 카드 길이 상한과 절단 규칙은 점검에서 정해 고정하며 두 방식에 동일하게 적용한다. 여러 번 검색·수정하는 정책은 별도 후속 실험이다. 실제 전달 토큰 수와 반복 대화에서 발생한 입력·캐시 비용은 같다고 가정하지 않는다.

메모리 두 조건에는 같은 선택적 사용 안내·조회 인터페이스·한도를 알려준다. 시작 입력에 실리는 카드의 유무가 다르며, 자율 조건에 ‘반드시 기억부터 확인하라’는 지시를 넣지 않는다. `none`은 기존 무메모리 입력을 유지한다. 따라서 무메모리 대비 효과에는 조회 안내의 영향도 포함된다. 안내만의 효과가 의심되면 같은 안내·빈 저장소 대조를 후속으로 둔다.

**4a. 전체 정책의 효과와 내용·시점의 원인을 구분한다.** `agent_search−preload`에는 검색 여부, 시점, 쿼리, 선택된 내용, 입력 위치, 조회 동작과 비용이 함께 들어 있다. 이를 ‘시점 하나의 순수한 효과’라고 해석하지 않는다. 가능한 가설은 초기 기억이 탐색을 돕거나 고착을 일으키는 경우, 현재 코드를 확인한 뒤 더 맞는 기억을 찾는 경우, 필요한 기억을 조회하지 않거나 너무 늦게 조회하는 경우다. 아직 관측된 결론은 아니다.

| 후속 조건 | 고정하거나 바꾸는 것 | 해석 범위 |
| --- | --- | --- |
| `deferred_same` | `preload`의 사전 선택 카드와 바이트 단위로 같은 내용을, 에이전트가 `read`를 선택한 시점에 반환 | `preload`와 비교해 내용 선택 차이를 제거. 조회 여부·시점·호출 비용·입력 역할 차이는 남음 |
| `preload_reassigned` | 같은 형식·분량의 다른 이용 가능한 경험을 시작 시 제공 | 과제에 맞춘 내용 선택에 관한 진단. 대조 기억도 유익·유해할 수 있음 |
| 정해진 시점의 같은 카드 | 같은 내용을 같은 메시지 역할·형식으로, 실행 전에 정한 서로 다른 시점에 자동 노출 | 시점에 더 집중하는 후속 개입. 모델 결과를 보고 유리한 시점을 고르지 않음 |

`deferred_same`은 저장소를 자유 검색하는 조건이 아니다. 제공받을 내용이 같을 때 스스로 여는 선택을 검사한다. 그 카드 ID는 평가 실행 전에 고정한다. 자율 검색 결과를 사후에 골라 처음부터 넣는 재실행은 미래 정보가 들어가는 탐색 진단이므로 주 정책 비교나 새 과제 전이 결과로 합치지 않는다.

재배정 대조에서는 같은 저장소·시간상 이용 가능성·원경험 성공/실패 분포·카드 형식·분량을 가능한 범위에서 맞춘다. 배정과 seed를 미리 고정하고 차이가 남으면 기록한다. 다른 기억이라는 이유로 무관하거나 효과가 0이라고 가정하지 않는다. 모든 후속 조건을 첫 파일럿에 동시에 추가하지 않는다.

**4b. 검색한 실행만 비교하지 않는다.** 조건을 배정받은 전체 실행으로 정책 효과를 계산한다. 조회 0회·빈 결과·검색 오류도 따로 기록하며, 조회하지 않았다는 이유로 분모에서 빼지 않는다. 조회한 과제만의 성공률은 기술 통계로 표시한다. 어려운 과제에서 더 자주 검색할 수 있으므로 조회 실행과 비조회 실행의 차이를 검색의 인과 효과로 읽지 않는다. 인프라 오류·미채점·모델이 만든 채점 실패는 기존 규약대로 보존하고 사전 분석 규칙을 적용한다.

최종 성공률과 함께 최초 조회의 모델 호출 번호·경과 시간, 조회율, 빈 결과율, 카드 중복·내용 일치, 최초 수정·테스트 실패와 조회의 순서, 실제 노출 토큰과 총비용을 기록한다. 조회가 없으면 최초 조회 시점은 0이 아니라 `null`이다. 도구가 반환했다는 사실, 다음 API 입력에 실렸다는 사실, 행동에 영향을 미쳤다는 주장은 서로 구분한다. 행동 기여는 카드 삭제·교정 및 별도 반복 실행으로 확인한다.

**5. 기억은 실제 경험에서 동일한 규칙으로 만든다.** 수집 과제는 메모리 없이 한 번씩 실행하고 공식 채점 결과를 보존한다. 같은 고정된 추출기로 다음 내용을 카드 하나에 기록한다.

```text
source_id / repo / version / 원본 로그 위치
관측: 실제로 확인한 사실과 도구 반환값
시도와 결과: 어떤 접근을 했고 어디까지 확인했는가
교훈 후보: 다음 과제에서 참고할 수 있는 추정
알려진 적용 조건과 확인하지 못한 부분
```

성공과 실패 기록을 모두 보존한다. 실패한 시도 모두를 금지 규칙으로 만들지 않는다. 알려지지 않은 적용 조건을 작성자가 임의로 채우지 않는다. 카드 생성기는 평가 문제·정답·후속 결과를 보지 않는다. 제공 분량은 점검 단계에서 한 번 정해 고정한다. 예를 들어 카드당 300–500토큰을 출발점으로 검토할 수 있지만, 모델 선정 후 실제 길이와 절단 여부를 기록해야 한다.

사실·교훈·조건을 분리해 저장하면, 나중에 사실 부분만 제공하거나 교훈 한 문장만 바꾸는 실험을 위해 새 데이터를 만들 필요가 줄어든다. 기억 카드의 형식을 개선하는 것은 후속 처리이며, 첫 결과를 본 뒤 카드를 고치면 새 버전의 실험으로 기록한다.

**6. 모델 선정용 실행을 분리해 단계별로 진행한다.**

| 단계 | 제안 규모 | 완료 조건 |
| --- | --- | --- |
| 무메모리 연결 점검 | 별도 2과제 × 2모델 × 1회 = 4회 | 동일 환경 초기화, 패치 제출, 공식 채점, 로그 저장 확인 |
| 모델 선정 | 별도 6과제 × 2모델 × 2회 = 24회, 무메모리 | Luna·DeepSeek의 기본 수행과 실제 비용을 보고 주 모델 확정 |
| 전달 경로 점검 | 주 모델·별도 2과제 × 3조건 × 1회 = 6회 | 시작 제공·자율 조회·조회하지 않음의 기록 경로, 제출·채점 확인 |
| 현상 탐색 | 수집 10개 + 별도 평가 10개 × 3정책 × 3회 | `none / preload / agent_search`의 성능·비용·행동 차이 |
| 독립 확인 | 후보에 맞춰 사전에 정한 추가 실행·새 과제 | 선택한 문구·조건의 영향이 다시 나타나는지 확인 |

경험 수집과 메모리 평가의 기본 에이전트 실행은 `10 + 10×3×3 = 100회`다. 주 평가 조건은 3개를 유지하며 재배정 대조를 후속으로 옮겼다. 기존 연결·모델 선정 예시 28회와 전달 경로 점검 6회를 합하면 134회다. 카드 생성, 재시도, 후속 개입, 채점·인프라 비용은 별도다. 이 숫자는 지출 한도나 검정력 계산 결과가 아니다. 점검 단계의 실제 사용량으로 다음 단계 비용을 추정한다. 다른 모델에서 무메모리와 한 전달 정책을 확인하는 예시는 추가 60회이며, 세 정책 모두 확인하면 90회다.

주 메모리 실험은 선정한 모델 하나, 에이전트 하나, 고정된 입력·도구·예산으로 진행한다. 실행 순서는 과제별 시간 블록 안에서 조건을 섞는다. 매번 새 컨테이너와 대화를 사용하고 평가 중 기억은 갱신하지 않는다. 인프라 실패의 재시도 규칙과 결과 제외 규칙을 미리 정한다. 여러 모델을 바꾸어 가장 좋은 메모리 효과만 선택하지 않는다.

**7. 시작 제공과 자율 조회를 별도로 구현해야 한다.** mini-SWE-agent의 배치 코드는 문제 설명을 `task`로 읽고 `agent.run(task)`를 호출한다. 기본 에이전트의 `run(task, **kwargs)`는 추가 변수를 입력 템플릿에 전달한다. 따라서 작은 래퍼에서 `memory`를 넘기고 사용자 입력 템플릿의 고정 위치에 렌더링하는 방식이 가능하다. [배치 실행 코드](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/run/benchmarks/swebench.py), [기본 에이전트 코드](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py)

```python
# 설계 예시. 설치·실행·검증을 마친 코드가 아니다.
memory_text = render_memory(task_id, condition, frozen_bank)
agent.run(problem_statement, memory=memory_text)
```

실제 연결 시 기존 템플릿에 `memory`를 렌더링하는 부분도 함께 추가해야 한다. `run` 인자만 추가한다고 자동으로 입력에 나타나지는 않는다. 렌더링된 최종 프롬프트를 저장하고 점검한다. 현재 문제, 기본 지시와 도구 규칙은 동일하게 유지하며 기억을 시스템 명령으로 승격시키지 않는다.

설치된 2.4.6의 Responses 어댑터와 파서는 `bash` 호출을 전제로 한다. 같은 bash 인터페이스 안의 예약 명령 `memory search --query '...'`를 호스트 실행기가 처리하도록 구현했다. 검색어는 셸 코드로 실행하지 않고 데이터로 읽는다. 현재 검색기는 버전을 고정한 어휘 겹침·IDF 점수이며 동점은 카드 ID 순으로 처리한다. 정답을 이용한 재정렬은 없다. `deferred_same`에는 `memory read` 동작을 구현하고 로컬 검증했다.

기억 저장소 전체를 과제 컨테이너에 넣으면 에이전트가 `cat` 등으로 조회 기록을 우회할 수 있다. 저장소는 호스트에 두고 허용된 반환 카드만 모델 입력으로 보낸다. 정답을 포함한 감사 폴더도 접근 경로에서 제외한다. 오프라인 검증으로 조건별 최초 입력, 원문 일치, 빈 결과·조회 0회, 한도, 여러 도구 호출의 처리 순서, 도구 반환이 다음 요청에 실리는지 확인한다. 조회가 자발적으로 일어나지 않는 점검 실행은 그대로 기록하고, 반환 경로 자체는 모의 도구 호출로 검증한다. 점검 중 사용을 강제하는 별도 프롬프트를 쓰면 그것은 연결 점검으로만 분류한다.

공식 채점에는 고유한 실행 ID를 사용한다. 숨겨진 평가 자료는 에이전트 입력에서 분리한다. API·모델·총 계산 상한, 코드 버전, 실행 환경은 실제 실행 전에 확정한다. 자율 조회로 쓰인 모델 호출·도구 시간도 같은 총예산에서 차감하고, 시작 전 자동 검색의 시간·비용도 포함한다. 현재 기능 점검의 카드 본문 상한은 1,800문자이고 표시 시 출처 공식 판정을 별도로 첨부한다. 본문·표시·최종 API 입력을 모두 남긴다.

**8. 첫 결과에서 읽을 것은 성공률·비용·행동이다.** 주 비교는 과제별 반복 성공률을 평균낸 `agent_search−preload`이며, 각 정책의 `none` 대비 효과를 함께 보고한다. 전체 실행의 비용·시간, 기존 통과 테스트의 회귀, 조회 시점과 탐색·수정 행동을 보조적으로 기록한다. 실패로 일찍 종료해 비용이 줄어든 경우와 성능을 유지하며 비용이 줄어든 경우를 구분한다.

| 관측 | 가능한 해석 | 다음 실험 |
| --- | --- | --- |
| 자율 검색이 시작 제공보다 좋음 | 시점·조회 선택·검색 내용·노출량 중 하나 이상이 기여할 가능성 | 같은 카드의 지연 조회, 카드 ID·행동 비교 |
| 시작 제공이 자율 검색보다 좋음 | 미조회·늦은 조회·검색 실패 또는 초기 정보의 이점 가능성 | 미조회 포함 전체 결과와 같은 카드 대조; 원인 단정 금지 |
| 두 정책 모두 무메모리보다 좋음 | 이 저장소와 과제군에서 기억 접근이 유익할 가능성 | 재배정·문구 삭제로 내용 기여 확인 |
| 자율 검색은 무메모리와 비슷하고 시작 제공만 나쁨 | 초기 제공의 손해를 피했을 가능성 | 자율 검색의 적극적 이득과 손해 회피를 구분 |
| 어느 기억 정책이 무메모리보다 나쁨 | 내용 불일치·조회 비용·행동 고착 등의 가능성 | 같은 카드·적용 조건 교정 및 별도 반복 확인 |
| 성공률은 비슷하고 비용이 다름 | 효율 효과의 가능성 | 동일 품질 여부와 구축비 포함 총비용 확인 |
| 모두 비슷함 | 관련 경험 부족, 입력 처리, 능력의 천장·바닥 또는 작은 효과 등 | 전달된 입력·경험 관계·변동성 진단 |

이 표는 점 추정의 순위만으로 판단하라는 뜻이 아니다. 반복 결과와 불확실성을 함께 보고, 10개 과제의 작은 차이는 탐색 관측으로 남긴다. 한 번의 성공→실패 전환은 원인 분석 후보이며 확정된 유해 기억 라벨이 아니다. 같은 과제의 반복과 비교 조합을 독립적인 새 과제 수로 세지 않는다.

**9. 원인 확인은 한 문장 또는 한 조건에 집중한다.** 자연 발생한 후보에서 원래 기억, 의심 문구 삭제, 해당 조건·사실만 교정, 비슷한 분량의 일반 조언을 비교한다. 재검증용 반복 수와 종료 규칙은 새 실행 전에 정한다. 발견에 사용한 우연한 실행이 다시 좋아지는 현상을 피하려면 확인용 기준 실행도 새로 수행한다.

예를 들어 기억의 명령을 따르다 현재 환경에서 지원 오류가 났는데 반복하는 사례라면, 적용 조건을 복구했을 때 **지원 확인 증가 → 오류 반복 감소 → 최종 성공·비용 개선**이 함께 나타나는지 본다. 행동만 바뀌면 행동 영향까지만 주장한다. 전체 실행 재실행을 먼저 하고, 환경 상태 복제가 가능한 경우에만 같은 중간 상태에서 분기하는 실험을 추가한다.

정보와 행동 지침의 비교는 이후 **사실 F / F+일반 조언 / F+경험 특이 지침**으로 수행한다. 원본 로그와 카드의 차이가 의심되면 **같은 출처의 원본 / 카드 / 누락 내용을 복구한 카드**를 비교한다. 모든 축을 첫 100회에 넣으면 조건마다 데이터가 부족해진다.

**현재의 실행 순서는 ‘후보 관계 점검 → 모델 선정·전달 경로 점검 → 무메모리/시작 제공/자율 검색 비교 → 같은 카드·문구 개입을 통한 독립 확인’이다.** 충분한 과거 경험 관계를 확보할 수 있고 비교 실행이 안정적이라는 것이 다음 단계의 조건이다. 그 조건을 만족한 뒤에도 효과가 없으면 무효과를 그대로 보고할 수 있다. 유해 사례가 나오지 않았다는 이유로 일부러 틀린 기억을 만들어 자연 발생 피해처럼 제시하지 않는다.
