# 데이터 역할 정리와 누적 컨텍스트 실험안

**첫 세팅 테스트:** [Luna 4문항 결과](reports/2026-11-12-luna-session-setup.md)를 추가함. 입출력·원문·예산·동일 상태의 기록은 작동하지만 실제 누적 답변 노출과 조회/추천 계약이 부족하여 전체 실험은 시작하지 않았음. 2k/4k는 이 테스트에서 o200k_base 기준으로 명시하고 실제 provider 사용량을 따로 저장함. 아래 본 설계와 4문항용 시험 실행기를 구분함.

2026-11-12. **같은 사건·질문을 누적 세션과 문제별 새 세션에서 짝지어 평가하는 설계임.** 확인된 사건이 차례로 쌓이는 조건에서, 이전 대화·답변 이력의 영향과 기억 선택의 득실을 함께 분석하는 방향임. 현재의 고정 시점 대조는 원인 분해 진단으로 유지함. 새 모델 탐색보다 데이터 버전·입력·예산을 먼저 맞추는 안임.

이번 작업은 자료 목록·사용 안내 보완과 CPU 재생 검사임. 원본 JSON·메시지·라벨·manifest·다른 작업 트리는 수정하지 않았으며 작업자 호출·새 학습·GPU 사용은 없음.

[전체 재검토](reports/2026-11-12-overall-protocol-review.md)를 반영해 같은 총예산의 최근 대화 기준선, 질문 답에서 생긴 원본 기록의 분리, 같은 직전 상태의 제공/보류 비교를 추가함. 아래는 수정된 설계이며 실행기·새 입력의 구현 완료를 뜻하지 않음.

## 1. 처음 질문과의 연결

처음 질문은 “기억이 도움이 되는가”에서 출발해 **“같은 과거 기록도 현재 상태에 따라 어떤 득실을 만드는가”**로 구체화됐음. 누적 세션에서는 다음을 함께 볼 수 있음.

- 같은 예약 기록이 처음에는 필요하고, 변경 뒤에는 잘못된 행동을 유도하며, “처음 예약”을 물으면 다시 필요한지.
- 최근 대화에서 이미 본 사실과 오래전에 저장한 사실을 구분하여 필요한 것을 보충하는지.
- 오래된 기록·닮은 이름·추가 방문이 함께 쌓일 때, 선택한 기억이 실제 답과 비용을 어떻게 바꾸는지.

학습 선택기가 검색이나 전체 제공을 이긴다는 결론을 전제하지 않음. **같은 상태에서 제공·보류·다른 묶음의 결과를 검산할 수 있는 데이터와 평가 절차**도 기여 후보임. 기록의 필요성·유효성은 관계 정답이고, 실제 득실은 고정 작업자의 출력으로 따로 측정함.

이번 여행 세션은 확인된 사실과 상태 변경의 기억을 다룸. 과거 작업 실패에서 얻은 절차의 재사용이나 실제 행동이 환경을 바꾸는 에이전트 전체의 개선으로 범위를 넓혀 해석하지 않음. 좁은 상황에서 기억의 적용성과 실제 득실을 연결하는 평가로 설명함.

## 2. 현재 자료를 세 역할로 구분함

기계가 읽는 역할·해시·미해결 항목은 [기존 데이터 목록](../datasets/catalog.json)의 `current_focus`에 추가함. 다른 옛 자료의 목록과 분할은 유지함.

| 자료 | 역할과 규모 | 다음 사용 |
| --- | --- | --- |
| [상태 관계 증강](../datasets/memory_state_augmentation/20261112-v1/README.md) | 기존 train 11가족, 1,056상태·4,224핵심 입력. 새 출처·실제 득실 없음 | 학습용 관계 감독 후보. 다른 판독기의 입력 계약을 자동으로 충족하지 않음 |
| [이전 상태 대조 보완본](../datasets/memory_state_supplement/20261112-v3/README.md) | 이전 84판단 패킷에서 만든 96쌍·192상태. 기존 4가족의 dev | 고정 조건·근거 누락 진단. 새 납품본과 바로 결합하지 않음 |
| [새 긴 세션 패킷](../datasets/hidden_memory_traps/pilot-20261112-v1/README.md) | 4세션·92판단, 2표현×3길이의 552사례. 실제 득실 없음 | 누적 세션의 사건·표현 출발점. 예산과 선택기 입력 계약을 보완한 별도 버전 필요 |

부모 패킷 manifest는 이전 보완본이 `010189…`, 새 납품본이 `a097c765…`임. 두 패킷에서 같은 기록 키 338행의 본문이 달라졌음. **`memory_id`만으로 라벨·임베딩·결과를 연결하지 않음.** 최소한 `dataset manifest + session + surface + tier + memory_id`로 기록을 식별하고, 실제 본문의 해시도 보존함.

작업자 결과 캐시는 실제 메시지와 모델 revision·tokenizer/채팅 템플릿·디코딩 설정·도구/환경을 포함한 실행 계약으로 구분함. 같은 메시지의 반복 측정은 별도 반복 ID로 남김. 중복 호출을 줄이기 위한 캐시를 독립 반복으로 세지 않음.

## 3. 이번에 정리한 것과 실행 전 보완할 것

| 항목 | 이번 처리 | 남은 일 |
| --- | --- | --- |
| 버전·용도 혼동 | 데이터 목록에 세 역할·manifest·이전 부모를 명시함 | 새 버전 생성 시 부모·코드·입력 해시를 함께 갱신함 |
| UNKNOWN 해석 | 새 README·인계에서 “무기억이 반드시 맞고 기억은 손해만 가능”이라는 설명을 정정함 | 기존 `needs_memory`를 효용/제공 정답으로 학습하지 않음. 정보 충분성과 실제 성공은 별도 판단함 |
| 부가 메시지 설명 | 닮은 이름이 들어 있는 부가 기록 108행을 안내에 반영함 | 예약 사실을 추가하지 않는 방해 문장이라는 범위를 유지함 |
| 전달 예산 | 실제 블록 기준 초과를 사용 안내에 표시함 | 생성기의 packing을 고치고 별도 버전으로 입력·해시·확보율을 재생성함 |
| 총예산·기준선 | 최근 대화만 전체 예산으로 읽는 조건을 주 비교에 추가함 | 채팅 템플릿까지 적용한 최종 입력 상한과 정책별 실제 비용을 검사함 |
| 긴 은행의 선택기 입력 | 전체 은행과 작은 모델의 읽기 범위를 구분함 | 모든 후보에 적용하는 동일한 입력 생성 규칙을 먼저 고정함 |
| 질문 답의 미래 의존 | 아래 CPU 검사에서 정답 의존이 없음을 확인함 | 조회형 질문의 실제 문장·동작 계약과 누적 실행기를 새로 검증함 |
| 질문 답의 원본 기록 | 원본 테이블의 408행이 과거 평가 답에서 생긴 예약 확인임을 집계함 | 새 읽기 전용 은행에서 제외하고 후보·본문·입력·관계 주석을 함께 재생성함 |

예산 문제는 기록별 토큰 합만 세고 머리말·줄바꿈 등을 포함한 실제 블록을 세지 않은 것임. 새 패킷의 552사례에서 2k 조건은 254개, 8k는 132개가 각각 최대 49·50토큰 초과함. 본문 전체를 만들어 후보 추가 때마다 다시 세고, 최종 전달 블록도 검사해야 함. **이 문제는 아직 코드와 원본 입력에서 고치지 않았음.** 현재 패킷의 검색 누락 수 9/2를 수정본 결과로 재사용하지 않음.

UNKNOWN은 12판단이고 그중 4판단에는 무효화 기록이 정답 근거로 필요함. 상수 UNKNOWN 정책이 해당 정답을 맞힌다는 것과, 실제 무기억 작업자가 맞힌다는 것은 다름. 기억이 환각을 줄이는 이득도 측정 가능함. 원본 `protocol.json`의 설계 설명과 `needs_memory` 필드는 그대로 보존하며, 위 안내를 해당 필드의 해석 정정으로 사용함.

M/L에서 후보 주석이 없는 출현은 각각 1,356/4,496개임. 자동 음성으로 넣지 않음. 다른 기록을 함께 봐야 판단되는 주석 20개도 있으므로, 후보 한 개만 주고 원래 정답을 그대로 요구해서는 안 됨.

## 4. CPU로 확인한 누적 실험 전환 가능성

[재현 코드와 사례별 결과](design-data/memory-context-stream-20261112-v1/README.md)를 추가함. 새 생성기나 모델을 쓰지 않고 납품된 공개 패킷을 별도 장부로 다시 계산함.

| 검사 | 결과 |
| --- | ---: |
| 원래 대본처럼 질문의 정답을 새 예약으로 저장한 재생 | 92/92 정답 일치 |
| 질문 답을 저장하지 않고 외부 확인 사건만 갱신한 재생 | 92/92 정답 일치 |
| 각 질문 시점의 접두부만 읽는 재생 | 92/92 정답 일치 |
| 생략한 대본 정답의 예약 저장 | 72회 |
| 이전 질문의 답 기록이 필수 근거인 판단 | 0개 |
| 세션 | 4개, 각 53사건 = 확인 사건 30개 + 질문 23개 |

따라서 현재 사건의 상당 부분을 재사용해 **정답을 과거에 몰래 보충하지 않는 누적 실험**을 만들 수 있음. 다만 기존 요청은 “예약해줘” 같은 행동 문장이므로, 첫 실험에서 읽기 전용으로 쓰려면 “어느 예약/장소가 맞는가”라는 조회 계약으로 다시 렌더링하고 검토해야 함. 정답 집합이 유지된 검사는 새 문장의 의미나 작업자 성능을 검증한 것이 아님.

**정답 장부만 바꾸는 것으로 충분하지 않음.** 원본 `records.jsonl`에는 대본 정답으로 생성한 예약 확인이 S/M/L 각각 136행, 합계 408행 있음. 같은 원 기록의 표현·길이 변형을 포함한 수이며 독립 사건 408개가 아님. 원래 행동 대본에서는 타당한 기록이나, 새 조회형 실험의 외부 확인 사실로 가져오면 안 됨. 현재 후보 주석에서 이 출처의 772출현은 모두 irrelevant이고 필수 근거는 0이므로, 제거 후 정답 보존을 다시 확인하며 은행을 재생성함. C의 실제 이전 답은 대화 이력으로만 남김.

## 5. 먼저 만들 누적 세션

### 공유하는 사건과 누적하는 것

원문 보관소, 현재 작업창, 기억 은행을 구분함.

| 구성 | 규칙 |
| --- | --- |
| 사건 스트림 | 예약 확인·변경·선호·무효화·추가 방문·부가 메시지가 차례로 도착함. 모든 정책이 같은 외부 사건과 질문 일정을 받음 |
| 원문 보관소 | 전체 도착 기록을 수정 없이 보존함. 평가기가 열람할 수 있다는 이유로 작업자에게 전부 주지 않음 |
| 최근 작업창 | 최근 도착한 공개 메시지. 첫 설정은 작업자 tokenizer 기준 최대 2,048토큰으로 제안함 |
| 기억 은행 | 공개 확인 기록을 고정 작성 규칙으로 차례로 추가함. 변경·무효화 때도 옛 기록을 삭제하지 않음. 처음 기록을 묻는 질문에 여전히 필요할 수 있음 |
| 전달 기억 | 최근 작업창과 별도로 최대 2,048토큰. 실제 머리말·구분자 포함하여 셈 |
| 선택기 | 목표·공개 현재 상태·동일한 후보 풀만 읽음. 구조화된 대본/정답/필수 ID는 읽지 않음 |

2k+2k는 첫 설계 설정이지 최종 최적 예산이라는 주장이 아님. 주 비교에는 **같은 가용 예산 4,096토큰을 전부 최근 대화에 쓰는 조건**도 둠. 추가 기억 없음·최근 창 2k는 국소 제공 효과를 위한 제거 진단이고, 2k+2k 정책의 같은 총예산 기준선으로 쓰지 않음. 분배 예산에는 해당 블록의 머리말·구분자·메시지 직렬화 비용을 포함함. 카탈로그·공통 지침·현재 질문·응답 예약 공간은 공통으로 고정하고, 채팅 템플릿을 적용한 최종 입력에도 동일한 총 상한을 검사함. 이 전체 예산 검사기는 아직 구현 전임.

최근 창은 시간상 뒤에서부터 완전한 메시지를 담는 등 고정 규칙으로 구성함. 한 메시지가 상한보다 긴 경우는 저장 시 고정 청킹 규칙을 적용하고 청크를 식별함. 필요한 문장만 정답을 보고 잘라 넣지 않음. 부분 청크를 받아 증거가 부족한 경우도 기록함. 원문 기록 단위의 확보와 사실의 충분성을 구분함.

주 비교에서는 최근 창에 이미 포함된 동일 기록/청크를 추가 기억에서 중복 전송하지 않는 공통 규칙을 적용함. 중복 내용이 있는 서로 다른 기록은 그대로 후보로 남기고 그 비용을 셈. 이 규칙도 데이터와 함께 고정함.

작성기는 확인 사건의 공개 채널만 은행에 추가함. 과거 대본 답이나 C의 모델 답변을 문장이 예약 확인처럼 보인다는 이유로 외부 사실로 저장하지 않음. 원본 기록의 출처를 구분하는 메타데이터는 재생/검증에만 사용하고 함정 종류·정답·유효성 라벨을 선택기에 전달하지 않음.

### 질문 시점과 순서

먼저 기존 순서로 동작을 확인하고, 이어서 **독립 사건들의 순서를 바꾼 사전 고정 일정**을 사용함. 완전 무작위 섞기는 쓰지 않음. 예약 후 변경·무효화, 선호 이후 조건 질문 같은 인과 순서는 지킴. 순서가 바뀌면 각 접두부에서 정답과 관계를 다시 계산함. 기존 시점 라벨을 옮겨 붙이지 않음.

질문은 최근/먼 과거, 변경 전/후, 현재/최초 예약을 포함하도록 결과를 보기 전에 배치함. 과거 기준으로 잘 풀린다는 이유로 어떤 정책에 유리한 질문만 남기지 않음. 이미 최근 창에 답이 있는 상태·UNKNOWN·효과가 없는 상태도 전체 평가에 포함하고 조건별로 나눠 보고함.

문장 수보다 **정답 근거가 최근 창에서 얼마나 멀어졌는지, 유사한 기록이 몇 개 생겼는지, 상태 변경이 몇 번 있었는지**를 기록함. 같은 메뉴·표를 반복한 L 단계만으로 장기 기억의 자연스러움을 주장하지 않음. 길이 실험은 근거 거리와 방해 기록 수를 함께 설명해야 함.

### 두 주 평가 조건을 짝지음

사용자 후속 요청을 반영해 누적/분리를 같은 질문의 주 비교로 둠. 새 세션에서의 단독 해결과 누적 대화에서의 해결을 서로 다른 문항으로 비교하지 않음.

| 조건 | 질문 직전의 입력과 상태 | 다음 질문으로 넘어갈 때 |
| --- | --- | --- |
| **D: 문제별 분리 세션** | 매 질문마다 새 대화를 시작함. 그 시점까지의 확인 사건에서 만든 최근 작업창과 같은 시점의 기억 은행을 제공함. 이전 평가 질문·모델 답변·정책 내부 상태는 넘기지 않음 | 답은 평가 로그에만 저장함. 다음 질문의 은행은 공통 외부 사건 접두부에서 다시 구성함 |
| **C: 하나의 누적 세션** | 같은 외부 사건이 도착하는 대화를 이어가며, 이전 질문과 해당 정책의 실제 답변도 최근 작업창의 후보에 남김 | 질문·답변 이력을 계속 보존하되 실제 모델 입력은 정한 창 크기로 제한함. 답변을 확인된 예약 사실로 승격하지 않음 |

D에서도 과거 정보에 접근할 수 있음. 새 세션이라고 은행을 비우거나, 정답에 필요한 근거만 골라 주지 않음. C와 D의 질문 ID·시점·외부 확인 사건 접두부·은행 본문 해시는 같아야 함. 모델·작성 규칙·선택 정책·디코딩·최근 창과 전달 기억의 예산 상한도 고정함. 실제 주입 기록은 정책과 현재 입력에 따라 달라질 수 있음.

C와 D 모두 대화 원문은 보존하며, 작업자가 읽는 것은 예산 안에서 직렬화한 메시지임. C만 모델 문맥 한도를 넘도록 계속 붙이는 방식은 쓰지 않음. 같은 세션이라는 이름이나 세션 ID만 바꾸고 실제 메시지·상태가 같으면 별도 기억 조건이 되지 않음. API의 암묵적 이력·외부 저장소에 의존하지 않고 모델이 실제로 읽은 메시지와 상태를 기록함.

최근 창은 같은 상한을 쓰지만 **실제 보이는 사실까지 같아지는 것은 아님.** C의 이전 질문·답변이 확인 사건을 밀어낼 수 있음. 이 차이는 주 비교에서 누적 대화의 전체 효과에 포함하고, 질문마다 확인 사실/과거 질문/자기 답변의 토큰과 필요한 근거의 가시성을 나눠 기록함. 두 조건의 점수 차이를 곧바로 오답 전염이나 기억 선택 오류라고 부르지 않음.

C에서는 한 질문의 답이 다음 질문의 입력에 영향을 주므로 같은 세션의 질문을 독립 실행으로 병렬화하지 않음. D의 질문은 각 접두부가 고정되면 독립 실행할 수 있음. 재실행도 질문 하나만 임의로 바꾸지 않고 누적 모드의 반복 ID와 전체 선행 답변 경로를 보존함.

기존 **공통 접두부 분기 진단**은 D의 기반으로 유지함. C에서 실패한 시점의 실제 상태를 저장해 기억 묶음만 바꾸거나, 보이는 확인 사실과 제공 기억을 고정한 채 이전 답변을 제거하는 재생 진단도 가능함. 후자는 입력 길이도 달라지므로 자기 답변 내용의 영향과 길이 효과를 완전히 분리한 증거는 아님. 필요하면 결과 확인 전 정한 길이 대조를 추가함.

**모델의 실제 예약 행동이 환경을 바꾸는 완전한 자율 진행은 별도 후속 단계**임. 현재는 조회 답변이 환경의 진실을 바꾸지 않으며, 공통 외부 사건으로 정답을 계산함.

## 6. 선택기 비교와 기록

첫 구성은 hidden/M·4설계 세션·고정 순서·고정 작업자 1종을 제안함. S는 동작 점검, L은 길이 스트레스에 남김. 모든 길이·표현·모델·순서의 조합을 한 번에 실행하지 않음.

| 정책 | 목적 |
| --- | --- |
| 최근 대화만 4k | 같은 총 가용 예산에서 외부 기억 검색 없이 해결할 수 있는지 보는 주 기준선 |
| 추가 기억 없음·최근 창 2k | 2k+2k 조건에서 추가 기억만 제거하는 진단. 위 4k 기준선과 구분함 |
| BM25 검색 | 같은 추가 전달 예산의 단순 기준선 |
| 공개 상태 규칙 | 라벨이 아닌 도착한 문장에서 예약·변경 등을 판독하는 규칙 기준선 |
| 학습 선택 | 후속 모델 연구의 비교 후보. 현재 누적/분리 측정의 필수 조건이 아님 |
| 필요한 근거만 / 필요한 근거+방해 기록 | 라벨을 사용하는 원인 진단. 실행 가능한 정책이나 성능 상한으로 취급하지 않음 |
| 전체 이력/전체 기록 | 모델 한도가 허용할 때만 별도 진단. 2k 전달 정책과 같은 예산인 것으로 표시하지 않음 |

긴 은행 전체를 작은 판독기에 넣지 않음. 고정 검색기로 예를 들어 상위 32기록의 공통 후보 풀을 만들고, 최근 창·현재 질문·후보 및 공개적으로 검색한 보조 근거를 정해진 형식으로 제한함. 32는 설계 출발값이며 최종 입력 tokenizer의 길이를 보고 고정함. 긴 기록의 청킹, 보조 근거 조회 수, 묶음화 비용도 모든 후보에 같은 규칙으로 적용함.

처음에는 목표+현재 상태로 공통 후보 풀을 한 번 만들고, 그 풀을 고정한 채 목표만 읽는 판독기와 현재 상태도 읽는 판독기를 비교하면 **후보 생성 이후의 판독 효과**를 볼 수 있음. 이 경우 후보 생성기가 이미 상태를 사용했다는 사실을 명시함. 파이프라인 전체에서 상태 입력의 효과를 보려면 목표만 쓰는 검색기+판독기와 상태를 쓰는 검색기+판독기를 별도로 비교해야 함.

정답의 `judge_with`를 특정 후보에만 붙이지 않음. 보조 근거가 후보 생성에서 빠지면 정보 부족으로 기록하고, 필요한 ID가 원 은행에 있었는지도 함께 셈. 작업자가 정답을 틀렸다는 이유로 관계 양성을 음성으로 바꾸지 않음.

현재 측정에서는 주 모델·은행·기억 전달 정책을 고정함. 초기 구현은 기존 BM25 예산 정책을 사용할 수 있으며, 검색 모델의 우열을 비교하는 실험으로 확대하지 않음. 학습 선택기가 기본 검색보다 낫다는 별도 주장을 검증할 때 기본 Harrier 등 기준선을 검토함. 학습 모델의 기반 encoder로 Harrier를 사용한다는 사실과 별도 비교군을 추가하는 것은 구분함.

질문마다 도착 사건 접두부·최근 창·은행·후보 풀·선택 ID/실제 메시지 해시, 각 구성의 실제 토큰, 선택 시간·작업 시간, 원 출력·채점을 저장함. 세션 모드에서는 이전 답변 이력과 정책별 상태도 보존함.

첫 주 비교는 **D/C × 최근 대화만 4k/고정 전달 정책의 최근 2k+기억 2k**임. 같은 직전 상태의 제공/보류 분기를 함께 두어 국소 득실을 따로 측정함. Harrier·다른 검색기·새 학습 모델의 경쟁은 이번 필수 비교에서 제외함. 정답 근거·전체 제공·규칙 진단은 별도 배정으로 표시함. D/C 결과 중 한쪽에 맞춰 방법을 수정한 뒤 다른 쪽을 독립 확인이라고 부르지 않음.

## 7. 지표와 해석

관계 단계는 필요한 근거 확보, 무효/다른 사람 기록 제공, 이미 관측한 사실의 중복 제공, 근거 부족을 보고함. 기록 ID 확보가 사실의 의미적 충분성을 자동 보장하지 않음을 명시함.

작업 단계는 질문별 정답·근거 없는 구체 답변·적절한 UNKNOWN을 보존함. 같은 직전 상태의 제공/보류에서는 개선/악화/둘 다 성공/둘 다 실패를 집계함. UNKNOWN 출력 자체가 언제나 적절한 보류인 것은 아님. 정답과 확인 근거에 따라 채점함. 원문이 제공되지 않아 지침대로 보류한 것과, 충분한 근거가 있는데 작업자가 잘못 적용한 것을 구분함. 한 묶음의 실제 효과를 구성 기억 각각의 인과 효과로 분배하지 않음.

같은 질문 접두부에서 제공/보류를 비교하면 **국소적인 득실**, 답변 이력까지 쌓인 세션 전체를 비교하면 **정책의 누적 효과**임. 한 번의 생성은 관측된 결과 쌍이며 성공 확률의 차이라고 단정하지 않음. 반복은 사전 고정한 질문 구간에서 함께 수행하고 개선한 사례만 재실행하지 않음.

**국소 득실의 짝은 사건 시점만 같아서는 안 됨.** C의 검색 정책 실행과 C의 무기억 실행은 이전 답변이 달라 질문 직전 상태도 달라질 수 있음. 같은 상태의 결과처럼 합치지 않음. 국소 득실은 한 실제 궤적의 질문 직전 상태를 저장한 후, 이전 답변·최근 창·은행·작업자 설정을 그대로 둔 제공/보류 분기에서 측정함. 분기 결과를 다음 실제 궤적에 정답으로 합치지 않으며, 계속 진행할 주 경로도 사전에 정함.

결과 키에는 `mode / policy / trajectory_repeat_id / query_id / predecision_snapshot_sha256 / action / input_sha256`을 포함함. 제공/보류의 실제 입력 해시는 달라져도, 기억 추가 전 스냅샷과 실행 계약은 같아야 국소 득실 쌍으로 인정함. 서로 다른 상태의 결과를 짝짓는 것을 실행기에서 거부함. 동일 상태의 메모리 제거 비교와 같은 총예산의 최근 대화 기준선은 서로 다른 질문이므로 별도 결과로 보존함.

### 분리/누적의 차이를 읽는 법

각 정책에서 같은 질문을 다음 네 칸으로 집계함. 이는 분리/누적의 결과 대조이며, 기억 제공/보류의 득실 네 범주와는 별도 표임.

| 분리 D | 누적 C | 우선 확인할 내용 |
| --- | --- | --- |
| 성공 | 성공 | 두 조건에서 유지되는 해결 능력. 같은 기억을 제공했는지와 비용도 비교함 |
| 성공 | 실패 | 누적 조건의 악화 사례. 근거 밀려남·선택 변경·이전 오답 재사용을 각각 점검함 |
| 실패 | 성공 | 누적 이력이 보완한 사례. 유용한 이전 답변·반복 언급·추가 근거를 점검함 |
| 실패 | 실패 | 공통 실패 사례. 근거 부족·작업자 오용·형식 오류를 먼저 분리함 |

위 해석은 원인 후보임. 출력에 과거 오답과 같은 장소 ID가 있다는 것만으로 인과를 확정하지 않음. 질문 직전 상태를 고정한 재생 진단으로 선택/작업 단계의 변화를 확인함.

정책 `p`마다 `세션 격차(p) = 성공률(C,p) − 성공률(D,p)`를 보고함. 이어서 `같은 총예산 대비 정책 이득 = 성공률(조건,p) − 성공률(조건,최근 대화만 4k)`을 따로 보고함. C에서는 각 정책이 만든 이전 답변 경로까지 포함하는 세션 수준 비교임. 두 조건의 정책 이득 차이는 누적 환경에서 상대 효과가 커졌는지 보는 기술 통계이며, 개별 기억의 국소 득실이나 네 파일럿을 넘는 일반적인 효과·유의성을 단정하지 않음.

질문 순서에 따른 성공 추이·첫 오답 시점·오답 이후 회복·오답과 같은 값을 되풀이한 빈도를 보조 분석함. 전체 92질문과 사전 정의한 상태 변경/근거 거리 구간을 함께 보고하고, 관측된 성패를 기준으로 주 평가 집합을 고르지 않음. 가족별 쌍 차이를 우선 집계하며, 누적 세션의 각 질문을 독립 표본으로 처리하지 않음.

성공·손해·토큰·지연을 먼저 각각 보고함. 비용 가중 효용 `성공 이득 − 토큰/지연 비용`은 가중치를 결과 확인 전에 정하거나 민감도 분석으로 제시함. 선택기의 읽기·임베딩·조회 비용도 포함함. 처음부터 하나의 임의 점수로 모든 득실을 합치지 않음.

독립 단위는 원천 가족/세션임. 4파일럿의 92질문이나 여러 순서 seed를 독립 표본으로 세지 않음. 세션별 점수와 차이를 먼저 보고하고, 충분한 새 가족에서 가족 단위 신뢰구간을 사용함.

## 8. 보존할 분할과 다음 순서

현재 4파일럿은 설계 dev이며 새 최종 test가 아님. 본 자료 후보 20가족도 stage1 노출 이력이 있으므로 프로젝트 전체에서 미사용 출처라고 하지 않음. `new-b` 40가족은 계속 봉인하며 내용·정답을 열지 않음. 같은 가족의 순서·길이·표현 변형은 같은 분할에 둠.

다음은 **예산 수정·질문 답 원본 기록 분리 → 누적/분리 입력 계약과 새 조회 문장 → 4세션 CPU 접두부·은행·스냅샷 짝 검사 → D/C 기준선 동작 점검 → 같은 문항의 누적/분리와 제공/보류 분석** 순서가 적절함. 작업자 비교 이전에 모드·질문 일정·예산·청킹 규칙과 각 실행에서 저장할 입력 형식을 고정함. C의 실제 메시지 해시는 선행 답변이 생성된 뒤 매 시점 저장함. 새 본 자료에서 학습·평가 역할을 정할 때는 가족 단위로 먼저 예약하고, 기존에 결과를 본 자료의 용도를 유지함.

4세션의 같은 92질문을 두 모드·2전달 조건으로 실행하면 368질문 배정임. 이전의 4모델/정책·736배정안은 현재 측정의 범위에서 제외함. 같은 직전 상태의 제공/보류 분기·2k 제거 진단·규칙·정답 근거·반복·오류 재시도·선택기의 별도 호출은 포함하지 않은 계획 단위이며 시간·요금 추정은 아님. 실제 메시지와 실행 계약이 같은 경우에는 출력을 공유할 수 있으나 이를 독립 반복으로 부풀리지 않음. C의 다음 입력은 선행 답변에 따라 달라지므로, 전체 고유 호출 수를 실행 전에 위 배정 수와 같다고 단정하지 않음.

현재까지 확인한 것은 **기존 사건을 재사용하면서 대본 정답의 미래 주입 없이 누적 평가를 만들 수 있다는 것**임. 누적 상태에서 선택기가 이득을 주는지, 답변 이력의 오류를 줄이는지, 새 출처에서도 통하는지는 아직 측정 전임.
