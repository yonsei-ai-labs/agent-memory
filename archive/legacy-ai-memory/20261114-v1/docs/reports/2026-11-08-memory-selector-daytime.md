# 11월 8일: 기억 선택 모델의 학습·자료·평가

시작 07:29 KST, 검토 목표 18:00 KST. [작업 계획](../ai-memory-daytime-2026-11-08-plan.md)의 비용·원본 보존 범위 안에서 학습·실제 효용·두 번째 seed 반복과 공유 검사를 완료했다. 같은 확인 자료에서 더 좋은 모델을 계속 고르는 대신, 실패 조건과 다음 데이터 요건까지 정리했다.

## 먼저 읽을 판단

**기존 모델은 손상되지 않았다. 관계 판독을 개선할 수는 있었지만, 실제 기억 선택의 일반화와 비용 이득은 아직 입증하지 못했다.** 작은 모델·새 손실·추가 layer를 비교하는 방향은 실험 가능하다. 다만 좋은 확인 점수만 고르기보다, 개발에서 고른 정책이 새 환경에서도 고정 기준선을 이기는지를 중심에 둬야 한다.

이번에는 실제 작업자의 기억 제공·보류 결과까지 연결했다. 확인 28상태의 결과는 다음과 같다. 9B에서는 **4B에서 이미 정한 선택**을 그대로 사용했다.

| 정책 | Qwen3.5-4B | Qwen3.5-9B |
| --- | ---: | ---: |
| 무기억 | 15/28 | 18/28 |
| 개발에서 고른 고정 절차 | 14/28 | **21/28** |
| 항상 전체 기억 | 11/28 | 17/28 |
| 사전 주 선택기: 가치 회귀 | 13/28 | 16/28 |
| 선호 학습, 두 seed 각각 | **17/28** | 20/28 |
| 개발에서 고른 작은 보정층 | 11/28 | 16/28 |

선호 학습은 탐색적으로 긍정적이다. 4B·9B에서 각 seed가 무기억의 성공을 해치지 않고 2개씩 개선했다. 그러나 개발에서는 이 방법을 고르지 못했고, 9B에서는 사전에 고른 고정 절차보다 낮았다. 4B에서도 확인을 사후에 보고 고른 고정 기억은 17/28이었다. 따라서 학습한 선택기가 꼭 필요한지의 답은 아직 아니다.

주 선택기의 추가 Harrier 인코딩은 상태당 평균 0.456초였다. 28상태의 선택·작업 시간을 별도 단계의 warm 측정값으로 더하면 59.27초, 무기억 작업자는 40.62초였다. 주 모델은 성적도 낮으므로 현재 구성에서는 이 비용의 보상이 없다. 실제 한 프로세스의 end-to-end 측정은 아니며 모델 다운로드·초기화도 제외했다.

자세한 근거는 [4B 실제 효용 결과](../../training/memory_selector/reports/2026-11-08-api-worker-utility-results.md)와 [9B 전이 결과](../../training/memory_selector/reports/2026-11-08-api-worker-transfer-results.md)에 있다.

## 무엇을 새로 배웠나

**원래 checkpoint가 망가진 것은 아니었다.** 원래 다섯 모델의 기존 1,170행 예측이 전부 재현됐다. 새 어려운 범위 대조에서 원래 LoRA는 1/24·4/24, 원래 대조 LoRA는 0/24·2/24였다. 원래 모델이 두 역할의 차이를 충분히 배우지 못했다는 해석이 맞다. [원래 모델 재평가](../../training/memory_selector/reports/2026-11-08-original-model-recheck.md).

**단순 LoRA 외의 학습 신호는 차이를 만들었지만 반복에서 안정적이지 않았다.** 첫 seed의 같은 초기화·대조 배치에서 두 판단의 gradient 충돌을 완화한 PCGrad는 기본 CE보다 외부 범위 정답 69→81/108, 핵심 역할 대조 4→14/24로 개선됐다. 그러나 같은 예산의 두 번째 seed에서는 전체 75→65/108로 악화됐고 어려운 조건은 둘 다 0/24였다. PCGrad의 어려운 학습 조건도 첫 seed 259/296에서 둘째 2/296로 달랐다. 충돌 보정만으로 실패를 해결했다고 할 수 없다. 문자열 규칙으로 풀 수 있는 좁은 진단이며 실제 기억 효용과 별개다. [첫 방법 비교](../../training/memory_selector/reports/2026-11-08-scope-method-comparison.md), [두 seed를 함께 본 결과](../../training/memory_selector/reports/2026-11-08-scope-method-repetition.md).

**추가 layer가 자동으로 이득을 주지는 않았다.** 고정된 문장 끝 표현에 attention reader를 학습하거나 평균을 빼서 보정하는 비교는 두 seed에서 안정적 개선을 보이지 못했다. 고정 head의 학습을 늘리는 것만으로 일부 성적이 좋아져, 처음의 LoRA 우위를 모두 encoder 학습의 효과로 설명할 수도 없었다. 작은 semantic head는 개발에서 좋아졌다가 확인에서 악화됐다.

**학습 신호가 사라지는 문제와 일반화 문제는 별개였다.** 직접 기대 성공 목표는 4,096회로 늘려도 학습 26/50에 머물렀다. 틀리게 확신한 상태의 성공 확률과 gradient가 거의 0이 됐다. 같은 초기값·512회에서 성공 행동 집합의 log 확률을 학습하니 두 seed 모두 31/50으로 올랐지만 개발은 5/18로 나빠졌다. 이 사후 진단은 학습·개발에서만 했고 기존 확인 성적을 다시 고르는 데 쓰지 않았다. [목표함수 진단](../../training/memory_selector/reports/2026-11-08-api-utility-optimization-results.md).

## 데이터의 역할과 한계

새 API 자료는 실제 라이브러리의 34개 구현·일곱 가족을 두 입력씩 544번 실행해 만들었다. 학습 200행/50상태, pandas 개발 72행/18상태, NetworkX·scikit-learn 확인 112행/28상태다. 각 상태의 과거 절차 후보 네 개를 독립 과제로 합산하지 않는다. 과거 성공 근거와 현재 선택 전 관측, 직접 적용 정답, 실제 작업자 득실을 분리했다. [자료](../../datasets/api_transfer/20261108-v1/README.md), [분할·실행 감사](data/api-transfer-20261108/data-audit.json).

직접 적용성을 판독한 26개 모델에서 일반 LoRA는 확인 76/112, 실행 속성 보조는 75/112, 속성 병목은 87/112, 구문 tree는 84/112였다. macro-F1은 tree 0.736이 속성 병목 0.717보다 높았다. 직접 후보 선택 성적은 또 달랐다. 임계값 0.5에서 일반 LoRA는 10개 선택 중 9개가 통과했지만 보조 감독은 10개 중 2개만 통과했다. 버전 때문에 정답이 바뀌는 두 대조에서는 26개 모델 모두 두 버전을 함께 맞히지 못했다. [API 판독 결과](../../training/memory_selector/reports/2026-11-08-api-transfer-results.md).

작업자 효용은 그 라벨을 복사하지 않고 4B의 96상태×10행동에서 새로 측정했다. 21개 head의 학습은 50상태, 선택은 18상태에서 했다. 960개 생성이 960개 독립 경험을 뜻하지 않는다. 개발 가족이 하나뿐이고 많은 모델을 비교했기 때문에 개발의 최고값 자체가 불안정하다.

더 구체적으로, 학습 50상태 중 선택 행동에 따라 성공·실패가 갈린 것은 31개였다. **개발 18상태에서는 고정 절차가 이미 관측한 아홉 행동의 성공 상한 11개에 도달했다.** 상황별 선택으로 성공 수를 더 높일 여지가 없었고, 작업자 토큰 27개 차이로 작은 보정층을 골랐다. 그 동률 판정에는 선택기 계산 비용도 빠져 있었다. 확인의 “최선 고정 행동 → 상태별 oracle” 간격도 4B는 17→21개, 9B는 21→22개로 작았다. 다음에는 개발 출처의 다양성과 실제 선택 여지를 함께 점검해야 한다. 확인 결과를 보고 유리한 상태만 골라 남기지는 않는다.

원문 전체와 절차만 제공한 확인 112개 후보 쌍에서는 전체가 나은 경우 4개, 절차만 나은 경우 5개였다. 전체 기억이 추가하는 여러 사실과 길이가 함께 바뀌므로 특정 정보 조각의 효과로 해석하지 않는다. 같은 단일 기억 행동의 무기억 대비 효과는 작업자를 4B에서 9B로 바꾸자 224개 중 46개에서 달라졌다.

현재 과제는 사람이 작성한 작은 유형별 처리 코드로 96상태 모두 풀렸다. 처음에는 sparse 정렬 metadata를 놓쳐 학습 2개가 실패했으며 수정 전후를 보존했다. 이는 과제가 불가능해서 모델이 실패한 것은 아니라는 근거이면서, **이 자료만으로 별도 기억 에이전트의 필요성을 주장하기에는 범위가 좁다**는 한계다. 사후 인간 코드를 사전 모델 비교의 승자로 넣지는 않는다. [가능성 확인](../../training/memory_selector/reports/2026-11-08-api-task-feasibility.md).

## 다음 연구를 어떻게 좁힐까

작은 모델의 역할은 계속 “현재 조건에서 이 경험을 썼을 때 생길 이득·손해를 구별하는 것”으로 두는 것이 적절하다. 직접 적용 가능성은 보조 신호, 실제 작업자의 제공/보류 결과는 최종 검증으로 유지한다. 이번처럼 양성 성적이 나온 모델 하나만 고르지 말고 개발 선택의 실패도 포함해야 한다.

다음 주요 자원은 layer 추가보다 **새 독립 경험과 다양한 개발 조건**에 쓰는 편이 타당하다. 초기화가 필요한 상태/이미 충족된 상태, 현재 검사 범위와 과거 검사 범위가 다른 상태, 과거 수정법이 직접 적용되거나 원리만 남는 상태를 실제 로그에서 확보한다. 미래 실패·공식 정답·기억을 받은 뒤의 명령을 시작 시 선택 입력으로 쓰지 않는다. 관계 라벨의 불확실성과 실제 득실도 분리한다.

학습 후보로는 상태 안의 선호 학습, 포화를 줄이는 성공 집합 log 목표, 조건의 속성을 함께 배우는 보조 감독을 남길 수 있다. 각각 새 출처에서 검증할 후보이며 이번에 일반 효능이 입증된 방법은 아니다. 문헌과의 관계는 [추가 문헌 노트](../ai-memory-daytime-literature-2026-11-08.md)에 정리했다.

이 방향의 출처도 제한해서 검토했다. 공개 로그의 고정된 1,024개 trajectory 구간에서 처음 20개 오류 기록, 이어서 다른 16개 가족의 첫 오류를 대조했다. 총 36개 호출·19개 가족 중 전제와 후속 진행이 연결되는 후보는 8개·4개 가족이었다. 설치 명령이 성공했어도 전제가 채워지지 않은 경우, 같은 import 오류에 다른 처방이 필요한 경우, 좁은 검사만 진행된 경우를 구분했다. **학습 행과 실제 효용 라벨은 아직 만들지 않았다.** [원문 근거·제외 사유·다음 데이터 조건](../design-data/memory-prerequisite-sources-20261108/README.md).

## 검산과 자원

4B와 9B의 실제 checkpoint shard·tokenization·prompt·출력·반복을 검산했고 모두 회수 후 종료했다. 4B 생성 코드 964개, 2,494개 fixture/world 실행을 pinned 환경에서 새로 반복해 실행 시간 외의 trace가 재현됐다. 실제 head checkpoint의 8,694개 행동 점수도 재계산했다. 공유본에서 표준 라이브러리만으로 정책과 실행 결과의 연결을 확인할 수 있다.

```bash
python3 -m data_pipeline.verify_api_worker_utility datasets/api_worker_utility/20261108-v3
python3 -m evaluation.verify_api_utility evaluation/results/api-worker-utility-20261108
python3 -m evaluation.verify_api_worker_transfer datasets/api_worker_utility/20261108-9b-transfer-v1
```

공유 대상 6,942개 파일만 복사한 새 임시 사본에서 `python -S`로 추가 패키지를 차단하고 README 첫 실행·데이터 감사·모든 공유 예측·실제 효용 연결·학습 내보내기·검사를 포함한 **25개 명령을 모두 통과**했다. 원시 출력과 가중치는 사본에 없었다. 측정 테스트 74개와 평가 테스트 21개도 통과했다. 로컬 학습 검사는 92개 중 5개가 Torch 부재로 skip됐고, 그 5개는 별도 CPU Torch 환경에서 전부 통과했다. 새 사본에서 이전 생성 자료가 없어 skip된 class와 항목은 구별해 기록했다. [검사 요약](data/daytime-20261108/final-checks.json), [공유 사본 재현 기록](data/daytime-20261108/fresh-share-check.json).

원래 고정 파일 **5,528개**, 최초 학습 산출물 **54개**, 기존 전역 실행 **318행**과 해시가 모두 보존됐다. [마지막 보존 검사](data/daytime-20261108/original-preservation-final.json).

로컬 Laya GPU와 유료 모델 API는 사용하지 않았다. Colab은 자기 L4 한 개씩 총 14회 순차 사용했고 모두 결과를 회수·종료했다. 공유 검사 뒤에도 **활성 할당 0·사용률 0**을 확인했다. 시작 593.70→마지막 587.19 CU로 관측 감소는 **6.51 CU**, 초기 8 CU 목표 안이다. 청구 반영 시차가 있어 정밀한 실행별 요금이나 확정 청구액을 뜻하지 않는다. [실행별 잔액·종료와 전체 자원 기록](data/daytime-20261108/resources.json).
