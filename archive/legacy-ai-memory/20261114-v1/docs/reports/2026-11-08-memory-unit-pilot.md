# 과거 초기화 정보를 나눠 제공한 첫 실행

**출처의 초기화 정보를 추가하면 정해 둔 현재 설정 계약을 만족한 실행이 1/8에서 6/8로 늘었다. 그러나 작은 선택기를 학습할 필요성은 아직 확인되지 않았다.** 초기화 정보만 항상 제공해도 6/8이었고, 관측한 다섯 행동 중 상태마다 최선을 골라도 6/8이었다.

이번 결과는 Django 한 출처 경험에 연결된 두 실제 코드 버전과 연구자가 구성한 여덟 프로세스 상태의 진단이다. 새로운 자연 SWE 과제 여덟 개나 패치 해결률로 해석하지 않는다. 추가 선택기 학습은 진행하지 않았다.

## 원래 연구 목표와 이번 실험의 위치

사용자의 방향 재점검 요청에 따라 [원래 연구 질문](../ai-memory-direction-reassessment-2026-11-07.md)과 대조했다. 목표는 **작은 별도 모델이 현재 상태와 과거 경험을 함께 읽고, 기억의 제공·보류를 학습해 실제 코드 작업의 성과와 비용을 개선하는가**다. 같은 경험에서 무엇을 보존해야 하는지에 대한 득실 분석은 그 판단을 설명하고 학습 신호를 만드는 역할이다. 관계 분류 정확도나 초기화 코드의 정답률만으로 목표 달성을 판단하지 않는다.

이번에는 정보 복원 효과를 실제 실행에 연결하고 평가 계약을 분명히 한 진전이 있다. 다만 현재 프롬프트에도 필요한 모듈·경로가 있고 상태를 연구자가 구성했으므로, 과거 경험의 고유 가치와 일반적인 초기화 예시의 효과를 분리하지 못했다. 자연스러운 작업 중의 기억 선택보다 좁은 초기화 문제에 무게가 실렸다. 이 자료에서 반복 학습이나 층 추가만 계속하면 원래 목표와 거리가 생긴다.

자료의 양도 구분한다. 이번 40개 기본 생성은 8상태×5조건이고, 독립적인 출처 가족은 하나다. [이전 API 자료와 선택 학습](2026-11-08-memory-selector-daytime.md)을 대체하거나 폐기한 것이 아니라 별도의 진단 자료를 추가한 것이다. 기존 자료까지 합쳐 행 수를 늘려도 실제 경험의 다양성이 충분해지는 것은 아니다.

다음 실험의 권고 기준은 아래와 같다. 아직 새 데이터 수집·학습을 수행했다는 기록은 아니다.

1. **실제 개발 경험과 별도의 현재 작업을 연결한다.** 판단 시점을 하나로 고정하고, 기억을 보기 전의 현재 관측만 선택기에 준다. 과거 경험이 추가하는 정보와 현재 오류·문서만으로 알 수 있는 정보를 구별한다. 출처 근거·재현 가능성을 기준으로 후보를 고르고, 기억 효과가 좋게 나온 사례만 남기지 않는다.
2. **같은 현재 상태에서 제공·보류를 실행한다.** 성공·회귀·토큰·지연의 차이를 별도로 기록한다. 항상 같은 기억, 검색, 전제 확인 규칙과 일반 코드 예시도 비교한다. 중복·무효·단순한 해법으로 충분한 사례를 보존한다. 작은 성공률 표본만으로 선택의 기대 이득을 확정하지 않는다.
3. **별도 작은 모델의 학습과 독립 평가로 연결한다.** 독립 출처를 확보하고 파생 자료 생성 전에 가족별 분할을 정한다. 관계 주석은 보조 감독, 실제 제공 결과는 정책 학습·평가 근거로 구분한다. 선택기를 포함한 비용을 세고, 새로운 출처에서 고정 제공·무기억·단순 정책보다 좋아지는지 확인한다. 직접 실행한 초기화 규칙 8/8은 실행 가능성 대조이며 기억 선택 정책의 승리로 세지 않는다.

이번 결과에서 학습한 선택기의 필요성이 입증되지 않았다는 사실은 그 연구 목표를 포기한다는 뜻은 아니다. 동시에 선택기가 필요해 보이도록 자료를 구성해서도 안 된다. 다음 자원은 이 한 가족의 성적 최적화보다 독립 경험의 수와 현재 작업과의 연결을 늘리는 데 우선 배분하는 것이 적절하다.

## 비교한 정보와 현재 상태

과거 경험은 `django__django-11019` 실행의 기존 수정 절차 카드 P와, 그 카드에서 빠진 초기화 관측 E다. E는 source의 agent 명령 17번(0부터 센 agent-only 순서, 전체 명령 파일에서는 22번)에 연결된다. 실제 명령은 `PYTHONPATH=tests:. DJANGO_SETTINGS_MODULE=test_sqlite` 환경에서 `import django; django.setup()`을 실행한 뒤 forms 재현을 진행했다. P는 Media 순서 문제의 잠정 수정 절차이며, source의 공식 평가 미완결·미해결 상태를 그대로 유지했다.

E는 초기화 과정의 사실·코드 예시이고 P는 기존 수정 절차다. 이를 일반적인 ‘서술형 근거 대 지시형 처방’ 비교로 부르지 않는다. 두 정보에는 과거 로컬 결과 일부가 겹치며, E를 더하면 내용과 길이가 함께 바뀐다.

실제 Django 14534·16041 checkout의 고정 Docker image에서 다음 네 프로세스 상태를 각각 구성했다.

| 상태 | 이미 실행된 설정 | 추가로 필요한 일 |
| --- | --- | --- |
| cold | Django만 import, 설정 모듈과 tests 경로 없음 | 현재 checkout의 설정 모듈과 경로를 지정하고 앱 초기화 |
| environment_only | tests 경로와 `DJANGO_SETTINGS_MODULE=test_sqlite` 지정 | 앱 초기화 |
| configured_not_ready | 별도 설정이 이미 구성됨 | 기존 설정을 유지하고 앱 초기화 |
| ready | 별도 설정과 앱 초기화 완료 | 기존 상태 유지 |

모든 조건은 현재 prelude와 같은 작업 계약을 받았다. 현재 프롬프트에도 `test_sqlite` 모듈명과 파일 경로가 들어 있다. 따라서 E의 효과를 새로운 저장소 고유 사실을 처음 알려준 효과로 한정할 수 없다. 올바른 절차 예시가 작업자의 실행 방식을 바꾼 효과일 수 있다.

과거 source와 두 target 버전은 이전 연구 설계에 사용됐다. 여덟 상태 모두 `diagnostic`이며 하나의 연결 가족으로 묶었다. train/dev/test로 나누거나 문장 변형을 독립 표본으로 세지 않는다. [고정 자료와 설계](../../datasets/memory_units/20261108-django-startup-pilot-v1/README.md), [실행 전 고정 기록](data/memory-unit-pilot-20261108/pre-model-freeze.json).

## 결과

작업자는 이전 실험과 같은 Qwen3.5-4B revision이다. BF16, non-thinking, greedy, 최대 입력 4,096·출력 256 token을 사용했다. 8상태×5조건의 40개 출력과 동일 prompt 재생성 4개를 수집했다. 사전 조건과 출력 한도는 결과에 따라 바꾸지 않았다.

주 지표는 **앱 초기화와 forms probe 실행, 요청된 설정 모듈 사용 또는 기존 설정 보존을 함께 만족했는가**다. 보조 지표는 설정 모듈 계약을 제외하고 실제 probe 렌더링까지 진행했는가다.

| 제공 조건 | 현재 설정 계약까지 통과 | probe 렌더링까지 진행 | 무기억 대비 개선 / 악화 |
| --- | ---: | ---: | ---: |
| 무기억 N | 2/8 | 2/8 | — |
| 수정 절차 P | 1/8 | 5/8 | 1 / 2 |
| 수정 절차 + 일반 주의 안내 P+G | 2/8 | 4/8 | 1 / 1 |
| 초기화 관측 E | 6/8 | 6/8 | 4 / 0 |
| 수정 절차 + 초기화 관측 P+E | 6/8 | 6/8 | 4 / 0 |

사전에 정한 주 비교 P+E−P는 계약 통과 수에서 +5다. **렌더링만 보면 5→6으로 +1**이다. P의 네 실행은 자체 설정을 만들어 probe를 실행했지만, 현재 checkout의 설정 모듈을 사용하라는 요구를 지키지 않았다. ‘초기화 실패 다섯 개를 모두 해결했다’고 요약하면 안 된다.

기존 설정 보존의 v1 실행 검사는 `DEBUG`와 `MEMORY_PILOT_MARKER`를 비교한다. 모든 설정·Django 전역 상태의 무변경을 증명하는 검사는 아니다. 설정 모듈 검사는 `SETTINGS_MODULE`을 사용한다. 관측된 모듈 불일치 여섯 건은 새 설정을 직접 작성한 코드였으며, 등가 설정을 복사한 모든 가능한 프로그램의 타당성을 검증한 것은 아니다.

결과를 확인한 뒤에는 기존 설정이 있는 20개 코드를 재실행해 prelude의 여섯 설정(`SECRET_KEY`, `INSTALLED_APPS`, `USE_I18N`, `DEBUG`, `MEMORY_PILOT_MARKER`, `TEMPLATES`)을 모두 비교했다. 기존 통과 사례에서 변경은 없었고, 원래 실패한 P의 한 사례만 `INSTALLED_APPS`를 바꿨다. 주 지표의 20개 판정은 모두 유지됐다. 이 검사는 [별도 사후 감사](data/memory-unit-pilot-20261108/setting-preservation-audit.json)이며, 동결된 주 평가기나 점수를 변경하지 않았다. 여섯 설정 밖의 모든 전역 상태까지 보장하지는 않는다.

P와 P+G에서 각각 한 출력이 256-token 한도에 닿았다. 두 사례도 제외하지 않았다. 네 동일 prompt 반복은 입력·출력 token 배열과 실행 성공 여부가 모두 일치했다. 이는 재생성 일치 검사이며 독립 출처 반복이나 성공 확률의 추정이 아니다.

## 실제 출력에서 확인한 것

- **이미 설정됐지만 앱 초기화가 안 된 상태:** 무기억은 불필요한 `import test_sqlite`로 실패했다. E와 P+E는 `import django; django.setup()`을 생성해 두 버전에서 모두 통과했다.
- **완전히 새 프로세스:** E와 P+E도 `django.setup()`만 생성해 두 버전 모두 실패했다. 기억에 있는 환경 변수와 `PYTHONPATH` 사실을 현재 Python 프로세스의 설정으로 옮기지 않았다. 정보 포함 여부와 실행에 필요한 단계 전체의 사용을 구분해야 한다.
- **환경 변수만 설정된 상태:** 무기억은 두 버전에서 통과했다. P를 추가하면 현재 설정 모듈 대신 별도 설정을 만들어 두 실행이 계약 실패로 바뀌었다. E를 함께 주면 다시 통과했다.

## 이 결과로 학습을 확대하지 않은 이유

여섯 상태에서 제공 정보에 따른 성패 차이가 있었지만, **고정 E의 6개 성공이 관측 행동의 상태별 최선 6개와 같았다.** 현재 후보 중 상황별로 더 잘 고를 여지가 성공 수 기준으로는 없다. 비용이나 새로운 정보 묶음의 효과는 다른 질문이다.

실행 전 작성한 상태 확인 규칙은 8/8을 통과했다. 이 규칙은 source 기억 없이 현재 설정 여부를 확인해 필요한 초기화만 직접 수행한다. 작업자에게 규칙 문장을 전달한 결과가 아니라, 실행 가능성과 간단한 해법을 확인한 대조다. 규칙·무작업·조기 종료를 포함한 24개 사전 검사가 모두 기대한 대로 동작했다.

따라서 이번에 확보한 것은 **고정 작업자의 정보 제공 차이에 따른 실행 관측**이다. 별도 선택기의 우위나 추가 LoRA 학습의 일반화 근거는 아니다. 원본 수치 판독이나 API 결과에 이 여덟 상태를 섞어 학습 효과를 확대 해석하지 않는다.

다음 데이터에는 현재 관측만으로 알아낼 수 있는 것, 과거 경험이 추가하는 것, 구체적 코드 예시가 추가하는 것을 구분해야 한다. source에 근거한 실행 단계 간 연결을 유지하고, 같은 기억이 다른 현재 조건에서 유용하거나 불필요한 사례를 독립 출처에서 확보한다. 일반적인 현재 문서·코드 예시와 같은 표현 수준의 기준선도 필요하다. 효과가 없는 사례와 단순 해법으로 충분한 사례를 남긴다.

## 공개 후보 여덟 개의 준비 상태

기존 공개 로그 후보 8개·4가족을 하나씩 검토하고 원본 기록의 SHA, 호출과 응답의 연결, 발췌 offset 27곳을 재검산했다. 모두 일치했다. Pydantic 다섯 에피소드는 같은 가족이다.

아직 새로운 target의 판단 전 상태·재현 가능한 검사 계약·제공/보류 실행이 없으므로 **추가 학습용 효용 자료로 승격한 것은 0개**다. 설치 후 다음 오류로 진행한 사실, 일부 검사 통과, 최종 문제 해결을 구분했다. Dask에서는 Graphviz 설치 성공이 관측되지 않았고, gTTS의 출력 문구는 assertion 검증이 아니다. ## 코드 수정과 재현

기존 API 실행기는 동결 사본과 함께 보존했다. [v2 실행기](../../data_pipeline/api_worker_interpreter_v2.py)는 `+=`, `*=`, `|=` 등에서 Python의 in-place 의미와 왼쪽 대상의 한 번 평가를 구현한다. [8개 의미 비교 검사](../../training/memory_selector/tests/test_api_interpreter_v2.py)가 통과했다. 새 API 실험은 v2를 명시적으로 선택하고 의존하는 v1 파일과 v2 파일의 hash를 함께 기록해야 한다. 기존 `api_worker_judge.py`의 역사적 실행 경로를 조용히 바꾸지는 않았다.

이번 Django 파일럿은 AST API 실행기를 사용하지 않고 실제 Python을 새 Docker container에서 실행한다. 네트워크·호스트 mount 없이 1 CPU/1 GiB/read-only root로 제한하고, 각 container를 정리했다. shell 반환코드만으로 성공을 판정하지 않으며, `SystemExit(0)` 조기 종료도 대조에서 실패로 기록됐다.

GPU 없이 저장된 결과를 검산하려면 저장소 루트에서 실행한다.

```sh
python3 -B -m evaluation.verify_memory_units
python3 -B -m unittest training.memory_selector.tests.test_api_interpreter_v2 training.memory_selector.tests.test_memory_unit_worker -v
```

실제 Docker 재실행은 [자료 README](../../datasets/memory_units/20261108-django-startup-pilot-v1/README.md)를 따른다. Docker images가 없는 새 컴퓨터의 산술 검산은 새 Python 실행 재현과 구분한다. [공유 결과](../../evaluation/results/memory-unit-pilot-20261108/README.md)에는 worker 입력·출력·고정 코드·가중치 hash·판정이 연결돼 있다.

로컬 학습 코드 검사는 105개 중 100개 통과·5개 기존 optional Torch 검사 skip, 평가 검사는 24개 통과했다. 원본 실행 로그와 학습 출력이 없는 공유 대상 파일 사본에서도 README의 74행 검사·444개 기존 예측 검산, 이번 44개 출력 검산, 관련 16개 검사와 worker 입력의 바이트 단위 재생성이 통과했다. 이는 원격 저장소의 새 clone이 아니라 현재 공유 대상 파일을 복사한 검사다. [검사 기록](data/memory-unit-pilot-20261108/checks.json), [공유 사본 검사](data/memory-unit-pilot-20261108/fresh-share-check.json).

## 자원과 비용

Colab L4 한 세션에서 44회 생성했다. 신경망 학습·유료 모델 API 호출·로컬 GPU 사용은 없었다. controller는 327.78초 후 결과를 회수하고 세션을 종료했다. 잔량은 587.19→587.08 CU로 관측됐으며 **0.11 CU는 잔량 차이**다. 별도 서버 조회에서도 활성 세션 0·사용률 0을 확인했다.

8상태 전체의 입력+출력 token은 N 3,726, P 7,050, P+G 6,930, E 5,269, P+E 6,990이다. E와 P+E는 같은 성공 수였고 E가 1,721 token 적었다. 생성 지연은 실행 순서와 warm 상태의 영향을 받으므로 이 소규모 합계로 일반적인 속도 우위를 주장하지 않는다. 기억 작성·서비스 초기화·미래 선택기 비용까지 포함한 시스템 비용 비교는 아니다.
