## 실행 중단과 분석 범위

05:44 UTC경 상태 파일과 실제 프로세스를 대조하다 기존 배치가 종료 코드143으로 끝난 것을 확인했다. 발신 주체·종료 원인은 확인하지 못했다. 완료8회 뒤 Django14534의 S 배정은 응답14개를 저장하고15번째 요청을 기다리던 상태였다. 원본 manifest·요청·명령·저장본466개의 당시 해시를 보존했다. 미실행23개만 동일한 고정 설정으로 이어서 종료했고 중단 배정의 재생성·대체는 없다. 이후에는 분리 실행 프로세스와 종료 신호 기록을 추가하고 실제 프로세스 생존도 함께 감시했다.

[이어가기 규칙](data/process-restoration-20261107/interruption/continuation-protocol.json)과 [분석 보완](data/process-restoration-20261107/interruption/analysis-amendment.json)은 별도 파일이다. 기존 동결 분석 코드는 그대로 두고, 미확정 한 건의 가능한 결과를 모두 포함하는 성공률·주 대비 범위와 기존 Hoeffding 구간의 합집합을 보고한다. 완결 실행만의 비교를 원래 전체 배정의 인과 효과로 제시하지 않는다. 응답이 없는 마지막 요청은 비용 미확정으로 남기고 $1을 예산상 유보했다. 유보액은 실측 비용이나 증명된 청구 상한이 아니다.

주 질문은 같은 source 경험의 **선택된 procedure 카드 S**에 없던 과정 정보 O를 더한 M=S+O가 새로운 target의 예산 내 공식 성공·전체 비용·관측 오류를 어떻게 바꾸는가다. 주 성과 대비는 M−S, 보조는 무기억 N 및 원문 근거 R과의 비교다. 오류·비용만 개선되면 그 범위의 결과로 보고한다.

처음 후보는 SymPy 18621, pytest 5221, Sphinx 7686, scikit-learn 11281과 source별 새 target 두 개다. 공개 설명·source PR 시점·이력으로 선택했고 이전 모델 실행 과제와 겹치지 않음을 확인했다. 원본/정답 대조를 먼저 수행하며 가족 전체의 통과 여부로 대상 호출 전에 포함·제외를 확정한다. 기억 조건의 성과를 보고 과제를 교체하지 않는다.

source 경험은2026년에 과거 문제를 재실행해 수집했다. PR 시점과 Git 이력은 source/target의 정보 관계를 확인하는 기준이며 실제 과거의 에이전트 기록이나 모델의 사전학습 지식 제한을 재현하지는 않는다.

공통 마지막 예산 안내와 수동 개입 없는 tracked/비ignored untracked 패치 저장을 추가했다. 기존 실행기를 수정하지 않고 별도 어댑터를 사용한다. 사후 채점 결과는 에이전트 입력으로 돌려주지 않는다. 최종 제출 성공과 중간 상태의 통과는 별개 지표다.

source-only 작성기는 facts/procedure 두 카드를 만들고 이번 S는 procedure 하나만 선택했다. scikit-learn/SymPy는 표준 작성기, Django는 파싱 불완전·확실한 실패를 보존하도록 보완한 작성기를 사용했다. 실제로 S에 없던 관측만 source 근거로 점검했다. **두 source의 facts 카드에는 복원한 검사 명령이 이미 있었다.** 따라서 V 대비는 카드 선택 뒤의 보강 효과이며 작성 결과 전체에서 V가 소실됐다는 증거가 아니다. 환경 관측 E와 검사 절차 V를 구분한다. R은 S와 O의 근거를 포괄하는 규칙적 발췌이며 전체 원문·검색 oracle과 같지 않다. M−S는 정보·출력 재제시·길이·헤더를 더한 패키지 효과다.

## 실제 준비 과정에서 바뀐 범위

초기 pytest 가족은 원본 내부 오류에 따른 기대 출력 누락, Sphinx 가족은 정답에서도 해결되지 않은 검사·출력 문제로 사전 제외했다. 이는 현재 환경과 엄격한 출력 기준에서의 제외이며 해당 벤치 전체의 부적합 판정은 아니다. 초기 SymPy와 scikit-learn은 기술 대조를 통과했다.

그 뒤 새 SymPy 요약을 확인하니 pytest 부재와 bin/test 명령·16개 통과가 이미 명시되어 있었다. 의미상 보존된 정보를 중복 제공하고 ‘복원’이라고 부르지 않도록 이 출처를 제외했다. scikit-learn은 검사 결과는 남겼지만 구체적인 실행 명령·경로·옵션이 빠져 있었다.

서로 다른 출처를 확보하려고 첫 대상 호출 전에 추가 Django 가족 하나만 점검하는 변경을 기록했다. Django source의 원본 로그는 80개 검사를 실행했으나 subtest 출력이 합쳐져 네 canonical 이름이 파서에서 누락됐다. 원본 실패·정답 성공과 원본 실행의 실제 원문 근거를 보존해 source에 한해 사전 판정을 보완했다. 두 target은 원래의 엄격한 대조를 모두 통과했다.

Django source 에이전트는 실제로 미해결 패치를 제출했다. 공식 보고서는 false이며, 열 개의 명시적인 필수 검사 비통과가 있어 미해결은 확실하지만 네 이름은 파싱되지 않았다. 원본의 evaluation_incomplete 상태를 그대로 두고 별도 판정 근거를 저장했다. 이 실패 경험의 요약·R/S/M 공통 메타데이터에도 미해결과 불완전한 파싱을 표시한다. 에이전트를 재실행하거나 실패를 성공으로 바꾸지 않았다.

따라서 최종 은행은 **성공한 scikit-learn source와 미해결 Django source, 각각 새 target 두 개**다. 복원 대상은 두 경우 모두 V(검사 명령의 구체적 실행 정보)다. E(도구 부재) 복원 효과나 source 성공/실패 유형의 인과 차이를 검증한 설계가 아니다. 해당 비교와 미래 새 출처 일반화에는 별도 자료가 필요하다.

## 계측·판정 점검

기존 과제의 10/20응답 교정 실행은 모두 제출·공식 성공했으며 공통 마지막 예산 안내와 저장을 확인했다. 20응답이라는 대상 예산은 결과 전에 정한 값을 유지했다. 이를 예산 효과의 증거로 쓰지 않는다.

source 수집 중 Python 3.6에서 미추적 파일 저장 코드의 capture_output 인수 호환 문제를 발견했다. 해당 source의 저장 실패와 수정 전 코드를 보존하고, 대상 호출 전에 stdout/stderr PIPE로 고쳤다. 실제 대상 이미지 네 개에서도 미추적 파일 저장을 확인했고 관련 로컬 검사 70개가 통과했다. source 수집 중 저장되지 않은 상태를 사후 복원했다고 주장하지 않는다.

주 성공은 예산 내 실제 제출·공식 성공이다. 정상 미제출과 완전한 채점에서의 공식 실패는 성공 지표를0으로 기록한다. 이는 발생 건수가0이라는 뜻이 아니며 이번 정상 미제출은0건, 알려진 공식 실패는7건이다. 일부 이름이 파싱되지 않아도 유효한 채점 로그에 필수 검사의 명시적 비통과가 있으면 미해결은 알 수 있으므로 별도 근거와 원래 상태를 함께 보존한다. 명시적 비통과도 없거나 API·과금·채점 실행 자체가 불완전하면 미확정으로 두고 배치를 멈춘다. 성공은 완전한 공식 검사 통과를 요구한다. 이 규칙은 첫 대상 호출 전에 고정했다.

원래 배치는 `runs/batch-process-restoration-20261107/batch.json`의 중단 상태, 이어간 배치는 `runs/batch-process-restoration-continuation-20261107/batch.json`의 완료 상태로 각각 보존한다. 전역 집계는318기록으로 갱신했고 기존278행과 기존235개 모델 요약의 해시는 동일했다. 새로운40개 모델 기록은 대상32·출처수집3·기억작성3·교정2다. 중간 패치 진단과 검사 범위·회귀·실패 사례 분석은 별도 보조 자료다.

## 같은 실패의 사후 진단

Django14534의 완결 일곱 제출은 모두 사용자 지정 ID 요구를 고쳐 F2P1개를 통과했다. 그러나 ID가 없는 경우의 반환값에서 다른 F2P1개가 실패했다. 여섯 제출은 예전의 `id_name_0` 같은 ID를 대체값으로 남겼고, S 한 제출은 빈 문자열을 반환했다. 공식 요구는 `None`이다. 일곱 제출 모두 호환성이 확인된 P2P118개는 통과했다. 이는 새로운 회귀와 구별되는 **요구사항의 불완전한 수정**이다.

사후에 확인한 검사 패치는 같은 기존 검사의 기대값을 `'id_name_0'`에서 `None`으로 바꾼다. 별도 새 컨테이너에서 같은 기존 검사1개를 원본·정답 코드에 각각 실행했다. 검사 파일의 SHA256은 두 경우 같고 벤치의 검사 패치는 설치하지 않았다.

| 검사 계약 | 원본 코드 | 정답 코드 |
| --- | --- | --- |
| 에이전트가 볼 수 있는 기존 검사1개 | 통과 | 실패 |
| 공식 검사의 수정된 기대값 | 실패 | 통과 |

따라서 이 사례에서는 기존 검사 통과가 공식 요구사항 충족과 반대로 움직였다. 여기서 정답은 벤치가 제공한 공식 참조 패치다. 기존 검사는 이전 버전의 계약을 표현하며 이를 일반적으로 잘못된 검사라고 보지 않는다. [최초 검사 충돌 대조](data/process-restoration-20261107/legacy-test-conflict-probe.json)와 리뷰의 [같은 선택자·자원 조건4셀 대조](data/process-restoration-20261107/review/contract-2x2.json)에 명령·이미지·결과·파일 해시를 저장했다. 이 대조는 모든 대상 실행이 끝난 뒤 실패 사례를 골라 수행한 **사후 진단**이며 모델 호출은0회다. 정답·검사 패치를 기억이나 실행 중 에이전트에 제공하지 않았다.

이는 무기억 조건에서도 생긴 실패다. 복원한 과거 Media 검사 명령이 이 오류를 만들었다고 결론내릴 수 없다. 아래 수정 경로 분석에서 한 실행의 시간순 연결을 확인했지만, 검사 피드백만을 바꾼 에이전트 실험은 하지 않았다. 기존 검사를 무시하면 좋아진다는 일반 규칙도 도출하지 않는다. 다음 질문의 후보는 **검증 결과와 함께 검사 대상·버전·기대 계약을 기록하고, 현재 요구와의 충돌을 판단하게 하면 달라지는가**다. 현재 문제의 정답을 알려주는 실험으로 다시 평가하지 않고 새로운 출처·대상에서 확인해야 한다.

제출 패치의 회귀 보조 진단에서는 원본·정답 모두 통과한 공식 P2P를 기준으로31개 모두 새 비통과0개였고 중단1개는 미확정이다. 과제별 관측 가능 범위는54·9·118·113개 검사다. 이 범위 밖 회귀나 일반적 무해성은 확인하지 않았다. [실행별 회귀 자료](data/process-restoration-20261107/regression-audit.json).

## 복원 정보의 사용과 검사 범위

선택한 과거 검사 대상 문자열이 검사 명령에 나타난 실행은 N/R/S/M **각각2/8개**였다. 모두 같은 GaussianMixture 대상의 두 반복이며 기억이 없는 조건에서도 나타났다. Django source의 `forms_tests.tests.test_media` 선택자는 모든 조건에서0회였다. `runtests.py`라는 공통 실행기만 사용한 것을 과거 Media 검사를 채택한 것으로 세지 않았다. 다만 넓은 `forms_tests` 실행에 Media 검사가 포함될 수 있으므로 정확한 선택자0회가 관련 검사 미실행이나 기억 미채택을 뜻하지는 않는다. 명령 수는 N/R 각3회, S/M 각2회다. [문자열 표지와 원문 명령](data/process-restoration-20261107/selector-marker-audit.json).

source의 정확한 V 명령을 현재 각 대상의 원본·정답 코드에서 별도로 실행한8개 대조는 모두 통과했다. 이때 벤치의 검사 패치는 설치하지 않았다. 따라서 **그 명령만으로는 이 네 원본/정답 대비를 구별하지 못했다.** 기존 동작의 회귀를 점검할 가치는 있을 수 있으며, 무용·유해한 검사라는 판정은 아니다. 실제 실행한 표지도 기억의 채택이나 성공의 매개 원인을 증명하지 않는다. [검사 범위 대조](data/process-restoration-20261107/verifier-scope-audit.json).

저장 로그의 `rg`/`pytest` 부재 표지는 N1·R1·S0·M1개 실행에서 관측됐다. S 한 실행은 관측이 중간에 끊겼다. 표지는 정한 오류 문자열의 관측이며 모든 도구 실패의 완전한 집계가 아니다. 오류 감소의 근거도 얻지 못했다. 과거48회의45/48과는 대상·저장소·환경·제공 내용이 달라 감소 효과로 비교하지 않는다.

### 리뷰에서 찾은 다른 과정 정보 후보

사후에 Django의 독립 Python 실행에서 `settings are not configured` 오류를 따로 집계했다. 이는 새로 발견한 탐색 지표이며 원래 오류 지표를 대체하지 않는다.

| 조건 | Django 배정 | 해당 오류를 관측한 실행 | 해당 오류 명령 |
| --- | ---: | ---: | ---: |
| N | 4 | 4 | 5 |
| R | 4 | 0 | 0 |
| S | 4 | 4 | 4 |
| M | 4 | 4 | 4 |

중단된 S 실행에서도 중단 전에 오류를 관측했다. 다만 R 한 실행은 설정 모듈만 지정한 첫 시도에서 `AppRegistryNotReady`를 겪었다. 설정 누락과 앱 레지스트리 미초기화를 함께 세면 오류 실행 수는 N4/4·R1/4·S4/4·M4/4다. 잘못된 설정 모듈 지정까지 포함한 명령 수는6·1·7·6다. 이 중4명령은 traceback 뒤의 `git diff` 등이 성공해 전체 셸 반환코드는0이었다. 좁은 오류 문구나 반환코드만으로 초기화 실패 전체를 판정하지 않는다. [정의별 민감도와 실제 출력](data/process-restoration-20261107/review/startup-sensitivity.json).

source의 실제 명령17에는 `PYTHONPATH=tests:.`, `DJANGO_SETTINGS_MODULE=test_sqlite`, `django.setup()`을 함께 사용하는 독립 실행 예제가 있었다. R에는 들어갔지만 S/M과 두 생성 카드 모두에서 빠졌다. R의 Django4개 실행은 모두 최종적으로 이 초기화 절차를 포함한 독립 재현을 사용했지만 첫 시도부터 모두 올바른 것은 아니었다. M에 복원한 검사 실행기의 `--settings` 옵션은 독립 Python 초기화 예제와 같지 않다.

이 결과는 **실제 반복 오류에 맞는 누락 정보를 복원하지 못했을 가능성**을 보여준다. 한 source·두 target의 사후 발견이고 R은 코드·정보량·길이도 다르므로, 초기화 조각의 인과 효과나 해결률 개선으로 주장하지 않는다. [source 근거·관측 명령](data/process-restoration-20261107/review/observations.json), [아직 사용하지 않은 source-only 후보](data/process-restoration-20261107/review/proposed-source-setup-unit.json).

완결31개 실행의 합산 시간은104.5분, 그중 공식 채점은81.1분으로 약77.6%였다. 완료 응답의 요청 시간은16.5분, 에이전트 명령은4.1분, 저장 명령은약0.85분이었다. 합산 구간은 일부 겹치거나 초기화 시간을 제외할 수 있어 완전한 시간 분해로 주장하지 않는다. 외부 중단 실행의 전체 시간·미완료 요청 시간을0으로 채우지 않았다. 이 호스트 채점 시간을 메모리의 모델 요청 비용으로 더하지 않는다. [시간 자료](data/process-restoration-20261107/phase-timings.json).

![성공·확인된 비용·주 대비의 불확실성](figures/process-restoration-overview.png)

그림의 S 세로 막대와 주 대비의 두꺼운 구간은 중단 결과의 가능한 범위다. 가는 가로선은 표본 변동까지 포함한 조건부 범위이며 다르다. 비용 삼각형은 중단 실행의 불완전한 확인액이다.

## 다음 실험에서 바꿀 것

이번에 확인한 것은 기억 조각을 정확히 복원·삭제하고, 배정 성과·비용의 누락·기존 동작 회귀·중간 수정 상실을 따로 기록할 수 있다는 점이다. **어떤 기억 특징이 보편적으로 유익하거나 해로운지는 아직 확인하지 못했다.** 새 모델 호출을 추가하거나 현재 결과가 유의해질 때까지 반복을 늘리지 않았다.

리뷰 뒤 첫 우선순위는 **실제 source에서 누락된 독립 실행 초기화 전제**다. source-only 추출 규칙으로 S와 S+초기화 조각을 만들고 새 source·target에서 설정 오류·비용·예산 내 최종 성공을 각각 비교한다. 일반적인 초기화 주의 안내나 현재 환경 정보를 이미 가진 조건도 대조해 추가 숙고와 중복 안내의 효과를 구분한다. 단순한 환경 사용법의 효과로 설명된다면 그 범위의 발견으로 보고한다. 현재 네 대상은 이 후보를 발견한 자료로 남긴다.

그다음 후보는 **검사가 무엇을 어느 조건에서 입증했는지와 실패 뒤 평가 피드백을 보존하는 조각**이다. 실제 이전 경험의 정보만으로 작성하고 새 source·target에서 포함/정확한 삭제를 비교한다. 현재14534의 `None` 정답을 같은 문제에 기억으로 주고 전이 이득이라고 보고하지 않는다.

후속에서는 과거 검증이 현재 요구와 맞는 사례와 충돌하는 사례를 사전 구분하고, 같은 대상에 서로 다른 기억을 배정해야 한다. 범위·전제를 담은 기억과 일반적인 “요구사항과 검사를 다시 보라”는 안내를 대조해 추가 숙고 안내만의 효과도 구분한다. 적용성·집단 구분은 대상 결과를 보고 유리하게 바꾸지 않는다. 성공률과 새 회귀·검증 비용을 함께 측정한다. 기존 검사를 모두 보류하는 전략은 별도의 손해를 낼 수 있다.

또한 새 source·과제를 늘려 과제별0/100% 집중을 완화할 필요가 있다. 실제 실행 예산은 별도 발견용 교정에서 정하고 확인 집합에서 재조정하지 않는다. 동일 정보의 서술/지시 비교는 주장 집합·함수명·검증 정보·길이·위치를 맞춰 그다음 축으로 둔다. 이 내용은 다음 설계 제안이며 새 유료 실행은 하지 않았다.
