- 실패, 미제출, 빈 검색, 무조회, 평가 불완전 상태를 보존한다. 실행·과금 오류의 재시도는 자동으로 하지 않는다.

- 관찰은 **조회 선택 → 반환 결과 → 입력 노출 → 행동 → 최종 성과·비용**으로 나누어 기록한다. 입력 노출을 실제 활용이나 이해로 간주하지 않는다.

### R02 — 실제로 관련된 다른 과제로의 전이

출발 관찰: 첫 저장소는 `reindl` 경험 하나인데 대상은 golden-section/IAM이었다. 같은 라이브러리와 숫자 경계 문제라는 연결만으로는 재사용할 내용이 충분하지 않을 수 있다.

- Sphinx 출처 8282·8435 → 대상 8627·10451: `autodoc` 타입 힌트·타입 별칭·표기 처리. 두 출처의 실제 병합 시점이 두 대상보다 앞서고, 병합 커밋이 각각 대상 기준 커밋의 조상임을 [확인](data/2026-11-04-sphinx-relation-audit.json)했다. 서로 다른 사례여서 같은 수정의 재현을 전이라고 부르지 않는다.

SHA-256 `e16490821d92a3d37059ca3ae6cb20b18c51cd0874ba265ec3e2d2ce6618f93e`. 출처 3회에는 기억이 없다. 각 실제 출처에서 사실·절차 카드 각 하나를 생성하며, 카드마다 공식 판정과 근거 명령 인덱스를 별도로 저장한다. 새 카드 작성 규칙은 앞선 오류를 반영한 구현 보완이며, 다른 출처에서의 결과만으로 이전 규칙보다 정확하다는 인과 주장을 하지는 않는다.

출처 수집 결과: Sphinx 8282 실패, Sphinx 8435 성공, Django 14667 실패. 세 실행의 모델 요청은 45회, API 비용은 $0.024209995다. Django 실패에는 기존 통과 테스트 1개의 회귀도 포함됐다. 출처 실패를 제거하거나 성공할 때까지 다시 돌리지 않았다.

카드 작성: 출처마다 새 규칙으로 1회 요청해 사실·절차 카드 각 1개, 총 6개를 생성했다. [품질 확인](data/2026-11-04-r02-memory-quality.json)은 공식 판정 일치·명령 인덱스의 유효성과 선택한 사실·로컬 결과를 검사한 기록이다. 맹검된 전체 주장 정확도 벤치마크는 아니다. Django 카드의 `P2P 28/1`은 통과 28·실패 1을 압축해 적은 표현이라 분수처럼 읽힐 수 있다는 한계도 남겼으며 원문을 고치지 않았다.

대상 실행 직전 [은행](../../experiments/swe_memory/banks/overnight-r02-related-memory.json)을 SHA-256 `639524072e31f4060c56fe2f97e6a4bab7f41a397b6b5dfce45cbb6234e64c91`로 고정했다. 출처·작성 실행의 원본과 카드별 근거를 모두 연결했다. 대상 ID나 문제·정답·평가 로그는 카드 작성 입력에 들어가지 않았음을 확인했다.

출처 중간 관찰: Sphinx 8282는 14회 모델 요청 후 패치를 제출했지만 공식 목표 테스트 0/1, 유지 테스트 16/16으로 실패했다. 에이전트가 자체 선택한 관련 테스트 세 개와 간단한 함수 예제는 통과했으나 전체 요청을 충족하지는 못했다. [원본 실행 · 별도 원본](../reproduction.md) (`runs/20261103T150718Z-8bb04726/summary.json`)을 실패 경험으로 포함한다. ‘실패 경험’은 출처의 성과이며, 그 경험이 미래 과제에 해로운 기억이라는 뜻은 아니다.

R02 중간 관찰 1 — 검색: [고정 검색기의 사전 선택 검사](data/2026-11-04-r02-retrieval-precheck.json)에서 세 대상 모두 실패 출처의 절차 카드가 자동 선택된다. R02 중간 관찰 2 — 현재 코드와의 적용 범위: 카드에 명시된 이름을 대상의 앱 소스에서만 찾아 [검사](data/2026-11-04-r02-card-compatibility.json)했다. Django 16910에는 `deferred_to_data` 정의가 없고 `add_immediate_loading`·`add_deferred_loading`은 있다. Sphinx 두 대상에는 문서화 클래스들과 타입 관련 함수가 있지만, 출처 에이전트가 추가했던 `_apply_type_aliases`는 없다. 이름의 존재가 동작의 동일성을 보증하지 않고, 부재만으로 카드의 피해를 입증하지도 않는다. **에이전트가 과거 과제를 풀며 만든 코드가 실제 upstream에 병합된 코드와 동일한 것은 아니다.** 원사례 병합 커밋의 조상 관계를 확인해도, 모의 경험에서 추가한 도우미 함수가 미래 checkout에 있다는 뜻은 아니다. 이를 기억의 적용 범위와 출처 추적에서 구분해야 한다.

R02 중간 관찰 3 — 읽지 않은 기억을 실패 원인으로 분류하지 않기: Sphinx 8627의 첫 반복에서 무메모리·시작 제공은 성공했고 자율 조회 조건은 실패했다. 실패 실행의 조회·카드 노출은 모두 0이다. 제출 패치는 같은 `sphinx/util/typing.py`를 수정했지만, 두 성공 패치는 문자열 표기와 reST 참조 표기 경로를 다루고 실패 패치는 문자열 표기 경로만 수정했다. 이는 관측된 패치 범위 차이이며 기억 카드의 인과 효과를 입증한 것이 아니다. 범위 안내 자체의 영향과 모델 변동성도 아직 구분되지 않았으므로 두 번째 반복과 별도 확인을 기다린다.

R02 행동 분석: [명령과 실제 API 입력의 연결 기록](data/2026-11-04-r02-behavior.json)에 모든 함수 호출을 call ID로 연결하고 인수를 대조했다. Django의 두 번째 시작 제공 실행은 첫 요청에서 카드에만 있던 `deferred_to_data`를 검색했다. 이 이름은 현재 checkout에 없지만 해당 실행은 성공했다. 과거 안내가 탐색에 쓰였을 가능성을 보여주되, 그 행동이 성공의 원인이었다는 주장과 구분한다. 탐지 규칙은 식별자 포함 검색 명령에 대한 휴리스틱이며 원문을 함께 남겼다.

측정 원칙은 [득실 측정 노트](../ai-memory-measurement-notes.md)에 별도로 정리했다. 특히 같은 반복 번호의 성공→실패를 동일 난수의 반사실 비교로 취급하지 않으며, 평균 순효과와 개별 이득·손해 비율의 식별 문제를 구분한다.

### R03 — Django 이득 후보의 재현과 내용 분해

출발 관찰: R02의 Django 16910에서 시작 제공은 두 반복 모두 목표 2/2·유지 36/36으로 성공했고, 무메모리는 두 반복 모두 목표 1/2·유지 36/36으로 실패했다. 제공된 것은 실패 출처의 절차 카드다. 성공 패치는 역방향 관계의 처리에서 `parent_link` 예외를 두지 않았고 실패한 무메모리 패치는 예외를 두었다. 카드에는 그 대상 특유의 수정 내용이 없으므로 이 패치 차이를 카드의 직접 지시라고 해석하지 않는다.

가설: 이 특정 과제에서 과거의 조사 절차를 포함한 카드가 도움이 되었을 수 있다. 우연한 실행 차이와 구분하기 위해 새 기준 실행을 포함해 확인하고, 같은 출처의 사실과 추가 안내를 나눠 비교한다.

계획: [20회 고정 계획](../../experiments/swe_memory/plans/overnight-r03-django-content.json), SHA-256 `6bdf0c30b773772149e7e62ab94e44f1842e3c1936614aaa7ef73130e8c3d6d6`. 무메모리·원래 절차 본문·사실 본문·사실+일반 안내·사실+경험의 조사 절차, 각 4회다. 모델·과제·이미지·기억 출처·공식 판정·예산을 유지하고 모든 카드 조건에 같은 불투명 카드 ID를 사용한다. 그 때문에 원래 절차의 본문은 R02와 같지만 ID까지 완전히 같은 재현은 아니다.

두 추가 안내는 301문자와 284문자로 비슷한 분량이지만 토큰 수가 동일하다고 가정하지 않는다. 경험 안내는 원래 출처의 `only/defer` 호출 경로와 저장 상태를 추적하는 절차만 사용한다. 현재 대상에서 발견한 `parent_link`, `_get_only_select_mask` 등의 해결 단서는 넣지 않았다. 변형한 문구는 직접 만든 개입임을 은행의 파생 기록에 표시했으며 원래 카드 작성 모델이 만든 문구인 것처럼 저장하지 않았다.

주 비교는 원래 절차 본문 대 새 무메모리, 그리고 사실+경험 안내 대 사실+일반 안내다. 원래 절차가 새 기준에서 더 낫지 않으면 첫 이득은 미확인으로 남긴다. R02 발견 결과와 새 확인 결과를 선택적으로 합치지 않는다. 같은 출처의 사실·절차 본문은 여러 특성이 달라 이 사례로 ‘모든 사실 대 모든 행동 안내’의 우열을 주장하지 않는다. 한 과제에서 반복한 사례 연구다.

행동 관측: 카드가 있는 16/16 실행에서, 해당 명령의 모델 입력 중 카드 이외에는 아직 등장하지 않았던 `deferred_to_data`를 검색했다. 무메모리 네 실행에는 이 형태의 카드 유래 검색이 없다. 이름이 현재 코드에 없다는 점은 이미 확인했다. 그러나 검색은 다른 유효한 이름과 한 명령에 묶인 경우도 있고 성공·실패 양쪽에서 나타났다. 따라서 이를 곧바로 낭비나 실패 원인으로 세지 않는다. **기억이 탐색에 반영된 흔적이 있어도 최종 성과 향상이 재현되지 않을 수 있다**는 사례다. 이름 삭제 같은 별도 개입이 경로 기여와 비용을 검증하는 후속 후보가 된다.

패치 관측의 반례: R02에서는 `parent_link`가 들어간 실패 패치와 그렇지 않은 성공 패치가 구분됐지만, 새 20회에는 이 이름이 없는 실패도 3회 있었다. 두 실행은 상속 관계를 `issubclass`로 예외 처리했고, 하나는 다른 파일인 `compiler.py`를 수정했다. 단순 문자열 특징은 패치 의미나 실패 원인을 완전하게 대체하지 못한다. 기존 휴리스틱을 확정 유해 기억 라벨러로 사용하지 않는다.

검증: 원본 파일 3,885개, 대화 전환 338개, 실제 함수 호출과 명령 493개를 대조했다. 기본 입력·모델 설정·이미지·활성 제어 코드가 조건 간 유지됐고 모든 필수 평가 결과가 있다. 16개 카드 조건은 본문이 실제 API 입력에 포함됐다. 같은 한 과제의 20회 실행이며 서로 다른 20개 과제의 결과가 아니다.

### R04 — 남아 있던 도구 지시 충돌의 직접 비교

새 관측: 실제 입력을 다시 읽었더니 `any_tool_v1`이 핵심 요구사항의 bash 필수 문구를 바꿨지만, 앞부분의 `Provide one or more bash tool calls to execute`는 그대로 남아 있었다. [감사 자료](data/2026-11-04-prompt-consistency-audit.json)에 해당 입력과 해시를 보존했다. 이전 도구 보고서의 변경 설명을 이 사실에 맞게 정정했으며 기존 결과를 삭제하거나 다시 쓴 것은 아니다.

이 문구는 기억 함수만 호출하는 응답과 충돌할 수 있지만 bash와 기억의 동시 호출은 가능했다. 따라서 이것이 무조회 원인이라고 아직 결론 내리지 않는다. 이 한 줄의 효과를 직접 검증하는 일이 안내 범위나 내용 삭제 비교보다 우선이라고 판단했다.

비교 설계: Sphinx 8627에서 무메모리·시작 제공·범위 안내가 있는 native 조회의 세 정책과 기존/수정 문구 두 가지를 교차한다. 각 조합 4회, 총 24회다. 수정 문구는 해당 한 줄을 `Provide one or more tool calls (bash or an available memory tool) to execute`로 바꾸며, 나머지 모델·은행·검색·안내·예산을 유지한다. 무메모리·시작 제공에도 같은 변경을 적용해 일반적인 작업 문구 효과와 조회 조건의 차이를 볼 수 있게 한다.

모든 조건에 동일한 중간 패치 저장을 적용했다. API 요청 4·8·12·16·20·24·28·32회와 종료 시점에서 저장하고, 전체 실행 종료 뒤 별도 채점한다. 첫 관측 통과 단계는 정확한 최초 통과 시점이나 짧은 예산을 고지한 실험과 다르다. 준비 당시 R03가 진행 중이었으므로 활성 제어 코드는 바꾸지 않았다. 새 저장 보조 모듈의 격자·오류·단계 복원 검증 세 개를 먼저 확인하고 통합 검증은 R03 종료 후 수행했다.

### R05 — 새 과제·수신 모델 비교와 예산 내 미제출

탐색 대상을 같은 세 과제에만 한정하지 않기 위해 Lite test에서 Verified와 겹치지 않는 Sphinx 8801을 추가 후보로 정했다. 공개 문제 설명은 상속된 클래스의 타입 주석만 있는 속성이 문서화되지 않는 사례다. 현재 은행의 autodoc 경험과 주제가 연결되고 두 출처의 병합 뒤에 발생했다. 후보 선정에는 이 과제의 모델 실행 결과·정답 패치·평가 테스트를 쓰지 않았다.

[시간 순서·조상 관계](data/2026-11-04-sphinx8801-relation-audit.json)를 원본 이미지의 Git 이력으로 확인했다. [이미지 감사](data/2026-11-04-sphinx8801-build-tree-audit.json)에서 앱 소스는 같고 `setup.py`의 의존성 제한·`tox.ini`의 `-rA`·파일 모드 변경만 있음을 검토했다. [원본/정답 대조 · 별도 원본](../reproduction.md) (`runs/audit-controls-20261103T162908Z-7a63d1/control-result.json`)는 원본 목표 0/1·유지 8/8, 정답 목표 1/1·유지 8/8이며 9개 결과를 모두 읽었다.

당초 설계는 새 Sphinx 8801과 이미 관찰한 Django 16910에서 Luna·DeepSeek의 무메모리/시작 제공/native 조회를 각 2회씩 비교하는 24회였다. 두 모델에 같은 Luna 출처·작성 카드 원문을 재사용하므로 **수신 모델을 바꾸는 전이**이며 DeepSeek 자신의 경험을 축적한 비교가 아니다. 기존에 연결을 확인한 OpenAI/Luna medium, DeepInfra FP8/DeepSeek high 설정을 각각 유지했다. 같은 수치 예산이 같은 계산량을 뜻하지 않으며 모델 순위를 만들지 않는다. 다른 모델의 native 왕복은 별도의 명시적 연결 점검으로 확인했다.

은행에는 Sphinx 카드 네 개의 대상 허용 목록만 새 과제로 확장했다. 본문·ID·출처 판정·작성 실행은 그대로다. [자동 선택 사전 검사](data/2026-11-04-r05-retrieval-precheck.json)에서는 `sphinx8282-facts`가 선택됐고 주요 일치 단어는 `autodoc`, `behavior`, `example`, `ext`, `foo`, `index`, `py`, `sphinx`다. 이를 관련성 정답이나 도움이 된다는 근거로 삼지 않는다. 다른 카드가 더 좋을 가능성은 실제 선택 카드의 효용을 비교해야 확인할 수 있다.

R04 완료 후 명시적 DeepSeek native 연결 점검을 통과했다. 이 두 요청은 자율 조회율에서 제외하며 비용에는 포함한다. [R05 계획](../../experiments/swe_memory/plans/overnight-r05-receiver-transfer.json)의 SHA-256은 `308002058684756859b1cc25de0029b16198b85552e228788166bec4ad69868d`다. 02:28 KST에 시작했고 **02:52 KST에 6/24 실행 후 사전 중단 규칙으로 멈췄다.**

여섯 번째 DeepSeek 무메모리 실행은 API 오류 없이 32회 응답을 받았지만 제출 단계에 도달하지 못해 `LimitsExceeded / no_submission`으로 끝났다. 제출 패치는 비어 있고 작업 트리 저장 패치는 별도로 존재한다. 공식 하네스가 미제출을 테스트하지 않았으므로 `official_resolved=null`을 유지한다. 운영상 해결물을 제출하지 못한 결과와 공식 테스트로 판정된 오답을 구분한다. 이 실행을 재시도하지 않았고, 남은 Django 12회와 Sphinx 두 번째 반복 6회는 **시작하지 않았다.**

### R06 — 검색 점수와 카드 효용을 구분

R05의 새 Sphinx 8801에서는 현재 어휘 검색기가 `sphinx8282-facts`를 선택했다. 일반적인 코드·문서 단어의 겹침이 크다는 관찰에서, 변수·속성 주석 경로를 다룬 다른 실제 카드 `sphinx8435-facts`와 비교할 가설을 세웠다. 두 후보는 **Sphinx 8801의 첫 모델 결과를 보기 전에** 정했다. 대안 카드를 관련성 정답이나 성공을 보장하는 카드라고 부르지 않는다.

### R07 — 검색어 없는 선택적 카드 읽기

R02에서 관련 Django 은행의 자율 조회가 없었고, R03에서는 실제 카드를 제공한 16회 모두 과거 함수 이름을 탐색에 사용했다. 이는 읽을 내용과 행동 경로가 존재해도 사용 결정을 건너뛸 수 있다는 관측이다. 검색어를 작성해야 하는 추가 부담이 후보 원인인지 별도 비교를 준비한다.

같은 한 장의 Django 사실 카드를 두고 `memory_search(query)`와 인수 없는 `memory_read()`를 비교했다. 두 조건 모두 조회는 선택적이며 시작에는 본문을 주지 않는다. 읽기 조건은 공개 문제 설명으로 미리 고른 카드만 반환한다. 검색 조건은 같은 한 장에서도 질의가 맞지 않으면 빈 결과가 날 수 있다. 도구 이름·인수·사용 안내·선택 방식이 함께 달라지는 구체적 정책 비교이며, 글자 수를 맞춘 순수 문법 비교는 아니다.

주 관측은 호출·본문 노출률이다. 조회가 늘어도 과제 효용이 늘었다는 뜻은 아니다. 성공률·회귀·전체 배정 비용·시점도 함께 남긴다. 기능 구현은 별도 사본에만 준비했고 R04–R06 도중에는 적용하지 않는다. 앞선 배치가 끝난 뒤 전체 테스트와 명시적 연결 점검을 통과해야 사용할 수 있다. 연결 점검은 자율 조회율에서 제외한다. 같은 과제의 과거 풀이를 재시도 기억으로 허용하는 변경은 아니다.

### R08 — 오래된 함수 이름의 행동 효과와 성과 효과

R03에서 카드가 있는 16회 모두 `deferred_to_data`를 검색했지만, 그 행동은 성공·실패 양쪽에 있었다. 다음 가설은 이 이름을 제거하면 탐색이 바뀌는지, 바뀐다면 비용·공식 해결도 달라지는지다. [사전 검사](data/2026-11-04-r08-precheck.json)와 별도 초안을 준비했다.

같은 Django 사실 카드에서 한 번 등장하는 `` `deferred_to_data()` ``를 `the deferred-field selection routine`으로 바꾼다. 카드 ID·출처·공식 실패 판정·나머지 본문을 유지하고 두 조건 모두 시작에 제공한다. 새 현재 코드 이름이나 정답 접근법은 추가하지 않는다. 본문 해시와 길이(715→731자)는 함께 달라지며 이 차이를 숨기지 않는다. 렌더링된 시작 문맥도 이 본문 교체와 SHA 변경 외에는 일치함을 확인했다.

이는 이미 관찰한 한 과제의 수동 편집 개입이다. 새로운 무메모리 조건 없이 원문과 변형을 비교하므로 절대적인 기억 이득을 다시 추정하는 실험은 아니다. 오래된 이름의 사용이 줄어드는 것만으로 성과 이득을 주장하지 않는다. 검색 명령·현재 입력에서의 정보 출처·공식 해결·회귀·전체 비용·중간 상태를 함께 남긴다.

R07 종료 후 두 조건 각 4회, 총 8회를 고정해 모두 완료했다. [R08 계획](../../experiments/swe_memory/plans/overnight-r08-obsolete-identifier.json)의 SHA-256은 `d3f03e4347d7f6ce0126eec858782e4b248bda267e42d8eb049d16c8248374f9`다.

### 로컬 테스트를 만족시키는 수정이 공식 성공을 되돌린 사례

R07 첫 조회 조건 실행 `20261103T181938Z-31f054d3`의 저장 패치는 요청 8회 시점에 공식 목표 2/2·유지 36/36을 통과했으나 12회부터 목표 1/2가 됐다. 실제 궤적에서 9번째 요청은 기존 `select_related_onetoone` 테스트를 실행해 `test_inheritance_deferred2` 실패를 보았고, 11번째 요청은 `parent_link` 예외를 추가해 그 기존 테스트를 통과시켰다. 최종 제출에도 이 예외가 남았다.

공식 테스트 패치를 읽어 보니 이 테스트의 기대값 자체가 바뀌어 있었다. 선택하지 않은 필드를 나중에 읽을 때 추가 쿼리를 **0회**로 기대하던 기존 부분을 **2회**로 바꾸고, 선택한 필드는 0회임을 별도로 확인한다. 이 차이는 과제의 새 동작을 검사하는 수정이다. 따라서 공식 평가를 통과하던 패치가 기존 로컬 테스트에서 실패한 사실만으로 그 중간 패치에 새로운 회귀가 있었다고 결론낼 수 없다.

이를 [별도 대조](data/2026-11-04-django-test-version-diagnostic.json)로 확인했다. 같은 원본 이미지의 수정 전 테스트 파일 내용을 유지하고, 공식 테스트 패치를 적용하지 않은 채 네 코드 상태에서 같은 로컬 테스트 22개를 실행했다.

| R07 최종 제출 | 22/22 통과 | 실패 |

실패한 두 상태의 로컬 실패는 같은 `test_inheritance_deferred2`였다. 첫 진단 시도에서는 기존에 알려진 이미지 파일 모드 변경까지 검사해 실행 전 멈췄다. [수정 기록](data/2026-11-04-django-test-version-preflight-repair.json)을 남기고 테스트의 Git blob 내용이 기준 커밋과 같은지 직접 대조한 뒤 진행했다. 원래 공식 결과·실행 기록·에이전트 제어 코드는 바꾸지 않았다.

완료된 R02·R03·R07의 같은 Django 대상 34회에서 이 실패 헤더가 실제 명령 출력과 다음 모델 입력에 있었는지도 [사후 조사](data/2026-11-04-django-local-test-conflicts.json)했다. 당시 24회에서 관측됐고 이 중 최종 성공 1회·실패 23회였다. 감지되지 않은 10회는 모두 성공했다. 이는 사후에 고른 패턴의 기술 통계이며, 로컬 검증을 무작위로 배정한 실험도 독립된 34개 과제도 아니다. 감지 없음은 테스트 미실행·다른 검사·출력 차이도 포함할 수 있다. 성공 반례 `20261103T161817Z-10235092`는 사실+경험 안내 조건에서 같은 실패를 보았지만 최종 패치에 `parent_link` 예외를 추가하지 않았다. 이 한 반례를 그 카드의 효과라고 주장하지 않는다.

R08·R09까지 마친 [최종 목록](data/2026-11-04-django-local-test-conflicts-final.json)은 같은 대상 46회다. 패턴이 감지된 31회 중 성공 1회·실패 30회, 감지되지 않은 15회 중 성공 14회·실패 1회였다. 초기 34회 파일도 보존했다. 이 강한 관측 연관을 검증 행동이나 메모리의 인과 효과로 해석하지 않는다. 패턴을 본 뒤 새 데이터로 독립 검증한 분류기가 아니며, 실패를 보았을 때의 에이전트 선택·수정 경로가 함께 얽혀 있다.

회고: **과거 정보에는 저장된 카드뿐 아니라 현재 checkout의 기존 테스트 기대값도 포함될 수 있다.** 평가 기준이 바뀌는 과제에서는 기존 테스트를 되살리는 행동이 공식 과제 성공과 충돌할 수 있다. 이는 이번 실험의 평가 해석에 필요한 확인된 사례지만, 공식 벤치가 무효라거나 테스트를 무시해야 한다는 결론은 아니다. 다음 가설은 ‘과거 검증 절차를 언제 그대로 따르고 언제 새 요구사항에 비추어 재검토해야 하는가’다. 이 대상의 숨겨진 평가 내용을 진행 중인 카드에 넣지 않았으며, 이를 바탕으로 만든 지침의 효능은 새 과제에서 따로 검증해야 한다.

### 공식 채점 밖의 회귀를 검사한 추가 진단

R06의 모든 조건이 성공했더라도 공식 테스트 밖에서 다른 기능을 깨뜨렸을 수 있다. R06 종료 후 Sphinx 8801의 기존 `tests/test_ext_autodoc*.py` 10개 파일을 검사하도록 범위를 정했다. 같은 이미지·공식 테스트 패치를 유지하고 실행 명령의 대상만 넓혔다. 새 정답 테스트를 작성하거나 추가 결과를 에이전트에 돌려주지 않았다. 비교 계획은 이 추가 검사의 결과를 보기 전에 별도 저장했다.

[확대 검사 결과](data/2026-11-04-expanded-autodoc-regressions.json): 원본·정답 대조, R05 제출 패치 5개와 미제출 최종 작업 트리 1개, R06 제출 패치 12개를 검사했다. 모든 변형에서 144개 결과와 공식 필수 9개를 파싱했고 대조 결과 대비 누락이 없었다. 원본·정답이 **공통으로 통과한 142개에서 새 실패·비통과는 18개 후보 패치 모두 0개**였다. 이 범위에서는 추가 회귀가 발견되지 않았다.

`tests/test_ext_autodoc.py::test_autodoc`은 원본·정답 양쪽에서도 실패하여 추가 회귀로 세지 않았다. 원본의 또 다른 실패는 이번 과제의 목표 테스트이고 정답 패치에서는 통과했다. 미제출 작업 트리의 진단 성공은 공식 최종 성공으로 승격하지 않는다. 동일 패치 채점의 재사용 여부와 모든 원문 결과를 남겼다. [실행 스크립트](../../experiments/swe_memory/scripts/audit_expanded_autodoc.py)는 계획에 기록한 코드 해시와 같다.

회고: ‘공식 점수 동일’의 이면에 숨어 있는 손해를 찾는 방법은 실제로 구현할 수 있었다. 이번에는 이 추가 범위에서도 손해가 관측되지 않았다. 선택한 한 과제·기존 테스트의 결과이므로 전체 회귀 부재를 증명하지 않으며, 이후 보고서에서 공식 점수를 이 검사로 대체하지 않는다. 검사 기간에 R07 모델 실행이 일부 겹쳤으므로 R07 벽시계 시간에는 공유 호스트 부하라는 한계도 있다.

### 중간 감사에서 확인한 또 다른 과거 정보 경로

메모리 문헌의 정보 격리를 다시 읽고 현재 컨테이너와 실제 명령을 확인했다. 우리 실행기는 네트워크를 끄지만 Git 이력 읽기를 막지는 않는다. 따라서 `none`은 **외부 경험 카드가 없는 조건**이며 저장소의 과거 커밋까지 없는 조건은 아니다. 같은 이미지와 정책 안에서의 비교는 이 접근 가능성에 조건부다.

R05의 첫 DeepSeek native 실행 `20261103T172830Z-53ef2cc2`는 기억 조회 없이 `git log --all`과 `git show`로 과거 변경을 실제로 읽었다. 15·18번째 API 요청에서 과거 수정 내용을 읽었고 16번째 저장 격자에는 아직 패치가 없었다. 20번째 격자의 패치는 최종 통과 제출과 같은 해시였다. 과거 정보를 다른 경로로 얻은 사례지만, 그 정보가 성공의 원인이었다는 증명은 아니다. 이후 비교할 가설은 **Git 이력이라는 대체 경로가 외부 기억의 한계 이득과 조회 선택에 영향을 주는가**다.

그때 읽은 Sphinx 커밋 세 개는 [별도 조상 검사](data/2026-11-04-observed-git-ref-ancestry.json)에서도 모두 대상 기준 커밋의 과거였다. 이전 Django 실행에서 직접 읽은 `42ee31930b`는 준비 이미지의 초기 HEAD였다. 준비 커밋의 날짜가 문제 시점보다 늦다는 사실만으로 정답을 읽은 것으로 분류하지 않는다. 해당 앱 소스와 빌드 설정 차이는 기존 트리 감사에서 확인한 상태다.

시작 제공 실행 `20261103T173842Z-1a055380`에는 과거 출처 번호 `8282`를 포함한 이력 검색도 있었다. 외부 Git 접근 시도는 DNS 실패로 끝났다. 해당 셸은 파이프와 `echo` 때문에 반환 코드 0을 기록했지만 원본 출력은 `Could not resolve host`였다. 따라서 명령 반환 코드만으로 외부 조회나 테스트의 성공을 판정하면 안 된다. 원본 출력·함수 호출 ID를 함께 보존한다.

무메모리 DeepSeek 실행의 31번째 요청에도 `Sphinx==4.0.0` 패키지 다운로드 시도가 있었으나 네트워크 이름 조회 실패로 끝났고 내려받은 버전은 없었다. 이 명령 역시 셸 반환 코드만 보면 0이었다. 네트워크 제한의 실제 작동과, 현재 기본 프롬프트가 이런 시도 자체를 금지하지 않는다는 사실을 함께 기록한다.

[이미지의 Git 접근 감사](data/2026-11-04-git-information-access.json)는 여섯 대상 이미지를 별도 컨테이너에서 읽기만 했다. Sphinx 세 대상과 Django 대상의 ref로 도달 가능한 커밋은 모두 현재 HEAD의 조상이었다. 다만 pvlib 1606·1707에는 HEAD의 조상이 아닌 커밋 345·288개가 미래 태그 등에 남아 있었다. 이는 잠재적으로 접근 가능한 경로의 발견이며 실제 정답 이용의 증거가 아니다. R01의 기록된 Git 조회는 현재 HEAD를 기준으로 한 `git log`였다. pvlib 기능 점검 결과를 엄격한 미래 정보 차단 환경의 결과로 부르지 않는다.

[실제 명령 목록](data/2026-11-04-recorded-information-access.json)은 이력·외부 접근 관련 패턴과 원본 위치를 남긴다. 패턴 검사는 완전한 셸 분석이 아니고, 이번 이미지 검사는 도달 불가능한 Git 객체·설치된 다른 프로젝트 사본·모델 학습 이력까지 배제하지 않는다. 다음 확인 실험에서 이력 접근을 제한하려면 작업 트리·의존성·기본 테스트 상태를 유지한 별도 환경을 만들고, 새 기준 실행과 함께 비교해야 한다. 현재 회차 도중에는 정보 접근 조건을 바꾸지 않는다.

종료 뒤 [최종 명령 목록](data/2026-11-04-recorded-information-access-final.json)을 별도 저장했다. 에이전트 행동 2,511개에서 관련 패턴이 있는 명령 69개·실행 54개를 기록했다. 한 명령이 여러 패턴에 해당할 수 있으며, 패턴 수를 정답 누출 수로 세지 않는다.

## 종료 상태와 자료 사용

[최종 세션 감사](data/2026-11-04-session-final-audit.json)는 원본 파일 25,135개의 해시, 1,853개 요청과 과금 메타데이터, 중간 패치 306개의 채점 상태, 고정된 계획·구성, 모델 실행 종료 시각을 확인했다. 발견된 문제 목록은 비어 있다. 이는 기록·회계·채점 완료의 검사이며 연구 가설이 입증됐다는 뜻은 아니다.

대상 108회 중 107회는 공식 채점 완료, 1회는 R05의 예산 내 미제출이다. 출처 수집 3회·카드 작성 3회·명시적 연결 점검 2회는 효능 비교에 섞지 않는다. R05의 미실행 18회 때문에 `all_planned_batches_completed=false`는 의도된 최종 상태이고, `all_started_run_evidence_complete=true`와 구분한다. R10은 고정된 대상 배치를 시작하지 않았으므로 이 18건과 별도로 미실행 기록을 보존한다.

실제 출처 경험의 카드 은행은 평가 중 자동으로 갱신하지 않았다. 이 밤의 자료는 고정된 출처·카드·정책의 전이와 개입을 조사한 것이며 장기 누적 학습 성능을 검증한 결과가 아니다. 과제는 소수이고 여러 회차에서 재사용했으므로 실행 수를 독립 과제 수로 삼거나 모든 회차를 합쳐 단일 메모리 효과로 보고하지 않는다.

다음 설계와 표본 규모의 가정은 [후속 검증안](../ai-memory-next-validation-plan.md)에 있다. 조회 안내의 재현, 충분한 새 과제에서의 전체 정책 효과, 적용 조건·테스트 버전의 역할을 순서대로 확인할 후보로 남겼다.

후속 분석에 쓸 수 있도록 [관찰 9건의 구조화 기록](data/2026-11-04-findings.json)에 주장·근거 파일 해시·해석의 한계를 연결했다. 이는 확정된 유익/유해 기억 학습 라벨이 아니다. 준비 초안·배치 대기 스크립트·검사 로그 27개는 [보조 자료 목록](data/2026-11-04-support-archive.json)과 함께 보존했다. [마감 후 정리 기록](data/2026-11-04-post-deadline-finalization.json)에는 재개 시각과 추가 실험 API 요청 0회를 명시했다.
