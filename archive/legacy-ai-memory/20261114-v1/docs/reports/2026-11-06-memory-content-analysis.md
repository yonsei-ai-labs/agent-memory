# 실제 사용한 메모리의 내용과 전이 조건 분석

2026-11-06 · 새 모델/API 호출 없음. 최근 24회에 사용한 두 원천 카드와 앞선 표현 비교 12회에 사용한 두 카드를 원문·실제 입력·명령·결과와 대조했다. **네 카드 모두 과거의 관측·수정 절차·검증·판정·주의를 묶은 기록이다. 현재 문제에 직접 적용할 수 있는 정도가 다르며, 어느 부분이 성과를 바꿨는지는 이번 내용 분석만으로 확정하지 않는다.**

먼저 개선의 의미를 구분한다. 최근 24회는 무메모리·정보형·지침형 모두 6/8 해결이었다. 지침형은 평균 요청 수가 9.375회에서 8.625회로 줄었지만 평균 API 비용은 약 15.3% 높았다. 앞선 Sphinx에는 1/2→2/2의 개선 후보가 있었고 Django에는 1/2→0/2의 악화 후보가 있었다. 모두 조건별 두 반복의 관측으로, 안정적인 개선·악화나 동등성을 입증하지 않았다. ## 1. pytest 7373 — 문자열 조건 평가와 캐시

본문 890자, 출처 공식 해결. 실제 핵심 내용은 다음 여섯 부분이다.

| 부분 | 카드에 담긴 내용 | 내용의 역할 |
| --- | --- | --- |
| 문제 관측 | skipif/xfail 문자열 평가가 항목별 globals에 의존하는데 표현식만으로 결과를 캐시했다 | 출처의 오류 조건·원리 |

재사용 가능한 원리 후보는 **결과가 실행 문맥에 의존하면 캐시의 재사용 조건이 그 의존성을 보존하는지 확인한다**는 것이다. 이는 카드의 구체적 cache 제거 코드보다 넓은 가설이며, 어느 과제에도 캐시를 제거하라는 규칙으로 만들면 안 된다.

현재 대상과의 접점은 약하다. pytest 7432는 `--runxfail`이 skip **위치 보고**에 영향을 주는 문제이며 공개 설명에 이미 `skipping.py`의 `pytest_runtest_makereport`라는 조사 위치가 있다. pytest 8906은 **모듈 수준 skip 안내 문구** 문제다. 카드의 네 내부 식별자는 두 대상의 초기 앱 코드에 모두 없었다. 따라서 과거 함수명을 그대로 찾거나 캐시 제거 처방을 복사할 조건이 확인되지 않는다.

도움 후보는 문맥을 바꾼 최소 재현과 관련 skip 테스트 파일이라는 조사 경험이다. 손해 후보는 현재 코드와 맞지 않는 위치에 주의를 쓰는 것, source의 76개 통과를 현재 문제의 충분한 검증으로 오해하는 것이다. 실제 명령에서는 과거 평가 파일·함수명을 사용한 흔적이 없었다. `testing/test_skipping.py`는 무메모리 4/4·정보형 4/4·지침형 3/4 실행의 명령에 등장했다. 읽기·실행을 합친 등장 수이므로 이 카드 때문에 검증 경로를 찾았다고 볼 수 없다.

**내용 판단:** 출처에 근거한 구체적인 성공 기록이지만 이번 두 대상에 새로 더하는 직접 해결 정보는 제한적이다. 일반 원리와 당시 구현의 수정법을 별도 요소로 나누어 볼 가치가 있다.

## 2. scikit-learn 10508 — LabelEncoder의 빈 입력과 자료형

본문 927자, 출처 공식 미해결. 내용은 아래와 같다.

| 부분 | 카드에 담긴 내용 | 내용의 역할 |
| --- | --- | --- |
| 문제 관측 | 수치·문자열로 학습한 LabelEncoder의 빈 입력 변환이 달랐고 문자열에서 TypeError 발생 | 입력 표현별 차이 |
| 수정 방법 | fitted-state와 `column_or_1d` 검증 뒤, 길이 0이면 `np.intp` 빈 배열 반환 | 특정 API·경계조건의 처방과 검증 순서 |
| 재현 범위 | `[1, 2]`, `['a', 'b']`, 일반 문자열 변환, 미지 레이블 거부 | 실제 확인한 사례 |
| 로컬 검증 | `test_label.py` 19개 통과·3개 xfail | 로컬 검사 결과 |

| 공식 결과 | 미해결이며 원인 설명은 없음 | 출처 전체 판정 |

재사용 가능한 원리 후보는 **수치형과 문자열에서 같은 경계조건을 비교하고, 조기 반환을 넣을 때 기존 입력 검증을 보존한다**는 것이다. 카드에는 실제 원인으로 확인된 범위를 넘는 일반적 dtype 해결 규칙이 들어 있지는 않다.

현재 OneHotEncoder 12471의 재현 입력은 문자열 두 개이며, 문제 설명이 이미 **문자열 폭 부족 → 대체 범주 잘림 → 오류**라는 경로와 object로 변환하는 수정 아이디어를 제공한다. 군집 지표 15535의 재현 입력도 길이 20이며 object 문자열을 부적절하게 float로 변환하는 것이 문제다. 두 재현 모두 비어 있지 않으므로 이 카드의 빈 입력 조기 반환은 제시된 오류를 직접 해결하지 않는다. `LabelEncoder`가 코드에 존재한다는 사실도 OneHotEncoder나 군집 지표의 현재 오류와 같은 경로라는 뜻은 아니다.

이 카드는 **미해결 시도의 기록**이다. 무엇 때문에 공식 실패했으며 어느 행동을 피해야 하는지에 관한 구체적인 진단은 없다. 이후 별도 사후 분석에서 `transform([])` assertion을 지난 뒤 `inverse_transform`이 실패한 것을 확인했지만, 그 설명은 실제 주입한 카드에 없었다. 이를 카드가 이미 제공한 실패 회피 지식으로 세면 안 된다.

명령과 추가 패치 줄에서 조사한 LabelEncoder·검증·빈 배열 처방의 리터럴은 발견하지 못했다. 일부 도구 출력에는 코드 탐색 중 해당 이름이 나왔지만 무메모리 출력에도 있었고, 출력에 보인다는 것만으로 처방을 채택했다고 판단하지 않았다. 출처의 `test_label.py` 실행 경로도 어떤 대상 명령에도 등장하지 않았다.

**내용 판단:** 유효한 좁은 관측과 검증 순서의 단서가 있지만 현재 두 대상에 처방을 직접 옮길 조건은 약하다. 공식 미해결을 표시한 것은 투명하지만 그 표시만으로 실행 가능한 실패 교훈이 만들어지지는 않는다.

## 3. Sphinx 8435 — 주석의 두 처리 경로와 실패한 조회

본문 1,112자, 출처 공식 해결. 변수·속성에 `autodoc_type_aliases`가 적용되지 않은 문제를 다루며 **평가된 주석과 분석기가 가진 문자열 주석이라는 두 경로**, `get_type_hints()`만으로 해결하지 못했던 `NameError`, 별칭을 출력에 반영한 보완 구현과 문서 빌드 검증이 들어 있다. 로컬 경고 assertion 실패와 공식 해결도 구분한다.

이 카드의 특징은 **실패한 하위 접근과 그 한계가 구체적**이라는 것이다. 성공 경험 안에도 ‘그 조회만으로는 충분하지 않았다’는 음의 근거가 있다. 재사용 원리 후보는 현재 문서 출력에 주석의 어느 표현·경로가 개입하는지 확인하고 실제 출력까지 검증하는 것이다.

대상 8627은 함수 인자·반환값의 `struct.Struct` 참조 해석 문제다. 주석·이름·출력이라는 접점이 있지만 source의 변수·속성 별칭 문제와 동일하지 않다. `_apply_type_aliases`는 source 에이전트가 제출 패치에서 만든 helper이며 현재 대상에는 없었다. 이를 일반 API나 반드시 있어야 할 함수로 취급하면 잘못된 탐색 단서가 된다.

`get_type_hints`가 명령에 등장한 실행은 무메모리 1/2·정보형 1/2·지침형 2/2였다. source helper와 별칭 설정·예제 이름은 명령과 추가 패치 줄에 등장하지 않았다. 따라서 관측된 해결 개선 후보를 source의 alias 처방을 복사한 결과라고 설명할 수 없다.

**내용 판단:** 여러 처리 경로와 실패한 접근에 대한 설명이 있어 조사 가설을 만드는 재료가 비교적 구체적이다. 다만 그 성질이 관측 개선의 원인이라는 것은 검증하지 않았다.

## 4. Django 14667 — only/defer 상태와 버전별 조사 위치

본문 787자, 출처 공식 미해결. `QuerySet.only()/defer()`에서 내부 로딩 함수로 내려가 `(field_names, defer)` 상태와 `deferred_to_data()`를 살핀 기록이다. 빈 이름의 조기 반환 조건을 바꾸고 로컬 defer 29개가 통과했지만, 별도 SQL 재현 결과는 없다고 명시한다. 공식 목표 테스트 실패와 유지 테스트 1개 실패를 함께 기록하며 원인은 확정하지 않는다.

재사용 원리 후보는 선택 필드의 저장 상태와 최종 생성 SQL을 연결해 확인하는 것이다. 그러나 **실제 카드의 구체적 수정은 공식 해결을 얻지 못한 시도**이고, 실패 원인·대안은 담겨 있지 않다. 로컬 29개 통과만 보고 현재 과제에서도 같은 변경을 권장하면 근거의 범위를 벗어난다.

대상 16910은 Django 4.2의 역방향 OneToOne과 `select_related().only()` 문제다. `only()`라는 접점은 있으나 예전 `deferred_to_data`는 초기 앱 코드에 없다. 이 이름을 포함한 명령은 메모리 조건 4/4·무메모리 0/2에서 나타났다. 네 카드 중 출처의 구체적 이름과 연결된 탐색 흔적이 뚜렷한 사례지만, 이 행동이 공식 실패를 만들었다는 증거는 아니다. 원래 이름을 실제 추가 패치에 복사한 흔적도 없다.

**내용 판단:** 상태 표현의 단서는 재사용 후보이고, 현재에 없는 조사 위치와 미해결 처방은 별도로 경계할 부분이다. ‘실패 경험이므로 전체가 틀렸다’거나 ‘낡은 이름을 검색했으므로 손해였다’는 라벨은 맞지 않는다. 이전의 별도 이름 삭제 실험 R08에서도 검색은 줄었지만 해결률 개선은 입증되지 않았다. [이전 기록](2026-11-04-overnight-research.md).

## 정보형·지침형과 제공 패키지의 실제 구성

네 카드 모두 body는 절차형이다. 정보형에도 ‘어느 함수를 조사하고 어떻게 바꾸었는가’가 남아 있고, 지침형은 동일 body 앞의 사용 안내 한 문장만 바꾼다. 본문에는 잠정·과거·다른 입력 미검증이라는 한계가 유지된다. 따라서 이번 비교는 **같은 기록의 사용 안내 효과**이며 사실 목록과 행동 지침을 완전히 달리 구성한 비교가 아니다.

실제 입력에는 중립 제공 안내, 공식 source 판정, 공통 적용성 확인 규칙, 사용 안내, body가 함께 있다. 공식 source 판정은 메타데이터와 body 모두에 들어 있다. 이 층들이 만드는 신뢰·검증 지시·맥락 부담도 메모리 유무 비교에 포함된다.

## 이번 분석에서 얻은 연구상 판단

잘된 점은 실제 source 관측과 로컬/공식 판정을 분리하고 검증 범위를 명시한 것이다. 보완할 점은 **일반화할 원리, source 전용 수정법, 그 수정법을 적용할 조건, 검증한 범위가 한 문단에 섞여 있다**는 것이다. 특히 현재 두 카드의 직접 처방은 이번 대상의 주된 오류와 맞는 정도가 낮다.

내용상 우선 분리해 볼 요소는 `문제 원리 / 현재와 연결할 조건 / 구체적인 코드 위치·수정법 / 검증 경험 / source 판정`이다. 일반화한 원리만 남기거나 구체성을 줄이면 효과가 좋아질지는 새 대조가 필요하다. 일반화는 유용한 구체 정보도 잃을 수 있다. 이미 수행한 Sphinx 부분 삭제 기능 검증은 모든 조건이 2/2로 득실을 확정하지 못했으므로 같은 아이디어를 검증된 해결책으로 제안하지 않는다. [기존 구성요소 검증](2026-11-05-component-measurement-feasibility.md).

**현재 가장 방어 가능한 결론은 ‘어느 카드가 좋다/나쁘다’보다 ‘출처에 근거한 어떤 조각을 현재 문제의 어느 조건에서 쓸 수 있는가’를 분석 단위로 삼아야 한다는 것이다.** 네 카드의 사후 비교만으로 공통된 이익·손해 요인을 학습했다고 주장하지 않는다. [분석 자료와 재현 방법](data/memory-content-analysis-20261106/README.md).
