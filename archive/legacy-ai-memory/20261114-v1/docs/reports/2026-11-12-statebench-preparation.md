# STATE-Bench 적용 재검토와 학습 기록 준비

2026-11-12. **STATE-Bench는 과거 경험을 현재 행동에 적용하는 득실 평가에 적합한 후보임. 공개 학습 기록 300개를 확보하고, 관측 가능한 860개 판단 시점과 선택기 연결 경로를 검증함. 이번 단계는 자료·실행 경로 준비이며 새 학습이나 작업 성공률 측정은 아님.**

원래 질문은 작업자와 기억 은행을 고정했을 때, 현재 목표·진행·실패를 고려한 선택이 실제 성공·손해·비용을 개선하는가임. [공식 Agent Learning Track](https://github.com/microsoft/STATE-Bench/blob/5644b1838d96bc4483da29642d058ecaa6f80f7f/docs/AGENT_LEARNING_TRACK.md)은 과거 실행에서 만든 학습 내용을 새 업무에 적용하는 구조여서 이 질문과 연결됨. 기존 [공유 PDF 검토](2026-11-11-shared-pdf-review.md)에서도 후속 후보로 남겨둔 벤치임.

## 적용안에서 보완한 점

1. **기록을 곧바로 성공 처방으로 바꾸지 않음.** 공개 train 파일에는 대화와 도구 호출·응답만 있으며 최종 성공·실패 정답이 없음. 도구가 `returned`라고 응답한 반품도 이후 분류 오류가 드러날 수 있음. 출처 근거, 현재 적용성, 실제 제공 효과를 각각 보존해야 함.
2. **모든 선택기에 같은 관측을 제공하는 기준선을 둠.** 목표만 보는 Harrier와 학습 선택기만 비교하면 상태 입력의 이득과 학습의 이득이 섞임. Harrier에도 목표+관측을 주는 조건을 포함함. 학습한 두 입력 조건도 같은 모델·학습량·기억 은행으로 비교해야 함.
3. **검색 시점을 고정함.** 공식 기본 에이전트는 작업 모델이 검색 도구를 호출함. 첫 통제 실험에서는 비종료 사용자 턴 직전에 한 번 선택하고, 이어지는 도구 루프 중에는 다시 선택하지 않음. 선택 모델의 효과와 검색 시점 결정의 효과를 분리하기 위한 자체 프로토콜임.
4. **개수와 토큰을 함께 제한함.** 최대 3개·1,024토큰으로 고정하고 안내문·기억 ID·구분자를 포함한 실제 주입 문자열을 계산함. 긴 기록은 자르지 않고 예산 초과로 제외하며 그 수를 보고함. 전체 작업자 입력 길이와 선택기 입력·시간·비용도 후속 실행에서 별도 측정함.
5. **정책 문서 캐시와 경험 재사용을 구분함.** 기록에 `get_policies` 호출 310회와 서로 다른 인수·응답 조합 62개가 있음. 이 내용만 추출하면 과거 경험 선택보다 정책 검색을 시험할 수 있음. 정책만 담은 기준선과 조건·행동·관측을 남긴 경험을 구분해야 함.

첫 비교는 `무기억 / Harrier 목표 / Harrier 목표+관측 / 학습 선택기 목표 / 학습 선택기 목표+관측`임. 표준 임계값 0.5를 새로운 도메인의 정답으로 간주하지 않으며, 보류 기준은 개발 자료에서만 결정함. 기존 ConvoMem·AMA의 검색 약점은 회귀 결과로 유지함.

| 실제 관측 | 활용 가능한 연구 대조 | 주의할 해석 |
| --- | --- | --- |
| 장바구니에 두 개가 있는데 세 개를 추가해 상한 세 개로 거부됨. 고객 승인 후 한 개 추가는 갱신됨 | 현재 수량을 모르는 상태 / 이미 확인한 상태에서 필요한 경험 | 과거 상한·수량을 새 고객의 값으로 복사하지 않음 |

이는 관계 대조를 만들 수 있는 근거임. 이 기록을 주면 실제 성공이 높아진다는 측정 결과는 아님. 기존 학습 모델을 곧바로 재학습하기보다, 어떤 과거 관측과 조건을 전달할지 검토하고 제공 전후 실행 결과를 확보하는 순서가 적절함.

## 입력 경계와 실행 연결 검사

공식 `AgentRuntimeContext`에는 `task_summary`, `state_requirements`, `task_requirements`가 함께 있음. 기본 모델이 이를 읽는다는 뜻은 아니지만, 객체 전체를 새 선택기에 넘기면 채점 조건이 섞일 수 있음. 새 선택 경로는 영역·첫 요청·현재 요청·이전에 관측한 대화/도구 결과만 받으며 runtime 객체를 읽지 않음.

저장된 assistant 메시지는 여러 도구 호출과 마지막 답변을 하나로 합침. 이 메시지의 마지막 설명을 앞선 도구 호출 직전 상태에 넣으면 미래 정보가 유출됨. 따라서 공개 기록에서는 완료된 메시지 뒤의 사용자 턴 경계만 추출함. 원본 환경 객체가 없는 860개 접두부를 그대로 다시 실행 가능한 상태라고 부르지 않음.

[입력·선택 어댑터](../../evaluation/statebench_protocol.py)는 은행을 고정하고, 개발 출처·자기 출처를 후보에서 제외하며, 예산과 출처 경계를 검사함. 검토하지 않은 기억 관측은 CPU 진단에만 쓸 수 있고 실제 작업자 연결에서는 거부함. **현재 검토 완료한 실험용 기억 은행은 아직 없음.**

공식 `_run_harness_executed_agent_turn`에 모의 작업자를 붙여 선택 1회→도구 실행→응답의 경로를 확인함. 원래 대화가 변경되지 않고, 숨겨 둔 채점 문자열이 작업자/선택기 입력으로 들어가지 않는 것을 검사함. 실제 LLM의 도구 사용 능력 검증은 아직 아님.

또한 현재 공개 여행 환경을 사용한 합성 도구 진단 두 개를 수행함.

- Basic economy 예약의 수하물 변경에 불필요한 `cabin_class=economy`를 함께 넣으면 거부되고, 같은 환경에서 필요한 필드만 갱신하면 처리됨. 원문 에이전트가 말한 “시스템상 불가능”을 성공 처방이나 확정 사실로 저장하면 안 됨.
- 수하물 변경과 잘못된 지연 보상을 한 번에 요청하면 오류 응답이 나와도 수하물 값은 바뀜. 오류가 곧 롤백을 뜻하지 않으므로 다음 판단에는 최신 관측이 필요함.

이 두 검사는 새로 만든 최소 환경의 도구 동작 진단이며 원래 benchmark 과제의 성공을 재현한 것은 아님. 원본 코드와 원본 기록은 수정하지 않음. 단위·공식 런타임 연결 검사 총 17개가 통과함.

개발 접두부 189개에서 무기억·BM25 목표·BM25 목표+관측의 총 567회 선택을 CPU로 실행함. 두 검색 조건의 후보 은행은 같고 실제 주입 문자열은 모두 1,024토큰 이내임. 상태 입력에 따라 153개 접두부의 선택이 달라졌지만, 이는 입력이 선택에 반영된다는 점검이며 개선 성적이 아님. 선택 ID·출처·입력 해시·전달 토큰은 별도 검산기로 재계산함.

길이 문제는 실제 실행 전에 보완해야 함. 기억 출처의 원문 관측 2,297개 중 825개(35.9%)가 하나만 넣어도 안내문 포함 예산을 넘음. 앞선 도구 응답을 누적한 후보 형식이 영향을 줌. 이런 기록을 조용히 잘라 비교하지 말고, **적용 조건·관련 관측·결과를 보존한 경험 단위**를 원문과 연결해 정리한 뒤 모든 선택기에 같은 단위를 제공해야 함. 짧게 만들며 근거를 잃는지도 검토 대상임. 상태를 포함한 선택기 입력은 작업자 tokenizer 기준 최대 7,991토큰이므로, 실제 선택기의 tokenizer·공통 입력 상한·절단 규칙도 개발 단계에서 고정하고 누락을 기록해야 함.

## 실제 측정으로 넘어가는 순서

1. **239개 출처에서 재사용할 경험을 정리함.** 원래 관측과 제안한 절차를 구분하고, 현재 확인해야 하는 전제·적용하지 말아야 할 상태를 기록함. 반복 오류를 여러 독립 양성 사례로 늘리지 않음. 정책 문서만 주는 기준선도 유지함.
2. **61개 개발 출처에서 실행 가능성과 선택 여지를 확인함.** 저장 접두부만으로 실행하지 않고, 해당 train 과제·초기 환경을 별도로 확보해 실행기에만 공급해야 함. 먼저 고정 작업자가 현재 도구와 과제를 수행할 수 있는지 보고, 같은 기억 은행·같은 예산의 정책 비교를 수행함. 작업자가 충분한 근거를 줘도 못 푸는 경우를 선택기의 실패로 처리하지 않음. 이 과정에서 좋은 사례만 골라 공식 test를 구성하지 않음.
3. **선택기 학습용 득실을 확보할 때는 분기 상태를 새로 저장함.** 기존 로그 뒤에 새 답변만 생성해 실제 득실로 채점하지 않음. 같은 판단 시점의 환경 내부 상태·대화·시뮬레이터 조건을 복제해야 함. 현재 DB 값뿐 아니라 도구의 내부 추적 상태도 포함해야 함.
4. **정책을 고정한 뒤 고객지원·쇼핑의 공식 test 각 50개를 평가함.** 작업자·은행·표현·임계값을 평가 결과로 바꾸지 않음. 전체 연속 실행에서는 정책에 따라 후속 상태가 달라지므로 정책 효과를 보고하고, 개별 기억의 직접 효과는 같은 시점에서 분기한 비교로 별도 보고함.

이 실험은 STATE-Bench를 이용한 통제 비교임. 기존 외부 자료로 학습한 선택기, 자동 주입 시점, 토큰 제한이 공식 제출 규약에 맞는지는 별도 문제이므로 공식 순위표 성적으로 부르지 않음.

## 실행 자원과 남은 준비

공식 평가용 사용자 시뮬레이터·채점기는 GPT-5.4이며 공식 트랙은 과제당 5회 실행함. 작업 모델은 바꿀 수 있음. [고정 평가 클라이언트 안내](https://github.com/microsoft/STATE-Bench/blob/5644b1838d96bc4483da29642d058ecaa6f80f7f/docs/setup/eval-client.md)

현재 세션에는 해당 endpoint/deployment 설정이 없음. 따라서 공개 자료 수집·CPU 검사·독립 Python 3.12 환경 구성까지 진행했으며, 유료 호출·GPU 할당·새 학습·공식 test 실행은 없음. 실제 작업자의 실행 가능성, 유용한 기억 은행, 적용성 및 실제 득실 라벨은 남은 준비임. 기존 작은 관계 학습이 새 업무에서도 도움이 되는지는 이번 준비만으로 판단할 수 없음.

재현 명령과 공유 원본은 [데이터 README](../../datasets/statebench_preparation/20261112-v1/README.md)에 있음. 준비용 CPU 선택 로그는 정책 점수나 작업 성공 성적이 아니라 같은 후보·관측·예산이 유지되는지 확인하는 자료임.
