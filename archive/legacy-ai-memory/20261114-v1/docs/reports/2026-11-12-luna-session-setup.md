## 3. 주 테스트의 실제 결과

| 조건 | 성공 /4 |

국소 제공/보류는 둘 다 성공 6쌍·둘 다 실패 2쌍임. 이번에는 관측된 개선·악화가 없음. 그러나 **모드 대응 8개 중 6개가 실제로 같은 입력**이므로 누적과 분리의 동등성을 입증한 결과로 읽을 수 없음. sparse 질문 사이의 긴 관측이 이전 답변을 최근 창 밖으로 밀었음. 특히 고정 기억 조건은 모든 모드 입력이 같았음.

최소 필요한 기록의 확보율은 의미적 충분성의 대체가 아님. 선호 기반 추천(t16)은 최근 4k에서 선호 근거가 빠졌고, 기억 조건에서는 필요한 선호 기록이 완전히 포함됐으나 둘 다 dinner=UNKNOWN을 출력함. 필요한 기록 확보와 작업 성공을 구분해 기록하는 것이 유용했음.

## 4. 실패 1문항의 제한된 진단

원문 선호는 Dmitri가 여행 내내 French 음식을 원한다는 내용이며, 카탈로그에 조건을 만족하는 R7948·R1528이 있음. 주 테스트는 기존 예외 예약 등 추가 기록도 함께 전달했음.

주 결과를 수정하지 않고 같은 문항에 두 번만 진단함. 정답 근거를 쓰는 사후 진단이며 운영 가능한 선택 정책으로 평가하지 않음.

| 진단 입력 | dinner 출력 | 판정 |
| --- | --- | --- |
| 기존 지시 + 필요한 선호 기록만 | UNKNOWN | 실패 |
| 같은 입력 + “가상 추천은 기존 예약이 없어도 조건에 맞는 ID를 고를 수 있음”을 명시 | R7948 | 정답 |

“새 예약을 만들지 말라”는 조회형 지시와 “아무 적합한 장소를 고르라”는 요청의 경계가 영향을 주었을 가능성이 있음. 한 문항·한 생성씩의 사후 비교이며, 문구가 모든 실패의 원인이라고 확정하거나 수정 지시의 일반적 효과로 보고하지 않음. 원 3/4 성적과 v1 입력은 그대로 보존함.

## 5. 토큰·비용·현재 경계

로컬 tiktoken 0.14.0에는 Luna 네이티브 매핑이 없고 OpenRouter의 `/responses/input_tokens`는 404임. 따라서 이번의 2k/4k는 **명시한 o200k_base 기준**임. 공식 OpenAI의 정확한 카운터는 역할·경계 토큰까지 계산하지만 현재 연결 경로에서 사용한 것은 아님. [OpenAI 토큰 계산 문서](https://developers.openai.com/api/docs/guides/token-counting)

주 테스트의 실제 입력은 총 57,097토큰·출력 282토큰임. 동일 입력의 출력 공유를 독립 호출로 세지 않음. 기본 연결 점검 $0.000598275 + 주 테스트 $0.007277075 + 사후 진단 $0.00022 = **총 $0.00809535**가 provider 사용량에 기록됨. 공급자 원 응답과 비용 예약을 함께 보존함.

다음 한 단계는 조회/추천 계약을 명확히 하고, 질문 일정에서 실제 이전 답변 노출을 확인한 뒤 **다시 작은 테스트만** 수행하는 것임. 입력·코드가 바뀌면 새 버전으로 만들고 v1 점수를 덮어쓰지 않음. 전체 92질문·다른 출처·새 모델·학습은 아직 진행하지 않음.
