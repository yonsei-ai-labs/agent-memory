# 전체 질문에서 여러 과거 기억을 찾는 학습 실험

학습·평가·CPU 검산을 완료했다. **전체 질문에서도 관계를 읽는 추가 학습은 효과가 있었고, 이번 구성의 주된 한계는 앞단 검색의 후보 누락이었다.** 실제 작업자의 성공·비용 개선이나 학습 선택기의 일반적 필요성까지 입증한 결과는 아니다.

## 이번에 바꾼 조건

이전 여행 참조 실험은 문장 하나와 6개 후보에서 정답 1개를 찾았다. 이번에는 전체 질문과 해당 시점 이전의 모든 기억 26–336개를 사용한다. 같은 질문에 필요한 기억이 여러 개일 수 있다. 사용자와 합의한 관계 기반 기억 검색을 직접 학습하며, 작업자의 성공·실패 개선은 이번 회차에 새로 측정하지 않는다.

기본 계획 45개의 분할 30/7/8을 유지했고, 전체 질문은 train 813/dev 189/test 219개다. test의 후보 쌍은 25,867개이고 정답 참조 기록은 768개다. 독립 평가 단위는 질문 219개와 함께 계획 8개를 표시한다. 이전에 관찰한 동일 test 계획이므로 새 출처 일반화 확인이 아니다.

자료는 공개 참조 계획이다. 전체 질문의 명시적 사람·날짜·항목 연결을 주석할 수 있는 경우만 남겼다. train/dev의 표본 질문 18개·참조 75곳을 검토하고, 모든 입력·과거 기록을 원문에서 재구성했다. 독립 주석자가 검수한 자연 기억 관련성 자료는 아니다. [자료 카드](../../datasets/travel_retrieval/20261109-full-request-v1/README.md)와 [학습 전 계획](../ai-memory-full-request-retrieval-2026-11-09.md)에 범위와 해시를 고정했다.

## 학습과 비교

기반 모델은 Harrier 0.6B의 고정 revision이다. BM25, 고정 임베딩 cosine, 두 검색의 RRF 결합을 비교한다. 학습 모델은 RRF 상위 32개 후보를 같은 조건으로 재순위화한다. 후보에 정답을 강제로 넣지 않는다. 앞단 검색의 Recall@32가 두 판독기의 상한이다.

두 판독기는 전체 질문과 기록을 함께 인코딩한 특징을 MLP(1024→128→2)로 판독한다. 고정 모델은 MLP만 12epoch, LoRA 모델은 q/v rank 8과 MLP를 2epoch 학습한다. 같은 초기 head·seed 731·질문당 16개 학습 후보를 사용한다. 균형 분류 손실과 복수 정답 순위 손실을 합친다. 학습량이 다르므로 같은 업데이트 수에서 구조의 우열을 증명한 비교는 아니다. dev의 계획별 macro nDCG@10으로 checkpoint를 선택한다.

test 정답은 Colab에 전송하지 않았다. 원래 후보와 정답을 제거한 후보를 함께 보내면 정답이 노출되므로 제거 진단도 전송하지 않았다. 원래 상위 44개 기록의 점수만 미리 저장하고 제거 진단은 로컬에서 수행한다. 이 진단은 제거 후 BM25 통계를 다시 계산하지 않는 조건이며 자연 미확인 자료가 아니다.

## 결과

test 전체 질문 219개·기본 계획 8개다. Recall은 질문별 정답 기억을 얼마나 찾았는지의 평균이다. nDCG는 정답이 앞쪽에 놓이는 정도이며 계획별 평균을 쓴다.

| 방법 | Recall@10 | 필요한 기억을 전부 상위 10개에 포함 | 계획별 nDCG@10 |
| --- | ---: | ---: | ---: |
| BM25 | 26.3% | 24/219 | 0.159 |
| 고정 Harrier 임베딩 | 37.0% | 35/219 | 0.231 |
| BM25+임베딩 RRF | 35.5% | 36/219 | 0.213 |
| 고정 encoder + 학습 MLP | 56.9% | 72/219 | 0.379 |
| **LoRA + 같은 MLP** | **68.6%** | **96/219** | **0.710** |
| 주석 생성 규칙 | 99.9% | 218/219 | 1.000 |

규칙은 같은 주석 규칙을 재실행한 것이므로 구성상 완전한 기준이다. 정답 12개가 필요한 질문 하나는 상위 10개만으로 전부 담을 수 없어, 규칙도 218/219다. 상위 20개에서는 규칙 219/219다. 이 과제로 학습 모델이 규칙보다 필요하다고 주장할 수 없다.

고정 임베딩 단독의 Recall@10은 사전에 고정한 RRF보다 높았다. 검색 결합 자체의 우위는 확인되지 않았다. 두 학습 판독기는 같은 RRF 후보로 비교했으며, test 결과를 보고 첫 검색 방식을 교체하지 않았다.

LoRA는 개발 기준으로 2epoch 체크포인트를, 고정 MLP는 7epoch 체크포인트를 선택했다. LoRA의 계획별 nDCG 향상은 고정 MLP 대비 +0.330이다. 계획을 묶어 재표집한 탐색적 95% 구간은 +0.294~+0.363이다. 계획이 8개이고 seed가 하나이며 과거에 노출한 계획이므로 독립 확인이나 여러 학습 반복의 불확실성까지 반영한 구간은 아니다.

### 현재 병목은 후보 검색

정답 참조 기록은 총 768개다. RRF의 첫 후보 32개에는 그중 **470개만 들어왔고 298개는 빠졌다.** 후보에 들어온 470개 중 LoRA는 468개를 상위 10개로, 470개 모두를 상위 20개로 올렸다. 이는 후보에 들어온 기록으로 조건을 제한한 수치이며 전체 기억의 검색률이 99.6%라는 뜻은 아니다.

질문별 평균으로도 LoRA Recall@10 68.57%는 첫 검색 Recall@32 68.68%에 가깝다. 필요한 기록이 모두 후보에 들어온 질문은 96개이며, LoRA가 전부 상위 10개에 넣은 질문도 96개다. 첫 후보가 불완전한 질문은 123개였다. 따라서 이번 구성에서 판독층만 더 개선해 얻을 수 있는 추가 Recall@10은 작다. 관계를 반영한 후보 검색까지 연결하는 것이 다음 우선순위다. **전체 질문을 하나의 임베딩으로 표현한 것이 원인인지는 이 비교만으로 확정하지 않는다.**

조건별 LoRA Recall@10은 단일 참조 28질문에서 96.4%, 복수 참조 191질문에서 64.5%였다. 은행이 100개 이하인 100질문에서는 91.4%, 100개를 넘는 119질문에서는 49.4%였다. 은행 크기·질문 복잡도·기본 계획이 함께 달라지므로 크기 자체의 인과 효과로 해석하지 않는다.

### 실제 사례

- `travel-bank-110-turn-6`: 현재의 첫날 숙소를 고르기 위해 **Isaac의 둘째 날 숙소**, 둘째 날 숙소를 고르기 위해 **Chelsea의 첫날 숙소** 등을 찾아야 한다. 필요한 세 기록이 일반 검색에서는 15·17·18위였고 LoRA 후 2·3·1위가 됐다. 현재 날짜와 참조 날짜를 구분한 사례다.
- `travel-bank-67-turn-6`: 필요한 다섯 기록이 첫 검색에서 33·42·52·83·92위였다. 32개 후보를 보는 판독기는 이들을 받을 수 없었다. 첫 후보 누락이 그대로 남는 사례다.
- `travel-bank-45-turn-2`: 후보 안에도 남은 오류가 있다. “Susan의 그날 저녁”이 가리키는 6일째 저녁은 20위에서 13위가 됐지만 상위 10개에는 들지 못했다. 후보 내 판독이 완벽하다는 주장도 하지 않는다.

[원문·기억·실제 순위](../../evaluation/results/travel-full-request-retrieval-20261109-v1/error-cases.json)에 예시와 집계를 보존했다. 사례는 결과를 설명하기 위해 사후 선정했으며 학습·모델 선택에 사용하지 않았다.

### 보류와 전달량은 별도 문제

dev의 정답 제거 진단에서 잘못 제공하는 비율을 5% 이하로 제한해 정한 LoRA 임계값은 0.993469다. test에서 정답을 모두 제거하면 4/219질문에서 잘못된 기억을 제공했다. 원래 정답이 있는 상태에서는 145/219질문에 정답을 하나 이상 제공했고, 전부 제공한 질문은 68/219였다. 선택한 기록의 정밀도는 98.4%, 평균 제공량은 1.16개였다. 엄격하게 보류할수록 필요한 기억도 더 많이 빠진다.

고정 MLP는 같은 개발 선택 절차에서 test 정답 제거 시 11/219 오제공, 원래 상태에서 정답을 하나 이상 제공한 질문 6/219였다. 이 결과는 고정 첫 검색 순서에서 정답만 제거한 진단이며, 자연 발생 미확인 문제나 실제 득실에 대한 위험 보장이 아니다. 이번 회차에는 작업자 생성·성공률·선택기 추론 지연을 새로 측정하지 않았다.

## 검산과 다음 판단

CPU에서 1,221질문의 BM25와 저장 임베딩 cosine을 다시 계산했고 일치했다. 고정 MLP의 저장 확률 17,522개를 실제 가중치·저장 특징으로 재계산했으며 최대 차이는 6.6e-7이었다. 두 방법의 초기 head가 같고, 선택한 head의 파라미터와 LoRA 112개 텐서가 변경됐으며 optimizer 업데이트 수가 체크포인트와 일치했다. train 813질문이 고정 MLP에서는 12회, LoRA에서는 2회 모두 학습에 사용됐다. LoRA의 encoder 출력을 CPU에서 다시 생성한 검산은 아니다.

학습 파라미터는 head 131,458개, LoRA 1,146,880개다. 새 clone에서 공개 원본 다운로드·데이터 생성·해시 검증·학습 내보내기와 관련 검사 56개를 통과했다. [공유 결과 묶음](../../evaluation/results/travel-full-request-retrieval-20261109-v1/README.md)에 원본 예측·검산·자원 기록을 연결했다.

다음 비교는 **관계를 반영해 후보를 찾는 앞단**에 초점을 맞추는 것이 맞다. 질문을 관계별로 나누어 검색한 뒤 합치는 단순 방법과, 이번 판독기의 검증된 점수를 이용해 검색용 임베딩을 학습하는 방법을 비교할 수 있다. 이는 후속 제안이며 이번 test를 보고 새 실험을 실행하거나 점수를 고치지는 않았다. 다음 확인에는 새 출처·표현을 남겨야 한다. 이후 고정 작업자에게 같은 기억 예산으로 제공해 성공·실패·비용을 측정하면 처음의 기억 득실 질문과 연결된다.

## 재현과 자원

학습 코드는 [train_travel_retrieval.py](../../training/memory_selector/train_travel_retrieval.py), 설정은 [travel-retrieval-v1.json](../../training/memory_selector/configs/travel-retrieval-v1.json)이다. 로컬 평가는 [travel_retrieval_results.py](../../evaluation/travel_retrieval_results.py), 가중치·저장 특징 검산은 [audit_travel_retrieval_run.py](../../evaluation/audit_travel_retrieval_run.py)에서 수행한다.

실행 경로는 `training/memory_selector/outputs/travel-full-request-retrieval-20261109-a100`이다. 하나의 A100 세션만 사용하며 스크립트 3,600초, 컨트롤러 3,900초 한도를 둔다. 로컬 GPU와 유료 LLM API는 사용하지 않는다. 전체 제어 시간에는 설치·특징 생성·학습·예측·압축·다운로드가 섞이므로 작업당 추론 지연이나 정확한 GPU 과금 시간으로 해석하지 않는다.

실제 제어 구간은 1,064.4초(17.7분), 스크립트 구간은 978.6초다. 관측 사용률은 할당 중 6.73 Colab 단위/시간, 종료 후 0.00/시간이었다. 결과·checkpoint 회수 후 세션 종료와 활성 세션 부재를 확인했다. 가중치까지 전체 검토하려면 실행 폴더의 실제 **upload.zip과 results.zip 둘 다** 필요하다. Git의 예측 묶음은 전체 가중치·특징 캐시를 포함하지 않는다.
