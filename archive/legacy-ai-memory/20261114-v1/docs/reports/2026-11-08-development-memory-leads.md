# 실제 개발 이슈로 넓힌 기억 학습: 2026-11-08

이 회차는 초기화·설치 문제에 치우친 좁은 진단에서 벗어나, 실제 이슈와 과거 코드 경험을 연결하는 학습을 실행한다. **진단 단서의 관련성**을 배우는 중간 과제이며, 별도 모델의 기억 선택이 작업 성공과 비용을 개선했다는 최종 검증은 아니다.

**학습과 검산은 완료했으나 새 이슈의 기억 선택 개선은 확인하지 못했다.** 관련 단서가 있는 평가 이슈 4개에서 12개 학습 모델 모두 첫 선택 0/4였다. 별도 CPU 진단에서는 같은 고정 표현과 MLP로 학습 432쌍을 모두 맞힐 수 있었다. 학습 적합 가능성과 일반화 실패를 구분해야 한다. Colab은 종료됐고 활성 세션 0개·사용률 0을 확인했다.

## 데이터와 판단 시점

공개 SWE-rebench OpenHands의 고정 첫 row group에서 결과를 보지 않고 저장소·이슈 ID로 **30개 저장소·77개 실행**을 선정했다. 그중 관측한 과거 수정 경험 16개와 다른 실제 이슈 40개를 연결해 640쌍을 만들었다. 원본 명령을 다시 실행하거나 공식 정답 patch를 입력으로 사용하지 않았다.

현재 입력은 사용자 이슈 설명뿐이다. 미래 에이전트의 명령·관측·성공 여부를 시작 시점 선택기에 넣지 않는다. 다만 실행 중 코드 상태를 판단하는 과제까지 다룬 것은 아니다. 8개 설명은 2,200자에서 잘렸고 입력 범위에 맞춰 주석했다. 과거 기억의 관측 부분은 실제 수정 명령·응답 26쌍에 연결했다. 진단 원리와 적용 경계는 작성자의 해석이다.

| 분할 | 현재 이슈 | 현재 저장소 | 쌍 | 관련 / 다른 원리 / 미확인 |
| --- | ---: | ---: | ---: | --- |
| 학습 | 27 | 16 | 432 | 18 / 391 / 23 |
| 개발 | 7 | 4 | 112 | 9 / 102 / 1 |
| 평가 | 6 | 4 | 96 | 4 / 85 / 7 |

**640쌍을 독립 경험 640개로 세지 않는다.** 현재 저장소를 나눴지만 16개 기억 은행은 공유한다. 평가 저장소의 다른 과거 이슈가 은행에 포함되므로, 완전히 새 저장소·새 기억으로의 전이가 아니다. 시간순 선후도 검증하지 않았다.

주석은 한 assistant의 검토이며 독립 합의나 실제 효과 정답이 아니다. 평가 주석을 작성자가 알고 있고 약한 어휘 기준선도 먼저 보았다. 다만 모델 학습·checkpoint 선택에는 개발 라벨까지만 사용하고 **평가 라벨은 Colab에 업로드하지 않았다**. 원본 근거와 한계는 [데이터 카드](../../datasets/development_memory_leads/20261108-v1/README.md), [자료 감사](data/development-memory-leads-20261108/data-audit.json), [사전 계획](data/development-memory-leads-20261108/pre-training-plan.json)에 있다.

## 비교 조건

`microsoft/harrier-oss-v1-0.6b`의 revision `f9b9dc8d367d443f2479d27aa5d8d2850c0774ee`에서 매번 새로 시작했다. 기존 실험의 모델 가중치를 덮어쓰거나 이어서 손상시키는 방식이 아니다.

- 고정된 함께 읽기 표현 + 선형 판독층 / MLP 판독층.
- 현재 문제만 / 기억만 읽는 MLP 대조.
- 함께 읽는 Harrier + LoRA + MLP.
- 같은 LoRA에 후보 순위 손실 0.2를 추가한 비교.

각각 seed 731, 1729를 사용한다. 한 업데이트에 같은 현재 이슈의 기억 16개를 모두 넣고 128회 업데이트한다. 학습 432쌍은 각 4–5회 노출된다. 클래스 빈도의 역수에 비례한 가중 분류 손실을 사용한다. LoRA는 q/v, rank 8, alpha 16, FP32다. 입력 상한 1,536토큰에 실제 최대 969토큰으로, tokenizer 단계에서 잘린 입력은 없다.

32/64/128회에서 개발 macro-F1이 처음 최대가 된 checkpoint를 저장하고, 그것을 다시 읽어 예측한다. 방법 선택은 두 seed의 개발 macro-F1 평균이다. 관련 기억 첫 선택과 미제공/오제공도 별도 기록한다. **분류 F1을 최적화하는 것과 후보를 잘 고르는 것은 같은 목표가 아니다.** 평가 결과에 맞춰 선택 기준을 바꾸지 않는다.

원래 임베딩의 코사인 유사도, BM25, 학습에서 긍정이 가장 자주 나타난 기억, 항상 다른 원리라고 답하는 기준선도 비교한다. 코사인은 이미 저장된 두 단독 입력의 임베딩을 사용하며, 별도로 최적화한 검색 prompt의 성능은 아니다. 검색 점수에 임의의 확률 의미를 부여하지 않는다.

## 고정한 모델의 평가 결과

아래 F1은 평가 96쌍의 3분류 macro-F1이다. 첫 선택은 그중 관련 단서가 있다고 주석한 **현재 이슈 4개** 기준이다. 관련 단서가 없는 두 이슈를 성공 분모에 섞지 않았다. seed별 결과를 모두 보존했다.

| 방법 | 평가 F1: 731 / 1729 | 관련 기억 첫 선택: 731 / 1729 |
| --- | --- | --- |
| 고정 표현 + 선형 | 0.2880 / 0.2989 | 0/4 / 0/4 |
| 고정 표현 + MLP | 0.3565 / 0.3131 | 0/4 / 0/4 |
| 현재 문제만 + MLP | 0.3131 / 0.3131 | 0/4 / 0/4 |
| 기억만 + MLP | 0.2984 / 0.3010 | 0/4 / 0/4 |
| LoRA + MLP | 0.2538 / 0.2924 | 0/4 / 0/4 |
| LoRA + 후보 순위 손실 | 0.2489 / 0.2764 | 0/4 / 0/4 |
| 항상 다른 원리 | 0.3131 | 후보를 선택하지 않는 분류 기준선 |

항상 다른 원리라고 답해도 정확도는 85/96 = **88.5%**다. 이것을 높은 기억 선택 성능으로 읽으면 안 된다. 별도 검색의 첫 선택은 BM25 1/4, 학습 긍정 빈도 기준선 1/4, 저장된 Harrier 단독 표현의 코사인 0/4였다. 이 자료에서 특정 검색법의 일반적 우열을 정할 표본 크기도 아니다.

개발에서 고른 방법은 `lora-ranking`이다. 평균 개발 F1은 0.331013으로 고정 선형 0.330992보다 **0.000021** 높았을 뿐이다. 현재처럼 작은 개발 자료에서 사실상 동률인 차이가 배포 선택을 바꿨다. 두 seed 모두 평가 여섯 이슈의 최상위 후보는 `specific_precedence`였고, 0.5 제공 문턱을 넘은 이슈는 **0/6**이었다. 전부 보류했으므로 오제공이 없다는 사실도 적절한 선택 능력의 증거가 아니다.

| 실제 평가 이슈 | 현재 주석의 관련 기억 | 선택된 두 seed의 최상위 후보 | 관련 기억의 순위: 731 / 1729 |
| --- | --- | --- | --- |
| null 필드가 직렬화에서 빠짐 | 변환 과정의 필드 보존 | 설정·태그의 우선순위 | 8 / 5 |
| Literal 객체 비교의 TypeError | 래퍼와 원래 값의 변환 | 설정·태그의 우선순위 | 10 / 8 |
| `pytest.raises`를 Act로 잘못 셈 | 중첩 블록의 역할 구별 | 설정·태그의 우선순위 | 11 / 15 |

현재 문제에 따라 확률이 전혀 변하지 않는다는 뜻은 아니다. 다만 최상위 선택이 상황별로 달라지지 않았다는 직접적인 실패다. [모든 사례 CSV](../../evaluation/results/development-memory-leads-20261108-v1/test-cases.csv)와 [전체 예측](../../evaluation/results/development-memory-leads-20261108-v1/README.md)에 상수 기준선까지 포함한 8,320개 기록을 남겼다. 다른 모델·문턱을 평가 정답에 맞춰 다시 고르지 않았다.

## 학습 자료를 맞출 수 있는가

주 학습이 진행되는 동안 CPU에서 학습 자료만 사용하는 별도 진단을 했다. 같은 초기 선형/MLP 판독층에 고정된 함께 읽기 표현을 주고, 전체 432행을 묶어 2,048번 업데이트했다. 개발·평가 자료는 채점하지 않았고, 이 모델을 추가 평가 후보로 고르지 않았다.

| CPU 진단 | 128회 학습 정답 | 512회 | 2,048회 |
| --- | ---: | ---: | ---: |
| 선형, seed 731 | 202/432 | 222/432 | 302/432 |
| 선형, seed 1729 | 202/432 | 220/432 | 302/432 |
| MLP, seed 731 | 306/432 | 416/432 | **432/432** |
| MLP, seed 1729 | 289/432 | 416/432 | **432/432** |

저장 가중치·optimizer·확률에서 1,728개 예측을 CPU로 다시 계산했고 일치했다. 34.9초가 걸렸고 추가 GPU는 쓰지 않았다. [학습 곡선](data/development-memory-leads-20261108/train-fit-results.json)과 [가중치 검산](data/development-memory-leads-20261108/train-fit-audit.json)을 보존했다.

이는 고정된 표현과 MLP가 **현재 학습 주석을 맞출 능력은 있다**는 증거다. 새 문제의 성능, 주석 품질, 실제 기억 효용은 증명하지 않는다. 주 비교와 배치 구성·전체 노출량을 모두 바꿨으므로 학습 길이만의 효과로 해석할 수 없다. 선형 모델의 최적화가 끝났다는 보장도 없다.

학습 입력의 함께 읽기 표현을 분해하면 변동의 59.2%는 현재 문제, 36.9%는 기억, 3.8%는 두 항의 상호작용에 해당한다. 이는 [서술적 통계](data/development-memory-leads-20261108/feature-diagnostic.json)이며, 상호작용 비중만으로 관계 정보가 없다고 단정할 수 없다.

## 이번 자료가 아직 해결하지 못한 문제

학습 긍정은 18쌍이고 10개 기억에만 있다. 개발 긍정 중 1/9, 평가 긍정 중 1/4은 같은 기억의 학습 긍정 사례가 없다. 개발에는 관련 기억이 하나도 없는 이슈가 없으므로, 보류 문턱을 충분히 검증하지 못한다. 정확도만 보면 대부분 무관하다고 답하는 모델도 좋아 보인다.

더 중요한 것은 **관련성과 추가 정보의 가치가 다르다**는 점이다. 예를 들어 null 필드 직렬화 이슈에는 이미 원하는 동작과 수정 위치가 쓰여 있다. Literal 비교 문제도 이슈가 `isinstance`와 `_value` 확인을 제안한다. 관련 기억을 맞혀도 작업자에게 새 정보가 없을 수 있다.

반대로 `pytest.raises` 안의 호출을 Act로 잘못 세는 문제에서는 “중첩 노드를 더 찾아라”는 옛 수정만 복사하면 문제가 커질 수 있다. 과거 경험을 진단 단서로 쓰는 것과 그 패치를 재사용하는 행동을 분리해야 한다.

전방 참조의 지연 평가와 f-string escaping을 같은 원리로 볼지, 기본값의 맥락 오류와 덮어쓰기 우선순위를 같은 원리로 볼지도 독립 검토가 필요하다. [일곱 검토 사례](data/development-memory-leads-20261108/annotation-review-followup.json)를 남겼으며, 시작한 학습의 정답을 사후에 바꾸지 않았다.

## 원래 연구 질문으로 연결할 다음 자료

이 자료를 큰 분류 benchmark로 늘리는 것만으로 끝내지 않는다. 다음에는 관련 단서가 명확한 여러 코드 문제에서 공통의 초기 관측 지점을 고정하고, **기억이 새 정보를 주는 경우·이미 알려진 경우·조건이 어긋나는 경우**를 구분한다. 주석 가능한 현재 코드·관측만 입력에 담고, 같은 종류의 관계가 여러 독립 출처에 나타나게 보강한다.

관계 주석과 별도로 고정 작업자에게 기억을 제공/보류해 얻은 성공·첫 유효 패치까지의 비용·불필요한 확인을 저장한다. 그 차이를 별도 모델이 배워야 할 효용 신호로 삼는다. 검색과 작은 모델의 역할도 비교한다. 핵심은 기억과 문제의 주제가 비슷한지를 넘어서, **지금 어떤 정보를 전달해야 실제로 이득인지**를 배우는 것이다.

기억을 항상 통째로 주는 행동뿐 아니라, 같은 출처의 관측·수정 지침·적용 조건 중 무엇을 보존하거나 빼는지도 비교 대상으로 남긴다. 이번 관련성 자료에는 그 조각별 인과 효과 라벨이 없으며, 640쌍을 그 목적의 효용 학습 자료로 자동 전환하지 않는다.

## 실행을 다시 확인하는 방법

새 학습은 Colab L4 사용량이 발생한다. 다음 명령의 출력 경로는 새 이름을 사용한다.

```bash
python3 training/memory_selector/prepare_development_leads.py \
  --source datasets/development_memory_leads/20261108-v1 \
  --output training/memory_selector/data/development-leads-reproduction
python3 training/memory_selector/run_colab.py \
  --profile development-leads \
  --data training/memory_selector/data/development-leads-reproduction \
  --max-runtime-seconds 3600 \
  --output training/memory_selector/outputs/development-leads-reproduction
```

원래 실행은 `training/memory_selector/outputs/development-leads-20261108-v1/`에 보존한다. 전체 감사에는 그 폴더의 `upload.zip`, `results.zip`, 실행 상태와 풀어 놓은 `artifacts/`가 필요하며 Git에는 대용량 가중치를 넣지 않는다. CPU Torch와 [감사 의존성](../../training/memory_selector/requirements-development-leads-cpu.txt)을 준비한 뒤 실행한다.

```bash
CUDA_VISIBLE_DEVICES='' python3 training/memory_selector/probes/audit_development_leads.py \
  --run training/memory_selector/outputs/development-leads-20261108-v1
```

고정 표현 위 판독층의 실제 forward, LoRA tensor 변화, optimizer, 데이터 노출, 선택 시점, 실행 코드 해시를 확인한다. **전체 LoRA encoder의 CPU forward까지 재계산하는 검사는 아니다.** 원격 학습은 선택 adapter를 다시 읽은 뒤 개발 확률을 대조해 저장 예측을 만들었다.

공유 예측만 재계산할 때는 Torch·GPU·원본 로그가 필요 없다.

```bash
python3 -m evaluation.verify_development_leads evaluation/results/development-memory-leads-20261108-v1
```

## 검산과 자원

- 학습 코드 검사 112개가 CPU Torch 환경에서 전부 통과했고 평가 검사 30개도 통과했다. 표준 Python의 학습 검사에서는 Torch 의존 5개가 skip되므로 CPU 환경에서 보완했다.
- 원본 로그·가중치가 없는 임시 공유 사본에서도 자료 검사, 학습 내보내기, 새 평가 검사 6개, 8,320개 저장 예측 검산이 통과했다. 전체 저장소의 새 clone 검사가 아니라 이번 자료·평가 경로의 독립 복사 확인이다.
- 공개 원본 77개를 새 수집 코드로 다시 받아 원래 파일과 바이트 단위로 일치함을 확인했다. 현재 설명 40개와 과거 수정·응답 26쌍도 정확히 연결됐다.
- 고정 모델 8개의 실제 판독층으로 5,120개 확률을 CPU에서 재계산했다. 최대 차이는 5.96e-8이었다. 네 LoRA 실행에서 각각 **112개 adapter tensor**가 실제로 바뀌었다. 56개 q/v 모듈의 A/B tensor를 따로 센 수다.
- 128개 optimizer 업데이트, 모든 학습 행의 4–5회 노출, 개발 checkpoint 선택, 저장 후 재로딩을 확인했다. 원격 재로딩의 개발 확률 차이는 전부 0이었다. 주 실험의 사전 hash 열 개는 변경되지 않았다.
- 첫 로컬 감사의 scalar norm 절대 허용오차 1e-8은 FP32 합산 차이 최대 4.32e-7에 너무 엄격했다. 실제 tensor 대조 후 상대 1e-6·절대 1e-8로 수정했고 [실패 기록과 이유](data/development-memory-leads-20261108/audit-numerical-tolerance.json)를 보존했다. 학습 산출물과 순전파 확률 허용오차는 바꾸지 않았다.
- Colab L4 하나를 2,356.2초, 약 **39.3분** 사용했다. 잔액 관측은 587.08→585.85 CU, 차이 1.23 CU다. 지연 청구가 있을 수 있는 스냅샷 차이이며 정확한 최종 청구액으로 보지 않는다. 종료 후 사용률 0.00/hr·활성 할당 0을 확인했다. 로컬 GPU·새 유료 모델 API는 사용하지 않았다.

결과는 구현이 실제로 학습·저장됐다는 점과 이번 제한된 선택 실험의 실패를 지지한다. 자료와 학습 예산을 고정한 이번 회차만으로 LoRA 전체나 특정 모델 계열이 부적절하다고 단정할 수 없다. 다음 변경은 여러 층을 무작정 더하는 것보다, 의미가 명확한 긍정·보류 관계의 출처를 보강하고 충분한 학습 적합을 확인한 뒤 별도 새 평가에 연결하는 순서가 적절하다.
