## 질문과 범위

이전 12회에서는 정보형·지침형의 해결률이 같았고, 메모리 유무의 관측 차이는 Sphinx와 Django에서 반대였다. 두 번의 반복으로 득실을 확정하지 않았다. 이번에는 기존 두 문제를 더 반복하지 않고 새 원천 경험 두 개와 새 대상 네 개로 범위를 넓힌다.

주 질문은 같은 경험 본문에 붙이는 정보 안내와 지침 안내의 차이다. 메모리 유무의 성과·비용 차이는 보조 비교다. 기억 내용은 타입 주석·ORM 필드 선택에서 조건 평가·캐시 범위, 배열 자료형·빈 입력으로 넓힌다. 이 배치에서 사용하는 카드 종류는 실행 전에 `procedure`로 정했다. 별도로 생성한 `facts` 카드도 보존하지만 이번 배정에는 넣지 않는다. 따라서 내용 유형의 독립적인 효과를 추정하는 요인 실험은 아니다.

## 환경과 평가를 먼저 검사한다

공식 이미지 여섯 개는 코드 내용이 기준 커밋과 같았지만 파일 권한이 달라 소스 트리 검사에서 중단됐다. 원본 태그를 그대로 두고 별도 `ai-memory` 이미지에서 정확한 기준 커밋으로 복원했다. 의존성을 재설치하지 않았다. 별도 이미지의 reflog와 도달 불가능한 Git 객체를 정리했고 과거 조상 이력은 유지했다. [원래 차이](data/new-content-transfer-20261105/upstream-tree-differences.json), [복원 기록](data/new-content-transfer-20261105/source-tree-audit.json).

추가 Git 객체 검사는 상속된 `refs/remotes/origin/HEAD`가 존재하지 않는 참조를 가리켜 처음 실패했다. 진단용 일회성 컨테이너에서 해당 symbolic ref만 삭제하고 재검사하자 여섯 개 모두 종료 코드 0, unreachable/dangling 객체 0이었다. scikit-learn의 오래된 tree에 관한 filemode 경고는 남았다. 실제 실험 이미지와 조상 이력은 바꾸지 않았고 [실패 검사](data/new-content-transfer-20261105/git-object-audit.json)와 [후속 진단](data/new-content-transfer-20261105/git-object-audit-without-dangling-remote-head.json)을 모두 보존한다. 이 검사는 모델 사전학습 오염까지 배제하지 않는다.

scikit-learn의 공식 채점 스크립트는 editable 설치를 수행하므로 빌드 시간도 포함된다. 실행 시간 전체를 기억 내용의 계산 효율로 동일시하지 않는다. **에이전트가 코드를 조사하는 컨테이너**에는 CPU 2개·메모리 4GiB를 부여하고 네트워크를 끈다. 공식 채점은 SWE-bench 하네스가 별도 컨테이너를 만든다. 실제 채점 컨테이너의 `docker inspect`와 설치된 하네스 소스를 대조하니 bridge 네트워크, 별도 CPU·메모리 상한 없음이었다. 처음 보고서의 자원 제한 문장이 모든 컨테이너에 적용되는 것처럼 읽힐 수 있어 [환경 경계 감사](data/new-content-transfer-20261105/resource-boundary-audit.json)를 남기고 문장을 고쳤다. 실행 중 환경·코드·배정은 바꾸지 않았다.

## 출처 경험과 기억 작성

출처마다 무메모리로 한 번 실행한다. 공식 해결과 미해결 모두 경험으로 남기며, 원하는 결과가 나올 때까지 다시 실행하지 않는다. 카드 작성기에는 해당 출처의 공개 문제·실제 명령·제출 패치·공식 결과만 준다. 대상 문제 설명·대상 정답·로컬 진단은 주지 않는다. 출처 판정과 근거 인덱스, 길이를 검사하고 선택한 절차 카드의 관측 문장을 원본 명령과 대조한 뒤 고정한다.

실제 출처 결과는 pytest 7373 해결(수정 대상 테스트 1/1, 유지 테스트 81/81), scikit-learn 10508 미해결(수정 대상 0/2, 유지 18/18)이었다. 각각 890자·927자의 절차 카드를 채택했다. 원래 명령과 로컬 결과, 공식 판정을 대조했고 **본문 수정은 0건**이다. [검토 기록](data/new-content-transfer-20261105/source-card-review.json). 별도로 생성한 사실 카드는 원본 은행에 보존한다. 출처의 성공 여부가 주제·저장소와 함께 달라지므로 이 실험은 성공 기억 대 실패 기억의 독립 효과를 식별하지 못한다. 실패 출처에서 얻은 관측도 다른 과제에 유용할 수 있어 이를 자동으로 손해 기억이라고 분류하지 않는다.

카드 고정 후 별도로 읽은 [출처 실패 로그](data/new-content-transfer-20261105/supplementary-source-failure-review.json)에서는 scikit-learn의 두 공식 실패 모두 `inverse_transform`과 연결됐다. 빈 입력 테스트의 traceback은 `transform([])` 결과의 assertion을 지난 뒤 `inverse_transform([])`에서 실패한다. 제출 패치는 `transform`만 수정했다. 따라서 좁은 관측의 검증과 과제 전체 해결은 서로 다른 단위다. 이 사후 해석으로 카드를 수정하지 않았고, 그 관측이 대상 과제에 이익을 줬다는 증거로도 쓰지 않는다.

두 표현에서 본문·출처·공식 결과·공통 적용성 안내·도구·위치는 같다. 이전 실험의 안내 문구를 그대로 재사용하며 새 대상 결과에 맞춰 문구를 고치지 않는다. 지정한 카드를 시작에 제공하고 별도 조회 선택 효과는 이번 비교에 넣지 않는다. 정보형에도 적용성 확인 안내가 있고 본문에 조사 절차가 있으므로 순수한 사실 대 순수한 명령의 비교는 아니다.

## 배정·예산·분석

새 대상 네 개 × 무메모리·정보형·지침형 × 두 반복, 총 24회다. 별도의 출처 실행 2회와 카드 작성 요청 2회는 대상 성과의 분모에서 제외한다. [배정](data/new-content-transfer-20261105/allocation.json)은 새 출처 실행 전 고정했다. seed `2026110503`을 사용했고, 각 과제의 두 반복에서 각 조건이 서로 다른 위치를 차지하도록 순서를 순환시켰다. 전체 조건·위치 조합은 각각 2~3회다. 숨은 모델 난수나 캐시는 통제하지 않는다.

모델은 기존 Luna·OpenAI 제공자 고정, medium, 최대 출력 8192다. 코딩 실행은 각각 모델 요청 32회·에이전트 600초·요청 120초·공식 채점 600초·응답 비용 $0.05의 중단 기준을 적용한다. 이번 전체 추가 비용 중단 기준은 $1.50, 대상 배치 기준은 $1.20다. 이전 알려진 비용 $1.15419835464에 합산하며 초기 미확인 HTTP 404 한 건은 계속 별도로 둔다. 비용은 응답 후 검사하므로 요청 하나까지 포함한 정확한 하드 상한은 아니다.

주 지표는 예산 내 공식 해결물 제출이다. 정상 한도 도달의 미제출은 배정에서 유지하고 공식 판정은 `null`, 전달 성공은 0으로 기록한다. API·환경·불완전 채점·응답 비용 불명에는 중단한다. 결과에 따른 대체·자동 재시도·조건 추가는 하지 않는다.

메모리를 만드는 비용도 대상 실행 비용과 함께 보존한다. 이번 출처 수집은 $0.004081730, 카드 작성은 $0.002524225로 합계 $0.006605955였다. 실제 사용의 추가 API 비용을 추정할 때는 대상의 평균 비용 차이에 생성 비용을 향후 사용 횟수로 나눈 몫도 더해야 한다. 실험에서 같은 카드를 여러 조건에 제공한 횟수가 실제 서비스의 재사용 횟수를 정해 주지는 않는다. 컨테이너·저장·사람의 검토 비용은 측정하지 않았다.

과제별 해결률·유지 테스트 회귀·전체 배정 평균 비용을 먼저 보고한다. 주 대비는 지침형−정보형, 보조 대비는 각 메모리 조건−무메모리다. 네 고정 과제의 동일 가중 평균과 iid 반복 가정 아래 대비별 보수적 95% 범위도 계산한다. 과제 모집단·새 출처로의 일반화 구간이나 비용 유의성 검정은 아니다. 사전 지정 출처 이름이 들어간 검색 명령을 실제 API call ID와 연결하되 기억 채택·손해의 확정 라벨로 쓰지 않는다.

실행 중 계산한 [가상 극단의 설계 진단](data/new-content-transfer-20261105/design-resolution-diagnostic.json)도 남겼다. 네 과제·조건별 두 반복에서는 한 조건 8/8 대 다른 조건 0/8이라는 최대 관측 차이조차 현재 고정한 보수적 범위가 −88.82~+100%p로 0을 포함한다. 이는 실제 결과가 아니라 판정 규칙의 정밀도 한계다. 이 파일럿으로 방향을 확정할 수 있을 것처럼 해석하지 않으며, 결과를 본 뒤 더 유리한 검정으로 바꾸지도 않는다. 다음 확인 실험은 중요한 최소 차이와 과제·출처의 변동에 맞춰 별도로 설계해야 한다.

사전 지정한 출처 식별자를 포함하는 `rg`/`grep` 형태 명령은 **모든 조건에서 0/8회**였다. pytest 출처의 네 이름은 대상의 초기 앱 코드에 없었고, scikit-learn 출처의 세 이름은 있었다. 이 지표에서는 이전 Django 탐색과 같은 오래된 이름 검색 패턴을 관측하지 못했다. 지표 자체가 좁으므로 기억을 무시했다거나 일반적인 조사 절차를 옮기지 않았다고 단정하지 않는다. `sed`·Python으로 코드를 읽거나 개념적으로 절차를 옮기는 행동은 이 검색 지표에 잡히지 않을 수 있다. ## 연구 방향에 대한 판단과 다음 설계

**효과를 분리해 기록하는 경로는 작동했지만, 이번 데이터로 어떤 기억 성질이 득이나 실을 만든다고 결론 내릴 수는 없다.** 네 대상이 두 출처를 공유하고, 적용성이 명확한 긍정 사례가 부족하며, 관측 성과가 과제별로 모두 성공 또는 모두 실패에 몰렸다. 같은 저장소나 기능군이라는 접점만으로 경험이 현재 과제에 새 정보를 더한다고 보장하지 않는다. 원천 경험 수·관련성·표현 문구의 다양성을 늘려야 한다는 설계상의 근거이며, 특정 요소의 인과 효과를 발견했다는 뜻은 아니다.

데이터 제작은 기존 벤치의 문제·환경·공식 테스트를 이용하고 실제 경험에서 카드를 작성하는 방식으로 가능했다. 두 출처를 위한 새 문제 작성은 필요하지 않았다. 그러나 환경 복원과 출처의 관측 문장 대조, 출처·대상 관계 선정에는 검토가 필요했다. 모델 API 비용이 낮다는 사실만으로 데이터 제작 전체가 저렴하거나 자동화됐다고 판단하지 않는다.

다음 회차의 우선순위는 아래와 같다. 아직 새 배정을 실행하지 않았다.

1. **적용성이 명확한 출처·대상과 약한 출처·대상을 결과 전에 구분한다.** 공개 문제·코드·API 존재 여부를 근거로 하고, 같은 저장소라는 이유만으로 적합하다고 정하지 않는다. 출처와 대상을 더 확보하고 이미 본 과제는 탐색 집합으로 남긴다.
2. **과제 전체 성공 여부와 기억 속 관측의 검증 범위를 나눈다.** 이번 실패 출처에는 좁게 통과한 관측이 있었고, 대상의 공식 실패 패치에도 추가된 안내가 있었다. 이 사실들을 기억의 이익으로 자동 라벨링하지 않고 현재 과제에서 해당 부분을 바꾸는 대조로 검증한다.
3. **정보·행동 표현의 더 넓은 비교에는 명제 대응표를 만든다.** 한 안내 문장 비교를 여러 문구에서 확인하고, 본문을 다시 쓰는 실험에서는 사실·조건·실패 결과를 같은 수준으로 담았는지 검사한다. 체크리스트 형식·조건 경고·입력 역할은 별도 요인으로 둔다.
4. **성공률 개선과 효율 개선을 별도로 설계한다.** 예산별 성공을 보려면 다음 실행에서 고정한 시점·예산의 중간 패치를 미리 수집하고 나중에 채점한다. 이번 최종 패치만으로 더 일찍 해결했는지 추정하지 않는다. 표본 수는 의미 있는 최소 차이와 과제·출처 변동에 맞춰 [확인 실험안](../ai-memory-next-validation-plan.md)에서 다시 정한다.

[전체 자료 안내](data/new-content-transfer-20261105/README.md)에 원본 위치·재분석 명령·실패한 준비와 보조 집계 기록을 연결했다. 이 회차는 측정 가능성과 사례 해석을 확인한 작은 탐색으로 보존한다.
