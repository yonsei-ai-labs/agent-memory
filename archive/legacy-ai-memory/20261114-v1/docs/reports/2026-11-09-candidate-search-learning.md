# 후보 검색을 학습하면 적은 후보로 필요한 기억을 더 찾는가

2026-11-09 완료. [학습 전 고정한 계획](../ai-memory-candidate-search-training-2026-11-09.md), [저장 예측·검산·재현](../../evaluation/results/travel-candidate-search-20261109-v1/README.md), [입력 계약](../../datasets/travel_candidate_search/20261109-v1/README.md).

## 판단

이번 자료에서는 **검색용 LoRA를 학습한 32개 후보가 기존 검색의 64개 후보보다 필요한 기억을 더 많이 전달했다.** 이전 관계 판독기는 그대로 고정했다. 후보 수를 무조건 늘리지 않고 검색 표현을 학습하는 경로를 더 확인할 근거가 생겼다.

다만 같은 8개 test 기본 계획을 다시 사용한 한 seed의 탐색 실험이다. 공개 참조 이력의 명시적 사람·날짜·항목 연결을 찾는 과제이며, 주석 규칙으로 푸는 방법은 이 과제에서 거의 완전하다. **실제 에이전트의 성공·비용 개선이나 학습 선택기의 필요성을 입증한 결과는 아니다.**

## 주 비교

Harrier 0.6B 원래 가중치에서 검색용 LoRA만 새로 학습했다. BM25와 임베딩의 RRF 결합은 같고, 모든 조건에 이전 LoRA+MLP 판독기를 적용했다. 최종 전달 한도는 10기록이다. 표의 Recall은 질문마다 필요한 정답 기록 중 찾은 비율을 계산해 평균한 값이며 작업 성공률이 아니다.

| 방법 | 판독 후보 한도 | 후보 안의 정답 Recall | 최종 Recall@10 | 정답을 전부 찾은 질문 | 처리 시간 중앙값 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A. 기존 검색 | 32 | 68.68% | 68.57% | 96/219 | 284.8 ms |
| B. 기존 검색, 후보 확대 | 64 | 87.48% | 86.87% | 144/219 | 439.4 ms |
| C. 검색 LoRA 추가 | 32 | 92.54% | **92.00%** | **166/219** | **283.4 ms** |

질문 평균에서 C−A는 +23.43%p, C−B는 +5.13%p다. 기본 계획마다 동일 가중치를 주면 A/B/C Recall@10은 65.27/84.96/90.53%다. C는 A보다 8개 계획 모두에서 높았고, B보다 6개에서 높고 2개에서 같았다. 계획 단위 2,000회 재표집한 C−B 차이는 평균 +5.58%p, 탐색적 95% 구간 +1.85~+9.12%p였다. 이미 관찰한 8개 계획의 재표집이므로 확증적 유의성 주장에 쓰지 않는다.

**질문별 퇴행은 남았다.** C−A는 정답 기록 수가 114질문에서 늘고 4질문에서 줄었으며 101질문은 같았다. C−B는 44질문에서 늘고 22질문에서 줄었으며 153질문은 같았다. 평균 개선이 모든 상황의 개선을 뜻하지 않는다.

## 별도로 고정한 보조 비교

| 후보 생성 | 판독 후보 한도 | 최종 Recall@10 | 정답을 전부 찾은 질문 |
| --- | ---: | ---: | ---: |
| D. 고정 임베딩 단독 | 32 | 69.92% | 92/219 |
| E. 학습 임베딩 단독 | 32 | **96.96%** | **191/219** |

E는 C보다 높았다. 이 자료에서는 학습 임베딩에 BM25 순위를 같은 비중으로 섞는 것이 일부 정답을 후보 밖으로 밀어냈다. dev에서도 같은 방향(C 94.07%, E 98.15%)이었지만, 이번 checkpoint 선택 기준과 주 비교는 사전에 정한 learned-hybrid Recall@32를 유지했다. E를 test에서 고른 새로운 주 방법으로 바꾸지 않았다. D/E의 온라인 시간은 이번 회차에 측정하지 않았다.

최종 판독기를 생략하고 검색 순위에서 바로 10개를 고른 사후 진단은 기존 hybrid 35.55%, 학습 hybrid 63.16%, 학습 dense 82.04%였다. 학습한 검색과 고정 관계 판독기의 역할이 모두 남아 있다. 이 진단은 새로운 GPU 실험이 아니라 저장 순위의 집계다.

## 어디에서 개선됐고 무엇이 남았는가

test의 정답 연결 768개를 합산하면 다음과 같다. 이 합산 Recall은 위의 질문별 평균 Recall과 분모가 다르다.

| 방법 | 후보에 들어온 정답 | 최종 전달한 정답 | 첫 검색에서 누락 | 후보에는 있었으나 최종 10개에서 제외 |
| --- | ---: | ---: | ---: | ---: |
| A. 기존 32 | 470 | 468 | 298 | 2 |
| B. 기존 64 | 643 | 633 | 125 | 10 |
| C. 학습 hybrid 32 | 675 | 667 | 93 | 8 |
| E. 학습 dense 32 | 734 | 722 | 34 | 12 |

주 개선은 첫 검색 누락 감소다. 후단 제외는 판독 순위와 10기록 한도의 영향을 함께 포함하므로 전부 판독 오류로 부르지 않는다. 정답이 12개인 질문도 있어 한도 자체로 완전 검색이 불가능한 경우가 있다.

은행이 100기록보다 큰 119질문에서 정답을 모두 전달한 수는 A/B/C가 18/46/69개였다. 단일 참조 28질문에서는 27/28/28개였다. 어려운 큰 은행·복수 참조에서 더 많은 차이가 나타났다. 조건들은 서로 겹치며 독립 표본으로 더하지 않는다.

실제 사례는 [error-cases.json](../../evaluation/results/travel-candidate-search-20261109-v1/error-cases.json)에 질문·정답 원문·후보 순위·판독 확률과 함께 보존했다. 각 유형에서 query_id 순 첫 사례를 고른 사후 설명이다.

- **검색 개선:** `travel-bank-10-turn-3`은 여러 사람의 식사·숙소를 연결해야 한다. Walter의 4일차 숙소가 기존 검색 54위라 32개 후보에서 빠졌지만, 학습 hybrid에서는 32위로 들어와 판독 후 3위가 됐다. 최종 정답은 4/5→5/5였다.
- **검색 퇴행:** `travel-bank-112-turn-5`의 Paul 3일차 저녁은 기존 후보 31위였으나 학습 hybrid에서는 35위로 밀려 빠졌다. 학습 dense 단독에서는 14위였다. 학습과 순위 결합을 함께 살펴볼 이유다.
- **후보 내 판독 실패:** `travel-bank-223-turn-2`의 Paul 1일차 저녁은 학습 후보 6위로 확보했지만, 판독 후 11위라 전달하지 못했다. 정답이 7개인 질문이므로 10개 한도로 불가피한 누락은 아니다. 후보를 찾는 것과 최종 선택이 별개임을 보여준다.

최종 10개를 항상 채워 보내므로 C는 2,190개 전달 중 canonical 정답 667개, 정밀도 30.46%다. 나머지를 곧바로 해로운 기억이라고 부를 수는 없다. 정답 주석이 모든 유용한 대체 근거를 포괄하지 않으며 실제 작업 효과도 측정하지 않았다. 보류·전달 개수·토큰 예산은 후속 평가 대상이다.

## 학습·검산

- 데이터: 같은 기본 계획 45개, train/dev/test 30/7/8. 질문 813/189/219. 새로운 독립 경험은 추가하지 않았다.
- 검색 LoRA: q/v rank 8, alpha 16, 학습 파라미터 1,146,880개. 모든 정답과 같은 은행의 어려운/무작위 음성을 함께 사용하는 다중 정답 순위 손실. 2epoch, 1,626 optimizer 업데이트, train 813질문 모두 정확히 두 번 노출.
- 선택: dev 계획별 hybrid Recall@32 92.42%→92.84%, epoch 2 선택. test 정답은 업로드하지 않았고 정답 제거 변형도 학습에 포함하지 않았다. 이전 판독기의 adapter·head는 실제 이전 results.zip과 바이트 일치하며 이번 optimizer에서 제외했다.
- 별도 CPU 계산: 두 dev epoch와 test의 검색 597질문, 고정 판독 확률 26,631개 검산. cosine 오차 0, head 확률 최대 오차 1.20×10⁻⁷ 미만. 검색 LoRA 112개 tensor 모두 변화했고 optimizer·노출 수가 일치했다. 같은 에이전트의 별도 계산이며 독립 사람 검토는 아니다. 전체 encoder forward를 CPU에서 다시 실행한 것은 아니다.
- 최초 CPU 검산은 Python 3.13과 3.11의 평균 계산 차이 1.11×10⁻¹⁶ 때문에 엄격한 float 동등 비교에서 실패했다. 검산만 절대 오차 10⁻¹² 허용으로 고쳤다. 라벨·예측·가중치는 수정하지 않았다. 실질적 점수 변경·개수 변경·NaN을 거부하는 검사도 추가했다.
- 이전 A와 비교해 219질문 모두 전달한 canonical 정답 집합이 같았다. 전체 10개 집합은 212질문에서 같고 7질문에서는 비정답 기록의 선택이 바뀌었다. 공통 9,378쌍의 확률 차이 중앙값은 약 5.22×10⁻⁷이지만, 61쌍은 0.01을 넘고 최대는 **0.1891**이었다. 따라서 전체 차이를 사소한 반올림이라고 설명할 수 없다. 모델·환경은 같고 배치 구성은 달랐지만, 이 검산만으로 원인을 확정하지 않았다. 이번 조건들은 같은 합집합에서 계산한 점수를 공유하므로 조건 간 비교에는 동일 점수를 썼다. 이전 확률 임계값을 그대로 재사용하거나 신뢰도가 안정적이라고 주장해서는 안 된다.

관련 로컬 검사 65개 통과. 원본 upload.zip/results.zip과 중간 회복 파일을 보존했고, 공유 예측 파일은 원본 바이트와 SHA256으로 검증했다. 새 clone의 공개 원본 재생성·공유 지표 재계산 결과는 결과 폴더의 `fresh-clone-check.json`에 기록한다.

## 자원과 시간 해석

A100 40GB 한 세션을 사용했다. 컨트롤러 전체 1,113.6초(약 18.6분), 실험 스크립트 895.8초, 검색 학습·dev·저장 구간 641.5초였다. 당시 관측 사용률은 6.73 Colab unit/시간이며 정확한 청구량을 측정한 것은 아니다. 로컬 GPU·유료 모델 API는 사용하지 않았다. 결과 회수 후 종료했고 서버에서도 활성 세션이 없음을 확인했다.

온라인 시간은 미리 인덱스를 만들고 모델을 올린 상태의 dev 21질문을 각 방법 한 번씩 측정한 값이다. 질문 인코딩·검색·후보 판독을 포함하고 모델 로딩·인덱스 구축·네트워크·작업자 생성은 제외했다. C의 중앙값은 B보다 약 35.5% 낮지만, 충분한 반복을 거친 서비스 지연 비교는 아니다.

배치 품질 평가와 단건 시간 측정의 선택도 비교했다. 63실행 중 6개는 최종 집합이 달랐고, 그중 1개(C의 dev 질문)는 찾은 정답 수가 5/7→6/7로 바뀌었다. 실행 구성에 따른 선택 차이를 보존했으며, 단건 실행 품질이 표의 test 평가와 완전히 동일하다고 가정하지 않는다.

## 다음 판단

이번 회차는 **관계를 읽는 판독기와 필요한 후보를 찾는 검색기를 함께 고려해야 한다**는 방향을 지지한다. 같은 작은 test에서 학습 설정을 계속 조정하기보다, 실제 생성한 과거 기록과 새로운 기본 계획에서 고정한 방법을 비교하는 것이 다음 확인이다. 여러 seed, 바꿔쓴 관계 표현, 정답이 없는 상태, 기억 토큰 예산을 포함해야 한다. 그다음 같은 작업자에게 무기억·전체 기억·검색·규칙·학습 검색을 제공해 성공·손해·비용의 차이를 측정해야 처음의 ‘메모리의 득과 실’과 연결된다.
