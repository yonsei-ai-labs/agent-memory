# MemoryArena 사용 가능성 점검

작성일: 2026-11-08. 상태: **후보 벤치마크의 실행 전 검토**. 채택·모델 학습·실제 기억 효용 실험은 아직 하지 않았다.

**MemoryArena를 활용할 수 있는 기반은 있다. 다만 확인한 공개 preview 코드를 그대로 우리 연구의 득실 측정기로 쓰는 것은 권하지 않는다.** 여행 계획 과제가 첫 후보지만, 기억을 주지 않는 조건과 채점의 보완, 학습·평가 분리가 먼저다. 이 판단은 논문의 이름이나 설명만이 아니라 공개 데이터 검산, 실행 경로 확인, 원래 함수에 대한 오프라인 재현에 근거한다.

## 우리 질문과 연결되는 부분

MemoryArena는 이전 행동과 정보를 다음 과제에 활용하는 연속 과제를 제공한다. 사람·일정·제품·검색 결과의 관계를 파악해 필요한 과거 정보를 선택하는 데 사용할 수 있다. [공식 프로젝트](https://memoryarena.github.io/)

여행 과제에서는 앞선 여행자의 계획을 다음 사람이 참조하거나 일부 조건을 바꾼다. 첫 공개 묶음에서 확인한 예는, 앞선 사람의 식당 변경을 기억하고 다음 사람의 숙소 요청에서는 정확한 사람과 날짜를 구분해야 하는 경우다. 따라서 다음 연결을 시험하기 좋다.

> 현재 요구와 과거 정보의 관계를 배운 작은 모델이, 필요한 기억을 선택하고 부적절한 적용을 줄여 실제 계획의 성공률·비용을 개선하는가?

다만 이는 **연속 작업에서의 사실·상태 기억 선택**에 특히 가깝다. 코드 문제에서 얻은 수정 원리를 별개의 새 문제에 재사용하는 능력까지 자동으로 검증하지는 않는다. 원래의 넓은 득실 질문에는 연결되지만, 연구 대상 기억의 종류는 명시해야 한다.

또한 기억이 필요하도록 설계된 벤치라고 해서 선택기의 가치까지 보장되지는 않는다. 이전 기록을 모두 주는 방법이나 단순 검색이 이미 충분할 수 있다. 같은 과거 기록에 대해 사람·날짜·현재 요구를 구별해야 하는 사례와 실제 제공 결과의 차이가 있는지 먼저 확인한다. 손해 사례를 만들기 위해 거짓 기억만 인위적으로 넣는 방식은 주 평가로 삼지 않는다.

다섯 파일의 총 크기는 약 12.3 MB다. 다운로드·해시·ID 중복·질문과 답의 개수 일치를 확인했다. 실행에 필요한 추가 DB 크기는 포함하지 않는다. [파일별 검산](design-data/memoryarena-feasibility-20261108/data-inventory.json)

여행의 `base_person` 전체 객체가 정확히 같은 경우를 묶으면 263개다. 그러나 **학습 준비 중 이름과 질문 표현을 제외하고 `daily_plans`만 비교하니 서로 다른 기본 계획은 45개이며, 각각 6개 행에서 반복된다.** 270개 행이나 263개 객체를 독립 여행으로 취급할 수 없다. 분할은 최소한 이 45개 기본 계획을 단위로 고정해야 하며, 유사한 계획 템플릿까지 독립적인지는 별도 검토가 필요하다. [구조 검사 결과](design-data/memoryarena-feasibility-20261108/offline-checks.json)

모든 구성은 공식적으로 `test`만 제공한다. 공개 파일에 질문·정답이 있다고 해서 관계 라벨이나 제공/보류 효과 라벨, 학습용 에이전트 실행 기록이 이미 있는 것은 아니다. 정답 계획을 에이전트가 실제로 얻은 과거 경험으로 바꿔 넣어서는 안 된다. [고정된 데이터 카드](https://huggingface.co/datasets/ZexueHe/memoryarena/blob/da1a37c8b19280e18627ca01cf368195a5e1d92e/README.md)

실행 자원은 다음처럼 구분한다.

- 여행의 도구는 로컬 표를 읽는다. 작업 LLM을 API로 호출하는 구성에서는 로컬 대형 GPU가 필수인 구조가 아니다. 다만 전체 환경 실행은 이번에 검증하지 않았다. 비행 CSV는 clone에 없고, 안내된 별도 Drive 링크의 파일 다운로드도 아직 확인하지 못했다. [여행 설치 안내](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/setup_travel.md)
- 쇼핑 제품 DB의 공개 파일 목록은 약 13.5 GB이며, 기본 경로의 `items_shuffle.json`만 약 5.48 GB다. 전체 목록에는 대체 색인과 중복 표현도 있어 13.5 GB를 최소 필요 용량으로 단정하지 않는다. JDK·검색 환경도 필요하다. 기본 속성 채점에는 LLM 호출이 있고 문자열 비교 옵션은 다른 측정 방식이다. [고정 DB 목록](https://huggingface.co/datasets/ai-hyz/MemoryArena-product-db/tree/46120a5c931d04a47bd791965d757207b7372b62), [쇼핑 설치 안내](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/setup_web_shopping.md)
- 검색은 별도 BrowseComp-Plus 코퍼스와 색인을 요구한다. 수학·물리는 작업 모델 외 채점 모델 설정도 있다. 이번에는 문서·코드 경로 검토까지만 했고 모두 실행 가능하다고 확인한 것은 아니다. [검색 환경 안내](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/setup_web_search_env.md), [추론 환경 안내](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/setup_formal_reasoning.md)

## 실제 코드에서 확인한 세 가지 조건

### 1. `none`은 우리가 정의하려는 무기억 조건이 아니다

여행 runner는 메모리 서버가 없으면 `include_previous_plans=True`로 이전 계획과 질문을 다시 전달한다. 첫 여행자의 기본 계획도 전달한다. 즉 `memory_system="none"`은 **외부 메모리 시스템을 사용하지 않는 조건**이며, 이전 기록을 보류한 조건이 아니다. 이 동작 자체를 버그로 부르는 것은 부적절하지만, 우리 실험의 무기억 기준선으로 이름만 보고 사용할 수는 없다. [runner](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/run_travel.py#L272)

실제 agent 메서드와 가짜 모델 응답을 사용해, 해당 플래그가 켜진 프롬프트에는 이전 계획 표시가 포함되고 끄면 빠지는 것을 재현했다. 선택한 기억만 별도로 주입되는 것도 확인했다. 이는 프롬프트 구성 검사이며 HTTP 서버·실제 도구·작업 모델까지 검증한 것은 아니다. [agent](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/agent/travel_planner.py#L172)

우리는 공통의 현재 요청과 제공된 기본 배경을 유지하고, 그 뒤 발생한 과거 실행 기록의 제공 여부만 바꿔야 한다. 기본 계획까지 보류하려면 별도 실험으로 정의한다. 제공되는 정보 집합과 프롬프트의 우회 경로를 함께 기록한다.

### 2. 공개 여행 채점기에 득실 측정을 왜곡할 수 있는 동작이 있다

첫 여행 묶음 1개, 8명의 정답을 이용해 원래 채점 함수를 실행했다. 이것은 채점기의 입력을 의도적으로 변형한 진단이며 모델 성능 실험이 아니다.

| 채점기 입력 | 실제로 확인한 출력 |
| --- | --- |
| 8명 모두 원래 정답 | 사람 통과율·그룹 성공률 100% — 정상 대조 |
| 채점되는 각 문자열을 첫 글자만 남김 | 사람 통과율·그룹 성공률 100% |
| 현재 도시만 모두 잘못된 값으로 변경 | 사후 채점 100%, 환경 내부 판정은 0/8 통과 |
| 8명 중 첫 1명만 정답 제출 | 분모가 1명으로 줄어 사람 통과율·그룹 성공률 100% |
| 원래 묶음과 그 복제본 2개를 기대하지만 원래 묶음만 제출 | 분모가 1묶음으로 줄어 성공률 100%; 복제본은 합성 진단용 |
| 아무도 제출하지 않음 | 0%; 빈 제출에 대한 정상 대조 |

문자열 비교가 두 값을 짧은 쪽 길이로 자른 뒤 유사도를 계산하기 때문에 앞부분만 남겨도 일치할 수 있다. 사후 채점은 `current_city`를 제외하고, 제출에 등장한 묶음·사람만 분모로 삼는다. [공개 사후 채점기](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/env/env_systems/travel_planner_env/eval.py), [환경 내부 판정](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/env/env_systems/travel_env.py)

이를 근거로 논문의 기존 점수가 잘못됐다고 단정하지 않는다. 실제 출력에서 얼마나 발생했는지는 조사하지 않았다. 다만 **현재 고정한 공개 코드로 우리 득실 라벨을 바로 생산하는 것은 피해야 한다.** 예상 제출 목록을 고정하고 누락을 실패/실행 실패로 구분하며, 필드 기준과 환경·사후 판정을 일치시켜야 한다. 개체·일정의 유효성과 요청 조건을 검사하고, 단순 완전 문자열 일치가 유효한 대안 계획까지 탈락시키지 않는지도 표본 검토한다. 수정 지표는 공식 원판 점수와 구분해 명명한다.

### 3. 입력 경계와 피드백 모드를 고정해야 한다

환경의 `reset()` 반환에는 전체 `questions`와 `answers`가 들어 있다. 공식 runner는 여기서 현재 질문을 골라 agent에 전달하므로, 이 사실만으로 기본 실행의 정답 유출이라고 판단하지 않는다. 하지만 새 선택기에 환경 객체 전체를 넘기면 미래 질문·정답이 섞일 수 있으므로 허용 필드만 내보내야 한다. [환경 reset](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/env/env_systems/travel_env.py#L117)

설정 파일 경로의 기본 판단 모드는 `none`이지만, 설정 파일 없이 사용하는 CLI 기본값은 `hint`다. `hint`와 `answer`는 정답 기반 피드백을 제공하며 이후 기억에 들어갈 수 있다. 우리의 첫 실험은 `judgement_mode=none`을 명시하고 실제 관측·도구 결과·에이전트 출력만 기억으로 만든다. 정답 기반 피드백의 이득은 필요하면 별도 조건으로 다룬다. [runner 설정](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/run_travel.py#L108)

## 선택기를 붙이는 방법과 측정 단위

기억 클라이언트는 `add(chunk)`로 경험을 저장하고 `wrap_user_prompt(question)`로 기억을 넣은 프롬프트를 받는다. 여기에 후보 생성과 선택을 넣거나 같은 인터페이스의 얇은 로컬 어댑터를 둘 수 있다. 아직 우리 모델을 연결한 것은 아니다. [공개 인터페이스](https://github.com/ZexueHe/MemoryArena/blob/6cd9de14b71915e39ac742a20dc33785e14b6aab/memory/client.py)

1. 고정한 작업자가 과거 단계를 수행한 기록을 저장한다. 현재 판단 이전의 기록만으로 후보 기억을 만든다. 후보의 문구·분할·출처·작성 비용도 고정한다.
2. 현재 질문, 공통 배경, 그 시점에 알려진 조건, 후보 기억을 선택기에 준다. 사람·날짜·대상·변경 조건의 관계 주석과 실제 이득 라벨은 별도로 유지한다.
3. 동일한 과거 기록과 현재 상태에서 기억 제공/보류로 분기한다. 작업자와 예산을 고정하며, 시드가 가능한 경우 짝지어 비교하고 확률적 변동은 반복으로 점검한다. 정책마다 다른 과거 기록에서 출발한 실행을 개별 기억의 효과로 해석하지 않는다.
4. 관계 판독 점수, 이득·손해 예측, 선택 정책의 실제 성공률·비용을 같은 사례 ID로 연결한다. `개선 / 악화 / 둘 다 성공 / 둘 다 실패`, 미제출·실행 실패, 토큰·시간·선택기 비용을 구분한다.

첫 기준선은 **과거 실행 기록 보류 / 이전 기록 전체 제공 / 단순 검색 / 학습한 선택기**가 적절하다. 검색과 선택기는 같은 후보와 토큰 한도를 사용하고 빈 선택을 허용한다. 전체 기록은 실제 길이와 비용을 함께 보고한다. 다음 단계에서만 자유롭게 상태가 달라지는 전체 연속 실행의 정책 효과를 별도로 평가한다.

벤치가 주는 완료 계획의 정답은 작업 성과의 참고 답이다. 이것을 '어느 기억을 주면 이득인가'라는 정답으로 대신 쓰지는 않는다. 우리의 기여 후보는 이 연결을 실제 실행으로 확보하고, 관계 감독이 추가로 도움이 되는지 검증하는 데 있다.

## 학습 자료와 평가 자료를 어떻게 나눌 것인가

권장 경로는 새로 만든 검증 가능한 여행 상황이나 별도 경험으로 학습하고, MemoryArena는 보지 않은 평가용으로 남기는 것이다. 공개 test를 일부 학습에 사용한다면 **MemoryArena에서 파생한 자체 분할 실험**이라고 명시하고, 원래 전체 test 성적과 같은 조건의 결과로 주장하지 않는다. 이번에 내용까지 확인한 여행 `id=1`, 쇼핑 `id=0`은 탐색·개발용으로 표시한다.

어느 경로든 같은 여행·배경·파생 조건·표현 증강은 한 분할에 둔다. 하위 과제 행을 무작위로 나누지 않는다. 유사한 여행 배경·제약 템플릿의 중복도 먼저 확인한다. 관계 주석을 여러 개 만들 수 있어도 독립 경험이 늘어난 것은 아니다. 현재 묶음 수만으로 LoRA 학습이나 넓은 일반화에 충분하다고 판단할 수 없다.

## 다음 단계의 채택 조건

회의에서 방향을 결정하기 전에는 **여행 과제를 조건부 후보로 유지**한다. 바로 전체 학습을 옮길 단계는 아니다.

- 실행 준비: 비행 DB·최소 의존성을 확보하고, 가짜 응답으로 전체 도구/저장 경로를 확인한다. 이번 검사는 그 단계까지 완료한 것은 아니다.
- 측정 준비: 입력 경계, 실제 보류 조건, 분모와 필드가 일관된 채점을 먼저 검증한다. 원판/수정 프로토콜의 차이를 기록한다.
- 소수의 개발 묶음에서 실제 실행: 필요한 과거 정보의 회수가 가능한지, 전체 제공과 검색에 비해 선택 여지가 있는지, 제공/보류 결과에 변화가 있는지 확인한다. 이 단계는 수집·측정 가능성 확인이며 일반화 주장용이 아니다. 효과가 큰 묶음만 골라 최종 평가에 넣지 않는다.
- 그 확인을 통과하면 독립 자료 확대와 학습을 설계한다. 검색과 전체 제공이 이미 충분하면 그 결과를 받아들이고, 선택기가 불필요한 시나리오에서 억지로 학습 목표를 만들지 않는다.

현재의 제안은 SWE를 당장 폐기하는 것이 아니라, **사실·상태 기억의 득실을 시험할 비개발 분야를 추가할 수 있는지 검증하는 것**이다. 다른 벤치로 이동하는 것만으로 학습 데이터 부족이나 효과 라벨의 부재가 해결되지는 않는다.

## 이번 작업의 범위와 재현

공개 코드 clone, 약 12.3 MB의 고정 데이터 다운로드, 5개 데이터 구조 검사, 채점 진단 6개, 가짜 모델을 쓴 프롬프트 진단 3개를 수행했다. 실제 작업 모델·임베딩·LLM 채점 호출, GPU 할당, 모델 학습은 모두 0회다. 새 효용 라벨도 0개다. 기존 데이터·실험 출력은 변경하지 않았다.

[검토 묶음과 재현 명령](design-data/memoryarena-feasibility-20261108/README.md)에 사전 범위, 해시, 원래 함수를 사용하는 검사 코드, 결과와 추가 자산 목록을 저장했다. 원본 외부 코드·벤치 정답은 공유 커밋에 넣지 않는다.
