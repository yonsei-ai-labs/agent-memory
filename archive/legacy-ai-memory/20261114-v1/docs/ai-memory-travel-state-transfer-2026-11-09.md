# 새 문제군에서 관계 검색과 기억 득실을 연결하는 파일럿

2026-11-09. 아래 설정은 새 worker 실행 전에 고정한다. 첫 실행은 학습 분할의 12개 문제군만 사용한다.

## 질문과 범위

이전 검색 LoRA와 관계 판독기를 그대로 고정했을 때, 새 문제군에서 필요한 기록을 찾고 실제 작업자의 선택도 개선하는가? 같은 과거 기록이라도 현재 관측·가용성·근거 유무에 따라 제공 효과가 달라지는가? 최종적으로는 관계 점수와 별도의 제공/보류 판단을 연결한다.

MemoryArena에서 사용했던 기본 계획 45개는 TravelPlanner train 45개와 요청이 겹친다. 이번에는 공개 TravelPlanner validation 180행에서 기존 요청 및 출발지·목적지·기간 조합과 겹치는 행을 제외한다. 해당 자료에는 완성된 과거 계획이 없으므로, 고정 worker가 실제 카탈로그를 보고 과거 선택을 생성한다. 정답 계획을 실행 기록으로 바꾸어 쓰거나 실패한 선택을 정답으로 대체하지 않는다.

이 실험은 **공개 여행 자료에 근거한 통제된 예약 선택 과제**다. 원래 전체 여행 요청의 모든 조건을 풀거나 공식 TravelPlanner/MemoryArena 점수를 산출하지 않는다. 새 경로·기간 문제군을 사용하지만 도시·카탈로그·문장 틀은 공유한다. 다른 도메인이나 독립 출처 일반화와 구분한다.

## 데이터 고정

- 공개 데이터 revision: `8736504ecfc31b7f8b7e40122873c337e83fff7c`.
- 선택 전 적격 문제군 173개에서 기간 3/5/7일별 40개씩 총 120개를 고른다. 난이도 표시는 원래 요청의 메타데이터이며 새 과제 난이도를 뜻하지 않는다.
- 출발지·목적지·기간을 묶어 train/dev/test 60/20/40으로 고정한다. 날짜나 표현이 다른 같은 묶음을 다른 분할로 보내지 않는다.
- 첫 12개는 train에서 기간별 4개씩 미리 지정한다. **12개를 보고 효과가 좋은 문제만 남기지 않는다.** dev/test의 실제 과거 기록과 worker 결과는 아직 생성하지 않는다.
- 문제군마다 실제 카탈로그의 식당 12개·숙소 8개, 과거 여행자 3명, 각 날짜의 점심·저녁·숙소를 사용한다. 숫자가 없거나 유효하지 않은 숙소 33행은 제외하고 제외 사유를 남긴다. 빈 속성을 요구 조건으로 사용하지 않는다.
- 과거 선택은 속성·평점·가격 조건을 만족하는 가장 저렴한 항목을 고르는 실제 모델 출력이다. 유효한 메뉴 선택 여부와 원래 조건 만족 여부를 별도로 평가한다. 틀린 선택도 해당 인물이 실제로 고른 역사적 기록으로 보존한다.
- 현재 요청은 서로 다른 두 사람의 저녁/숙소를 참조하며, 동일 선택 재사용과 과거 가격을 기준으로 한 비교의 두 유형이다. 문제군의 모든 과거 기록 27–63개를 검색한다. 정답 후보를 최종 목록에 강제로 삽입하지 않는다.

데이터 명세·전체 분할·원본 해시는 [공유 데이터](../datasets/travel_state_transfer/20261109-v1/README.md)에 보존한다. 기존 고정 자료와 실행 산출물은 변경하지 않는다.

## 같은 경험에 대한 네 현재 상태

| 상태 | 모든 정책이 공통으로 보는 정보 | 검증할 점 |
| --- | --- | --- |
| needed | 현재 카탈로그, 질문; 과거 선택은 기억 은행에만 있음 | 관련 기억을 찾아 전달하면 선택이 개선되는가 |
| visible | 위 정보와 필요한 두 과거 기록을 현재 도구 관측으로 제공 | 중복 기억의 이득·손해·추가 비용 |
| changed | 필요한 과거 선택의 현재 가용성을 false로 변경 | 역사적으로 맞는 경험과 현재 적용 조건을 함께 다루는가 |
| missing | 필요한 두 참조 기록을 공통 기억 은행에서 제거 | 비슷한 다른 기록을 잘못 적용하지 않고 UNKNOWN을 반환하는가 |

changed에서는 참조 항목만 유일하게 unavailable이 되어 답을 드러내지 않도록 식당 2개·숙소 1개도 결과와 무관한 해시 순서로 추가 변경한다. 과거 기록의 사실은 바꾸지 않는다. 이것은 실제 자연 발생 변화라는 주장이 아닌 명시적인 통제 개입이다. missing은 충분한 근거로 불가능함을 아는 `NONE`과 근거가 부족한 `UNKNOWN`을 구분한다. 네 상태를 같은 비율로 만든 것은 자연 발생 빈도 추정이 아니다.

## 정책과 실행

1. none: 기억을 전달하지 않음.
2. all: 해당 문제군의 사용 가능한 과거 기록 전체를 전달. 별도 토큰 비용 상한의 참고 기준.
3. fixed: 기존 임베딩+BM25 RRF → 후보 32개 → 기존 관계 판독기 → 최대 4기록/512토큰.
4. learned: 기존 검색 LoRA+BM25 RRF → 후보 32개 → **동일한** 관계 판독기 → 최대 4기록/512토큰.
5. rule: 질문에서 사람·날짜·항목을 읽어 참조 기록만 제공하는 명시적 규칙.
6. state_rule: rule에서 현재 관측에 이미 있는 기록은 보류.

Harrier 0.6B의 검색 LoRA와 판독 LoRA/MLP는 이전 실행의 실제 가중치로 고정한다. 새 데이터로 재학습하거나 결과를 보고 임계값을 바꾸지 않는다. 과거·현재 worker는 동일한 pinned Qwen3.5-9B, greedy, thinking off다. 모델 revision과 실제 가중치 SHA를 저장한다. 라이브러리 이동 점검은 이전 dev의 동일한 첫 배치 3개에서 확률 오차 ≤0.01 및 이진 분류 일치로 사전에 고정한다. 실패하면 본 수집을 중단한다.

첫 파일럿은 36번의 과거 생성(총 540개 기록 항목), 24개 현재 요청 × 4상태 × 6정책 = 576개 정책 결정이다. 동일한 입력 메시지는 동일 greedy 출력을 재사용하고 실제 고유 호출 수를 기록한다. 미리 정한 2개 입력은 재실행하여 출력 토큰 일치를 확인한다. 정책 행 수를 독립 실행 표본 수로 세지 않는다. 기억 순서는 ID 순으로 고정한다. 입력·기억을 조용히 잘라내지 않는다.

## 평가와 후속 학습

주 지표는 두 현재 선택의 동시 정답이다. 필요한 참조가 공통 기억 은행/현재 관측에도 없으면 `UNKNOWN`이 정답이다. 은행에는 있으나 선택기가 전달하지 않은 경우 `UNKNOWN`은 작업 미해결로 센다. **기억 없이 우연히 맞힌 구체적 답도 주 성공률에서는 정답으로 센다.** 실제 전달받은 근거에 기반한 정답은 별도 `grounded_success`로 기록한다.

여기서 `grounded_success`는 필요한 참조를 전달받았는지 확인하는 운영상 지표다. 모델이 실제로 그 기억을 사용한 추론 과정을 증명하지 않는다. `needed`라는 상태 이름도 “과거 선택이 현재 관측에는 없음”이라는 배치를 뜻하며, 모든 개별 선택에서 기억의 논리적 필수성이 증명됐다는 뜻은 아니다. 실제 득실은 제공/보류 실행 차이로 판단한다.

상태별로 무기억 대비 개선·악화·둘 다 성공·둘 다 실패를 나누고, 최종 두 참조의 전달율과 성공 변화의 연결도 확인한다. 이미 보이는 정보의 중복 비용, 현재 가용성 위반, 없는 기록의 잘못된 적용을 별도로 분석한다. 관계 점수를 득실 확률로 해석하지 않는다.

같은 현재 입력과 learned 제안 묶음을 읽는 frozen 특징, 현재만 읽는 특징을 결과 없이 GPU에서 저장한다. 결과를 로컬에서 판정한 뒤 **제공/보류 효용 판독층** 학습에 사용할 수 있다. 첫 12문제군에서 학습할 경우 문제군 단위 제외 검증만 하고 탐색 결과로 표시한다. 미래 test는 학습과 설정 선택에 쓰지 않는다. 충분한 개선/악화 변이가 없다면 복잡한 head를 추가해 점수를 만드는 대신 데이터 부족을 보고한다. 목표는 개별 기억의 기여가 아니라 이 단계에서는 **선택된 묶음의 제공 효과**다.

**파일럿 head 설정(현재 worker 결과 확인 전 고정):** 네 득실 범주에 대한 선형 softmax 판독층을 CPU에서 학습한다. 비교는 현재+제안 묶음, 현재만, 학습 라벨을 섞은 대조의 세 가지다. frozen 1024차원 특징을 train 평균으로 중심화하고 train의 전체 RMS로만 조정한다. L2=0.01, LBFGS 최대 200회, seed 731. 같은 입력 문장은 배치 패딩에 따른 수치 차이가 상태 단서가 되지 않도록 첫 저장 특징 하나로 통일하며 원래 차이를 기록한다. `p(개선)−p(악화)>0.05`일 때만 제공하는 설정을 고정한다. 이 수치는 보정된 인과효과 확률이라는 주장이 아니다. 12개 문제군을 하나씩 통째로 제외해 11개로 학습하고 남은 1개를 예측한다. 성공·제공 비율·놓친 개선·일으킨 악화·추가 기억 토큰을 항상 제공/항상 보류와 비교한다. 악화 사례가 없으면 악화 방지 학습이 확인됐다고 해석하지 않는다. 이 작은 탐색에서 복잡한 구조·임계값 탐색은 하지 않는다.

판정 코드와 생성 코드를 분리한다. 원시 출력에서 기록·선택·현재 메시지·지표를 재계산하고, 별도 계산으로 정답 집합을 대조한다. 주요 입력/출력 토큰·실제 호출 수·warm 생성 시간을 보존한다. 검색 특징을 캐시한 이번 수집의 시간은 완전한 온라인 선택 서비스 지연이 아니다. 추후 정책 배포 비교에서는 특징 계산과 선택기 비용을 포함해야 한다.

## 종료 조건과 다음 경계

Colab 전용 A100, 스크립트 3,600초·컨트롤러 3,900초 상한. 로컬 GPU를 사용하지 않는다. 중간 산출물을 회수하고 성공·실패 모두 이번에 할당한 세션만 종료한다.

**실행 전 운영 변경:** 첫 A100 요청과 한 번의 재시도 모두 180초 내에 할당되지 않았다. 새 worker 출력은 생성되지 않았다. L4를 대체 장치로 허용하고, 같은 정밀도의 worker와 두 인코더를 GPU에 차례로 올리도록 수정했다. worker가 과거 기록을 생성한 뒤 내리고, 인코더로 선택·특징을 계산한 뒤 내린 다음, 동일 worker를 다시 올려 현재 선택을 생성한다. 데이터·가중치·생성 설정·지표·시간 상한은 유지한다. 기존의 다른 실험 세션은 변경하지 않는다. 하드웨어 간 시간 비교를 하지 않으며 실제 장치와 실패 이력을 결과에 남긴다.

**과거 생성 단계의 파서 수정(v2):** L4의 canary는 통과했으나 과거 목록이 `json` 코드 블록으로 감싸져 원래 strict JSON 파서가 모두 무효로 처리했다. 현재 작업자 평가가 시작되기 전에 실행을 중단하고 완료된 과거 출력 22개와 가중치 provenance를 회수했다. v2는 완전한 단일 JSON 코드 블록의 외곽만 제거한다. 문장 속 답 추출, 잘못된 ID 수정, 정답 대체, 실패 출력 재샘플링은 하지 않는다. 22개 원시 출력은 그대로 재사용하고 남은 14개만 같은 worker로 생성한다. 현재 출력에도 같은 형식 정규화를 적용하며 코드 블록 비율을 별도로 기록한다. 데이터 분할·정답의 의미·정책·head 설정은 유지한다. 수정 전 실행도 삭제하지 않는다.

파일럿에서 기록 생성·판정·선택 복원이 정상인지 확인하고, 실제로 어떤 상태에서 차이가 생겼는지 보고한다. 이후 남은 train을 모아 head를 학습하고 dev로 설정을 고정한 뒤 test 40문제군으로 확인하는 것이 다음 단계다. 다른 출처 시험은 별도로 남기고, 업무·도구 사용 경험처럼 기억을 재사용할 실제 연결이 있는 자료를 선정한다. 이번 파일럿이 좋다는 이유로 출처를 평가 결과에 맞춰 고르지 않는다.
