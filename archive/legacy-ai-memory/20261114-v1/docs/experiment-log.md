## 2026-11-03 — OpenRouter 연결과 첫 환경 점검

**목적:** 무메모리 과제 한 개의 모델 호출 → 도구 사용 → 패치 제출 → 공식 채점 → 기록 저장을 연결한다. 본 실험의 효과 검정이나 주 모델 선정이 아니다.

**결정과 근거**

- 사용자가 지정한 OpenRouter와 기존 `OPENROUTER_API_KEY`를 사용한다. 키 값은 출력하거나 저장하지 않는다.
- mini-SWE-agent 2.4.6의 기존 Responses 어댑터·도구·프롬프트를 사용하고 전송 기록과 실행 기록을 추가한다. 패키지 수정 없이 하위 클래스로 연결한다.
- 기존 Lite 데이터 리비전을 유지하기 위해 공식 채점기 4.1.0을 고정한다. 조사한 5.0.2의 입력 요구 필드와 현재 Lite 행이 달랐다. 이 차이는 모델 실패와 구분한다.
- 점검용 `marshmallow-code__marshmallow-1359`는 Lite dev의 작은 Python 라이브러리 과제로 사전 선택했다. 본 실험의 Lite test 평가 집합에 포함하지 않는다.
- 모델마다 제공자를 고정하고 자동 fallback·자동 모델 재시도를 끈다. 날짜가 없는 DeepSeek V4.1 이름과 `-1017` 이름이 다른 버전으로 연결됨을 확인하여 `deepseek/deepseek-v4.1-flash-1017`을 명시한다.
- CPU·메모리·네트워크 제한, 요청·출력·시간·비용 제한과 불완전한 하드 상한이라는 점을 설정·방법에 기록한다.

**환경 점검 중 발견**

첫 시도 `20261103T124524Z-ec262e3c`는 컨테이너 HEAD와 데이터의 기준 커밋 SHA가 달라 모델 호출 전에 중단됐다. API 호출·비용은 0이다. 조사 결과 이미지에는 `SWE-bench`라는 준비용 커밋이 추가됐지만 기준 코드와 트리는 같았다. 검사를 ‘같은 코드 트리 + 깨끗한 작업 트리’로 수정하고 그 사례를 회귀 검증에 추가했다. 원본: [초기 요약 · 별도 원본](reproduction.md) (`runs/20261103T124524Z-ec262e3c/summary.json`).

DeepSeek 직접 제공자 경로의 시도 `20261103T124906Z-4370e44a`는 계정 데이터 정책으로 HTTP 404가 반환되어 도구 실행 전에 중단됐다. 모델의 해결 능력 실패로 세지 않는다. 계정 정책을 변경하지 않고 제공자를 `deepinfra/fp8`로 명시한 새 실행으로 점검한다. FP8 제공 방식은 별도 실험 조건으로 기록한다. 이 오류 응답에는 청구 내역이 없어 보고 비용 합계 0과 실제 총청구 확인을 구분한다. 원본: [라우팅 오류 · 별도 원본](reproduction.md) (`runs/20261103T124906Z-4370e44a/api/0001.response.json`).

**실행 결과와 분석**

결과 표, 비용, 캐시와 후속 분석 항목은 [첫 연결 점검 보고서](reports/2026-11-03-openrouter-smoke.md)에 정리한다. 원본 실행은 성공·오류 모두 보존한다.

연결 점검을 마쳤다. Luna는 목표 테스트 1/1·유지 테스트 76/76, DeepSeek(DeepInfra FP8)는 목표 테스트 0/1·유지 테스트 76/76이었다. 정상 모델 응답 21건의 보고 비용 합계는 약 $0.00595이고, 제공자·요금 사후 조회로 대조했다. DeepSeek가 자체 실행한 기존 테스트 911개는 통과했지만 공식 목표 테스트는 실패했으므로, 성공 기억의 판정 출처와 테스트 범위를 반드시 보존해야 한다는 후속 설계 항목을 기록했다. 메모리 자체의 득실은 아직 측정하지 않았다.

**후속 순서**

1. 기록 품질과 두 모델의 API·도구 연결을 점검한다.
2. 수집용·평가용 과제 관계와 역사적 이용 가능성을 검토하고 과제 분할을 고정한다.
3. 별도 과제의 모델 선정용 실행과 예산을 정한다. 연결 점검의 한두 성공으로 주 모델을 확정하지 않는다.
4. 기억 작성·출처·선택 기록을 구현한 뒤 A/B/C 비교를 시작한다.

## 2026-11-03 — 첫 결과의 타당성 감사

사용자 요청에 따라 원본 입력·프롬프트·이미지·실행 코드·채점 입력을 대조했다. 두 완료 실행은 같은 초기 조건이었고, 19개 대화 전환에서 도구 결과·응답 기록이 보존됐으며 모든 요청이 정상 완료됐다. 원본 파일은 변경하지 않았다.

`audit-20261103T131300Z-459716`에서 수정 전 / 정답 / Luna 제출 / DeepSeek 제출 패치를 새 컨테이너로 검사했다. 공식 목표 테스트 결과는 실패 / 성공 / 성공 / 실패로 재현됐다. 추가 동작 진단에서는 DeepSeek가 기본 List·Tuple의 예외를 없앴지만 상위 사용자 지정 포맷은 반영하지 못했다. 표기 차이만으로 실패한 사례는 아니며, 동시에 일부 문제는 고친 경험이다.

채점기의 `tests_status` 존재만으로 완료를 분류하던 검사를 보강했다. 실제 파싱된 테스트와 기대 테스트, 프로세스 종료 상태를 확인한다. 이번 두 실행은 모두 77개 기대 결과가 있어 기존 판정에 영향이 없다. 관련 회귀 검증을 포함한 로컬 테스트 10개를 통과했다.

모델 API 호출은 추가하지 않았다. 감사 대조군과 사후 작성한 8개 진단 항목은 모델 성능 표본이나 메모리 전이 결과로 세지 않는다. 상세 근거·남은 한계·다음 설계는 [감사 보고서](reports/2026-11-03-experiment-audit.md)에 기록했다.

## 2026-11-03 — 시작 제공과 자율 검색을 함께 비교하도록 설계 갱신

사용자가 시작 입력에 기억을 넣는 방식과 에이전트가 필요할 때 스스로 찾는 방식의 차이도 보고 싶다고 요청했다. 첫 주 비교를 `none / preload / agent_search`로 갱신하고, 기존 재배정 기억 대조는 후속 분석으로 옮겼다. 주 평가 조건은 3개를 유지한다. 전달 경로 점검 6회를 예시에 추가해 기존 128회 계획 예시는 134회가 됐으며, 실행 규모·예산은 아직 확정하지 않았다.

같은 고정 저장소·검색기·한도를 쓰되 자율 조건은 검색 여부·시점·쿼리를 스스로 선택한다. 첫 파일럿은 검색 최대 1회·카드 최대 1개로 제한한다. 주 비교에는 조회하지 않은 실행과 빈 결과도 포함한다. 두 정책의 차이는 내용 선택과 비용까지 포함하므로 순수한 시점 효과로 해석하지 않는다.

원인 확인용 `deferred_same`은 시작 제공의 사전 선택 카드와 같은 내용을 필요할 때 열게 한다. 이 조건은 자유 검색과 구분한다. 같은 카드라도 조회 여부·호출 비용·입력 위치가 달라질 수 있음을 기록한다. 조회 이벤트와 실제 API 입력 노출, 조회 전후 행동, 총비용의 기록 규약도 보완했다.

이번 변경은 [실험안](ai-memory-pilot-reassessment.md)과 관련 노트·기록 규약의 갱신이다. 실행기는 여전히 무메모리만 지원하며, 새 모델 호출·기억 실험·기존 결과 변경은 없었다.

## 2026-11-03 — 전달 기능 구현과 고정된 작은 비교 실행

사용자의 진행 요청에 따라 `none / preload / agent_search`와 후속 진단용 `deferred_same`을 구현했다. 호스트가 예약 조회 명령을 처리하고, 과제 컨테이너에는 저장소를 마운트하지 않는다. 조회·반환·요청 본문 포함을 각각 기록한다. API 요청 전 시작 이벤트도 추가했다. 실제 전달·한도·미조회·빈 결과·시간 필터·호스트 셸 실행 방지·공식 판정 표시 등의 검증을 포함한 로컬 테스트 19개가 통과했다.

과제·정책·순서는 모델 결과를 보기 전에 [delivery-smoke-v1 계획](../experiments/swe_memory/plans/delivery-smoke-v1.json)에 고정했다. 출처는 pvlib `1154`, 평가는 별도의 `1606`, `1707`이며 각 세 조건을 한 번씩 실행한다. 모델은 연결 점검용 Luna/OpenAI/medium이다. 출처 PR의 merge commit이 두 평가 base commit의 조상인 것을 GitHub 비교 메타데이터로 확인했다. 같은 저장소의 수치 경계값 사례라는 문제 설명의 관계로 선택했으며 평균 SWE 효과를 추정하는 표본이 아니다.

유료 실행 전에 공식 수정 전·정답 대조군을 검사했다. 기존 이미지에서는 NumPy 2가 제거한 `np.Inf` 때문에 출처 코드 import가 실패했다. 별도 `ai-memory/` 이미지에 NumPy 1.23.5·pandas 1.5.3·SciPy 1.10.1을 고정했다. 원래 태그와 코드·테스트는 유지했다. Docker FROM 식별자와 namespace 처리에서 생긴 준비 오류도 남겼고, namespace 회귀 검증을 추가했다. [환경 변경 기록](../experiments/swe_memory/plans/delivery-smoke-v1-environment-amendment.json)의 세 이미지 모두 원본 미해결·정답 해결과 기대 테스트 관측이 확인됐다.

출처 실행 `20261103T135629Z-3cafeecc`는 공식 목표 1/1, 유지 97/97을 통과했다. `memory-author-20261103T135832Z-79453a`에서 출처 실행만 입력으로 받아 카드 두 개를 작성했다. 생성된 본문은 실행 중의 기존 테스트 실패를 설명하면서 공식 성공을 누락했다. 본문은 보존하고 기계적으로 읽은 공식 판정을 모든 카드에 별도 표시한다. 이 검토와 표시 규칙은 평가 실행 전에 고정했다. [카드 품질 점검](reports/data/2026-11-03-memory-author-quality.json)은 한 응답의 관측이며 요약 오류율이나 기억의 손해를 증명하지 않는다.

첫 평가 문제 `1606`의 세 조건은 모두 해결됐으며 자율 검색 조건의 조회는 0회였다. 중간 관측을 이유로 사용 지시·카드·예산을 바꾸지 않고 남은 사전 배정 실행을 진행한다. 전체 결과와 제한은 별도 완료 보고서로 남긴다.

여섯 배정 실행을 모두 완료했다. 두 과제 모두 세 조건에서 해결됐으며 자율 조회는 0/2였다. 이후 별도 명시적 조회 점검에서는 실제 모델의 조회·반환·다음 입력 노출이 확인됐다. 이 검사는 자율 검색 결과에 합치지 않는다. 출처·카드 작성·여섯 실행·명시적 점검의 API 합계는 $0.031204835이며 71개 요청의 사후 청구와 일치한다. 원본 476개·대화 전환 51개·도구 기록 73개를 검사했다. [완료 보고서](reports/2026-11-03-memory-delivery-smoke.md)에 방법·결과·한계·원본 경로를 정리했다.

사용자는 조회 도구 자체가 적절하지 않았을 가능성을 제기했다. 명시적 조회 성공과 자발적으로 발견·사용하기 좋은 인터페이스를 구분하여, 첫 보고서를 보존한 뒤 별도 점검을 진행한다.

## 2026-11-03 — 조회 인터페이스 점검

첫 전달 보고서의 해시를 고정했다. 실제 요청에서는 도구 목록에 bash만 있었고, 기억 안내가 긴 사용자 입력 말미에 있으며, 기본 규칙이 매 응답의 bash 호출을 요구했다. 원래 조회는 동작하지만 별도 함수 도구로 확장할 때 지시 충돌과 발견 가능성을 점검해야 한다. 어휘 검색의 사후 진단에서는 자연스러운 `golden section search equal bounds` 질의가 빈 결과였고, 일부 질의는 `NaN` 한 단어만으로 카드를 선택했다. 이 관측을 기존 미조회의 확정 원인으로 간주하지 않는다.

`memory_search(query)`를 별도 API 함수로 추가하고 실제 에이전트 파서→호스트 조회→같은 call ID의 도구 결과→다음 요청 경로를 로컬 검증했다. 테스트 21개가 통과했다. 두 인터페이스 모두 같은 공통 프롬프트 수정·카드·검색기·한도·환경을 쓰는 새 4회 점검을 [사전 계획](../experiments/swe_memory/plans/interface-smoke-v1.json)에 고정했다. 이미 검토한 두 과제이므로 새 전이 성과로 세지 않는다. [도구 점검 노트](reports/2026-11-03-memory-tool-review.md)에 근거와 이후 결과를 분리해 기록한다.

네 실행을 완료했다. 새 bash 두 실행·native 두 실행 모두 해결했고, 양쪽 모두 자율 조회는 0/2였다. 코드·입력·환경·은행의 일치와 실제 native 스키마 노출을 검증했다. 별도 `guided-memory-tool-20261103T143424Z-5b9bf7`은 실제 모델의 native 호출과 다음 입력의 카드 노출을 확인했다. 이 양성 대조는 자율 조회 결과에 합치지 않는다. 도구 구조의 약점은 확인됐지만 이번 작은 비교에서 도구 교체만으로 조회가 늘지는 않았다. 기억의 범위 안내와 실제 과제 관련성을 다음 검증 대상으로 남긴다.

인터페이스 비교 4회와 native 연결 점검의 추가 API 비용은 $0.016784035다. 이번 출처 수집·카드 작성·전달 비교·인터페이스 비교·명시적 점검의 전체 API 비용은 $0.047988870이며 모델 요청은 109회다. 최초 보고서는 변경하지 않았다.

## 2026-11-04 — 야간 가설·비교·회고

사용자는 05:00 KST까지 반복 탐색하고 추가 API 비용을 $10 이내로 관리하도록 요청했다. [회차별 보고서](reports/2026-11-04-overnight-research.md)에 사전 계획·관찰·해석·후속 선택을 누적한다. 앞선 109회 비용과 야간 세션 비용을 구분하며, 기존 첫 전달 보고서는 그대로 보존한다.

## 2026-11-04 — 야간 실행 완료와 재개 후 최종 정리

R06–R09를 완료했다. R06의 Sphinx 카드 선택 비교는 세 조건 모두 4/4 해결이었지만 무메모리보다 카드 조건의 관측 비용이 높았다. 요청별 입력·출력 비용과 캐시 기록을 분해했으며, 캐시 상태를 통제하지 않아 특정 내용의 비용 효과로 단정하지 않았다. 같은 과제의 기존 공개 테스트를 넓힌 별도 진단에서는 원본·정답이 공통 통과한 142개 중 후보 패치 18개의 추가 회귀가 발견되지 않았다.

## 2026-11-04 — 진행 방식에 대한 회고

사용자가 실험을 어떻게 진행했고 무엇을 잘하거나 놓쳤는지 설명해 달라고 요청했다. 아래는 완료된 기록에 대한 회고이며 새 실험 결과가 아니다. 기존 계획·결과·원본 감사는 수정하지 않았다.

처음 질문은 과거 성공·실패 경험을 다음 문제에 전달했을 때 성과와 비용이 어떻게 달라지는지, 사실과 행동 안내 중 무엇이 작용하는지였다. 이번에는 사람이 새 문제와 정답을 만들지 않고 SWE-bench Lite의 문제·기준 코드·공식 평가를 이용했다. 실제 풀이와 기억 작성은 OpenRouter로 호출한 모델이 수행했고, 나는 에이전트 연결·조건 배정·기록·사후 분석을 구현했다. 주 실행 모델은 Luna였으며 야간 대상 108회 중 105회가 Luna, 3회가 DeepSeek였다. 이 자료를 충분한 두 모델 비교로 볼 수 없다.

**실제 데이터가 흐른 순서**

1. 출처용 과제를 메모리 없이 풀게 하고 명령·출력·패치·공식 성패를 저장했다. 초기 전달 점검의 pvlib 경험에 이어 야간에는 Sphinx 두 개와 Django 한 개의 경험을 새로 수집했다. 실패한 출처도 남겼다.
2. 출처 실행을 바탕으로 사실 카드와 조사 절차 카드를 작성했다. 야간 세 출처에서 카드 여섯 개를 만들고 출처 판정과 근거를 연결했다. 대상의 정답·숨겨진 평가 내용은 작성 입력에 넣지 않았다. 출처의 실제 병합이 대상보다 과거인지 확인했지만, 에이전트가 모의 실행에서 만든 패치까지 실제 병합됐다는 뜻은 아니다.
3. 별도의 대상 문제를 새 컨테이너에서 무메모리·시작 제공·선택적 조회 조건으로 반복했다. 같은 회차 안에서는 선언한 개입 외의 모델·이미지·기본 입력·예산을 맞추고 순서를 미리 고정했다. 같은 반복 번호가 동일한 모델 난수나 동일한 사고 경로를 보장하지는 않는다.
4. 제출 패치는 공식 평가로 채점했다. 조회·반환·API 입력 노출·실제 명령·토큰·비용을 따로 보존했다. R04부터는 정해진 요청 단계의 중간 패치도 저장하고 배치 종료 뒤 별도로 채점했다. 그 평가를 진행 중 에이전트에게 알려주지는 않았다.
5. 관측에서 다음 비교를 골랐다. 범위 안내(R01), 관련 출처로의 전이(R02), 초기 이득의 새 반복과 내용 비교(R03), 남은 도구 지시 교정(R04), 수신 모델 비교(R05), 카드 선택(R06), 검색어 없는 읽기(R07), 오래된 이름 교체(R08), 선택적인 사용 판단 안내(R09)를 진행했다. 일부 후속 초안은 앞선 회차 실행 중 준비했으므로 모든 회차가 직전 전체 결과를 본 뒤 만들어진 것은 아니다. 각 회차의 결과 관측 전 계획 고정과 전체 연구의 독립된 사전 등록은 구분한다.

평가 중 기억 은행을 고정한 것은 비교 조건이 실행마다 달라지는 것을 막기 위한 선택이었다. 따라서 실제 경험으로 카드를 만들고 다른 과제에 전이하는 단계까지 수행했으며, 대상의 성공·실패를 자동으로 다시 저장해 다음 대상으로 계속 누적하는 실험은 수행하지 않았다. 원본 경험 전체 대 요약의 비교, 사실 대 절차의 일반적 우열, 장기 누적의 효용은 아직 남아 있다.

**유지할 판단**

- 초기에 Django의 2/2 대 0/2 차이를 발견한 뒤 새 기준과 반복 비교를 했다. 1/4 대 1/4로 초기 이득이 재현되지 않은 결과도 남겼다. 기억의 득실을 한 번의 성공·실패 전환으로 확정하지 않은 점은 유지한다.
- 조회하지 않은 조건을 지우지 않고, 도구 연결 성공과 자율 사용을 구분했다. 실제 API에 카드가 들어갔다는 증거와 그 내용을 검색에 사용한 증거도 나눴다.
- 원본·정답 대조로 환경과 채점을 확인하고, 목표 수정과 기존 기능 회귀를 분리했다. 중간 패치를 저장한 덕분에 로컬 테스트의 옛 기대값을 맞추다가 공식 통과 상태를 잃은 사례를 조사할 수 있었다.
- 실패·미제출·중단·사전 초안 변경을 보존했다. 원본 해시와 요청별 과금 대조는 이후 해석을 수정할 수 있는 근거를 남겼다.

**내가 더 일찍 해결했어야 할 점**

- 초기 조회 인터페이스를 확장하면서 최종 API 입력 전체의 지시를 충분히 검사하지 않았다. bash 호출 요구 문구가 남았고 R04에서야 별도로 확인했다. 도구가 명시적 지시에 응답하는지 확인하는 것만으로 사용 가능한 실험 조건이 준비됐다고 판단한 것이 부족했다. 전체 입력·도구 설명·호출 규칙 검사는 첫 정책 비교 전에 끝냈어야 한다.
- 정보 접근 범위를 뒤늦게 감사했다. Git 이력은 실제 대체 정보 경로였고 초기 pvlib에는 미래 태그도 남아 있었다. 네트워크를 끈 것만으로 미래 정보가 차단됐다고 볼 수 없다. 다음에는 대상 코드 트리뿐 아니라 접근 가능한 이력을 함께 고정해야 한다. 실제 정답 누출이 확인됐다는 뜻은 아니다.
- 같은 과제의 원인 분석에 실행을 집중했다. 최종 감사의 대상 행을 다시 집계하면 Django 16910에 46회, Sphinx 8627에 30회로 합계 76/108회, 약 70%다. 이 집중은 조건별 행동 분석에는 도움이 됐지만 새 과제에서의 재현 범위를 늘리지 못했다. 사례 분석을 얼마나 진행하면 새 과제로 넘어갈지 미리 정하지 않은 점이 운영상의 약점이었다.
- R05는 예상 가능한 한도 내 미제출에도 전체 배치를 멈추도록 설계했다. 비용·기록이 완전한 모델 결과와 계속 실행하면 해석이 어려운 인프라 오류를 구분했어야 한다. 남은 18회가 미실행이므로 모델 비교를 마친 것처럼 해석할 수 없다.
- 분석과 환경 준비의 시간을 충분히 분리하지 않았다. 여러 시각 제한을 겹쳐 두었고 새 과제 R10은 준비만 마친 채 시간 규칙으로 실행하지 못했다. 마지막 모델 실행은 04:14:40 KST였고 최종 문서화는 마감 이후 사용자 재개 요청 뒤에 끝났다. 오전 5시까지 중단 없이 연구와 정리를 완료한 것으로 표현해서는 안 된다. API 비용 약 $0.93은 예산을 지킨 기록이며 시간 배분이 효율적이었다는 증거는 아니다.
- 관측 비용과 시간의 원인을 분리하는 설계가 부족했다. 캐시 상태는 통제하지 않았고 일부 환경 감사와 모델 실행은 같은 호스트에서 겹쳤다. 현 지출은 집계할 수 있지만 내용 자체의 계산 비용이나 속도 효과로 일반화하지 않는다.
- 사용자 설명에서 기록 감사의 완료를 연구 타당성과 더 명확히 분리했어야 한다. `issues=[]`는 해당 감사가 검사한 기록·회계·채점 완료 항목의 결과다. 비교 설계의 완전성이나 효과 입증을 뜻하지 않는다.

**다음 진행에서 바꿀 순서**

먼저 새 과제 몇 개에서 실제 요청 전체·정보 접근·공식 대조·미제출 처리를 점검해 실행 조건을 고정한다. 다음으로 '선택한 기억 제공 정책이 무메모리보다 예산 내 해결물 제출과 비용에서 나은가'를 주 비교 하나로 두고, 시작 제공·조회 안내의 효과는 정해진 보조 비교로 다룬다. 이번에 반복 사용한 과제는 발견용으로 남기고 여러 저장소의 새 과제에 대한 확인 시간을 먼저 확보한다. 같은 과제의 추가 변형과 사후 진단은 그 확인 시간을 침범하지 않는 범위에서 수행한다.

확인 비교가 끝난 뒤 필요한 실패 경로만 더 파고든다. 정책이 결정된 다음 단계에서 과제 순서·작성·저장·조회 규칙을 고정한 누적 메모리 실험으로 넘어간다. 이는 후속 제안이며 새 유료 실행을 시작하거나 기존 결과를 다시 분류한 것은 아니다. 상세 후보는 [후속 검증안](ai-memory-next-validation-plan.md)에 있다.

사용자가 학문적 접근이라면 같은 방식으로 진행하겠느냐고 물었다. 본 연구의 설계로는 그대로 반복하지 않겠다는 판단을 남긴다. 회차별 비교·기록·추가 확인은 유용했지만, 연구 전체에서 어떤 요인이 득실을 만드는지와 경쟁 설명을 구별할 핵심 대조가 충분히 정리되지 않았다. 단순히 새 과제 수나 반복 수를 늘리는 것만으로 이 부족이 해결되지는 않는다. 오래된 이름의 삭제 뒤 그 이름의 검색이 줄어든 것은 조작이 행동에 전달됐는지 확인하는 데 유용하지만, 득실의 원리를 설명하는 성과는 아니다. 로컬/공식 테스트의 충돌은 기억이 노출되지 않은 조건에서도 나타났으므로 메모리 고유의 실패 원인으로 제시할 수 없다.

후속 실행안 첫머리에 정책 효과 확인과 원인 설명 연구의 차이를 명시했다. 적용 조건의 표시 같은 한 요인을 연구 후보로 정할 경우 예상 결과·반대 설명·실패 판정 기준을 먼저 정하고, 전달 경로를 고정한 내용 개입과 새 과제에서의 확인을 설계해야 한다. 새로운 가설을 이미 얻은 결과로 확증한 것처럼 쓰지 않는다. 탐색과 확인의 구분, 변동성과 비교 단위·연구자 선택의 영향을 다루는 방법론 근거는 [A manifesto for reproducible science](https://pmc.ncbi.nlm.nih.gov/articles/PMC7610724/)와 [Empirical Design in Reinforcement Learning](https://jmlr.org/papers/v25/23-0183.html)을 참고했다. 이 문헌은 우리 실험 결과의 증거를 대신하지 않는다.

## 2026-11-05 — 구성요소별 득실을 연구의 중심으로 정렬

사용자는 기억의 어떤 부분이 이득·손해인지, 그 기여를 숫자로 측정할 수 있는지 알고 싶다는 목표를 다시 명시했다. [측정 노트](ai-memory-measurement-notes.md)에 전체 기억의 순효과와 부분의 조건부 기여, 조합의 상호작용을 구분해 추가했다. 40/60/35/50% 예시는 산식 설명용 가상 확률이며 실험 결과나 예상 성능이 아니다.

[후속 설계](ai-memory-next-validation-plan.md)는 전달 정책의 비교를 먼저 확대하던 우선순위를 바꾸었다. 출처가 같은 사실·지침 등의 구성요소를 고정한 방식으로 제공하고, 같은 부분의 유무 또는 선언한 성질의 편집을 비교하는 것을 첫 후보로 둔다. 단독으로 이해 불가능한 부분을 억지로 분리하지 않으며, 길이·일반 조언·정보량이 함께 바뀌는 한계를 검사한다. 조회 방식과 장기 축적은 별도 후속 질문으로 남겼다.

산출물은 부분·대상 조건별 해결률 기여(%p), 회귀, 전체 배정 평균 비용과 불확실성이다. 기억 전체가 유익해도 일부 내용의 기여가 음수일 수 있고, 같은 부분의 기여가 조합에 따라 달라질 수 있음을 명시했다. 새 모델 호출·실험 배정·유익/유해 정답 라벨 생성은 하지 않았다.

## 2026-11-05 — 구성요소 측정의 실제 기능 검증

사용자가 이 방향으로 측정 가능한지 먼저 확인하도록 요청했다. [별도 계획](../experiments/swe_memory/plans/component-feasibility-20261105.json)에 한 대상·다섯 조건·조건별 두 반복을 고정했다. 이전 R10은 미실행 상태를 유지하며 새 계획에서 준비된 Sphinx 10325를 사용한다. 출처는 이전 Sphinx 8435 카드이고, 원문의 관측 문장 묶음과 잠정 절차 문장을 그대로 삭제·유지한다. 대상 정답으로 새 기억을 작성하지 않았다.

처음 점검에서 기존 어휘 검색과 모델 입력에 표시한 내용 해시가 문장 개입 외의 차이를 만들 수 있음을 확인했다. 적격한 카드의 직접 고정 제공과 모델 입력에서만 해시를 숨기는 선택 옵션을 추가했다. 공통 출처 설명은 네 조건에 유지하고, 완전한 무메모리를 다섯 번째 조건으로 둔다. 비용·API 기록이 완전한 한도 내 미제출은 배정된 전달 실패로 유지하되 다음 실행을 계속하도록 새 계획에 명시했다. 환경·평가·비용 오류에는 자동 재시도하지 않는다.

유료 호출 전 43개 로컬 검사가 통과했고 이전 코드 사본과 원본 구간·계획·입력 해시를 보존했다. 추가 비용 중단 기준 $0.75를 두고 기존 $10 기준에 합산한다. 표본 두 번에서 큰 차이가 우연히 나올 수 있다는 정확한 가상 계산도 저장했다. 실제 관측값과 가상 정밀도 진단을 섞지 않는다. [기능 검증 보고서](reports/2026-11-05-component-measurement-feasibility.md)에 완료 상태와 결과를 정리한다.

## 2026-11-05 — 현재 상태·데이터 재점검과 집계 정정

사용자 요청으로 새 모델 호출 없이 전체 저장 상태를 다시 검사했다. 모델 실행 원본 29,345개의 해시와 요청·비용·채점 대조에서 불일치를 찾지 못했고, 최근 구성요소 분석의 원본 재집계도 기존 수치와 같았다. 야간 CSV 6개와 중간 패치 306개의 보존 상태도 확인했다. 현재 실행 중인 작업은 없다.

전체 목록이 최근 10회를 빠뜨려 177행에 머물러 있었다. 수정 전 CSV/JSON을 보존하고 187행으로 갱신했다. 144개 모델 설정과 43개 사후 진단을 명시적으로 구분하고, 대상 실행 128개·출처 수집·기억 작성·연결 점검·환경 점검을 각각 표시했다. 모델 없는 진단에 잘못 붙이던 `cost_complete=false`는 적용 대상 아님을 나타내는 `null`로 바꾸고 고유 `record_id`를 추가했다. 관련 로컬 검사 3개가 통과했다.

## 2026-11-05 — 내용의 다양성과 동일 본문의 사용 안내 비교

사용자는 기억의 내용을 다양화하고 같은 기억도 정보·행동·지침으로 다르게 제공하는 연구 축을 제안했다. [내용과 사용 안내 노트](ai-memory-content-and-framing.md)에 환경/API·코드 탐색·행동 순서·실패·검증·적용 조건 등의 내용 유형과 정보 참고형·제안형·지침형을 분리했다. 체크리스트 배치·조건 추가·입력 역할 변경은 각각 다른 요인으로 둔다. 기존 facts/procedure 카드와 원문 구간 삭제 실험은 같은 본문을 유지한 표현 비교가 아니었음을 명시했다.

기존 Sphinx 8435 성공 출처와 Django 14667 실패 출처 카드의 본문을 그대로 두고 안내 문장만 세 방식으로 바꾼 [예시 여섯 개](design-data/memory-framing-examples-20261105.json)를 만들었다. 본문 원본 해시와 안내 외 동일성을 확인했다. 새로 쓴 공통 적용성 안내는 모든 표현에 같으며, 길이·토큰 수를 맞춘 비교는 아니다. 이는 검토용 초안이고 실험 은행·배정·결과 목록에 넣지 않았다.

## 2026-11-07 — 득실 검증 프로토콜과 입력 대조 예시

사용자가 메모리 내용의 이득·손해를 어떻게 검증할지 물었다. [다음 프로토콜](ai-memory-validation-protocol.md)에 관측·검증 맥락 F, 구체적 과거 처방 P, 구체화한 적용 조건 A를 나누는 네 조건을 제안했다. 주 대비는 F+P−F이며, F−미제공은 경험 정보 패키지 전체 효과, F+P+A−F+P는 처방이 있는 상태의 적용 안내 추가 효과다. 순수한 지시 말투나 완전한 상호작용 실험으로 부르지 않는다. P×A 상호작용에는 F+A가 더 필요함을 명시했다.

적용 조건이 맞는 source/target 쌍을 먼저 감사하고, 최종 해결·회귀·전체 배정 비용과 행동을 분리한다. 기존 검색 행동 변화가 성과 개선과 같지 않았던 R08, 모두 성공했던 구성요소 검증, 최근 모두 성공/실패로 몰린 과제와 공식/로컬 검사 충돌을 반영했다. 표본 수·반복·실용적 최소 차이·확인 과제는 결과를 보기 전에 정하도록 했다. NIST 설계 안내와 JMLR의 실험 설계 논문을 확인했으며, 구체적 기억 분해와 평가 절차는 본 프로젝트의 제안으로 구분했다.

기존 LabelEncoder 카드의 정확한 원문 구간으로 [검토용 네 조건](design-data/content-validation-example-20261107.json)을 만들었다. 원문에서 P 구간만 제거하면 F, F+P에서 새 조건 안내 A를 제거하면 원문이 되는 검사를 통과했다. A는 source 제약에서 도출한 연구자 작성 안내로 표시했고, source의 미해결 판정은 유지했다. 현재 대상의 정답이나 사후 inverse_transform 진단을 카드에 추가하지 않았다. 예시는 실행 은행·새 확인 데이터·실험 계획이 아니며 모델/API 요청은 0회다.

## 2026-11-07 — 큰 방향과 별도 학습 모델의 역할 재검토

## 2026-11-07 — 동료 공유용 저장소 구성과 커밋 범위

사용자가 조사 노트의 커밋과 동료 공유를 위한 레포 구조·시점을 물어 [저장소 구성 노트](ai-memory-repository-structure-2026-11-07.md)를 작성했다. 하나의 Git 레포에서 측정 실험, 데이터 수집·생성, 모델 학습을 구분하고 데이터 버전·출처·분할·라벨·판정 시점을 공통 계약으로 연결하도록 권했다. 데이터 만드는 코드는 data_pipeline, 작은 버전 자료와 manifest는 datasets에 두는 목표이며 기존 동결 경로를 즉시 옮기지 않는다.
